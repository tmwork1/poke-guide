# 新規ページ作成パイプライン

**1回の呼び出し = 1フェーズ。** 状態は `docs/plan/pages/index.md`(索引)と `docs/plan/pages/<slug>.md`(ページごとの仕様・設計・受け入れ基準・実施結果)に永続化されているので、途中から再開できる。`/loop new-page` で繰り返し起動される前提で書かれている。

**特に指示のない限り `main` で直接作業する**(専用worktree/ブランチは作らない)。**各フェーズの作業が一区切りついたら Coordinator が `git commit` する**(`git push` はしない)。→ ルートの `CLAUDE.md`「作業方針」。

## `ui-loop` skill との境界(重要)

| | `new-page`(このskill) | `ui-loop` |
|---|---|---|
| 対象 | **まだ `src/pages/` に無いページ** | 既に動いているページ |
| 入力 | ワイヤーフレーム・ユーザーの要求・既存のデータモデル | **スクリーンショット** |
| 触ってよい範囲 | マイグレーション・API・lib・ページ・ナビ・テスト | 原則ページのCSS/DOMのみ。機能追加は禁止 |
| 反復単位 | フェーズ(P0→P6で1ページ完成) | ラウンド(指摘が出尽くすまで) |
| 終了 | 受け入れ基準を全件満たしたら **`ui-loop` に引き渡して終了** | 優先度A・Bの指摘が2ラウンド連続で出なかったら終了 |

**このskillのゴールは「見た目が完成したページ」ではなく「実データで一通り動き、ナビから到達でき、テストが通るページ」。** 見た目の磨き込みは `ui-loop`(単発の狭い直しなら `ui`)の仕事なので、ここで完璧を目指さない(ただし `00-foundation.md` のレイアウト原則・タイポグラフィ原則は最初から守る。後から直すと作り直しになるため)。

## 役割分担(厳守)

| 役 | モデル | やること | やってはいけないこと |
|---|---|---|---|
| Coordinator(メイン) | — | 現状把握、**ユーザーへの仕様確認**、3レビュアーの指摘の統合、計画書への記録、エージェントへの指示、受け入れ検証 | 大きな実装を自分でやる |
| データ設計レビュアー | **sonnet** | 設計案を既存のDB/API/libと突き合わせ、**マイグレーションの要否・RLS・API契約・既存機能への影響**を講評 | **ファイル編集・git操作・DB操作** |
| 導線レビュアー | **sonnet** | ワイヤーフレームと既存ページを読み、**情報設計・遷移・空状態・既存ページとの語彙の一貫性**を講評 | **ファイル編集・git操作・DB操作** |
| プレイヤー視点レビュアー | **sonnet** | 対戦準備の実務から、**そのページが解こうとしている問題に本当に答えているか・ゲームルール上の制約を満たすか**を講評 | **ファイル編集・git操作・DB操作** |
| 実装者(Implementor) | **sonnet** | 実際のコード作成と検証 | 担当外ファイルの編集、**git commit/push** |

**実装は必ずsonnetサブエージェントに委譲する**(ユーザーの明示指示)。3レビュアーは設計フェーズで1回だけ、1メッセージ内で並列起動する。

## フェーズ

### P0. 現在地を把握する(毎回最初に行う)

`docs/plan/pages/index.md` の「バックログ」表を読む。
- **進行中のページがある** → その `docs/plan/pages/<slug>.md` の「フェーズ表」を読み、`⬜` の最初のフェーズから始める
- **進行中が無い** → バックログの最上位を選び、P1から始める。**どのページを作るかユーザーが指定していない場合は、バックログの上から順に着手し、着手したことを報告する**
- **ユーザーが特定のページを指定している** → それが最優先。バックログに無ければ行を追加してからP1へ

### P1. 仕様を固める(**唯一、ユーザーに聞いてよいフェーズ**)

作るページの輪郭を決める。**ここで曖昧なまま進むと、P4の実装が丸ごと無駄になる。**

1. **ワイヤーフレームを全部見る。** `docs/ui_proposal/` を `Glob` で列挙し、対象ページに関係するものを **Read tool で実際に開く**(1枚だけ見て済ませない。例: チーム機能なら `チーム.png` と `チーム編集.png` の両方)。
2. **既存の実装から流用できるものを洗う。** 似た構造の既存ページ(`src/pages/box/index.astro` = 一覧、`src/pages/box/[id].astro` = 編集)、既存のlib・API・型。→ `references/stack.md`
3. **データモデルの要否を判定する。** 新テーブルが要るのか、既存テーブルの列追加で足りるのか、DBを一切触らずに済むのか。→ `references/stack.md`「マイグレーション」
4. 次を **`docs/plan/pages/<slug>.md` に書き出す**:
   - **このページが答える問い**(1文)。書けないなら仕様が固まっていない
   - **ルーティング**(URL・SSR/静的・認証の要否)
   - **スコープ内 / スコープ外**(「今回作らないもの」を明示。これが無いと実装が膨らむ)
   - **ファイル分割案**(画面に独立した2領域以上があるなら)。`references/stack.md`「画面が複数領域を持つときのファイル分割」を見て判断する。`box/[id].astro` は分割を後回しにした結果、8,500行・3領域が1クロージャに同居する構造になり並列実装ができなくなった(→ `docs/plan/ui_parallelization.md`)。**新規ページはこの段階で分割案を決めてしまう**(実装(P4)に入ってからでは遅い)
   - **受け入れ基準**(番号付き。**数えられる/実測できる形で書く**。「使いやすいこと」は基準にならない。「6体まで登録でき、7体目の追加ボタンが `disabled` になる」は基準になる)
5. **ワイヤーフレームからもユーザーの指示からも決まらない論点があれば、ここでまとめて `AskUserQuestion` で聞く。** 1問ずつ小出しにしない。聞くべき典型:
   - チーム上限・重複可否のような**ゲームルール上の仕様**(推測で決めない)
   - 既存データとの関係(例: チームは `owned_pokemon` を参照するのか、コピーを持つのか)
   - 公開/共有の有無(RLSとURL設計が変わる)

   **判断が付くものは聞かずに決めて、決めた根拠を1行残す。** 聞くのは「どちらを選んでも実装が丸ごと変わる」論点だけ。

### P2. 設計レビュー(3体並列、すべてsonnet)

`references/agent-prompts.md` の3テンプレートを使い、**1メッセージ内で3体同時に起動する**。渡すもの(3体共通):

- `docs/plan/pages/<slug>.md`(P1で書いた仕様)の**絶対パス**
- ワイヤーフレームの**絶対パス**と「Read tool で必ず実際に見ること」
- `docs/plan/ui_rounds/00-foundation.md`(レイアウト原則・タイポグラフィ原則。**現行仕様の唯一の正**)
- `.claude/skills/new-page/references/stack.md`(このプロジェクトの層構造)
- **「実装は絶対にしない。設計への指摘のみ」**

**スクリーンショットは無い。** 3体には「まだ存在しないページの設計を読んで、作る前に潰せる欠陥を挙げてもらう」と明示する(既存ページのレビューだと誤解させない)。

#### P2.5. 3件の指摘を統合する(Coordinator自身の作業)

- **重複排除**: 同じ問題は1件にまとめ、指摘者を併記する
- **矛盾の解消**: 逆方向の指摘はページの目的に照らしてCoordinatorが決め、採用しなかった側の理由を1行残す
- **スコープ拡大要求は原則却下**。「あった方がいい」機能は `<slug>.md` の「スコープ外(将来)」に落とす。**却下したことを記録する**(次のフェーズで蒸し返さないため)
- ユーザーがP1で明示した仕様と矛盾する指摘は**ユーザー指示が勝つ**

### P3. 計画書に記録する(**実装の前に必ず**)

ユーザーの明示的な指示: **「修正する前に必ず計画書に計画を記録するようにして」**。新規作成でも同じ。

`docs/plan/pages/<slug>.md` に追記する:

```markdown
## 設計レビュー(YYYY-MM-DD データ設計/導線/プレイヤー視点・Coordinator統合)
### 採用した指摘
- **R-1 見出し**(指摘者: データ設計): 【問題】… → 【対応】仕様のどこをどう変えたか
### 却下した指摘(理由つき。再提起しないこと)
### 確定した設計
- データモデル / API / ファイル分割 / 実装の順序と依存
```

書いたら**必ず** `docs/plan/pages/index.md` のバックログ表と、`<slug>.md` 冒頭の**フェーズ表**を更新する(索引が古いと次回P0で見つけられない)。

### P4. 実装させる(sonnetサブエージェント)

`references/agent-prompts.md` の「実装者用テンプレート」を使う。

**新規ページは層をまたぐので、`ui` の「1ファイル1エージェント」より依存関係の管理が重要。** 分割の基本形:

| 順序 | 担当 | 対象 | 依存 |
|---|---|---|---|
| 1(先に単独で完了させる) | 基盤 | `migrations/NNN_*.sql` + `src/lib/<name>.ts` + `src/lib/<name>-validation.ts` + `tests/<name>-validation.test.ts` | なし |
| 2(1の完了後、並列可) | API | `src/pages/api/<name>.ts` ほか | 1 |
| 2(1の完了後、並列可) | ページ | `src/pages/<name>/*.astro` | 1(型だけ) |
| 3 | ナビ・結線 | `src/components/AppSidebar.astro`(`準備中` バッジの解除)、`src/layouts/AppLayout.astro` の `current` 型 | 2 |

**DBスキーマとlibの型は必ず先に1体で確定させる。** ここを並列にすると、APIとページが違う型を前提に書いて必ず衝突する。基盤エージェントには**エクスポートする型・関数のシグネチャを報告させ**、そのまま次のエージェントの指示に貼る。

指示に必ず含めるもの:
- 計画書の**どのファイルのどの節を読むか**(`docs/plan/pages/<slug>.md` のファイル名と節タイトルを正確に。「計画書」とだけ書いて探させない)
- **編集してよいファイル**と**編集禁止ファイル**(理由つき)
- `references/stack.md` の該当節(マイグレーション規約・API層・RLS・レイアウト規約)
- `.claude/skills/ui-loop/references/pitfalls.md` の**「データ事故」「Playwright」「CSS/DOMの罠」**(踏んだ罠は既存ページも新規ページも同じ)
- 受け入れ基準のうち、そのエージェントが満たすべき番号
- **「git commit / git push は絶対にしない」**
- **「DBに検証用の個体を作らない。作った場合は必ず消す。既存個体の値を書き換えたら必ず戻す」**

### P5. 受け入れ検証(自分で)

エージェントの報告を鵜呑みにしない。**自分で動かして見る。**

1. `npm run build` 成功 / `npm test` **全件pass**(新規バリデーションのユニットテストが増えていること。**テストが1件も増えていない新規ページは未完成とみなす**)
2. **受け入れ基準を1件ずつ潰す。** 番号ごとに「どう確認したか」を書く。実測できる基準は `getBoundingClientRect()` / API叩き / Playwright で**実際に測る**
3. **`npm run shot -- --page <新ページのパス> --page box`** で1920×1080ライト・ダークを撮り、**Read tool で自分の目で見る**(Playwrightスクリプトを書き起こさない。→ `.claude/skills/ui-loop/references/pitfalls.md`「撮影は `npm run shot`」)
4. **既存ページの回帰確認**: `/box` `/box/[id]` が壊れていないこと(共通ファイルを触っているので必ず見る)
5. **DBが元の状態に戻っているか確認**(→ `pitfalls.md`「データ事故」)
6. 回帰・欠陥を見つけたら `<slug>.md` に記録してから直す

### P6. 引き渡してフェーズを締める

`docs/plan/pages/<slug>.md` に追記する:

```markdown
## 実施結果(YYYY-MM-DD)
### 受け入れ基準の判定(表: 番号 / 基準 / 結果 ※実測値を入れる)
### 実装中に見つかったバグ(このページとは別の実バグ)
### スコープ外に落としたもの(将来やるなら何から)
```

そのうえで:
- `docs/plan/pages/index.md` のバックログ表で当該ページを **✅完了** にする
- **`docs/plan/ui_plan.md` の「現在の状態」に「`/<path>` が新設されたため未講評」と1行足す。** これをやらないと `ui-loop` skill が新しいページの存在に気づかない(`ui-loop` は `ui_plan.md` の索引しか読まない)
- **Coordinatorが `git commit` する**(特に指示のない限り。`git push` はしない)
- ユーザーに「`/loop ui-loop` を回せば見た目の磨き込みに入れる(単発の直しだけなら `ui` でも良い)」と報告する

## ループの終了条件

以下がすべて満たされたら `ScheduleWakeup` に `stop: true` を渡してループを終える。
1. 対象ページの受け入れ基準が**全件pass**している
2. ナビゲーションから到達でき、既存ページに回帰が無い
3. `docs/plan/pages/index.md` と `ui_plan.md` の更新が済んでいる

**バックログに次のページが残っていても、1ページ終わったら一度止まってユーザーに報告する。** 続けるかはユーザーの判断(ページ新設はマイグレーションを伴うので、無断で次に進まない)。

P1でユーザーへの確認が必要になった場合も、**回答を待つ間はループを止める**(勝手に仕様を決めて実装しない)。
