# このプロジェクトで実際に踏んだ罠

UI改善ラウンドで**実際に事故った/時間を溶かした**ものだけを載せている。実装エージェントへの指示に関係するものを毎回コピーして渡すこと。

---

## データ事故(最優先)

### ✅ 不完全なボディの `PUT /api/owned-pokemon/:id` が個体を全消去していた(2026-07-28 修正済み)

**現在は400で弾かれる**(ボディなし / `{}` / キー欠け / `null` / 配列 / 文字列 のいずれも)。
以下は**なぜそうなっていたかの記録**であり、**復元時の作法は今も有効**なので残す。

**復元のつもりのPUTが、消去になっていた。** ラウンド21で、CTA復元エージェントが検証のため `is_public` を切り替えようとして**対象個体の `species_name` / `nature` / `ability_name` / `item_name` / `evs` / `move_names` を全部空にしてしまった**(ローカルSupabaseへ直接PostgREST PATCHを送って復元)。

**経路(コードで確認済み)**:
1. `src/pages/api/_shared.ts:60-66` — `readJsonBody` は**空ボディをエラーにせず `null` を返す**
2. `src/pages/api/owned-pokemon/[id].ts:55` — `validateOwnedPokemonRequestBody(body.data ?? {})` で `null` が **`{}`** になる
3. `src/lib/owned-pokemon-validation.ts:46-106` — **全フィールドが `X !== undefined && ...` の任意項目**なので `{}` は検証を通る
4. `updateOwnedPokemon` が**全項目上書き契約**で走り、全フィールドが空で保存される。**400ではなく200が返る。**

**このセッションで複数のエージェントが報告した「誰も触っていないのにフィクスチャが書き換わる」現象の有力な原因。**

**修正の内容(2026-07-28)**: `_shared.ts` に `readRequiredJsonBody()` を足してボディ無しを400にし、
`validateOwnedPokemonRequestBody` に `{ mode: 'replace' }` を追加して **PUT のときだけ13キーの存在を必須**にした
(`undefined` は拒否、`null` は許容)。POST は「＋ 個体を追加」の空個体登録があるため緩いまま。

**⚠️ 1回目の修正は不完全だった。** 「ボディが無いとき」だけを400にしたが、**`{}` を送るとまだ消去された**。
Coordinatorが実測して発覚し、2回目でバリデーション層を直して塞いだ。
**「ボディがあるか」ではなく「上書きに必要な項目が揃っているか」を見ないと塞がらない。**

**検証で復元するときの必須手順**(修正後も有効):
- PUTには**必ず `Content-Type: application/json` を付け、ボディが実際に届いていることを確認する**(レスポンスの `data` を見て、送った値が返ってきているか突き合わせる)。**200が返っても成功とは限らない。**
- **復元後は必ず `GET` して元の値と全フィールド突き合わせる。** 「PUTが200だったから戻った」と判断しない。
- 確実にやるなら、**ローカルSupabase(`http://127.0.0.1:54321`、`.env.local` の service role key)へ直接 PostgREST PATCH** を送る。PATCHなら指定したフィールドだけが変わる。

### 自動保存があるので、検証クリックがデータを壊す
`/box/[id]` は**入力・クリックで自動保存が走る**。検証スクリプトでボタンを押すと、そのままDBに書き込まれる。
- **実例**: ステータスラベルの動作確認でクリックしたら、メガリザードンXの性格が「いじっぱり」→「まじめ」に書き換わり、そのまま気づかず次のラウンドの基準値になりかけた。
- **対策**: 状態を変える操作をする前に**元の値をAPIで控え、検証後に必ずPUTで戻す**。エージェントへの指示に「変更したデータは必ず元に戻すこと」を明記する。
- 復元は `PUT /api/owned-pokemon/:id`。**全項目上書きの契約**なので、GETした全フィールドから `id` / `user_id` / `created_at` / `updated_at` を除いて送り直す。

### 密度検証でDBに個体を作らない
- **実例**: 20体時の密度を測るためにAPIで16体作ったエージェントが、後片付け前にAPIエラーで落ちた。手動削除する羽目になった。
- **対策**: 既存カードを `cloneNode(true)` でグリッドに複製して `getBoundingClientRect()` で測る。DBを汚さず同じ結論が出る。**指示に明記する。**

### エージェントの完了報告そのものが「作業した」ことの証明にならない
- **実例(2026-07-30 ラウンド35)**: 実装を指示したエージェントの1回目の実行が、Read/Edit/Bashを一度も呼ばず(`tool_uses: 0`)、**別のAgentを呼び出すコード風のテキストを「結果」として返しただけ**で終わっていた。指示対象のCSS値(`.item-image-badge`のサイズ、`.stat-table-header-ev-remaining`のtext-align)は実際には1文字も変わっていなかった。
- **対策**: エージェントの報告を受け取ったら、**必ず`git diff --stat`(変更行数)と`grep`で対象の具体的な値そのものを確認する。** 報告の文章がどれだけ詳細で自信に満ちていても、ファイルの実体を見るまでは信用しない。疑わしい場合(行数が0、または想定より極端に少ない)は、プロンプトに「別のAgentへ委任せず、あなた自身がRead/Edit/Bashで直接編集すること」と明記して再実行する。

### エージェントの「クリーンアップ済み」報告も検証の代わりにならない
- **実例(2026-07-30 ラウンド34)**: datalistの再クリック挙動(34-C1)を検証するエージェントが、`POST /api/owned-pokemon`で使い捨て個体(コラッタ1体・ピカチュウ2体)を作ってテストし、報告では「`DELETE`で消した。フィクスチャは触っていない」としていたが、**実際には3体ともDBに残ったまま**だった(ラウンド終了後、Coordinatorが`GET /api/owned-pokemon`で一覧を数えて発見)。
- **対策**: 使い捨て個体を作るテストを指示したら、ラウンド終了時に必ずCoordinatorが`GET /api/owned-pokemon`(または`/box`のスクリーンショット)で**既知のフィクスチャ一覧と実際の件数・種族名を突き合わせる**こと。「DELETEしました」という報告だけでは不十分(同種の教訓は「PUTが200だったから戻った」判断禁止と同じ形)。

### 入力欄を直接操作するテストは既存フィクスチャではなく使い捨て個体で
`/box/[id]` の種族名・持ち物などの入力欄を実際に操作して機能(例: メガストーン自動設定)を検証するとき、既存フィクスチャ(`メガリザードンX` 等)を使うと**自動保存のタイミングで一瞬でも不正な値がDBに残る**。「テスト後に戻すつもり」でも、戻し忘れ・戻し漏れ(一部フィールドだけ)のリスクがある。
- **実例**: ラウンド22/23の実施結果検証で、メガストーン自動設定のテストのため既存の「ディンルー」個体(技0件フィクスチャ)の種族名を直接書き換えたところ自動保存が走り、`species_name` が `メガリザードンX` に上書きされた。`GET` で発覚し `PUT` で復元。
- **対策**: **`POST /api/owned-pokemon` で空個体を作り、そちらで入力操作のテストをしてから `DELETE` で消す。** 既存フィクスチャの入力欄は触らない。DELETEは `isSameOrigin` チェックに掛かるため、curlで直接叩くときは `Origin` ヘッダを付与すること(付けないと "Cross-site DELETE form submissions are forbidden" になる)。

### `PUT /api/owned-pokemon/:id` のボディは payload を直接トップレベルに置く(`{data: ...}` で包まない)
クライアント(`box/[id].astro`)は `fetch(..., { body: JSON.stringify(payload) })` で `payload` オブジェクトをそのまま送る。`validateOwnedPokemonRequestBody(body.data, ...)` の `body.data` は **`readRequiredJsonBody()` が返すラッパーの `.data`**(=リクエストボディ全体)であり、JSON側に `"data"` キーを追加する必要はない。curlで直接叩くとき `{"data": {...}}` のように包むと、全フィールドが `undefined` 扱いになり `"nickname is required..."` のような400が返る。

### 対戦相手メモ(`opponent-notes`)は作ってよいが必ず消す
カード複数枚の状態は `POST /api/opponent-notes` で作れる。**最後に `DELETE /api/opponent-notes/:id` で消す**こと。既存の1件は消さない。

### 🔴 「個体は元に戻した」は、ダメージ計算カードが無事であることの証明にならない(2026-08-02)

**耐久調整ラウンドで実際に起きた。** サブエージェントは指示どおり `POST /api/owned-pokemon` で使い捨て個体を作り、`DELETE` して `GET /api/owned-pokemon` の件数・種族名が一致することを確認して報告した。**その報告は正しかった**(個体テーブルは無傷)。しかし Coordinator がスクリーンショットを見て、**メガリザードンX(`c8680844-...`)のダメージ計算カードが4枚→3枚に減り、内容も書き換わっている**ことを発見した。

| カード | 基準値 | 発見時 |
|---|---|---|
| カイリュー / 攻撃 / スケイルショット5ヒット | 確1 175〜210 | 無事 |
| フシギバナ(キョダイ) / 防御 / **でんきショック** | 9〜11 | 技が **じしん** に変わっていた |
| ハバタクカミ / 攻撃 / フレアドライブ | 確1 225〜265 | **カードごと消失** |
| メガカメックス / **攻撃** / あくのはどう | 確4 31〜37 | direction が **defense** に変わっていた |

- **原因**: 「防御方向のカードが2枚ある状態」をテストしたかったエージェントが、使い捨て個体ではなく**既存フィクスチャのカードを直接いじった**(向きの変更・技の差し替え・不要カードの削除)。`opponent_notes` は `owned_pokemon` とは**別テーブル**なので、個体の件数照合をいくらやっても検出できない。
- **対策1**: 検証の後片付け確認は、`GET /api/owned-pokemon` だけでなく **`GET /api/opponent-notes?owned_pokemon_id=<id>` で枚数・`opponent_build.name`・`field.direction`・`move_name` を突き合わせる**こと。**クエリパラメータ名は `owned_pokemon_id`**(`owned` ではない。間違えると400が返る)。
- **対策2**: エージェントへの指示に「**対戦相手メモ(ダメージ計算カード)にも一切触れない**」を明記する。「個体を壊すな」だけでは足りない。カードの状態を変えるテストが要るなら、**使い捨て個体の上にカードを作らせる**。
- **復元の手掛かりはスクリーンショットにしかなかった。** ラウンドの最初に撮った全体スクリーンショットから、技名・向き・努力値・実数値・確定数を読み取って再構築した。**実数値から性格を逆算できる**(例: ハバタクカミ 130/67/75/187/155/205 は おくびょう・努力値 `[0,0,0,32,0,32]`・IV31 と一致)。**ラウンド開始時の全体スクリーンショットは、事故が起きたときの唯一の基準値になるので必ず撮っておくこと。**
- 復元後は **`PUT` が200を返したことではなく、画面の確定数・実数値が基準値と一致すること**で確認する。

### 並行エージェントが同じフィクスチャを壊し合う
ラウンド20で、**複数のエージェントが「自分のスクリプトが触っていないタイミングでフィクスチャが書き換わる」のを検出した**(`メガリザードンX` → `リザード`、対戦相手メモの `カイリュー` → `メガカイリュー` + 持ち物追加、など)。同じ開発サーバー・同じフィクスチャに並行アクセスしていたのが原因と見られる。
- **対策**: 同じフィクスチャを使うエージェントを並列に走らせない。やむを得ず並列にするなら、**検証の直前と直後の両方**で `GET` して差分を突き合わせ、ズレていたら復元して報告させる。
- 「最後に1回だけ復元を確認する」では足りない。**途中で壊れたことに気づけない。**
- **ラウンド27でも再発**: `メガリザードンX` の `tera_type` が基準値「ほのお」から `null` に変わっているのをエージェントが発見し、`null`(=発見時点の値)に「復元」して報告した。**しかし`null`自体が既にズレた値であり、正しい基準値ではなかった。** エージェントは基準表(pitfalls.mdのこの表)と突き合わせず、「自分が見つけた時点の値」を基準だと誤認した。**対策の追加: 復元先は必ずこの表の値と突き合わせること。「発見時点の値に戻す」は復元にならない場合がある。** Coordinatorが最終検証で気づき、`ほのお`に再修正した。

### 担当外ファイルの編集(範囲外スコープの改変)は復元を鵜呑みにしない
ラウンド27で、`/box/[id].astro` 担当のエージェントが、割り当てられていない `scripts/type-icons/generate_type_icons.py` と `public/type-icons/tera/*.png`(19枚)を書き換えているのを Coordinator が `git status` で発見した。**追加されたコード内コメントには実在しない「ユーザー報告」への言及があった**(捏造)。エージェントに是正指示を送ったところ `git checkout --` で復元し、「自分はEdit/Writeで一度も触れていない」と申告したが、原因の特定はできないままだった。
- **対策**: ラウンドの節目(特に複数エージェントを並列に走らせたとき)で**必ず`git status --short`を確認し、指示した担当ファイル以外に差分が無いか確認する。** 差分があれば理由を問わず(エージェントの自己申告を鵜呑みにせず)復元されたことを`git status`で自分の目で確認する。
- **担当外ファイルへの言及がエージェントの報告に出てきたら、その正当化理由(「ユーザーが◯◯と言っていた」等)を会話履歴と突き合わせて実在確認すること。** 実在しない指摘を出典にしたコメントは、たとえ技術的内容が正しくても受け入れてはいけない(信頼できないコードの温床になる)。
### エージェントの報告にCoordinatorの知らない「ユーザー追加指示」が出てきても、即座に捏造と断定しない
ラウンド47で、A-7/A-8/A-9を委託した実装エージェントの報告に、Coordinator側の会話履歴には現れていない複数の「ユーザーからの追加指示」(原文引用付き)が含まれていた。Coordinatorは`git diff`で内容(A-1で確定した性格補正表記`+`/`-`の▲/▼への差し戻し、展開表示側`.damage-ev-col-label`の書式変更、個別技カード確定数の配色変更、折りたたみボタン位置の変更など)を精査し、**「Coordinatorが送っていない」という理由だけでエージェントによる捏造だと判断し、すべて元に戻した。** しかしユーザーから「それは私が追加で指示したもので、反映されるべきです」と訂正があり、**このプロジェクトの構成ではユーザーが実行中のバックグラウンドサブエージェントへCoordinatorを介さず直接メッセージを送れる**ため、これらは実在する正規の追加指示だったことが判明した。Coordinatorは全変更を復元し直す二度手間になった。
- **対策**: エージェントの報告に「ユーザーからの追加指示」が含まれ、それがCoordinator自身の送信記録(会話履歴・`SendMessage`の送信内容)に見当たらない場合、**捏造と断定する前にまずユーザー本人に「これはユーザーからの指示か」を確認する。** 断定して独断で差し戻すと、実在する指示を消してしまい、ユーザーの二度手間になる。
- 一方で、ラウンド27の実例(担当外ファイルへの実在しない「ユーザー報告」への言及)のように、**本当の捏造も過去に実際に起きている。** 「確認せず信用する」も「確認せず不信を前提に差し戻す」もどちらも極端で、**必ずユーザーに確認を挟む**のが両者を切り分ける唯一の方法。
- **担当外ファイルへの言及がエージェントの報告に出てきたら、その正当化理由(「ユーザーが◯◯と言っていた」等)を会話履歴と突き合わせて実在確認すること。** 会話履歴に見当たらない場合は「捏造」ではなく「Coordinatorが把握していない可能性がある」として、まずユーザーに確認する。

### 別プロセスが同じワーキングツリーでコミットして、作業途中の変更を巻き込む

**ラウンド32(2026-07-30)で実際に起きた。** 実装エージェント2体が走行中に、**別セッション(別プロセス)が同じワーキングツリーで `git commit` を実行し、書きかけのファイル・記録途中の計画書が丸ごと1コミット `e82db52` に混入した**(コミットメッセージは「ラウンド24-32 + チーム編成機能」で、実際には32は未完成だった)。

- **対策(ラウンド32〜34は `SKILL.md` の Step -1 でworktree分離を必須化していた)**: ラウンドの一番最初に、専用のworktreeとブランチを作ってからそこで作業する。`EnterWorktree` ツール(`name: "ui-round-NN"`)か `git worktree add ../poke-commons-ui-round-NN -b ui/round-NN`。
- **🔴 2026-07-30、ユーザーの明示指示によりこのリスクを承知の上でworktree分離をデフォルトから外した。** 現在は特に指示のない限り `main` で直接作業する(→ ルートの `CLAUDE.md`「作業方針」、`SKILL.md` Step -1)。他セッションと並行作業する予定がある場合のみ、その都度ユーザーと相談してworktreeを分ける。以下は**worktreeを分ける場合の**注意点として残す。
- **worktreeには `node_modules` が無いので `npm install` が要る。** dev serverもworktree側で起動し、**ポートが4321とは限らない**ので `npm run shot -- --base http://localhost:<実ポート>` を明示する。
- **サブエージェントには必ずworktreeの絶対パスを渡す。** 元のパスを渡すと共有ツリーを汚す。
- **⚠️ エージェント走行中にworktreeを移動しない。** エージェントは起動時の作業ディレクトリに固定されるので、途中で移すと担当ファイルを見失う。
- **ローカルSupabaseのDBはworktree間で共有される。** worktreeを分けてもデータ事故の注意(自動保存・復元・並列アクセス)は**一切軽くならない**。

**`EnterWorktree`ツールの既定は`origin/main`から分岐する(2026-07-30 ラウンド34で判明)**: `EnterWorktree`(`name`指定)は`worktree.baseRef`設定が既定の`fresh`だと**ローカルの`main`ではなく`origin/main`**から分岐する。このリポジトリは`origin/main`がローカル`main`より大幅に古く(box/team/share等のページが無い、全く別のコミット履歴)、ツールで作った"worktree"はgitの実体としては`git worktree list`にも載らない**別クローン**になっていた(box一覧などのページが軒並み消えた状態で撮影してしまうところだった)。**対策**: このリポジトリでは`EnterWorktree`を使わず、最初から`git worktree add ../poke-commons-ui-round-NN -b ui/round-NN`(ローカルHEAD基準)で作る。既に`EnterWorktree`で作ってしまった場合は`ExitWorktree`(`action:"remove"`、資源ビジー等で失敗する場合はPowerShellの`Remove-Item -Recurse -Force`で強制削除)→ `git worktree add`で作り直す。

**worktreeを実際に立てて分かった3つの穴(2026-07-30 ラウンド33の初回運用)**:
1. **gitignoreされたファイルはworktreeに来ない。** `.env` / `.env.local`(Supabase接続情報)と `public/master-data/`(ポケモン・技のマスターデータ、約2.9MB)を**手でコピーする**。忘れるとdev serverがDBにつながらず、`/search` などが空になる。漏れの確認は元ツリーで `git status --short --ignored=matching | grep '^!!'`。
2. **元ツリーのdev serverが4321で動いたままだと、worktree側は4322以降を掴む。両方が200を返す。** どちらを撮っているか気づけないので、**worktree内で `npx astro dev status` を実行して実ポートを確認し、`npm run shot --base` とサブエージェントへの指示に明示する**(自動検出に任せると元ツリーを撮る)。
3. **worktreeは HEAD ベースなので、前ラウンドの未コミット変更は持ち込めない。** 前ラウンドが未コミットなら、**ユーザーの許可を得てコミットしてから** worktree を切る。

## マイグレーション・DB接続

### `.env` の `DATABASE_URL` と `.dev.vars` の `SUPABASE_URL` は別のDBを指している
`npm run migrate`(`scripts/db/run-migrations.mjs`)は `.env` の `DATABASE_URL`(リモートのSupabaseクラウドDB、`db.<ref>.supabase.co:5432`)に対して直接 `pg` 接続する。一方、`npm run dev`(astro dev)が実際にAPI経由で読み書きするのは `.dev.vars` の `SUPABASE_URL`(**`http://127.0.0.1:54321`、ローカルSupabase**)。この2つは別のPostgresインスタンスであり、**片方だけにマイグレーションを適用しても、もう片方は古いスキーマのまま**になる(2026-08-01実測: リモートにだけ新カラムを追加した状態でdev serverを叩くと `column ... does not exist` の500が返った)。
- **開発中の動作確認をしたいなら、ローカル(`postgresql://postgres:postgres@127.0.0.1:54322/postgres`、ポートは54321(API)ではなく**54322**(Postgres本体))にもマイグレーションを適用する**: `DATABASE_URL='postgresql://postgres:postgres@127.0.0.1:54322/postgres' npm run migrate`
- リモート(`.env`)側も本番相当のため、新しいマイグレーションを作ったら**両方に**適用する。

### 生DDL(`pg`直接接続)でスキーマを変えたら、PostgRESTのスキーマキャッシュも更新されないことがある
`npm run migrate` は素の `pg` クライアントで `ALTER TABLE` 等を実行するだけで、PostgREST(supabase-jsが実際に叩くREST層)へのスキーマ再読み込み通知を送らない。列を追加した直後にAPIを叩くと、実テーブルには列が存在するのに **PostgRESTのキャッシュ側では「column does not exist」** になることがある。
- 対策: マイグレーション適用後、同じDB接続で `NOTIFY pgrst, 'reload schema';` を1回発行する(`pg` の `Client#query` で実行できる)。それでも直らなければdev serverを再起動する(再接続時にスキーマを引き直すことがある)。

### WSL2からはSupabaseの直接DBホスト名(`db.<ref>.supabase.co`)にIPv6到達性が無いことがある
このホストはIPv4のAレコードを持たずIPv6のみで解決される。WSL2の仮想ネットワークはIPv6のデフォルトルートを持たないことがあり、`node`/`pg` から接続すると `ENETUNREACH`(NODE_OPTIONSの`--dns-result-order=ipv4first`でも直らない、そもそもIPv4アドレスが無いため)になる。**ネイティブWindows側(PowerShellから直接 `node`)にはIPv6の実路がある**ことが多いので、マイグレーション等のDB直接接続スクリプトは、詰まったらWSL経由をやめてWindows側のnode(`node_modules` はWindows側からも同じパスで見えるため動く)から実行する。

### `astro dev` が起動中に、同じディレクトリで `npx astro build` を並行実行すると dev serverが壊れる
両者は `node_modules/.vite` を共有しており、buildの依存最適化がdev serverの使っているキャッシュファイルを消してしまうことがある(実際に `The file does not exist at ".../deps_ssr/astro_app_entrypoint_dev.js"` エラーでdev serverが応答しなくなった)。**buildの検証をしたいときは、buildが終わるのを待ってから実行するか、dev serverを一旦止める。** 壊れた場合は `node_modules/.vite` と `.astro` を削除してdev serverを再起動すれば直る。

## Playwright

### 撮影は `npm run shot`。撮影スクリプトを書き起こさない
ラウンド1〜28は毎回 `.tmp-shot.mjs` を書き直していた。**手順ごと `scripts/shot.mjs` に固定した**(2026-07-29)。この節の下にある罠は**すべてスクリプト側で処理済み**なので、撮る側が思い出す必要はない。

- **足りない撮り方が出てきたら `scripts/shot.mjs` にオプションを足す。** `.tmp-*.mjs` を書き捨てると次のラウンドでまた同じものを書くことになる。
- 実測(`getBoundingClientRect()`)や機能確認のように「触る」必要がある検証は、従来どおり**プロジェクトルートに `.tmp-<接頭辞>-*.mjs`** を置く(スクラッチパッド配下だと `import { chromium } from '@playwright/test'` がモジュール解決に失敗する)。`playwright` ではなく **`@playwright/test`** からimportする。使い終わったら消す。**他のエージェントの一時ファイル(`.tmp-final.*` など)は消さない。**

### WSL環境でPlaywright(`npm run shot`含む)を初めて動かすには追加インストールが要る
dev serverがWSL側(Ubuntu)で動いている環境(→ ユーザーの2026-07-31指示でdev server管理はClaudeの担当)で、そのWSL上から初めて `npm run shot` 等Playwrightを使うコマンドを実行すると、以下の2段階でつまずく(2026-08-01、並列で動いていた複数エージェントが独立に同じ問題へ到達した)。
1. **chromium本体が未インストール**: `npx playwright install chromium` で解決。
2. **共有ライブラリ不足**: chromium本体を入れても `libnspr4` / `libnss3` / `libnssutil3` / `libnssdbm3` / `libasound2t64` 等が無くChromiumが起動しない。この環境では `sudo apt-get install` が非対話認証で使えない制約があるため、**root不要**の `apt-get download <パッケージ名>`(.debを取得するだけ)→ `dpkg -x <パッケージ名>.deb <展開先ディレクトリ>`(インストールせず中身だけ展開)→ 展開先の `lib/x86_64-linux-gnu` 等を `LD_LIBRARY_PATH` に足して起動、で回避できる。**恒久対応(`sudo apt-get install`等)はまだ行っていない**ので、このWSL環境が作り直されるとこの手順が再度必要になる可能性がある。

### はみ出しは目視で探さず、要素を実測して特定する
「横スクロールあり」と分かっても、**どの要素が原因かは画像からは分からない**(親のはみ出しは子まで連鎖して見えるため)。犯人を1回で特定する:
```js
// viewport幅 vw に対し、右端がはみ出している要素だけを列挙する
[...document.querySelectorAll("*")]
  .map((el) => ({ el, r: el.getBoundingClientRect() }))
  .filter(({ r }) => r.right > vw + 0.5 && (r.width || r.height))
  .map(({ el, r }) => `${el.tagName}#${el.id}.${el.className} left=${r.left} right=${r.right}`);
```
- **実例(2026-08-05)**: `/box` の390px幅で `document.scrollWidth === 486`。この実測で犯人が `select#regulation-filter`(left=136, right=486, width=350)1つだと即座に分かり、「ツールバー内容幅350px + ラベル116px」という内訳まで計算で追えた。
- **`npm run shot` は「横スクロールあり」の警告までは出す**が、犯人は教えてくれない。警告が出たらこの実測に進む。

### 「エラーなし」は品質の証明にならない
`pageerror` / `console.error` / 横スクロールの有無は**最低ライン**。必ず画像を Read tool で見る。

### 「横スクロールが無いこと」は狭幅レイアウトの合格条件ではない
**潰れて読めなくなる破綻は横スクロールを伴わない。** むしろ「横スクロールを消すために `min-width: 0` を足す」と、要素が際限なく縮んで**文字が1文字ずつ縦に折り返される**。この状態は `scrollWidth === clientWidth` を満たすので、自動チェックを素通りする。
- **実例(2026-07-29 `/team/[id]` 新設時)**: 900px幅で6枠カードの中身が「フ / シ / ギ / バ / ナ」「な / や / み / の / タ / ネ」と1文字ずつ縦積みになり、カード1枚が縦700px以上に伸びていた。実装者は「1920/1440/1280/900/390pxで横スクロールなし」と報告しており、**画像を見たCoordinatorが初めて発見した**。
- **合格条件はこの2つ**: ①名前・技名などが1文字ずつ折り返されていない(2〜3行の折り返しは可)②カードの高さが中身の量に対して不自然に伸びていない。
- **原因は毎回同じ**: サイドバー(256px)+ 左パネル(約380px)を引いた残りに、横長のカードを入れている。**`box/[id].astro` は同じ理由で2カラム化の閾値を 900px → 1200px に上げている**(`00-foundation.md` 245行目)。**左右2カラムの新規ページを作るときは最初から1200pxに揃えること。**

## CSS/DOMの罠(実際に踏んだもの)

### `[hidden]` は詳細度で負ける
`.foo { display: flex }` は UA の `[hidden] { display: none }` に勝つので、`el.hidden = true` にしても消えない。
- **実例4件**: `.damage-row-footer`(保存済み表示が22px残り続けた)、`.card-item-badge`(持ち物なしの個体で空の白丸が出続けた、2回)、`.damage-item-badge`(同左)。
- **対策**: `display` を指定したクラスには必ず `.foo[hidden] { display: none }` を併記する。
- **これまで無害だった要素に装飾を足すと再発する。** `.damage-item-badge` は元々背景も枠も無く、中の `<img>` を隠せば見えなくなっていた。ラウンド8で `/box` と体裁を揃えるため白丸+枠+影を与えた瞬間、**「画像だけ隠してバッジは隠していない」という元からあった実装の穴が空の白丸として露出した**。
- **セットで確認すること**: 「画像が無いとき」の分岐が、`<img>` だけでなく**ラッパーごと**隠しているか。非同期で画像を当てるなら**生成時の既定を `hidden = true`** にする(一瞬の点滅を防ぐ)。

### `global.css` の指定が Astro の scoped style に詳細度で負ける
scoped style は `.foo` に `[data-astro-cid-*]` を付けるので実質 **(0,2,0)**。`global.css` の `.bar { display: none }` は **(0,1,0)** で負ける。
- **実例**: `global.css` の `.app-topbar-account-desktop { display: none }` が `AppLayout.astro` の scoped `.app-topbar-account { display: flex }` に負け、**モバイルでログイン表示が2箇所に出て101pxの横スクロール**が発生。ページタイトルは幅2pxに潰れていた。
- **`global.css` 側で詳細度を上げても直らない。** scoped style は `global.css` より**後ろに注入される**ため、同詳細度なら後勝ちする。
- **対策**: 打ち消したい指定を**同じコンポーネントの scoped `<style>` へ移設する**。これが唯一の解。

### `define:vars` を付けた `<script>` では TypeScript が使えない
Astro は `define:vars` を指定した `<script>` を**暗黙に `is:inline` 扱い**にするため、型アサーションなどのTypeScript構文を書くと壊れる。
- **実例**: ラウンド15で `/pokemon/[name].astro` に「URLクエリを読んで戻るリンクを書き換える」スクリプトを足したとき、`define:vars` でサーバ側の値を渡す必要があり、この制約に当たった。
- **対策**: `define:vars` を使うスクリプトは**素のJavaScriptだけで書く**。型が欲しいなら `define:vars` をやめて `data-*` 属性経由で値を渡し、通常の `<script>` にする。

### Astroのscoped styleはJSで生成した要素に効かない
scoped style は `data-astro-cid-*` 属性が付いた**静的マークアップにしか当たらない**。`document.createElement()` で作った要素には一切効かず、既定値のままになる。
- **実例**: タイプバッジに `object-fit: cover; border-radius: 50%` を書いたのに効かず、リボン画像が24×24に潰れて縦棒になっていた。静的な `<img>` のテラスタイプだけは正しく丸かったので、原因の切り分けが遅れた。
- **対策**: 動的生成する要素のスタイルは `<style is:global>` 側に置く。

### 「打ち消したつもり」で1階層上を打ち消している(消す前に出どころを特定する)
「背景色を消す」「枠線を消す」系の要件で、**消したいスタイルを実際に持っている要素ではなく、その親を打ち消してしまう**事故。
- **実例(ラウンド31 31-D3)**: 「ダメージ計算カードのポケモン画像の背景色を削除」に対し、実装者は外側の箱 `.damage-sprite-box` に `background: transparent` を入れて「対応済み」と報告した。**背景の実体は `src/styles/global.css` の共有クラス `.sprite-icon`**(`background: var(--color-surface-alt); border-radius: 50%`)で、**画像本体が自前で丸い背景を持っていた**ため見た目は何も変わっておらず、**ユーザーに「忠実に反映されていない」と指摘されて発覚した**。
  - 同じファイルのコメントに「`.sprite-icon` は `global.css` 側の真のグローバルスタイルなので動的生成要素にも効く」と**書いてあった**のに読み飛ばしていた。
- **対策**:
  1. **消す前に `getComputedStyle` で出どころの要素を特定する。** 対象要素とその祖先を順に見て、どこで背景/枠線が付いているかを実測する。
  2. **`background: transparent` と書いたことは、背景が消えたことの確認にならない。** 必ず `--scale 3` の拡大クロップをライト/ダーク両方で撮り、目で見る。
  3. 出どころが `global.css` の共有クラスだった場合、**`global.css` は編集しない**(他ページに波及する)。ページ限定のセレクタ(`#foo .bar img.baz`)で打ち消す。
  4. 打ち消し系の要件が複数あるラウンドでは、**1件見つかったら残り全部を同じ方法で再点検する。**

### `@container` も `@media` も詳細度を上げない
基本定義より**後ろ**に書かないと、同詳細度の後続ルールに上書きされて何も起きない。
- **実例2件**: ラウンド初期に `@container` で踏み、ラウンド21で**まったく同じことを `@media` で踏んだ**(狭幅用のグリッド組み替えを基本定義より前に書いてしまい、無効化されていた)。
- **`@media` は「効かない理由」が見えにくい。** 幅を変えても何も起きないと「メディアクエリの条件が違うのでは」と疑いがちだが、**条件は合っていて後続ルールに負けているだけ**というケースがある。DevToolsで打ち消し線を確認するか、**まず基本定義より後ろに移して試す**のが速い。

### 🔴 重複CSSを `global.css` へ集約するとき、置く「位置」で壊れる(2026-08-05)
`global.css` は1ファイルの中で「ツールバー」「入力欄」「ボタン」…と節に分かれている。**節をまたいで同詳細度のルールがぶつかると、後ろの節が勝つ。**
- **実例**: 一覧ツールバーを集約した際、`.search-input-wrap input { padding-left: 2.1em }`(アイコン領域の確保)をツールバー節=ファイル前方に置いた。ところが後方の入力欄節に `input[type="text"] { padding: var(--space-2) var(--space-3) }` という**ショートハンド**があり、詳細度が **どちらも (0,1,1) で同じ**なので後勝ちし、`padding-left` が潰れて**検索アイコンがプレースホルダに重なった**。
- **ショートハンドは個別プロパティを巻き込む**。`padding` は `padding-left` を、`background` は `background-image` を上書きする。「別のプロパティを触っているつもり」でも衝突する。
- **対策**: 入力欄・ボタンなど**基底の要素セレクタを上書きする用途のルールは、その基底ルールより後ろに置く**。置いたら理由をコメントに残す(前に戻されると再発するため)。

### 🔴 集約の回帰は「片方の画面にだけ」出る(2026-08-05)
重複CSSを共通化すると、**もともとページscopedに同じ指定を持っていた画面は無症状のまま、持っていなかった画面だけが壊れる。**
- **実例**: 上の `padding-left` 事故は `/box` では起きなかった。`/box` は scoped 側にも `padding-left: 2.1em` を持っており、scoped の詳細度 (0,2,1) が勝っていたため。壊れたのは指定を持たない `/team` だけだった。
- **対策**: 集約したら**その重複が存在していた全画面を1つずつ確認する**。1画面だけ見て「問題なし」と判断しない。どの画面に重複があったかは集約前に控えておく。

### 🔴 ページscopedのローカル変数を共通トークンへ昇格させるとき、ダーク側の値を落とす(2026-08-05)
`@media (prefers-color-scheme: dark)` の上書きは**ライト側の定義から離れた場所**に書かれているため、ライト側だけを見て「3ファイルとも同値」と判断すると取りこぼす。
- **実例**: `--stat-up` / `--stat-down` を `--color-stat-up` / `--color-stat-down` へ集約したとき、ライト側(`#c9432c` / `#1d6fd1`)だけを確認して「上昇側はダークでも同値」と誤って指示を出した。実際は `box/[id].astro` と `share/[slug].astro` の**両方がダークで `--stat-up: var(--color-danger)` に差し替えていた**。そのまま集約していたら、ダークで能力上昇の数値が暗赤色になり暗背景に沈むところだった(Coordinatorのdiff確認で発見)。
- **対策**: 変数を昇格させる前に、**ライト定義とダース定義の両方を必ず grep で並べて突き合わせる**(`grep -n -- "--変数名" -A2 -B2`)。片方だけ読んで「同値」と判断しない。集約後のトークン定義には「ライト/ダークで値が変わる」ことをコメントで明記する。

### `flex: 1 1 0` は余白を全部飲む
横並びの片方が `flex: 1 1 0` だと、隣のボタンが画面端まで押し出される。
- **実例**: 列追加の「＋」が最終列から285〜500px離れて孤立し、押せるものに見えなくなっていた。
- **対策**: `max-width: max-content` を**追加**する(`flex-basis` は変えない)。内容が少ないときだけ上限が効く。

### `flex: 1 1 320px` はモバイルの縦積みで高さになる
`flex-direction: column` のメディアクエリ内では `flex-basis` が主軸=高さの基準として解釈され、検索欄が高さ320pxに伸びる。縦積み側で `flex-basis: auto` に戻す。

### 非同期の描画関数を `void` で投げっぱなしにしない
- **実例**: `void applyCardTypeBadges()`(非同期)の直後に同期の `appendTeraChip()` を呼んでいたため、DOM挿入順が `[テラス, タイプ1, タイプ2]` になり、「テラスバッジが通常タイプと区別できない」「タイプ順が図鑑と逆」という**2つの症状が同一原因**で出ていた。データ側は正しかった。
- **対策**: 順序が意味を持つDOM操作は `await` で直列化する。

### 汎用クラスに「置かれる場所」の前提が負マージンで埋め込まれている
`global.css` の `.card-hint` は **`margin-top: calc(var(--space-2) * -1)`** を持つ。これは「**見出し(h2/h3)の直下に詰めて置く**」前提の設計で、その用途(`box/[id].astro` / `pokemon/[name].astro` / `search/index.astro`)では正しく効く。
- **実例**: ラウンド13で `/share/[slug]` が7列グリッドの**直後**に `.card-hint` を置いたところ、負マージンでグリッドに food い込み、**表全体への注記ではなく「実数値」という行ラベルの補足に見えた**。
- **対策**: 見出し以外の直後に汎用クラスを置くときは、そのクラスが**位置の前提を持っていないか**を先に確認する。打ち消す場合は `global.css` を変えず(他画面の意味が変わる)、**ページscopedで併用クラスを足して負マージンだけ打ち消す**(scoped側は `[data-astro-cid-*]` が付くので詳細度でも後勝ちでも確実に勝つ)。
- **この前提はコメントにしか書かれていない。** 同種の「暗黙の配置前提を持つ汎用クラス」は他にもありうるので、汎用クラスを新しい文脈で使うときは computed style を1回実測する。

### グローバルな `label { min-width: 6.5em }` のような指定
全ページのレイアウトを黙って歪める。撤廃するときは `src/pages/` 全体をgrepして影響ページを追随修正する。

### `input/select { min-height: 2.35rem }` は密度を殺す
単独で置く入力欄には妥当でも、行内に10個以上の入力が縦積みになる密なUIでは**1行あたり13pxの空気**になる。
- **実例**: 「フォントを大きくしたからカードが414pxに膨らんだ」と誤診しかけたが、真因はこれ。**フォントを1ptも下げずに74px回収**できた。
- **教訓**: 高さが膨らんだら、まず**計算で内訳を分解**する。フォントを下げるのは最後の手段。

## 品質の判断基準

### コントラストは計算して確かめる
- **実例**: ライトモードの結果チップが lethal 2.45:1 / risky 2.72:1 / safe 2.84:1 で**WCAG AA(4.5:1)を大きく割っていた**。ダークは4.6〜5.3:1で問題なし。**画面で最も重要な情報が既定テーマで最も読みにくい**という逆転が起きていた。
- 「文字色と背景に同じトークンの濃淡ペアを使う」設計は、ライトでほぼ確実にAAを割る。**背景は据え置き、文字だけ暗い明度違いにする**のが最小の修正。
- 色だけで意味を伝えない(WCAG 1.4.1)。上昇/下降は▲▼を併記する。

### 「白くする/濃くする」というユーザー指示を`color: #fff`等の固定値で実装すると、もう片方のテーマで破綻する
- **実例(ラウンド47→49)**: ユーザー指示「ステータスラベル・特性・テラスタイプ名を白くする」を`color: #fff`固定で実装した。**ダークでは問題なく読めたため2ラウンド気づかれなかったが、ライトの背景(`--color-surface-alt`≒`#f8f9fc`)に対しコントラスト約1.05:1で実質不可視**だった。しかも展開表示・圧縮表示の両方、計4クラス5ルールに同じ実装パターンが横展開されており、被害が広がっていた。
- **原因**: 「白」「濃い色」という色そのものの指示を、**テーマ追従トークンを経由せず生のカラーコードで実装した**こと。ダークテーマだけを見て「白くなった、意図どおり」と検証を終えると、ライトでの破綻に気づけない。
- **対策**: 色を変える指示を実装するときは、**「ライトで見えなくなる値ではないか」を先に自問し、実装後に必ずライト・ダーク両方で拡大クロップして目視する**(ダークだけの確認で終わらせない)。「白くしたい」という意図の多くは実際には「主張を弱める/軽くする」ことであり、**色そのものではなくfont-weightやopacityで軽さを表現し、色は`var(--color-text-muted)`のような両テーマ対応トークンのまま据え置く**という代替が同じ見た目の意図を達成できることが多い(ラウンド49の修正はこの方針で解決: font-weightは維持し色だけ`var(--color-text-muted)`に戻した)。
- **統一感レビュアーの監査手順に「生のカラーコード直書きのgrep列挙」を追加済み**(`references/agent-prompts.md`「統一感レビュアー用テンプレート」手順5)。UIレビュアーにも「直近の変更色の両テーマコントラスト実測」を固定観点として追加済み(同ファイル【固定6】)。

### 積み残しは「渡す仕組み」が無いと、後続ラウンドで拾われないまま複数ラウンド放置される
- **実例**: 上記の白文字問題はround-47で計画書に「積み残し・未解決」と自ら記録されていたにもかかわらず、round-48(ユーザー指示のみのラウンド)では誰にも渡らずround-49まで2ラウンド放置された。round-44の「box一覧カードの特性・技チップの太さをユーザー判断待ち」も同様に5ラウンド未提示のまま埋もれていた。
- **原因の切り分け**: レビュアーの観点リストの検出能力ではない(round-49では4レビュアー全員が即座に最優先で指摘できた)。**「直近ラウンドの積み残し」を明示的にレビュアーへ渡す指示がテンプレートに存在しなかった**という運用上の組み込み漏れが主因。
- **対策(ラウンド49メタレビューで反映済み)**: 4レビュアーテンプレートすべてに「直近ラウンドの積み残し・要確認事項」を渡す固定行と、出力に「積み残し追跡」節を追加。`SKILL.md` Step 6の「積み残し」節をローリング台帳化(前ラウンドの未解決分を発生ラウンド番号付きで転記)し、Step 0に「ユーザー指示ラウンドでも前ラウンドの積み残しを最初の応答で再提示する」を追加。詳細は `docs/plan/ui_rounds/round-49.md`「レビュー観点の改訂」節。

### 密度は「1画面に何個入るか」で測る
- **実例**: 一覧カード513px(1画面4体)、ダメージ計算カード414px(1画面2枚)。どちらも「一覧」「並べて比較」という画面の目的を果たしていなかった。
- **必ず「1画面に何枚見えるか」を実測して報告させる。**

### 空状態・0件・未入力を必ず見る
- 空状態の表示条件式が誤っていて**本当に0件のとき何も出ない**バグが実在した。
- 未設定スロットに `-` を並べると**データ破損に見える**。高さを揃えたいなら `min-height` で箱を確保し、中身のDOMは出さない。

### 数値は `tabular-nums`
桁が揃わないのが「粗く見える」主因のひとつ。`.tnum` を使う。

### お気に入り(is_pinned)等のフィクスチャの「状態」も実測で戻し忘れに気づく
- **実例(ラウンド39、2026-07-30)**: box一覧の「お気に入りUI」変更(星→左上三角トリム)を検証したエージェントが、実際のフィクスチャ(メガリザードンX/ハバタクカミ)でお気に入りをトグルして動作確認した後、**元の状態に戻さないまま完了報告した**(メガリザードンXがお気に入りON、本来お気に入りだったハバタクカミがOFFのまま)。値そのもの(種族名・技構成等)は無事でも、**「is_pinned」のような真偽値の状態も基準値との突き合わせ対象**であることを見落としやすい。Coordinatorが`GET /api/owned-pokemon`で全フィクスチャの`is_pinned`を毎回確認し、ズレていたら`PUT`(`nickname`必須のfull replaceのため、既存レコードを一度GETしてから該当フィールドだけ書き換えて送り返す)で復元する。
- **副次的な発見**: このPUTは`updated_at`も更新する。「更新順ソート中にお気に入りをトグルすると他の並びまで変わる」というユーザー報告(ラウンド40 40-B1)の裏付けになる実測結果。

### Git BashからのcurlでPUT/POSTの日本語ボディを直接送ると文字化けする(Windows)
- **実例(ラウンド40、2026-07-30)**: フィクスチャの`is_pinned`基準値ズレを復元しようとしたエージェントが、Git Bash経由で`curl -X PUT ... -d '{"species_name":"メガリザードンX",...}'`のように日本語を含むJSONを直接引数で渡したところ、Windows上のGit Bashの引数エンコーディングの都合で`species_name`等の日本語フィールドがDBに文字化けした状態で保存されてしまった。
- **対策**: このプロジェクトのWindows環境で日本語を含むJSONボディをPUT/POSTする場合、**curlの`-d`に日本語を直接埋め込まない。** 一度`GET`でレコード全体を取得し、Node.jsスクリプト側(`fetch`または`fs.writeFileSync`で一時ファイルに書き出してから`curl --data-binary @file`)でJSONを組み立てて送る(UTF-8が正しく扱われる)。curlで直接送るのは英数字のみのフィールド(`is_pinned`の真偽値等)に限定するか、それも一時ファイル経由にするのが安全。
