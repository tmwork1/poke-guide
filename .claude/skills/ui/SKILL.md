# UI単発修正

**単一の狭い指示を、その場で直して終わらせる。** 4レビュアーの講評・`docs/plan/ui_rounds/round-NN.md` への記録・sonnet実装者への委譲は行わない(これらは `ui-loop` skill の仕事)。2026-07-31、`ui-loop`(旧`ui`)がloop前提の重装備になり単発修正にも毎回フルコストがかかっていたため分離した。

## この skill を使ってよい条件

- ユーザーの指示が**1つの画面・1つの問題**に閉じている(複数画面にまたがる網羅的な見直しではない)
- 「講評してほしい」「品質を上げてほしい」のような**評価・磨き込みそのもの**を求める依頼ではなく、**直す内容がすでに指示に書かれている**

**作業中に想定より対象ファイルが多い/影響範囲が広いと分かったら、その場で頑張らず一旦止めてユーザーに「`ui-loop` で扱う規模かもしれない」と報告する。** 無理に軽量フローのまま進めない。

## 手順

### 1. 作業ブランチを確認する

**特に指示のない限り `main` で直接作業する**(→ ルートの `CLAUDE.md`「作業方針」)。`git status` で作業ツリーがクリーンか確認し、前回の未コミット変更が残っていたら先にそれをコミットするか、別作業中でないかユーザーに確認する。

### 2. 現状を確認する

対象要素・現在の値(余白・色・サイズ等)を、必要ならスクリーンショットで確認してから直す。**撮影は `npm run shot` を使う**(`scripts/shot.mjs`。Playwrightスクリプトを毎回書き起こさない)。

```bash
npm run dev            # 別ターミナルで先に起動しておく
npm run shot -- --page box/<id> --clip .card-damage --clip-pad 12 --scale 3
```

指示の対象が一目で分かる自明な修正(明確なクラス名・具体的な数値指定がある等)なら、この事前撮影は省略してよい。

### 3. 実装する

**基本は Coordinator 自身が直接編集する**(単一ファイル・小規模な変更が対象)。以下に該当する場合はsonnetサブエージェントへの委譲を検討する:
- 複数ファイルにまたがり並列化した方が速い
- ダメージ計算・jpoke絡みで `.claude/skills/jpoke/` の知識ベース確認を伴う実装
- サブエージェントに任せる場合も**「git commit / git push は絶対にしない」「DBに検証用データを作らない」を明記する**

守ること(`ui-loop` と共通):
- 配色トークン・ボタン方式など既存の確立済み規格を踏襲する。新しい値を作らない
- 育成ルール(IV=31固定・努力値0〜32スケール・Lv50固定)は**仕様でありバグではない**
- `.claude/skills/ui-loop/references/pitfalls.md` に載っている既知の罠(CSS/DOMの罠・データ事故・Playwright)を踏まない
- クラス名の改名・削除やAPI契約の変更はしない

### 4. 検証する(必須・省略しない)

- `npx astro build` 成功 / 関連する `npm test` pass
- **`npm run shot` で撮り直し、Read tool で自分の目で見る**(ライト・ダーク両方。省略しない)
- 数値目標があれば `getBoundingClientRect()` 等で実測
- DBを触った場合は元の状態に戻っているか確認

### 5. commit する

**Coordinator が `git commit` する**(特に指示のない限り。メッセージに直した内容を書く)。`git push` はしない。計画書への記録は行わない(変更内容の記録は commit メッセージと git log に任せる)。
