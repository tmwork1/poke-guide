# UI改修

**指示がすでに具体的な改修を、その場で直して終わらせる。** かつて存在したloop前提の重装備版`ui-loop`(4レビュアー講評・複数ラウンドの磨き込み)は成果が得られなかったため廃止した。実行手順(`.claude/skills/ui-loop/`)は削除済みだが、`docs/plan/ui_rounds/round-*.md`・`docs/plan/ui_plan.md`・`docs/plan/ui_parallelization.md`は`src/`のコードコメントから設計判断の根拠として引用されているため、凍結した記録として残してある(削除しない)。現在はこの`ui` skill1本で、単発の狭い指示から複数画面/複数ファイルにまたがるまとめ依頼まで対応する。

## この skill を使ってよい条件

- 「講評してほしい」「品質を上げてほしい」のような**評価・磨き込みそのもの**を求める依頼ではなく、**直す内容がすでに指示に書かれている**
- 画面・ファイルの数は問わない。1つの画面に閉じた狭い指示でも、複数画面/複数ファイルにまたがるまとめ依頼でもよい(後者は下記「3. 実装する」の複数ファイル分岐を使う)

**作業中に、直す内容が指示だけでは決められず評価・判断が必要だと分かったら、その場で頑張らず一旦止めてユーザーに相談する。** 無理に進めない。

## デザイン方針(判断基準)

**指示に書かれていない細部をどう直すか迷ったとき、また複数の直し方があるときは、この方針で決める。** サブエージェント/Codexへの委任プロンプトにも、関係する項目を必ず書き写して渡すこと。

- 実用性を最優先する。
- 情報密度は高く保つ。
- 長時間利用しても疲れにくい落ち着いたデザインとする。
- 装飾は最小限とし、レイアウト・余白・配置によって情報を整理する。
- 同じ役割のUIは全ページで同じ見た目・操作性とする。
- 一つの機能を一枚のカードとして構成する。
- 色は状態や重要な情報を示す目的に限定して使用する。
- 太字や派手な装飾による強調は極力避け、余白・サイズ・配置で視線を誘導する。
- ポケモン対戦経験者を主な利用者とし、自明な説明や内部実装の説明は表示しない。
- 編集画面と閲覧画面は分けず、その場で編集できるUIを基本とする。

この方針から直接導かれる、修正時の禁止事項:

- **視認性向上を理由に余白を増やしすぎたり、情報密度を下げたりしない**(コントラスト・文字サイズで解決できるならそちらを取る)。
- **新しいデザインを作らない。既存デザインを統一する。** 独自スタイルを追加せず、既存のデザイン体系(`src/styles/global.css` のトークン・共通クラス)に合わせる。
- **個別修正を増やさず、原因となる共通スタイル/共通コンポーネントを直す。** 同じ問題を複数箇所で繰り返し修正しない。同じ値(色・余白・フォントサイズ・角丸)が複数箇所でハードコードされていたら、トークンへ集約する。
- **画面・コンポーネント固有のスタイルは対象ごとの CSS ファイルへ集約する。** `box-card.css` や `box-page.css` のように、開発者が調整箇所を追える構成を必須とする。テンプレート内の `style` 属性、コンポーネント内に分散した `<style>`、同一対象のスタイルを無秩序に複数ファイルへ分割する実装は行わない。共有スタイルのみ `global.css` 等に置く。
- **UIの情報構造・操作フローは変更しない。** 機能や操作性を損なう変更は行わない。
- 判断に迷う場合は、**アプリ内で最も使用頻度が高く完成度の高いUIを基準**にする(現状は `/box/[id]` の育成画面)。

### 確立済みUIパターン: ソートボタン

複数のソート条件から1つを選ばせる、ポップアップ形式のボタン(候補が4件程度までの少数)は、次のデザインに統一する:

- ボタンの表示は「⇅ <現在の条件の短縮ラベル>」(⇅の直後に半角スペース1つ、ラベル末尾の「順」等の接尾辞は付けない。例:「⇅ 人気」)。
- クリックで選択肢のポップアップを開く。選択肢のラベルも同じ短縮形にする(例:「人気」「番号」「種族」)。
- 参照実装: `src/components/box-id/SpeciesSelectDialog.astro` / `src/lib/box-id/species-select-dialog.ts` / `src/styles/species-select-dialog.css` の `.species-select-sort-*` 系クラス。

この形式は新規に作る/少数候補のポップアップ選択に適用する。既存のネイティブ`<select>`によるソート(`/box`・`/team`・`/team/[id]`。モバイル標準ピッカー・キーボード操作を活かせる)は、「UIの情報構造・操作フローは変更しない」の方針により無理にボタン+ポップアップへ置き換えない。ただし見た目のアイコン・ラベル表記(接尾辞「順」の省略等)は、この形式の考え方(短縮ラベル・統一されたソート記号)に揃える。

この判断基準で決め切れない細部は、`references/design-notes.md`(監修から見えた傾向を蓄積するメモ。まだ「デザイン方針」ほど確定していない)も参照してよい。

## アプリ全体の一貫性レビューを頼まれたとき

「アプリ全体を見て不整合を直して」のような**対象が広く、何を直すかは自分で見つける**依頼のときは、下の手順の前にこの節を使う。1件ずつの指示ではないので「直す内容がすでに指示に書かれている」条件を満たさないが、**評価軸(下の「デザイン方針」)がユーザーから与えられていれば実行してよい。**

### 調査は「grepで数えられるもの」と「読まないと分からないもの」に分ける

Coordinatorが先に機械的な棚卸しをすると、委任先に渡す指示が具体的になり精度が上がる。実際に効いた順:

```bash
# 生値の乱立を数える(トークン化の対象が一撃で分かる)
grep -rhoE "font-size:\s*[0-9.]+(px|rem|em)" src --include=*.astro | sort | uniq -c | sort -rn
grep -rhoE "#[0-9a-fA-F]{3,8}\b|rgba?\([0-9][^)]*\)" src --include=*.astro | sort | uniq -c | sort -rn
grep -rhoE "@media[^{]*\([a-z-]+:\s*[0-9]+px\)" src --include=*.astro --include=*.css | sort | uniq -c | sort -rn
grep -rhA3 "focus-visible" src --include=*.astro --include=*.css | grep -oE "outline-offset:\s*[^;]+;" | sort | uniq -c
```
実測では、`--font-size-*` が7段あるのに **font-sizeの生値が37種類**(0.75/0.76/0.78/0.8/0.82/0.85/0.86/0.88rem が全部別々に存在)、`.toggle-switch` が**3ファイルに逐語コピー**、暗幕の色が **0.35 と 0.45 に分裂**、という形で不整合が数字として出た。

**残りの「同じ役割なのに別実装」「冗長・内部実装が漏れた表示テキスト」は読まないと分からない**ので、`codex exec --sandbox read-only` に観点ごとの調査を投げる(実装させないので read-only でよい。並列で投げてよい)。観点の切り方は「①生値の棚卸し ②同じ役割のUIの重複実装 ③表示テキスト」の3本が過不足なかった。

### 修正は「共有ファイル → 個別ファイル」の順に、実行ステップを分ける

`src/styles/global.css` は全エージェントが触りたがる**唯一の共有ファイル**なので、**global.cssを触るステップは必ず単独で走らせ、commitしてから次へ進む。** その後、担当ファイルが重ならない単位で並列に投げる。実際の分け方:

1. **ステップ1(単独)**: トークン化・共通クラスの新設(`global.css` + 参照側の書き換え)
2. **ステップ2(単独)**: 別グループの共通クラス新設(ツールバー・空状態など)
3. **ステップ3(並列)**: ファイル単位の生値トークン化 + 表示テキスト統一

並列ステップでは各エージェントに **`npx astro build` を実行させない**こと。同時に走ると `dist/` を奪い合って「自分のせいではないビルドエラー」を報告してくる。**ビルド検証はCoordinatorがまとめて1回行う。**

### 表示テキストの統一ルール(このアプリで確定させたもの)

- 進行中表示の三点リーダーは **「…」**(半角ピリオド3つは使わない)
- 空状態(未登録)は **「○○が登録されていません」**、検索0件は **「条件に一致する○○がありません」**(「いません」「見つかりませんでした」は使わない)
- エラーは **「○○を読み込めませんでした / ○○できませんでした」**(「取得に失敗しました」は内部通信を連想させるので使わない)
- **「アイテム」**(「持ち物」ではない。古いコード・古いコメントには「持ち物」が残っていることがある)、**「並べ替え」**(「並び替え」ではない)、**「すべて」**(「全て」ではない)
- **HTTPステータス・例外のメッセージ・ライブラリ名を画面に出さない**(ログには残してよい)
- **「ポケモン」と「個体」は統一しない。** 種族・検索カテゴリが「ポケモン」、保存された育成データが「個体」で、意味のある区別。

### 検証で必ずやること

- **撮影・実測の直前にdev serverを再起動する**(→ `references/pitfalls.md`「Windows側から編集した直後のスクリーンショットは『前のコード』を写している」)。これを怠ると、直っているのに直っていないと誤診して余計な修正を重ねる。
- **共通化したら、その重複が存在していた全画面を確認する**(1画面だけ見て判断しない)。
- **はみ出しは目視で探さず `getBoundingClientRect()` で犯人を特定する**(同上「はみ出しは目視で探さず、要素を実測して特定する」)。
- **委任先のdiffは必ずCoordinatorが読む。** 実際に、ダークモードの上書きを落としかけた回帰をこの確認で捕まえた(報告書には「判断に迷った箇所はありません」と書かれていた)。

## 手順

### 1. 作業ブランチを確認する

**特に指示のない限り `main` で直接作業する**(→ ルートの `CLAUDE.md`「作業方針」)。`git status` で作業ツリーがクリーンか確認し、前回の未コミット変更が残っていたら先にそれをコミットするか、別作業中でないかユーザーに確認する。

### 2. 現状を確認する

対象要素・現在の値(余白・色・サイズ等)を、必要ならスクリーンショットで確認してから直す。**撮影は `npm run shot` を使う**(`scripts/shot.mjs`。Playwrightスクリプトを毎回書き起こさない)。

```bash
npm run dev            # 別ターミナルで先に起動しておく
npm run shot -- --page box/<id> --clip .card-damage --clip-pad 12 --scale 3
```

指示の対象が一目で分かる自明な修正(明確なクラス名・具体的な数値指定がある等)なら、この事前確認・撮影は省略してよい。

**複数画面/複数ファイルにまたがるまとめ依頼、または対象コードに土地勘が無い場合は、下調べもサブエージェントに委託する。** **codexが使えるなら`codex exec --sandbox read-only`を優先し**、疎通不良のときだけExploreエージェント(sonnet)にフォールバックする。画面・観点ごとに独立した調査なら並列で投げる(例:「画面Aの対象クラスと現在値」「画面Bの対象クラスと現在値」を別々のエージェントに)。Coordinator自身が広範囲をRead/Grepして回るのではなく、報告を受けてから手順3(実装の割り当て)に進む。分担の考え方は手順3「ファイル単位で分担する」と同じ(担当範囲が重ならないよう仕分ける)。

### 3. 実装する

**実装(ファイルの編集)は、規模の大小を問わず必ずサブエージェントに委託する**(1ファイル・1行の修正でも例外にしない)。**委託先はcodexが使えるなら`codex` skill経由で`codex exec`を優先する。** codexが使えない(疎通不良)/このタスクにClaude Code固有ツールが要る場合だけ、sonnetのAgent toolにフォールバックする。Coordinator 自身は Edit/Write でコードを書かない。Coordinatorの仕事は、**要件を確定させる → 担当ファイル単位でエージェントに割り当てる → 上がってきた diff を検証する → commit する**の4つ。ダメージ計算・jpoke絡みで `.claude/skills/jpoke/` の知識ベース確認を伴う場合も、その参照ごとエージェントに指示する。

Coordinator が自分で手を動かしてよいのは次だけ: 現状確認(Read/Grep/スクリーンショット)、`git` 操作、検証(build/test/撮影/実測)、開発サーバーの管理、そして**指示書・計画書など `.claude/` 配下や `docs/` のドキュメント編集**(これらは「実装」ではない)。

**ファイル単位のsub agentへの分担手順**(単一ファイルなら1体、複数ファイルなら並列):

1. **依頼を「どのファイルを触るか」で仕分ける。** まず、複数の分割候補が共通して触る**土台となる共有ファイル**(デザイントークン=`src/styles/global.css`、共有lib、共有コンポーネントなど)への変更がないか確認する。あれば、それは**先に単独のsub agent 1体で片付けてcommitする**(並列agentが同じファイルを同時に編集して衝突するのを防ぐため)。
2. 残りの変更を、**担当ファイルが互いに重ならない単位**にグルーピングする。1つのファイルに複数の変更点が集中する場合(例: 1つの画面が1ファイルに収まっている)は、それらをまとめて1エージェントに割り当てる。**同じファイルを複数エージェントに同時に触らせない。**
3. グループごとにサブエージェントを起動する。**codexが使えるなら`codex` skillの手順で `codex exec` を、使えないときだけ Agent tool(sonnetモデル)を使う。** 独立したグループは並列実行する(codexなら複数の`codex exec`を個別のBash呼び出しで並列に、Agent toolなら1メッセージ内で複数Agent呼び出し)。各エージェントへの指示に含めること:
   - 担当ファイルのパスと、そのファイルに対する変更内容(具体的に)
   - この skill の手順2(現状確認)・4(検証)を踏んだうえで、指定した変更を実装すること
   - **「git commit / git push は絶対にしない」「DBに検証用データを作らない」を明記する**(commitはCoordinatorが行う)
   - 下記「守ること」を明記する
4. 各エージェントが完了するたびに、Coordinatorが diff を確認し、`npx astro build` 等で検証したうえで、**そのタスク単位でcommitする**(粒度に迷ったらユーザーに確認する。デフォルトはタスク=画面/ファイルごとの個別commit)。全エージェントの完了を待ってからまとめてcommitする必要はない。

守ること(sub agentに委譲する場合は指示に含める):
- 配色トークン・ボタン方式など既存の確立済み規格を踏襲する。新しい値を作らない
- 画面・コンポーネント固有のスタイルは対象別 CSS ファイルへ集約し、共有スタイルだけを `global.css` 等へ置く。テンプレート内の `style` 属性や分散した `<style>` は使わない
- 育成ルール(IV=31固定・努力値0〜32スケール・Lv50固定)は**仕様でありバグではない**
- `.claude/skills/ui/references/pitfalls.md` に載っている既知の罠(CSS/DOMの罠・データ事故・Playwright)を踏まない
- クラス名の改名・削除やAPI契約の変更はしない

### 4. 検証する(必須・省略しない)

- `npx astro build` 成功 / 関連する `npm test` pass
- **`npm run shot` で撮り直し、Read tool で自分の目で見る**(ライト・ダーク両方。省略しない)
- 数値目標があれば `getBoundingClientRect()` 等で実測
- DBを触った場合は元の状態に戻っているか確認
- **検証が終わったら、撮影に使った `.tmp-shots*` ディレクトリを削除する**(`--out` で指定した出力先。gitignore対象で放置すると蓄積する)

### 5. commit する

**Coordinator が `git commit` する**(特に指示のない限り。メッセージに直した内容を書く)。`git push` はしない。計画書への記録は行わない(変更内容の記録は commit メッセージと git log に任せる)。

### 6. 指針メモを更新する(該当があれば)

**機会的に行う。毎回の義務ではない。** 今回のやり取りで、ユーザーの監修コメントが「今回の指示そのもの」を超えて**今後の作業でも踏襲すべき傾向**を示していたら(例: 指示に無い細部の直し方をユーザーが訂正した、複数箇所で同じ理由の指摘をした等)、`references/design-notes.md` に1エントリ追記する。該当が無ければ何もせず終える。

- 既存のデザイン方針(手順前半「デザイン方針」節)に既に書かれている内容の言い換えなら、追記しない。
- 同じ傾向の既存エントリがあれば、新規追加せず観測日を1件足す。観測が3件に達したら、その場でユーザーに「デザイン方針への昇格」を提案する(昇格するかはユーザーが決める。Coordinatorが自動でSKILL.mdの「デザイン方針」を書き換えることはしない)。
- このステップは commit に含めてよい(指針メモの更新もドキュメント編集であり「実装」ではないため、Coordinator自身が直接編集する)。
