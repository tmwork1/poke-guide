# UI改善ループ

**対象は「既に `src/pages/` に存在するページ」に限る。** まだ作られていないページ(チーム登録・ホーム統計など)の**新規作成は `new-page` skill の担当**。このskillはStep 1のスクリーンショットを起点にしており、存在しないページには使えない(制約にも「機能追加は原則提案しない」と明記されている)。→ `.claude/skills/new-page/SKILL.md` と `docs/plan/pages/index.md`

**1回の呼び出し = 1ラウンド。** 状態は `docs/plan/ui_plan.md`(索引)と `docs/plan/ui_rounds/round-NN.md`(ラウンドごとの詳細)に永続化されているので、途中から再開できる。`/loop ui` で繰り返し起動される前提で書かれている。**ラウンドが増えても `ui_plan.md` 本体が肥大化しないよう、1ラウンド=1ファイルに分割している**(2026-07-27、ラウンド12終了時点で導入)。

## 役割分担(厳守)

| 役 | モデル | やること | やってはいけないこと |
|---|---|---|---|
| Coordinator(メイン) | — | 現状把握、4レビュアーの指摘の統合(重複排除・矛盾解消)、計画書への記録、エージェントへの指示、最終検証、**ラウンド完了時の git commit** | 大きな実装を自分でやる、**git push** |
| UIレビュアー | **sonnet** | スクリーンショットを見て**見た目の粗**(余白・配色・コントラスト・タイポグラフィ・密度)と、**規格そのものの妥当性**を講評 | **ファイル編集・git操作・DB操作**、整列/規格差の網羅列挙(統一感の担当) |
| UXレビュアー | **sonnet** | スクリーンショットを見て**使いやすさ**(情報設計・**常時表示情報の優先順位と退避**・導線・認知負荷・空状態/エラー状態の分かりやすさ)を講評 | **ファイル編集・git操作・DB操作** |
| プレイヤー視点レビュアー | **sonnet** | jpoke・ダメージ計算の知識で、**実際の対戦準備で使う場面**からUIの数値・表現・**並び順(操作頻度)**が正しく伝わるかを講評 | **ファイル編集・git操作・DB操作** |
| **統一感レビュアー** | **sonnet** | フォント・寸法・余白・整列・確立済みパターンを**実測で網羅監査**し、「規格表と逸脱一覧」を出す(**講評ではない**) | **ファイル編集・git操作・DB操作**、規格の良し悪しの判断、**どちらに揃えるかの裁定** |
| 実装者(Implementor) | **sonnet** | 実際のコード修正と検証 | 担当外ファイルの編集、git commit/push |
| メタアドバイザー | **fable** | **前回実施ラウンドから3ラウンド以上経過したとき**(Step -1の4.参照、剰余ではなく距離で判定)、4レビュアーの指摘傾向・見落としを分析し、`agent-prompts.md` の4レビュアーテンプレート(観点リスト)の改訂案を出す | スクリーンショットの毎ラウンド講評、ファイル編集・git操作・DB操作、実装 |

ユーザーは「実動にはsonnet sub agentを使用」と明示している。**実装は必ずsonnetサブエージェントに委譲すること。** 画面講評(UI/UX/プレイヤー視点/統一感)は4体ともsonnet、メタアドバイザーはfable。

**4体のレビュアーは毎ラウンド固定で呼ぶ**(対象画面によって省略しない。ダメージ計算と無関係な画面でもプレイヤー視点レビュアーは呼ぶ — コストより見落とし防止を優先する)。

**統一感レビュアーはラウンド32でユーザーの明示要求により新設した**(「同じUI領域でもフォント・サイズが微妙に統一されていなかったりする。UIの統一感をレビューする専門のsub agentを立ち上げてレビューさせる」)。役割の切り分けは **「要素と中身の突き合わせ=UI / 要素どうしの突き合わせ=統一感」**。→ `references/agent-prompts.md` 冒頭

## 1ラウンドの手順

### Step -1. 作業ブランチを確認する(**最初に必ず行う**)

**特に指示のない限り、`main` で直接作業する。** ラウンドごとに専用worktree/ブランチを作る運用はデフォルトでは行わない(→ ルートの `CLAUDE.md`「作業方針」)。

> 過去の事故メモ(ラウンド32、2026-07-30): 実装エージェントが走行中に、**別プロセス(別セッション)が同じワーキングツリーで `git commit` を実行し、作業途中の変更が丸ごと1コミット(`e82db52`)に巻き込まれた**ことがあり、これを受けて一時期このStep -1でworktree分離を必須化していた。**同日中にユーザーの明示指示でこのリスクを承知の上デフォルトを main 直接作業に戻した。** 詳細は `references/pitfalls.md`「別プロセスが同じワーキングツリーでコミットして、作業途中の変更を巻き込む」。

1. **ラウンド番号を確定する**(`docs/plan/ui_plan.md` の「ラウンド履歴」表の最大値 + 1)。
2. `git status` で作業ツリーがクリーンか確認する。前ラウンドの未コミット変更が残っている場合は、先にそれをコミットしてから今ラウンドを始める。
3. **他セッションと並行してこのリポジトリで作業する予定があると分かっている場合は、その旨をユーザーに伝え、worktreeを分けるか相談する**(`git worktree add ../poke-commons-ui-round-NN -b ui/round-NN`)。特に申し出が無ければ `main` で進める。
4. **確定した番号を `docs/plan/ui_plan.md`「現在の状態」の `最終メタレビュー: ラウンドNN` 行と突き合わせる。差が3以上ならこのラウンドの締め(Step 6)と同時にメタレビュー(Step 7)を実施する。**(ラウンド番号の剰余(3の倍数)ではなく距離で判定する。剰余判定は1回逃すと次の機会まで気づけず自己修復しないため、ラウンド32〜45で13ラウンド抜けた事故が再発した。距離判定なら毎ラウンドこのStep -1で必ず検知できる。)

### Step 0. 現在地を把握する
`docs/plan/ui_plan.md`(索引)の**「現在の状態」と「ラウンド履歴」表**を読み、最新ラウンドの `docs/plan/ui_rounds/round-NN.md` を開く。直近のラウンドが「要件/指摘の記録だけで実装がまだ」なのか「実装済みで次の講評待ち」なのかを判断する(**このファイルの末尾から遡って読む運用は廃止**。ラウンドごとにファイルが分かれているので、索引の「現在の状態」だけで判断できる)。
- **未実装の指摘・要件が残っている** → Step 4(実装)から始める
- **すべて実装済み** → Step 1(撮影)から始める
- **ユーザーから新しい指示が来ている** → Step 3(記録)へ。**ユーザー指示は3レビュアーの講評より常に優先**する

### Step 1. 撮影する
**`npm run shot` を使う。撮影用のPlaywrightスクリプトを毎回書き起こさないこと**(ラウンド28まで毎回書いていた `.tmp-shot.mjs` は `scripts/shot.mjs` に固定済み)。ライト/ダーク両方・Pyodide初期化待ち・dev toolbarの非表示は**スクリプト側で済んでいる**。

```bash
npm run dev            # 別ターミナルで先に起動しておく(ポートは自動検出する)
npm run shot -- --page box --page box/<id>                        # ライト・ダーク両方 1920x1080
npm run shot -- --page box --clone .card-pokemon --clone-count 40 # 密度検証(DBは汚さない)
npm run shot -- --page box/<id> --clip .card-damage --clip-pad 12 --scale 3   # 細部の拡大クロップ
```
ダメージ計算カード本体のクラスは **`.card-damage`**(`.damage-card` ではない)。`.damage-row` というクラスの要素は**存在しない**(2026-07-29 ラウンド29で実測)。
出力は `.tmp-shots/<画面>-<theme>[-<tag>].png`(gitignore済み)。撮影結果には HTTP status・リダイレクト先・Pyodide待ちの有無・横スクロール・console error が併記されるので、**まずそこを読んでから画像を見る**。

- Git Bashから叩くときは `--page box` のように**先頭スラッシュを付けない**(MSYSがパスを変換する)
- **実使用に近い状態**で撮る。空の状態だけ見て判断しない(ダメージ計算カードが複数ある `/box/<id>` を撮る。一覧は `--clone` で20〜40体に増やす)
- 撮ったら**必ず Read tool で自分の目で見る**。「エラーが無い」は「UIが良い」ではない
- スクリプトで足りない撮り方が出てきたら、`.tmp-*.mjs` を書き捨てるのではなく **`scripts/shot.mjs` にオプションを足す**(次のラウンドから全員が使える)

### Step 2. 4レビュアーに講評させる(UI/UX/プレイヤー視点/統一感、すべてsonnet)
`references/agent-prompts.md` の「UIレビュアー用」「UXレビュアー用」「プレイヤー視点レビュアー用」「統一感レビュアー用」の4テンプレートを使い、**1メッセージ内で4体同時に起動する**(並列)。要点(4体共通):

**ユーザー指示だけのラウンド(講評をしないラウンド)でも、統一感レビュアーだけは変更領域限定の軽量パスとして走らせる。** 不統一は「指示された部分だけ規格が変わり、指示されなかった部分との差が開く」形で**指示ラウンドに蓄積する**(round-29 冒頭のUI総評、ラウンド32のメタレビュー)。
- スクリーンショットの**絶対パス**を渡し、「Read tool で必ず実際に見ること」と明記する
- ワイヤーフレーム `docs/ui_proposal/*.png` と、`docs/plan/ui_rounds/00-foundation.md`(レイアウト原則)・直近の `docs/plan/ui_rounds/round-NN.md` の該当節を読ませる(**ファイルパスを具体的に渡す**。索引の`ui_plan.md`だけを渡して探させない)
- **実測値をこちらで先に測って渡す**(カード高さ、1画面に入る枚数など)。数字があると講評の質が跳ね上がる
- **優先度A/B/C + 「維持すべき点」** の形式で出させる
- **「実装は絶対にしない」を明記**する
- プレイヤー視点レビュアーには追加で `vendor/jpoke/src/jpoke/model/stats.py` と `src/pages/damage-calc/index.astro` のパス、および育成ルール(IV=31固定・努力値0〜32スケール)は**仕様でありバグではない**ことを明記して渡す(→ `references/pitfalls.md` の「育成ルールは仕様であってバグではない」)
- **画面固有・テーマ限定のラウンド(ユーザー指示が1つの狭い問題に絞られているとき)は、4体に同じ狭い問いをそのまま渡さない。** 同じ問いを4体に渡すと同一結論に収束し重複が増える(ラウンド44の実例、メタレビュー参照)。**同じテーマを各自の役割の形に割ってから渡す**: 統一感=実測の棚卸し、UI=その規格差・強調がそもそも妥当か、UX=情報の重要度上その階層が必要か、プレイヤー視点=ドメイン上の重要度、という具合に問いを立て直す。

### Step 2.5. 4件の講評を統合する(Coordinator自身の作業)
4体の報告を**そのまま鵜呑みにせず**、Coordinatorが以下を行ってから計画書に記録する:
- **重複排除**: 同じ問題を複数レビュアーが指摘している場合は1件にまとめ、どのレビュアーが指摘したか併記する
- **矛盾の解消**: 指摘が逆方向(例: UIレビュアーは密度優先、UXレビュアーは余白優先)の場合、画面の目的(一覧性 vs 個別編集のしやすさ、等)に照らしてCoordinatorが最終判断し、採用しなかった側の理由を1行残す
- **統一感レビュアーの逸脱一覧は「どちらの規格に揃えるか」の裁定がされていない**(そう設計してある)。Coordinatorが裁定し、根拠(確立仕様 / 出現数 / 直近のユーザー指示)を1行で書く。**「ユーザー判断待ち」と分類されたものは実装せず、ユーザーに提示する。**
- **レビュアーの新提案そのものにも「強調の層数」の観点を適用する**(UX固定2)。**レビュアー発案で足した装飾が次のラウンドでユーザーに撤回された実例がある**(29-R2 の区切り線への色付け → 32-R3 で撤回)。区切り・強調を足す提案は、**罫線・色より先に余白・既存アイコンで解決できないか**を確認してから採用する。
- ユーザーの過去の指示と矛盾しないか確認する。矛盾する場合は**ユーザー指示が勝つ**

### Step 3. 計画書に記録する(**修正の前に必ず**)
ユーザーの明示的な指示: **「修正する前に必ず計画書に計画を記録するようにして」**。

**`docs/plan/ui_plan.md` 本体には追記しない。** 新規に `docs/plan/ui_rounds/round-NN.md` を作成し(NNは新しいラウンド番号)、冒頭を次の2行にする:
```markdown
# UI改善ラウンド NN

[← 索引](../ui_plan.md)
```
続けて内容を書式どおり追記する:
```markdown
## ラウンドN の指摘(YYYY-MM-DD UI/UX/プレイヤー視点レビュアー講評・Coordinator統合: 対象画面)
### 優先度A(必ず直す)
- **A-1 見出し**(指摘者: UI/UX/プレイヤー視点): 【問題】どこを見てそう判断したか(実測値つき) → 【提案】どう直すか(CSS具体案)
### 優先度B / C
### 維持すべき点(壊さないこと)
```
ユーザー指示の場合は `## ラウンドN の要件(YYYY-MM-DD ユーザー指示)` とし、**ユーザーの言葉をそのまま引用**したうえで具体化する。過去のラウンドの判断を覆す場合は**「〜を撤回する」と明記**する(後から読んだエージェントが混乱しないため)。

書いたら**必ず** `docs/plan/ui_plan.md` の「ラウンド履歴」表に1行追加し、「現在の状態」を書き換える(索引が古いままだと次回Step 0で見つけられなくなる)。

### Step 4. 実装させる(sonnetサブエージェント)
`references/agent-prompts.md` の「実装者用テンプレート」を使う。

**ファイル単位で担当を割り、同じファイルを2体に触らせない。** 並列化の基本形:
- エージェント1: `src/pages/box/index.astro`(一覧)
- エージェント2: `src/pages/box/[id].astro`(個体編集)
- エージェント3: `src/styles/global.css` ほか共通基盤
- 資産生成(画像など)は独立したエージェントに切り出し、**ヘルパー関数のシグネチャを報告させて**使う側に渡す

指示に必ず含めるもの:
- 計画書の**どのファイルのどの節を読むか**(`docs/plan/ui_rounds/round-NN.md` のファイル名と節タイトルを正確に。「計画書」とだけ書いて索引から探させない)
- **編集してよいファイル**と**編集禁止ファイル**(理由つき)
- `references/pitfalls.md` の内容から関係するもの
- 検証手順(実測・スクリーンショット目視・全ブレークポイント)
- **「git commit / git push は絶対にしない」**
- **「DBに個体を作らない。変更したデータは必ず元に戻す」**

### Step 5. 検証する(自分で)
エージェントの報告を鵜呑みにしない。**自分で撮って見る。**
- `npx astro build` 成功 / `npm test` 全件pass
- 1920×1080 ライト・ダークのスクリーンショットを Read tool で目視
- 要件に数値目標があれば `getBoundingClientRect()` で実測
- **DBが元の状態に戻っているか確認**(→ `references/pitfalls.md` の「データ事故」)
- 回帰を見つけたら、それも計画書に記録してから直す

### Step 6. ラウンドを締める
**同じ `docs/plan/ui_rounds/round-NN.md`**(このラウンドの指摘・要件を記録したファイル)に**実施結果**と**積み残し**を追記する(実施結果だけを別ファイルに分けない):
```markdown
## ラウンドN の実施結果(YYYY-MM-DD)
### 実施済み(表: ラウンド / 対象 / 結果 ※実測値を入れる)
### 実装中に見つかったバグ(UI改修とは別の実バグ)
### 積み残し(次に着手する項目)
```
複数ラウンドにまたがる実装(例:「ラウンド6〜7の実施結果」)は、**指す範囲の最後のラウンド番号のファイル**に書く。
書いたら `docs/plan/ui_plan.md` の「ラウンド履歴」表と「現在の状態」を更新する。**実施結果に「メタレビュー: 実施(→観点改訂の記録)」または「メタレビュー: 不要(前回ラウンドN、現ラウンドM、差<3)」のどちらかを必ず1行書く**(Step -1の4.でチェックした結果を記録する。UI固定5の「該当なしなら『なし』と明記する」と同じ考え方で、書けない=チェックしていないことが記録上見える形にする)。
**最後に Coordinator が `git commit` する**(特に指示のない限り。メッセージにはラウンド番号と要点を書く)。`git push` はしない。
ユーザーへの報告は**実測値と、見つけた実バグ**を中心に。作業ログの羅列にしない。

### Step 7. メタレビュー(現ラウンド番号 − 最終メタレビュー実施ラウンド ≥ 3 のとき)
Step -1の4.で判定した距離が3以上なら、このラウンドの締めと同時にfableのメタアドバイザーを起動する(次のラウンドまで待たない)。

⚠️ **講評ラウンドかどうかにかかわらず実施すること。** 「3レビュアー講評をしたラウンドの後」という運用にしていたため、ユーザー指示ラウンドが続いたラウンド17〜28では**13ラウンド1度も実施できなかった**。この対策として「講評の有無にかかわらず3ラウンドごと」に変えたが、**トリガーが「ラウンド番号が3の倍数」という剰余判定のままだったため、1回逃すと次の機会まで気づけず自己修復せず、ラウンド32〜45で再び13ラウンド抜けた**(ラウンド45のメタレビューで判明)。**この再発を受けてトリガー自体を距離判定(Step -1の4.参照)に変更した。** ラウンド29・45のメタレビューが示したとおり、**ユーザーが自分で指摘するまで放置された問題こそ観点リストの穴の一次資料**であり、ユーザー指示ラウンドの方がむしろ材料として濃い。指摘者の分離が記録に無い場合は「**この指摘はUI/UX/プレイヤー視点のどのレビュアーが本来拾うべきだったか**」に読み替えて分析させること。
- 渡すもの: 直近3ラウンド分の `docs/plan/ui_rounds/round-NN.md` を**そのまま3ファイル**(各レビュアーがどんな指摘をしたか)と、現在の`references/agent-prompts.md`の4レビュアーテンプレート
- 依頼すること: 「どのレビュアーが同じ観点ばかり指摘しているか」「3ラウンド通じて一度も指摘が出ていない観点」「見落としていそうな観点」に加えて、**「13ラウンド抜けた運用面の原因と再発防止策」も毎回問うこと**(トリガーの仕組み自体がまた形骸化していないかを継続的に点検する)。3テンプレート+統一感テンプレートの「特に見てほしい観点」リストへの追加・削除案を出す(**ファイル編集はしない。提案のみ**)
- Coordinatorが提案を精査し、妥当なものだけ`agent-prompts.md`(必要なら`SKILL.md`自体の運用ルールも)に反映。直近ラウンドの`docs/plan/ui_rounds/round-NN.md`に「レビュー観点の改訂(ラウンドN時点)」として何を変えたか・なぜかを1〜2行で記録する。**`docs/plan/ui_plan.md`「現在の状態」の `最終メタレビュー: ラウンドNN` 行を今回のラウンド番号に更新する**(Step -1の4.が読む値、ここを更新し忘れると次回また距離判定が狂う)。
- **あわせて「ユーザー判断待ち」キューを棚卸しし、ユーザーに提示する**(メタレビューと同じタイミングで行う)。滞留中の「要ユーザー判断」項目・優先度Cの項目を一覧にして聞く。
  > 🔴 **これを怠ると、ユーザーが自分で指示し直す羽目になる。** テラスバッジの浮き感は27-B2で指摘 → 29でも再確認 → **「ユーザー判断待ち」に置かれたまま提示されず** → 31-B1でユーザー自身が指示、という経路をたどった。round-22 の U-1〜U-4 も未回答のまま10ラウンド以上滞留している。**「ユーザー判断待ち」に置いた時点では何も解決していない。**

## ループの終了条件

以下がすべて満たされたら `ScheduleWakeup` に `stop: true` を渡してループを終える。
1. 3レビュアーの優先度A・Bの指摘が残っていない
2. ユーザーからの未実装の指示が残っていない
3. 直近ラウンドで新しい指摘が出なかった(**2ラウンド連続で空振りしたら終了**)

「Cだけ残っている」は終了してよい(Cは好みの範囲)。
終了時は積み残しを計画書にまとめ、ユーザーに「何を残したか」を報告する。
