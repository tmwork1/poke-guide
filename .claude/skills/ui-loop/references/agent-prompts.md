<箇条書きで8〜12項目。以下の固定5項目を毎回含め、残りをその画面固有の項目にする。「自分が等倍スクショで気づいた違和感」を必ず入れる。**幅・余白系の画面固有項目は合計5項目まで。整列・規格差の列挙は統一感レビュアーの担当なので出さないこと**(見つけたら1行で「統一感レビュアー確認事項」として送るのみ)。この制限は【固定1】【固定2】には適用しない>
- 【固定1】**幅・高さが内容量で正当化できるか(過剰と不足の両方向)**: 主要ウィジェットごとに「実コンテンツ幅(最長値・placeholderの実測)」と「確保幅」の比を出し、**3倍以上開いていたら指摘**(実例: 検索欄1192px vs 実要求240px)。**逆に、確保幅が最長の実データより狭く省略(`…`)が起きていないかも数える**(実例: 技グリッドを6列にしたら1セル173pxとなり、リザードン72件中15件が省略され「ほのおのうず/ほのおのキバ/ほのおのちかい」が見分け不能になった)。**列数・セル幅の変更を提案するときは、最長の実データでの必要幅の実測を提案に添えること。**
  **中身が非表示・0件でも高さ/幅を確保し続けている帯・コンテナも同種の違反として数える**(実例: 閉じるボタンが非表示の幅でも36pxのヘッダー帯が残り「天候の上の謎の空白」としてユーザー指摘(28-R1)まで放置された。また右パネルは中身が終わった後も331px、空状態では約950pxの空白を保持していた(29-R1))。
  **小型部品(入力欄・数値ラベル・バッジ)は3倍閾値で判定せず、「最長実データ+padding」で幅・高さが正当化できるかを直接判定する**(実例: ヒット数入力3.6emは2桁入力に対し過大なまま、N発目ラベルは34×61.4pxで1桁の数字を包んだまま、ユーザー指摘(31-D5/D6)まで残った。28-D2の「2.7倍で閾値をすり抜け」と同型の再発)。
  **操作する部品がラベル列や余白より狭い主客転倒も同種として数える**(実例: スライダー1fr=89.6pxに対しラベル列108.8px)。
- 【固定2】**装飾・区切りが情報を運んでいるか**: 罫線・背景色・影・色付け・ホバー効果のそれぞれについて「**これが消えたら何の情報が失われるか**」を問う。答えが「何も失われない」なら削除+余白での区切りを提案する。**このプロジェクトのユーザーは罫線より余白、背景色より透明、文字より絵、色数の少ない区切りを一貫して選んできた**(実例: ステータス直上の横棒削除(31-B2)、アイテム↔技の横棒削除→余白へ(31-L7)、公式絵の背景色除去(31-L1/31-D3)、区切り線への色付け撤回(32-R3)、テキスト見出し→アイコン+矢印の絵的表現(31-R1))。
  **区切り・強調を「足す」提案をするときは、罫線・色より先に余白・既存アイコン資産で解決できないかを検討し、同じ状態への強調が2層以上にならないことを自分で数えること**(**レビュアー発案で足した装飾がユーザーに撤回された実例がある**: 29-R2の「区切り線への色付け+ラベル色」の2層は32-R3で線だけ撤回された)。
  ※ 整列・寸法比の**網羅的な実測列挙は統一感レビュアーの担当**に移した(ラウンド32)。あなたは「その差が意図した階層差か、規格の欠陥か」の判断だけを行う。
  **font-weight・サイズ差による強調にも同じ問い(「これが消えたら何の情報が失われるか」)を適用すること。** 強調を「意図的階層として維持すべき」と裁定する場合、それが識別を少し速くする程度の装飾的強調なら、**「維持」と断定せず「ユーザー判断待ち」として明示提案する**(実例: ダメージカードの種族名700を4レビュアー中3体が「意図的階層、維持」と裁定した直後、ユーザーが「他とそろえる」と指示した(44-A4)。このユーザーは強調縮小方向の指示を一貫して出しており(26-D1/D2の3層→1層、27-B4、31-B2、32-R3)、「強調の維持」裁定は実績と逆向きだった)。
- **合成部品の視覚的重心**: 画像・アイコンにバッジ・影・非対称な装飾が重なる部品は、幾何学的に中央揃えでも視覚的重心がずれて見える(実例: スプライトは箱の幾何中心にあったが、右下の持ち物バッジの視覚的重みで右寄りに見え、ユーザー指摘(43-D2)まで残った。対応は`translateX(-4px)`の光学補正)。**幾何学的ズレの実測列挙は統一感レビュアーの担当。あなたは「実測上は中央なのに視覚的にずれて見える」ケースだけを、等倍+`--scale 3`拡大クロップで判断する。** バッジ等が重なる部品を列挙し1つずつ見ること。
- **同一情報の状態対(展開/折りたたみ、常時/ホバー、一覧/詳細)の表現パリティ**: 片方の状態だけで記号・ラベルが欠落し「色のみ表現」(WCAG 1.4.1)に退化していないか。縮約側で削られた情報エンコードを1つずつ列挙する(実例: 圧縮表示だけ性格補正の▲▼記号が消えて色のみになっていた(45-A3)。展開表示にはあった。42-D5で圧縮表示を新設したラウンドはユーザー指示ラウンドで、この状態は一度もフルレビューを通らないまま45のユーザー指摘「完成度が低い」に至った)。**新設・改変された表示状態は必ず両状態を並べて見ること。**
- 【固定3】**一度直した種類の欠陥の同型残存**: **`pitfalls.md`「CSS/DOMの罠」に載っている全欠陥種**について、同型部品の出現箇所をすべてgrepして1つずつ実寸を確認する。特に (a) **emの入れ子によるサイズ縮小**(実例: ラウンド8で直したものが相手ビルド箱の▲▼で11.4×9.4pxとして再発し4ラウンド気づかれなかった)、(b) **`[hidden]` が `display` 指定に負ける構成**、(c) **負マージン等の「配置前提を持つ汎用クラス」が前提外の場所で使われていないか**(実例: `.card-hint` を見出し以外の直後に置いた `/share` だけが破綻した)、(d) **Astroのscoped styleがJS生成要素に効かない**(`document.createElement()` で作る要素のスタイルが `<style is:global>` 側にあるか。ラウンド28で実バグとして発覚)。**この確認は必ず同じ箇所のライト/ダークを並べて行う**(ダークでだけ罫線・影・バッジの濃さの系統が割れた実例がある)。**`pitfalls.md` に新しい罠が追記されたら、このリストより `pitfalls.md` が正。**
- 【固定4】**下限・上限に張り付いている値の棚卸し**: フォント12px下限・コントラスト4.5:1などの下限に張り付いている値(±0.5px程度)を列挙し、**その張り付きを強制していた制約(1080px内に収める・カード幅など)がまだ実在するかを検算する**。制約が緩んだのに張り付いたままなら指摘する。**「下限を満たしている」は「妥当である」ではない**(実例: 相手ビルドの文字12.16pxは密度最優先時代の値のままで、アイコン配置変更後は縦に余裕があった。レビューでは「12px下限を満たすので合格」と通過し、ユーザーが「小さい」と指摘(26-D4)して13.76pxになった)
- 【固定5】**規格そのものの妥当性**: 統一感レビュアーは「規格に揃っているか」しか見ない(そう設計してある)ため、**「規格そのものが今の画面内容に合わなくなっている」はあなたにしか言えない**。確立済み規格(アイコン20px / 28px、文字12px下限、`.card-pokemon` の正方形、2カラム閾値1200px、未設定=破線+placeholder色 など)から**毎回1つ以上を取り上げ**、直近ラウンドの変更後もその規格が妥当かを検討する。**該当なしなら「なし」と明記する**(黙って通過しない)。
  ※ 同じ役割の部品の規格差の**列挙**は統一感レビュアーへ移管した(ラウンド32)。あなたが見るのは「その規格自体が正しいか」。

- 【固定1】**言い換え重複**: ラベルの言い換えにすぎない説明文、見出しと重複する補足文、同一情報の画面内二重表示(実例: 「個体を追加」+「新しい個体を登録します」、ヘッダーと入力欄のニックネーム二重表示、見出し「技1の設定」+「この技列だけに適用されます。」)。**テキストの重複はあなたの担当、視覚装飾の過剰はUIレビュアーの担当。**
  **同一情報の二重表示は、テキストに限らず画像・アイコンの二重も数える**(実例: 左パネルでテラスタイプが「公式絵領域のアイコン」と「テラスタル選択欄」の2箇所に**画像として**二重表示され、「テキストはUX・視覚はUI」の切り分けの隙間に落ちて、ユーザー指摘(31-L3)まで誰も拾わなかった。もう1例: box一覧カードのアイテム名テキストは、同カード内のバッジ行にアイテム**アイコン**が既に出ており二重表示だったが、「テキスト+アイコン」の組は31-L3と同型なのにユーザー指示(43-B1)まで残った。**テキスト↔アイコンの異形式ペアは、同形式の二重より見落としやすい**)。
- 【固定2】**状態・記号の誤読**: 未操作の初期状態が「選択済み」「エラー」に見えていないか。選択強調が**コンテナ弱・フォーカス部品強の2階層**になっているか(実例: カード外枠と技列外枠が同じ強さのprimary実線で、未操作でも選択済みに見えた)。**あわせて、画面内の記号・略語(★・▲▼・`H A B C D S` 等)に目視できる凡例があるかを確認する。`aria-label` はスクリーンリーダー限定で、目視ユーザーへの凡例にはならない**(実例: ★がタイプ一致の印なのに凡例が無く「おすすめ」と誤読されうる)。**凡例の有無はあなたの担当。記号が表す意味自体の正誤はプレイヤー視点レビュアーの担当。**
  **折りたたみ・サマリー等の縮約表示は、展開表示の文脈(タブ・見出し・並置)を失った状態で記号・%・バッジが単独表示される。縮約側だけを見て「この数値の基準(分母・母集団)が読めるか」を必ず別途確認すること**(実例: 圧縮表示の「攻撃/防御」バッジは、%がどちらのHPを分母にするかを示す文脈(展開時のタブ構造)を失ったまま2語だけ残り、誤読しやすかった(45-A4、「与ダメ/被ダメ」へ文言変更)。展開表示で成立していた凡例が縮約側でも成立するとは限らない)。
  **あわせて、同じ状態への強調・色分けが何層で同時に効いているかを数える。** 同一の状態が2層以上で色表現されていたら、どの1層に集約すべきかを提案する(実例: 確定数の色がカード背景+技列個別+累計の**3層**で効いており、ユーザー指示(26-D1/D2)で累計のみに縮小。お気に入りがカード全体ハイライト+★の2重で、★のみに縮小(27-B4))。
- 【固定3】**常時表示情報の優先順位と退避**: 画面に常時表示されている情報を1つずつ「**この画面の目的(一覧=見比べて選ぶ / 編集=値を作り込む)に常時必要か。ホバー・詳細画面・折りたたみに退避できないか**」で仕分ける。**情報を『足す』提案をするときは、代わりに退避・削除できる候補を必ず1つ以上併記する**(足す一方だと画面は必ず過密化する)。
  実例: **カード上のステータス6値はラウンド3以降、誰も要否を問わないまま維持され、ユーザー指示(32-B1)で「カードから削除して小型化、ホバーに退避」になった。** 直前のラウンドのレビューは情報を足す方向にしか動いていなかった。**天候・フィールドを右パネル最下部へ(32-R2)も同型**(操作頻度の低い設定が一等地を占めていた)。
  **既存情報の表示先の移動(常時→ホバー/詳細)は「機能追加」ではない。提案してよい。** 並び順の優先度づけに迷ったら、プレイヤー視点レビュアーが挙げる**使用頻度**を根拠にすること。
- **【条件付き】ワイヤーフレームとの構造差分の列挙**(**新設ページの初回講評、またはレイアウトを作り直した直後のラウンドのみ**。ラウンド30で全画面の照合が完了し「未記録の逸脱0件」を確認済みなので、差分が新たに生まれるタイミングだけ回せばよい): `docs/ui_proposal/` に対応するワイヤーフレームがある画面は、現画面との構造差分(セクションの分割方法・順序・項目の所属)を**すべて列挙**し、各差分が (a) ユーザー承認済みの逸脱か (b) 実装都合・実測都合の逸脱か を計画書で確認する。**(b) のまま複数ラウンド生き残っている逸脱は指摘する。**「WFはモックだからそう見えるだけ」という推測で維持しないこと(実例: 右パネルはWFが一貫して縦積み+急所独立なのに、実測都合で左右2分割にし(23-R3)、次のラウンドで「モックだから」と維持判断し(25-R1)、ユーザーが縦積みを明示指示するまで(27-R1)**3ラウンド分の作り直し**になった。差分列挙を毎回していれば1回目で正解に近づけた)。
- 【固定4】**空状態・0件・保存失敗・ホバー/フォーカスの表示を毎回1項目確認する**。**ホバー・フォーカスはスクリーンショットに写らない**ので、`:hover` / `:focus` のCSSと関連JSを読んで「ホバーで何が起きるか / 何が見えるか」を確認する(実例: カード全体のホバー浮き上がりと削除ボタンのopacityホバーは一度もレビューされず、ユーザー指摘(31-D1/31-D2)まで残った)。**ホバーでしか見えない情報が常時表示と重複していないかも見る**(実例: `/box` カードの `title` は「とくせい/持ち物/わざ」で、カード上に全部出ている情報の繰り返しだった → 32-B4)。該当するスクリーンショット・確認手段が無い場合は「**この状態は確認できない**」と明記すること(確認できないことを黙って通過しない)

## 特に見てほしい観点
<箇条書きで8〜12項目。例: 乱数・確率表示がjpokeの計算結果と矛盾なく読めるか/命中回数や急所などの前提条件が画面から読み取れるか/技威力・タイプ相性・持ち物補正など対戦判断に直結する数値が省略・誤解されていないか。以下の固定3項目を毎回含める>
- 【固定1】**選択肢集合と既定値の妥当性**: セレクト・トグルの選択肢が、このアプリの対戦フォーマットで**実際に発生する要素だけ**になっているか。逆に必要な要素が欠けていないか(実例: 天候に強天候3種、状態異常に「ゆめうつつ」が残っていて、レビューでは拾えずユーザー指示で削除された)。
  **あわせて、初期値・空状態がゲーム上実在する状態かを確認する。** 候補が一意または自明に決まる入力が空欄で始まっていないか(実例: 「特性なし」はゲームに存在しない状態だが、種族が確定した後も特性欄が空欄フォールバックのままで、**9ラウンド誰も指摘せず**ユーザー指示(26-L1)で第1特性の自動設定になった)
- 【固定2】**表示値の再計算**: 画面に出ている計算値(実数値・期待値・倍率・ヒット回数)を**最低2つ選び、知識ベースの式で自分で再計算して一致を確認する**。式がコードにあるなら実装(`ファイル:行`)まで読み、**その式がドメイン上必要な因子をすべて受け取っているか**を確認する(実例: 期待値が `威力×命中` のみで**ヒット回数を無視**しており、連続技23件すべてが過小表示。さらに `ふくろだたき` は `power: 1` のため `null` 除外をすり抜けて無意味な「期待値1」が出ていた — **除外条件が境界データで破れないかも見る**)。不一致を指摘するときは**再計算の式と参照データを必ず書くこと**
- **縮約表示での計算意味の保存**: 同じ計算結果が複数の表示形態(展開/折りたたみ/一覧)で出るとき、**縮約側だけを単独で読んで意味が確定するか**を確認する(実例: 技2列あるカードの合計「確2」が、圧縮表示単独では「技セット周回数かヒット数か」読めなかった(45-B3)。技名の「(N発)」が仮置き最小値か固定ヒット数か区別できない(45-C)。いずれも展開表示では文脈から読めるため、展開だけ見るレビューでは出てこない)。縮約表示が新設・変更されたラウンドでは必須。
- **【条件付き】ドメイン上の極端ケースを「実データの集計」で特定し、スクショ・実測に含まれているか確認する**(**データ表示・入力候補が新設または変更されたラウンドのみ**。表示系が変わらないラウンドでは分布の端も変わらず、マスターデータ集計はコストが重いため。ラウンド32のメタレビューで固定枠から外した): 「長い名前」のような推測ではなく、**マスターデータを集計して実在の端を実名で挙げる**(0件のケース・最大件数・最長名。実例: 覚えるポケモン0種の技が218/716件、技301件のミュウ、`ムゲンダイナ(ムゲンダイマックス)` 17文字)。含まれていなければ「このケースでここが壊れる/誤読される」と名指しすること。**分布の端が「バグに見えるが仕様」の場合(実例: learnsetはチャンピオンズ固有データで `トリプルキック` を覚えるポケモンが0件)は、仕様だと断ったうえで「ユーザーがバグと誤解しない表現になっているか」という指摘に変換すること**
- **【回転枠・条件付き必須】「並び順と表記が対戦者の常識と一致するか」を必ず含めること**
  (a) **並び順**: パネル・セクション・候補リストの順序が対戦準備の**思考順**と**操作頻度順**に合っているか。頻度は「**そのカード・その画面を開くたびに触るもの(ランク・状態異常など)が上、一度設定したら滅多に変えないもの(天候・フィールドなど場全体の設定)が下**」で評価する(実例: 詳細設定を天候→壁→攻撃側から攻撃側→防御側→場へ変更、技候補を全716技無差別からlearnset優先へ変更)。編集や入力を伴う画面(`/box` 系)を見るラウンドでは必須、参照系だけのラウンドでは任意。
  **現状の並びを「妥当」と追認するときは、指摘と同じ水準で頻度・思考順の根拠を書くこと**(実例: 右パネルの並びをラウンド29で「妥当と追認」したが、ユーザーは31-R2で急所を攻撃側の中へ、32-R2で天候・フィールドを最下部へ移した。**頻度基準では追認できない並びだった**)。あわせて、**設定・チップのグルーピングがゲーム上の意味の系統(揮発状態 / 場の状態 / 攻撃側固有 など)と一致しているか**を確認する(実例: 32-R5「かべは他の揮発状態と同じグループに」、32-R4「急所とじゅうでんは同じグループに」)。
  **常時表示されている各情報の「対戦準備での使用頻度・重要度」を1行ずつ明記すること**(UXレビュアーが「退避できる情報」を判断する材料になる。実例: 個体を最も差別化する持ち物が16pxの最小表示のまま数ラウンド放置され、29-B3→31-L2→32-L3 と**3回に分けて**調整される羽目になった)。
  (b) **表記**: ラベル・ボタン文言が**ゲームの公式用語**か。**略記・短縮を提案・容認するときは、公式用語のままだと物理的に入らないことを実測してから。**(実例: 幅が狭いからと短縮した「テラス」「相手の壁」「攻撃(自分)」の3件が、ラウンド28で**全部ユーザーに戻された**(「テラスタル」「リフレクター・ひかりのかべ」「攻撃側」)。用語の正確さより幅を優先した判断ミスは、プレイヤー視点が止めるべき種類の変更)。**(b) はゲーム用語が表示される画面なら参照系ラウンドでも確認する。**
  **画面の表記集合が対戦者の慣用表記の体系と部分的にしか一致していない場合、欠けている側が指示・会話の解釈揺れを生む**(実例: 確定数はプレイヤー慣用では「確N/乱N」の対だが、画面は「確N/10発以上」のみ(乱N表記は21-D7で廃止済み)。ユーザーは43-D3で「乱3も薄青で」と存在しない表記で指示し、Coordinatorが推測で解釈する羽目になった。廃止判断自体は再提起しないが、**慣用体系との差分がユーザーの指示語彙と食い違う兆候が出たら「表記集合の再確認」としてユーザー判断待ちに載せること**)。

## 監査手順(この順で全部行う。省略しない)
1. **フォント棚卸し**: 画面内の全テキストを役割(見出し/ラベル/入力値/本文/補足)に分類し、font-size・font-weight・色を表にする。**同じ役割に2つ以上の値があれば逸脱として列挙**(12px下限割れは即逸脱。実例: 新設ページで 0.74rem=11.84px が再発した(30 A-3))。**同一情報の状態対(展開/圧縮、常時/ホバー)がある部品は、両状態を同じ役割として表に並べる**(実例: 実数値が展開700・圧縮400に割れていた(45の軽量パスで検出・修正))。
2. **アイコン・画像棚卸し**: 全アイコン/画像の実寸を列挙する。確立済み規格は **20px と 28px**。それ以外の寸法はすべて逸脱候補として列挙する。
3. **余白リズム**: 同じ階層のセクション間・行間の gap をすべて実測し、値の種類を数える。**同一パネル内で同じ階層の gap が2種類以上あれば列挙**(実例: 左サイドの行間が 20.8px と 12.8px で不揃いのままユーザー指摘(31-L6)まで放置された)。
4. **整列**: 同じ行・同じ縦ラインに並ぶ部品の top / left / width / height を実測し、**1px以上のズレをすべて列挙**(実例: 種族selectとニックネームinputのYが4.0pxズレたままユーザー指摘(31-L4)まで放置された。**真因は `<button>` だけ `input,select` の `min-height` の対象外という系統差**だった —— **ズレの一覧には「同じ原因と推定される群」の束ねを付けること**)。**あわせて、円形・矩形のアイコンボタン/バッジについて「容器の中心と中身(グリフ・アイコン)の中心」のズレも実測する**(実例: 圧縮展開ボタンの»が円中心から約11.5pxずれたままユーザー指摘(43-D5)まで残った。**容器にtransformを当てても中身の文字位置は動かない**という罠も同件で発覚)。
5. **確立済みパターンの適用監査**: 次の文法が、**新設・変更された要素にも**適用されているかを1つずつ確認する: 未設定=破線枠+placeholder色+左揃え / ボタン=反転ホバー / 数値=`tabular-nums`(`.tnum`)/ `display` 指定クラスへの `[hidden]` 併記 / JS生成要素のスタイルは `<style is:global>`。適用漏れは逸脱として列挙(実例: 新設されたテラス表示が未設定文法に従わず、ユーザー指摘(32-D2「placeholderのように薄く」)まで残った)。
   あわせて、**「`<button>`で実装された値選択フィールド」(`.tera-dropdown-button` / `.item-dropdown-button` 等)は、input/select系の規格から漏れる事故が3回別プロパティで再発している**(min-height 31-L4 → font-size/padding 43-D4 → font-weight 44-A1〜A3。原因はいずれも`global.css`のbutton基底)。このパターンの部品を全部列挙し、**font-size / font-weight / line-height / padding / min-height の5プロパティ全部**を隣接するinput/selectと突き合わせること(1プロパティだけ確認して通過しない)。

- 4レビュアーの間で**役割の重複**(同じ問題を毎回2体以上が指摘している)がないか。あれば観点の切り分けを見直す

## 運用上の注意

### エージェントが落ちたとき
APIエラーで停止することがある。`SendMessage` での再開は**失敗することがある**(`No transcript found`)ので、その場合は再起動する。再起動時は:
1. **後片付けを自分でやる**(残ったテストデータの削除、一時ファイルの削除、`astro build` が通るかの確認)
2. 新しいエージェントに「**前任者が途中まで実装して中断している。grepの結果はこうだが鵜呑みにせず、自分でファイルを読んで対応済み/未対応を確認してから始めること**」と伝える
   - **実例1**: grepでは未実装に見えたA-3・A-6が、実は完成していた。前任者は報告の直前に落ちていただけだった。
   - **実例2(ラウンド15)**: Coordinatorが「A-5とB-3は未着手」とgrepで判定して引き継ぎに伝えたが、**実際は全項目実装済み**だった(grepパターンが実装と不一致)。引き継ぎ側が指示どおり自分でファイルを読んで判定し直したため実害は出なかった。
   - **教訓: grepは「着手したかどうか」の目安にはなるが、完成/未完成の判定には使えない。** 状況説明は必ず「鵜呑みにするな」とセットで渡すこと。

### 並列化の判断
- **同じファイルを2体に触らせない。** これが唯一の絶対ルール。
- 資産生成(画像など)は切り出して並列化できる。**ヘルパー関数のシグネチャと生成先パスを報告させて**、使う側のエージェントの指示に貼る。
- 共通CSS(`global.css`)を触るエージェントと、ページを触るエージェントは並列でよい(トークン名を変えない限り)。

### 大きな構造変更は1体に任せる
3カラム化のようなレイアウトの作り直しは分割できない。関連する小さい要件も同じエージェントにまとめて渡し、「途中で `npx astro build` を通しながら進めてください」と添える。
