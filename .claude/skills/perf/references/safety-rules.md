# 検証操作でデータを壊さないための必須ルール

パフォーマンス計測はページを操作して実測するため、`ui` skillの検証(見るだけ)より**データを壊すリスクが高い**。シナリオ整備・原因調査・修正実装のいずれでも、このルールを踏まえること。

## 🔴 前提: 入力・クリックで自動保存が走る画面がある

`.claude/skills/ui/references/pitfalls.md`「自動保存があるので、検証クリックがデータを壊す」節を必ず読むこと。過去に検証クリックで実在個体(メガリザードンX)の性格が書き換わり、気づかれずに基準値として扱われかけた事故がある。

判明している自動保存画面(2026-08-31時点):
- `/box/[id]` — 入力・クリックで即座に自動保存
- `/team/[id]` — メモ入力・編成変更で700ms後に `PUT /api/teams/:id`

**新しい画面のシナリオを書くときは、まず自動保存の有無をソース(`src/pages/**/*.astro`)から確認すること。確認できない/読み切れない場合は「自動保存があるものとして」安全側で扱う。**

## 許可される操作 / 許可されない操作

| 操作 | 既存フィクスチャに対して | 使い捨てデータに対して |
|---|---|---|
| ページを開いて表示を見る(GET) | ✅ 常に安全 | ✅ |
| ダイアログを開いて、選択・確定せずに閉じる | ⚠️ 実装を確認し、開閉自体が保存処理(`scheduleSave()`相当)を呼ばないと確認できた場合のみ | ✅ |
| 値の選択・入力・確定(自動保存を誘発する操作) | 🔴 絶対に行わない | ✅ 必ず後始末する(下記) |

**少しでも自動保存の副作用が読み切れない操作は、無理に実装せず見送ってよい。** 安全側に倒すこと自体を成果として扱う(「〇〇は安全性の理由で見送った」と報告させる)。

## 使い捨てデータのライフサイクル(値を変更する計測をしたい場合)

1. **作成**: 対象APIのPOSTで使い捨てのレコードを作る(例: `POST /api/owned-pokemon` で空個体、`POST /api/teams` で空チーム)
2. **操作**: 作成した使い捨てレコードに対してのみ、計測したい操作を行う
3. **削除**: `test.afterAll` / `finally` 等で確実にDELETEする。**DELETEのレスポンスが200だったことだけで完了と判断しない**
4. **確認**: 一覧GET(`GET /api/owned-pokemon`・`GET /api/teams`等)を叩き、使い捨てで作ったIDが実際に0件になっていることを確認する。この確認結果を完了報告に含めさせる

過去の教訓(`.claude/skills/ui/references/pitfalls.md`より): 「DELETEしました」という自己申告と実際の削除は一致しないことがある。タイムアウト等で`finally`/`afterAll`が実行されずに使い捨てレコードが残留した実例もある。**サイクル開始前に、前回までの残留物が無いか一覧GETで確認してから始めるとより安全。**

## APIのPOST/DELETEに関する既知の注意

- `POST`/`DELETE` は `Origin` ヘッダのsame-origin検証(CSRF対策)にかかることがある。`page.request`(APIRequestContext)はブラウザのoriginと一致しないヘッダになる場合があるため、失敗する場合は`page.evaluate(() => fetch(...))`でブラウザのsame-origin fetchとして送る(`credentials: "same-origin"`)。
- `POST /api/owned-pokemon` のボディは空オブジェクト`{}`で空個体が作れる(2026-08-31時点)。API契約が変わっていないか、実装(`src/pages/api/owned-pokemon.ts`)で都度確認すること。

## 分析ログ等、削除不要な副作用について

`POST /api/search` のように、既存データを書き換えず**ログテーブルへのINSERTのみ**が起きる操作は、使い捨て後始末の対象外でよい(削除しなくても既存データへの影響が無い)。ただし実行のたびにログが増える副作用があることを `note` に明記すること。判断に迷ったら後始末不要と決めつけず、対象APIの実装を読んで確認する。
