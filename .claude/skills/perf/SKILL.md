# パフォーマンス計測・改善サイクル

**1回の呼び出し = 1サイクル(課題1件の 調査→実装→再計測→commit)。** 状態は `docs/perf/dashboard.md`(計測結果表 + 目標タイムの目安 + 既知の欠落シナリオ)に永続化されているので、途中から再開できる。`/loop perf` で繰り返し起動される前提で書かれている。

**特に指示のない限り `main` で直接作業する**(専用worktree/ブランチは作らない。→ ルートの `CLAUDE.md`「作業方針」)。**各サイクルの作業が一区切りついたら Coordinator が `git commit` する**(`git push` はしない)。

## 全体の仕組み(このskillが動かす実体)

- `docs/perf/dashboard.md` — 計測結果の一覧表(優先度・分類・目標(ms)・実測(ms)・超過率・備考)。**`<!-- PERF_TABLE_START -->`〜`<!-- PERF_TABLE_END -->` の間はレポーターが自動生成するので手で編集しない。** それ以外(冒頭の運用方針・目標タイムの目安・「表から欠落しているシナリオ」節)は自由に書き足してよい
- `tests/perf/scenarios/*.perf.spec.ts` — 計測シナリオ本体。画面/機能のまとまりごとにファイルを分ける(既存: `home-data.perf.spec.ts` / `box.perf.spec.ts` / `team-ranked.perf.spec.ts`)
- `tests/perf/lib/perf.ts`(`perfScenario`/`timeNav`/`timeAction`/型`PerfMeta`) / `perf-reporter.ts` — 全シナリオ共通の契約。**通常は編集しない**(変更が全シナリオに波及するため、必要になったらCoordinator自身が理由を明記して直す)
- `playwright.perf.config.ts` / `npm run test:perf` — 実行エントリポイント。`astro dev`(起動済みなら自動検出)を対象に、1シナリオ3回計測して中央値を取る

## 役割分担

| 役 | 担当 | やること | やってはいけないこと |
|---|---|---|---|
| Coordinator(メイン) | — | 現状把握、優先度判断、対応方針の決定、委任、diff検証、再計測、commit | 大きな調査・実装を自分で丸抱えする |
| 調査担当 | codexが使えれば優先(`--sandbox read-only`)、なければsonnet | 対象シナリオが遅い原因の特定 | ファイル編集・git操作 |
| 実装者 | codexが使えれば優先、なければsonnet | 修正の実装、シナリオ整備 | 担当外ファイルの編集、**git commit/push** |

**委譲するかどうかは規模で判断する。** 原因・修正箇所が既知で1箇所・数行に閉じる場合(P3で調査省略可としている既知原因のケースなど)は、Coordinatorが直接調査・実装してよい。`.claude/skills/codex/SKILL.md`の判断基準(委任のセットアップコストが本体作業を上回るか)を目安にする。

## 手順

### P0. 現状を把握する(毎回最初に行う)

`docs/perf/dashboard.md` を読む。

- 計測結果表が無い、または最終計測日時が直近のコード変更より明らかに古い → まず `npm run test:perf` で再計測する(`npm run dev` が起動していなければ先に起動する。バックグラウンド実行を使い、完了通知を待つ。全シナリオ実行は数分〜数十分かかることがある)
- 「表から欠落しているシナリオ」節の記載を確認する。**タイムアウト等で表から消えているシナリオは、表示上の🟢/🟡より優先度が高い**(計測不能=未知のリスクとして扱う)
- ユーザーが対象ページ/操作を指定している場合、対応する`.perf.spec.ts`に該当シナリオが無ければP1へ進む

### P1. シナリオのカバレッジを確認する(未整備なら実装より先に整備する)

ユーザーが指定した画面・操作、または新規追加されたページに対応するシナリオが無い場合は、先にシナリオを追加する。計測できない課題は改善サイクルに乗らない。

- 対象の`.perf.spec.ts`(画面のまとまりで分かれている。新しいまとまりなら新規ファイルにする)に追記する
- `tests/perf/lib/perf.ts` の `perfScenario` / `timeNav` / `timeAction` を使う。目標タイム(`targetMs`)は `docs/perf/dashboard.md` の「目標タイムの目安」表に従い、外れる場合は`note`に根拠を書く
- **`references/safety-rules.md` を必ず読んでから実装(または委任)する。** このアプリには入力・クリックで自動保存が走る画面があり、検証操作が既存データを書き換える事故が過去に起きている
- 複数画面/複数ファイルにまたがる整備は、ファイル単位で並列にcodexへ委譲してよい(`references/agent-prompts.md`「シナリオ整備テンプレート」)。**担当ファイルが重ならないよう分ける**
- 整備後、`npx playwright test --config=playwright.perf.config.ts <対象ファイル> --reporter=list` で新規シナリオがpassすることを確認する。**複数エージェントを並走させるときは、共有ファイル(dashboard.md・docs/perf/results/latest.json)を壊さないよう各自`--reporter=list`を必須にする**(通常の`npm run test:perf`はCoordinatorが全員完了後にまとめて1回だけ実行する)

### P2. 対応する課題を選ぶ

- ユーザーが対象を指定していればそれ
- 指定がなければ優先度順: **表から欠落(タイムアウト等) > 🔴 > 🟡**。同順位が複数あれば超過率が高い順
- 全て🟢・欠落なしなら、P1のカバレッジ確認に戻る(未計測の画面・操作が残っていないか)。それも尽きていれば、ユーザーに完了を報告してループを止める

### P3. 原因を調査する

対象シナリオが叩くページ・APIを読み、遅い原因を特定する。

- 既知の原因に一致するなら調査を省略してよい(既知の原因はdashboard.mdの各行`note`または「表から欠落しているシナリオ」節に記録されている)
- 未知の原因は`references/agent-prompts.md`「調査担当テンプレート」でcodex(`--sandbox read-only`)に委託する。単純な原因(不要な同期待ち・明らかなN+1等)ならCoordinator自身で読んでもよい
- **アプリのコードではなく計測対象の外部要因(devサーバー・外部API等)が原因と分かった場合、直接修正できないことがある。** その場合は無理に直そうとせず、dashboard.mdの該当行`note`または「表から欠落しているシナリオ」節に原因を明記し、次点の課題(P2)に進む

### P4. 実装する

`references/agent-prompts.md`「実装者テンプレート」で修正を委譲する(codex優先)。指示に必ず含める:

- 原因(P3の調査結果)と、直したい対象(ファイル・関数・クエリ等)
- **「git commit / git push は絶対にしない」**
- `.claude/skills/ui/references/pitfalls.md` の該当する罠(データ事故・CSS/DOMの罠)。修正がUIの見た目に影響する場合は `.claude/skills/ui/SKILL.md` の「デザイン方針」も踏襲させる
- 修正が計測シナリオ自体の書き方の問題(待機条件が不適切、目標タイムの設定ミス等)であれば、シナリオ側(`.perf.spec.ts`)を直す

### P5. 再計測して検証する

- `npx playwright test --config=playwright.perf.config.ts <対象ファイル>`(共有ファイルへの書き込みが起きるので、他に並走中の委譲があれば完了を待つ)
- 改善したこと(超過率が下がった/🔴→🟢、表から欠落していたシナリオが復帰した等)を確認する。改善しなければP3に戻る
- 可能なら `npm run test:perf` で全件を再計測し、他のシナリオに回帰が無いか確認する(時間がかかるためバックグラウンド実行を使う)

### P6. commit する

**Coordinator が `git commit` する**(`git push` はしない)。dashboard.mdは`npm run test:perf`実行時に自動更新されているので、内容が意図通りか(「表から欠落しているシナリオ」節の記載が古くなっていないか等)確認してからcommitに含める。**そのcommitに、このセッション以外(他セッション由来)の未コミット変更を巻き込まない**(`git status`で担当外ファイルの差分が無いか必ず確認する)。

## ループの終了条件

以下のいずれかで `ScheduleWakeup` に `stop: true` を渡してループを終える(`/loop perf` で起動されている場合)。

1. 表から欠落しているシナリオが0件、かつ🔴が0件になった(🟡以下を追うかはユーザーの判断に委ねてよい)
2. 残る課題がすべて計測対象の外部要因(devサーバー詰まり等)で、アプリ側の対応では改善できないと判明した
3. P0/P2でユーザーへの確認が必要になり、回答待ちで進められない

**1件直すごとに一度止まってユーザーに報告してよい。** 連続して複数件直すかはユーザーの判断に委ねる(`/loop perf`なら自動で次に進む)。
