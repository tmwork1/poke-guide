# jpoke 知識ベース

**目的**: `vendor/jpoke` / `../jpoke` のソースを**毎回読み直さない**こと。ここに書いてあることはソースを読まずに信用してよい。ここに無いことだけソースを読み、**読んだら必ずここに書き足す**(下の「蓄積のルール」)。

## 大前提(ここを間違えると全部が嘘になる)

| | パス | 位置づけ |
|---|---|---|
| **仕様の正** | `vendor/jpoke/` | **アプリが実際に実行しているのはこちら。v0.2.0。** 配布物は `public/master-data/pyodide/wheels/jpoke-0.2.0-py3-none-any.whl` |
| 上流 | `../jpoke/`(`C:\Users\tmtmp\Documents\pokemon\jpoke`) | 開発リポジトリ。読解の補助にはしてよいが、**食い違ったら `vendor/jpoke` が勝つ** |

**2026-07-27時点の両者の関係(実測)**: `diff -rq` の結果、`src/` の中身は**実質同一**。差分は上流にだけある空ディレクトリ `src/jpoke/utils/type_defs/`(中身0件、どこからも参照なし)のみで、`pyproject.toml` も両方 `version = "0.2.0"`。上流のgit HEAD(`d51e9c96b`)はドキュメントのみの変更だった。

- つまり**今は乖離していない**。「vendorが古い」という前提で上流を見に行く必要は現時点では無い。
- ただし**この関係は上流が動けば静かに崩れる**。乖離を疑う根拠にすべきは上流のコミット履歴ではなく、`diff -rq --exclude=__pycache__ --exclude='*.egg-info' vendor/jpoke/src ../jpoke/src` の実行結果。**履歴が進んでいること = ソースが乖離していること、ではない**(実際このドキュメント作成時、上流のコミットが進んでいるのを見て乖離していると誤認した)。

- `../jpoke/docs/quick_reference.md` は60KBある。**丸ごと読まない。** ここに要約が無い論点に限って、必要な節だけ開く。
- vendoring の方針と更新手順は `vendor/jpoke/VENDORING.md`。**このスキルはそれを複製しない**ので、更新作業をするときは必ずそちらを読む。

## 絶対に間違えないこと(誤指摘の常連)

**チャンピオンズルールは仕様であってバグではない。**

- **IV = 31 固定**
- **努力値は 0〜32 スケール**(素の 0〜252 スケールではない)
- **Lv50 固定**
- **努力値の合計上限 66**

これらを「バグでは?」と指摘したエージェントが何度も出ている。**直そうとしないこと。** 詳細と変換式は `references/ruleset.md`。

## 蓄積のルール(このスキルの本体)

このスキルは**書き足されることを前提に作られている**。読むだけで終わらせない。

### 1. 事実には必ず出典を付ける
```markdown
- 努力値は0〜32スケールで保持し、内部で×8して素の努力値に変換する(出典: `vendor/jpoke/src/jpoke/model/stats.py:123-130`)
```
出典の無い記述は、次に読むエージェントが**信用できないので結局ソースを読み直すことになり、このスキルの目的を達成しない**。出典を書けないなら書かない。

### 2. 確認できなかったことは `(未確認)` と印を付ける
推測を事実として書かない。`- (未確認) 急所時はランク補正の下降を無視する可能性がある` のように、**未確認であること自体を残す**方が、次のエージェントには価値がある。

### 3. 各ファイルの冒頭に「検証時点」を書く
```markdown
**検証時点**: jpoke v0.2.0 (`vendor/jpoke`) / 2026-07-27
```
**`vendor/jpoke` を更新したら、この行より古いファイルは全部「要再検証」になる。** 更新した人は各ファイルの冒頭に `> ⚠ jpoke vX.Y.Z 更新により未再検証` を追記すること(中身を消さない。古い記述でも出典があれば差分確認の出発点になる)。

### 4. ソースを読んだら書き足してから終わる
**ここに無いことを調べるためにソースを読んだら、その回のうちに該当ファイルへ追記する。** これをやらないと、次のエージェントが同じ調査を最初からやり直す。1〜2行でよい。

### 5. 短く保つ
**各 `references/*.md` は250行を上限**とする。長くなったら「コードを読めばすぐ分かること」から削る。残す価値があるのは:
- コードを読まないと分からないこと(端数処理の順序、変換式)
- 読んでも誤解しやすいこと(スケール、適用順)
- 複数ファイルを横断しないと分からないこと(接続面、更新時の影響範囲)

上限に当たったのに削れない場合だけ、`references/` にファイルを1枚足してこの表に行を追加する。

### 6. 事実だけを置く
「この画面をこう直すべき」といったUI上の判断は**ここに書かない**(それは `docs/plan/ui_rounds/` の仕事)。ここに置くのは **jpoke がどうなっているか**だけ。判断は変わるが、エンジンの仕様は変わらない。
