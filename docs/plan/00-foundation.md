# UI 改修プラン

## ページ構成
3ページ構成

1. ホーム：サイトの入り口。DBの統計情報などを表示する。
2. ポケモン育成登録：battle-assistant の移植。パラメータ調整とダメージ計算を同時に表示する。
3. チーム登録：登録したポケモンで6匹チームを作成する。


## 開発の流れ
ホーム、チーム登録は後回し

育成登録は、まずbattle-assistantのポケモン管理をまるごと移植してから細かく調整する。

## タイポグラフィ原則: 数値グリッドの本体値のサイズは「ページ内の階層」で決める

**確定済み現行仕様(2026-07-27、ラウンド16でCoordinatorが決定)。** 複数列の数値グリッドの本体値のフォントサイズは、**アプリ全体で1つに揃えない。** そのページで**主役の数値かどうか**で決める。

| 種別 | サイズ(実測) | 該当 |
|---|---|---|
| **脇役の数値グリッド** — 同じページに他の主コンテンツがあり、比較のために並べる表 | **16.8px**(`1.05em` / `font-weight: 700`) | `/box/[id]` の実数値行(基準)、`/pokemon` の種族値グリッド(下に技一覧300件を抱える)、`/share` の実数値グリッド |
| **主役の数値グリッド** — そのページが答えようとしている問いの答えそのもので、1行に収まる | **24px**(`1.5rem`) | `/moves` の6列グリッド(威力/命中/PP/優先度/急所/対象) |

**なぜ揃えないか**: ラウンド15でUIレビュアーが「同じ役割の部品なのに1.4倍差がある」と指摘した(`/pokemon` 16.8px vs `/moves` 24px)。構造は確かに似ているが、**ページ内での階層が違う**。`/moves` の6列は「この技は採用に値するか」の答えそのもので、そのページに他の主コンテンツが無い。`/pokemon` の種族値は、下に技一覧(最大301件)を抱えた3つのパネルのうちの1枚にすぎない。両者を1つの数値に揃えると、`/moves` から焦点が消えるか、`/pokemon` の種族値が技一覧を圧迫するかのどちらかになる。**「グリッド本体値の統一サイズ」という抽象化そのものが切り方を間違えている。**

**さらに、同じ「実数値」という概念でも、部品が置かれる箱の制約でサイズが分かれる**(2026-07-27、ラウンド17でCoordinatorが決定):

| 種別 | サイズ(実測) | 該当 |
|---|---|---|
| 単独で編集する実数値 | **16.8px** | `/box/[id]` 左パネルの `.stat-row-real` |
| **複数カードを並べる比較UI内の補助実数値** | **12.16px**(`0.76rem`) | `/box/[id]` 相手ビルド箱の `.damage-stat-value` — **ダメージ計算カード3枚を1080pxに収める制約がある** |
| **1画面に多数並ぶ集約カード内の実数値** | **11.8px**(`0.74em`) | `/box` 一覧カードの `.card-stat-real-value` — **218px正方形カードに6列を収める制約がある** |

②③を①に揃えると、**「幅・高さが内容量で正当化できるか」の別の違反(はみ出し・省略)を生む**。箱の制約が先にあり、文字サイズはその従属変数である。

**これらの差はすべて仕様であって不統一ではない。再提起しないこと。** 新しい数値グリッドを追加するときは、上の2つの表のどれに当たるかを判断して選ぶこと。

## レイアウト原則: カードとパネル

アプリ全体で「カード」「パネル」という語をどう使い分けるかの命名規約。**以下がこの節の確定済み現行仕様**(2026-07-26 帯構成+共通トップバー導入により全面差し替え。変遷の経緯は本節末尾の「変更履歴」を参照)。以下より後ろのラウンドログには、この現行仕様に至る前の前提で書かれた記述が残っている箇所があるが、内容が食い違う場合は常にこの節が優先する。

### 役割は2つ

- **カード** = 可算・追加削除できるコレクション要素
  - 該当: **ボックスカード**(ボックス一覧で登録済みポケモン1体を表すカード)、ダメージ計算カード(個体編集)、将来のチームカード
  - クラス: `.card` + 用途別修飾子(`.box-card` / `.card-damage`。`.card-pokemon` はボックスカードの旧識別子)
  - 視覚仕様: `--color-surface-alt` / `1px solid --color-border` / `--radius-md` / `--space-3` / `--shadow-sm`、hover で `--shadow-md` + `translateY(-2px)`、選択中は `.is-selected` で `border-color: --color-primary`
  - **浮いた箱**であることがカードの本質

### ボックスカードの命名・カスタマイズ

- **ボックスカード**は、`/box` 一覧に表示される「登録済みポケモン1体」のカードを指す固有の呼称とする。一般的な「ポケモンカード」や、個体編集画面のダメージ計算カードとは区別する。
- DOM の標準識別子は `.box-card`。既存の `.card-pokemon` は後方互換のため残すが、新しいコード・スタイル・ドキュメントでは `.box-card` を使う。
- 見た目を変える値は [src/styles/box-card.css](../../src/styles/box-card.css) の `--box-card-*` へ集約する。カードの大きさ、画像、文字、技リスト、持ち物バッジ、操作ボタン、モバイル時の値をここでカスタマイズできる。

- **パネル** = 画面端まで伸びる帯
  - 該当: 育成情報バー(左端)、詳細設定サイドバー(右端)、トップバー(上端)、ボックスのツールバー、検索結果・種族値表などの本文領域
  - クラス: `.panel` + 接する辺の修飾子
  - 視覚仕様: `--color-surface` / **角丸なし** / **外側marginなし** / `padding: --space-6 --space-5` / border は既定ゼロ
  - 罫線の修飾子: `.panel-left`(左端固定・`border-right`) / `.panel-right`(右端固定・`border-left`) / `.panel-top`(上端固定・`border-bottom`)
  - 縦に積んだ帯の継ぎ目: `.panel + .panel { border-top }`
  - 帯の中身の可読幅: `.panel-content { max-width: 1080px }`(`margin: 0 auto` を付けず**左寄せ**)

### `.panel-content` の使い分け(ユーザー確定仕様)
- **全幅にする(`.panel-content` を使わない)**: トップバー、ボックスのツールバー、カードグリッド
- **1080pxに押さえる(`.panel-content` を使う)**: 検索結果・注目枠、種族値表・特性・進化前・技一覧、共有ページの各項目
- 理由: 1920px幅で技一覧や本文の1行が長くなりすぎて読めなくなるため。操作系は全幅、読む対象は可読幅、という切り分け。

### 共通トップバー(`AppLayout`)
- `AppLayout.astro` が全ページ共通のトップバーを描画する。サイドバーの右隣から画面右端まで伸びる帯。
- `position: sticky; top: 0` で上端固定。z-index は 20(サイドバー30・オーバーレイ25・ダメージ詳細パネル60 より下で、被って操作を妨げない)。
- 高さは `:root` の CSS変数 `--topbar-height`(デスクトップ 65px / モバイル2段 129px)で公開する。左右の帯が `calc(100vh - var(--topbar-height))` で参照する。
- 中身: 左に「← 戻る」+ページタイトル+状態表示、右にページ固有操作+アカウント情報。
- ページ側のインターフェース:
  - props: `title`(トップバー見出しと `<title>` タグ兼用。`<title>` には「 | Poke-Commons」が自動付加される) / `backHref`(指定時のみ戻るリンク表示) / `backLabel`(既定「戻る」)
  - スロット: `topbar-status`(タイトル右の状態表示) / `topbar-actions`(右側の操作)
- アカウント情報は `AppLayout` が `Astro.locals.user` から自前で描画するのでページ側は不要。
- モバイル(900px未満)は2段。1段目=ハンバーガー+サイト名+アカウント、2段目=ページタイトル+操作。

### 「タイル」という語を使わない理由
tile は業界通念上「反復するグリッド項目」(Windows のライブタイル、Material の GridTile / ListTile)を指し、それは本プロジェクトの「カード」に当たる。領域の呼称に使うと意味が反転するため使わない。なおクラス名 `.add-card-tile`(カード追加枠)は**グリッド項目**なのでこの通念に沿っており維持する。

### 無効化したもの
- `.page` の中央寄せ(`max-width` / `margin: 0 auto` / 左右padding)を撤去した。帯が画面端まで届くようにするため。
- `.page-narrow` / `.page-wide` は空ルールに無害化した。参照が消えたら削除する。
- `box/[id].astro` の CSS変数保持セレクタは `.page-wide` から `.edit-shell` に付け替え済み。
- `.card-interactive` は廃止し、hover の浮き・影を `.card` 本体に統合した。

### 検証済みの事実
- `npm run build` 成功、ユニットテスト 199/199 パス。
- 1920px / 1280px で Playwright スクリーンショット実測。
- 個体編集ページで左右の帯がトップバー直下から画面下端まで途切れず伸びることを確認。

### 変更履歴
この節は次の3世代を経て現行仕様に至った。将来「なぜこうなっているのか」を追うための記録として残す。

1. **1世代目(2026-07-24頃 確定・現在は誤り)**: パネル = 角丸12px + 全周border + padding 24px の「囲み箱」。カードとの違いは色味と影の有無だけで、両方とも「浮いた箱」という形状は共通だった。
2. **2世代目(帯への再定義)**: ユーザーから「パネルはページの上下端もしくは左右端まで伸びている帯を期待していた」という指摘があり、パネルを**画面端まで伸びる帯**に再定義した。角丸・外側margin・影を撤去し、`.panel-left` / `.panel-right` / `.panel-top` の辺別修飾子と、本文の可読幅を絞る `.panel-content` を新設。`.page` の中央寄せは帯を妨げるため撤去した。この指摘が本節の設計そのものを覆す転換点であり、以降の実装はすべて帯を前提にしている。
3. **3世代目(現在。共通トップバーの新設)**: 帯構成にした結果、個体編集ページで左右の帯の上端がページ固有ヘッダーの高さに揺さぶられ、上側が途切れて見える問題が起きた。左右の帯が画面上端から一貫して始まるよう、全ページ共通の `AppLayout` にトップバー(帯)を新設し、`--topbar-height` を介して左右の帯の高さ計算をトップバーに固定した。

## ビジュアル原則: 角丸とフォントウェイトの使い分け

**確定済み現行仕様(2026-08-11、既存実装からCoordinatorが言語化)。** 「カードは丸角にしない」「太字はなるべく使わない」はユーザーの一貫した好みだが、実装は既に単純な全面禁止ではなく**要素の役割に応じた選別ルール**になっている。新しい部品を追加するときは以下の表に沿って判断し、独自の値を都度決め打ちしない。

### 角丸(border-radius)

値の大小ではなく**要素の種別**で決まる。

| 種別 | 値 | 該当 |
|---|---|---|
| **カードの外枠**(可算コレクション要素。上の「レイアウト原則」参照) | **0px**(`--radius-zero`) | `.card` 基底、`.box-card`、`.card-damage`、`.damage-row-build`(相手ビルド)、`.damage-column`(技カード)、`.damage-row-total`(結果表示) |
| 円形(アイコン・アバター・スイッチ・ステッパー) | `50%` | `.sprite-icon`、typeバッジ、`.rank-stepper`、`.toggle-switch-thumb`、`.box-add-button` |
| 入力欄・通常ボタン・カード内の小さな入れ子要素 | `--radius-sm`(8px) | input/select/textarea、通常ボタン、`.tera-dropdown-button`、`.damage-detail-icon-btn` |
| カード内部の中間コンテナ(カードそのものではない副次的な箱) | `--radius-md`(12px) | `.tera-dropdown-list`、`.damage-add-column-button` |
| 囲み枠・ダイアログ・空状態 | `--radius-lg`(16px) | `.empty-state`、`.add-card-tile`、`dialog#opponent-note-form-container` |

**注意**: 「カードは角丸なし」の対象は**カードそのものの外枠だけ**。カード内部に入れ子で置くドロップダウンリストのような副次的な箱は、通常のフォーム部品と同じ `--radius-sm`/`--radius-md` を使ってよい(=角丸禁止をカード内部の全要素へ機械的に広げない)。

**2026-08-14追記**: `.damage-row-build`/`.damage-column`/`.damage-row-total` は元々「カード内部の中間コンテナ」として `--radius-md` を割り当てていたが、ダメージカードのレイアウト改修(4ゾーンをそれぞれ独立した枠線+背景を持つ「カード」としてbg背景の上に並べる形、チームカードのグリッドと同じ視覚言語)により、実質的に「カードの外枠」になったため、`--radius-zero` に変更しユーザーの指摘で上表を訂正した。

### フォントウェイト(font-weight)

「太字を使わない」の実態は全面禁止ではなく、**同列に並ぶ属性値はフラットに揃え、太字は結果・数値・見出しなど"主役"にだけ残す**という選別ルール(ラウンド44で明文化)。

| 用途 | weight | 例 |
|---|---|---|
| 同列に並ぶ属性値(比較・列挙の文脈にある種族名・特性・持ち物・テラス・技名) | **400**(フラット) | ダメージカード相手ビルドの各項目、`.damage-row-collapsed-ability`。`.box-card .card-name` は500 |
| ページ見出し・パネル見出し・バッジ・ボタン | 600〜700 | `.page-title`、`panel h2`、`.badge`、button基底 |
| **結果・判定・数値**(ユーザーが最終的に見るべき箇所) | 700〜800 | `.damage-result-verdict`(800)、`.damage-stat-value`、`.damage-row-collapsed-stat-value`、`.damage-ev-row-label` |

**なぜ選別するか**: ラウンド44で「同じ役割の項目(種族名・特性・持ち物・テラス)の一部だけが太くなっている」ことが4レビュアー一致で指摘された。並列に見比べる項目を無闇に太くすると"何が主役か"が伝わらなくなる一方、判定結果や数値まで細字にすると今度は答えが埋もれる。**「太字を減らす」の判断基準は「その要素が比較対象の属性値か、答えそのものか」であり、フォントウェイトの絶対値ではない。**

**新規実装時の指針**: 新しい部品を追加するときは、まず「これはカードの外枠か・内部の入れ子箱か」「これは比較対象の属性値か・結果そのものか」を判断し、上の表のどのパターンに当たるかを選ぶ。独自のborder-radius/font-weightをその場で決め打ちしない。

## フォーム原則: 入力欄のラベルは可視`<label>`ではなくplaceholder + aria-labelを優先する

**確定済み現行仕様(2026-08-02、UI改修依頼により確定)。** 検索・絞り込み・並べ替え・テキスト入力等のフォーム部品は、`<label class="field-label">`のような常時可視のラベル文字列を置かず、入力欄自体の`placeholder`(またはアイコン)+ アクセシビリティ用の`aria-label`で用途を示す(`box/index.astro`のツールバー・`box-id/LeftPanel.astro`の`#regulation`等が先行例)。

**なぜ**: 可視ラベル+入力欄の組は縦方向の専有面積が大きく、ツールバーのような横一列の骨格領域では特に窮屈になる。placeholderは値未入力時にだけ表示され、入力後は自然に消えるため、値が入った状態での視覚的な余白効率が良い。

**新規実装時の指針**: 新しく検索欄・絞り込みセレクト・テキスト入力を追加するときは、まずplaceholder(+ 必要ならアイコン)+ aria-labelの組み合わせを検討し、それで用途が伝わらない場合(例: 複数の入力が横に並び、placeholderだけでは列の意味が読み取れない)にだけ可視`<label>`を使う。既存の可視ラベルを新規実装のためだけに他画面へ複製しない。

## 決定事項・進捗(2026-07-24)

### 加算ダメージ計算(累計致死率)の実装方針変更
当初は jpoke の `Battle.calc_lethal()` に攻撃列を `(技, ヒット数)` のリストで渡す方針だったが、**実装してブラウザで実測したところ機能しないことが判明したため、`calcLethalSequence()` は自前でHP分布を維持する方式に変更した。**
- 原因: `jpoke/core/lethal.py` の `_lethal_loop` は `fainted()`(=`any()` 判定)で「HP分布に1つでもHP=0の分岐が現れた」時点で計算全体を打ち切る。1発目で一部の乱数だけが致死する組み合わせ(例: 25%)では、生存している残り75%の分岐に対してすら2発目以降が計算されず、`lethal` が1件しか返らない(多段技では0件になる)。
- 変更後: `jpoke.utils.lethal_dist` の分布演算(`to_dist`/`subtract_dist`)でHP分布を関数側で維持し、打ち切りは「全分岐でHP=0(確率100%)」に限定する。
- **トレードオフ(既知の制約)**: `calc_lethal()` が内部で行うターン終了時処理(たべのこし回復、どく/やけどの継続ダメージ)と追加効果系ハンドラ(がんじょう・きあいのタスキ等)は加算計算に反映されない。単発の `calcDamages()` も従来からこれらを考慮していない(`Battle.calc_damages()` が1発分の乱数計算しか行わないため)ので、既存の精度レベルに揃えた形。
- 実測(ハバタクカミ→ディンルー、ムーンフォース、seed=1、相手HP230): 単発 `乱1 25.0%` / 3連 `attackCount 1→0.25, 2→1.0` で確定2発・3列目は「2発目で撃破済」/ 連続回数3の単発は `確1`。単発 `calcDamages` の値は変更前と一致(回帰なし)。

### JSテンプレートリテラルの注意
`src/lib/pyodide-engine.ts` の `BOOTSTRAP_PYTHON` はJSのテンプレートリテラルなので、**中でバッククォートを使ってはいけない**。Pythonのdocstring内であっても文字列がそこで終端し、以降のPythonコードがTypeScriptとしてパースされて `[PARSE_ERROR] Expected a semicolon ...` でビルドが落ちる(実際に踏んだ)。Python側でコメント中に識別子を引用したいときはシングルクォートか「」を使う。`${...}` も同じ理由で書かない。

### カードの構造
1枚のカード = **相手ビルドの箱** + **技列の箱 × N** + **加算条件追加ボタン(＋)**。両方の箱は同じ枠線・背景で、`align-items: stretch` により同じ高さに揃え、下端の区切り線+結果表示の位置を合わせる。

| 箱 | 上から | 最下段(区切り線の下) |
| --- | --- | --- |
| 相手ビルド(320px) | 攻守切り替えボタン+⚙+🗑 / 相手種族名+アイコン(名前の右) / 性格 / 特性 / アイテム / テラスタイプ / 努力値HABCDS / 実数値HABCDS | **加算後のダメ・致死率**(全技列の合計) |
| 技列(190px) | 技名 / 連続回数 / (空きスペース=今後「計算の細かい条件」を置く場所) | **技ごとのダメ・致死率** |

- 特性・アイテム・テラスタイプは図のとおり1項目1行の縦積みにした(以前は2列グリッド)。
- **性格は図に無いが残した**: 実数値の計算に必要で、これを外すと実数値行が正しく出せない。
- 努力値/実数値は「行ラベル1列 + H/A/B/C/D/Sの6列」の7列グリッド。DOMは行優先(見出し7セル→努力値7セル→実数値7セル)で生成すること。
- 「+ ダメージ計算を追加」タイルは図の「ダメージ計算追加ボタン」で、カードの外・下側に置く。
- 実測: 1枚あたり280px @1920x1080。第2弾の「1行149px」目安は図の構成(実数値・加算後結果が縦に積まれる)により撤回した。

### 結果表示の分担(重要)
- **技列 = その技だけを繰り返した場合の独立した判定**。エンジンが返す `lethal` は「攻撃列を先頭から順に当てた累計」なので列単体の値には使えない。列の1発分ダメージ(`perAttackDamages[i]`)から、エンジンと同じ分布演算(`subtract_dist(minimum=0)` 相当)をTS側で回して「何発で倒れるか」を求めている(上限10発、超えたら「10発以上」)。battle_assistant.jpg でも各列は独立した計算結果を表示している。
- **相手ビルドの箱 = 加算後(全列合計)**。累計ダメージと、最初に致死率が0を超える位置の判定。そこがまだ確殺でなければ確殺到達位置を「→確N」として併記する(例: `累計408〜480 (177〜209%) 乱1 (25.0%) →確2`)。
- 確率は小数第1位まで丸めるが、`0.0%` / `100.0%` になる場合は `<0.1%` / `>99.9%` と表示する(確率0・確殺と見分けが付かなくなるため)。

### 攻守切り替え(新機能)
1枚のカードにつき「この個体が攻撃」⇄「この個体が受け」を切り替えられるようにした。保存先は既存の `field` jsonb に追加した `direction: 'attack' | 'defense'`(**マイグレーション追加なし**。未指定の既存メモは `attack` として解釈)。
- `field.attackerBoosts` / `attackerAilment` / `attackerTerastallized`(と `defender*`)は「**攻撃側/防御側という役割**に対する値」であり、`direction` によってどちらが所持ポケモンかが入れ替わる。`attacker*` を「常に所持ポケモン」と読んではいけない。
- 相手が攻撃側になるとき、相手のspecに `moveNames` は積まない。`pyodide-engine.ts` の `_resolve_move()` が技リストに無い技名から `Move` を新規生成するため計算できる。
- 向きに追随して言い換える表示: 技列のplaceholder(「技」⇄「相手の技」)、詳細ダイアログの見出し(「攻撃側(この個体)」⇄「攻撃側(相手)」)、壁のラベル(「相手側の壁」⇄「自分側の壁」)。ダイアログは `row.dialogEl` にキャッシュされるので、切り替え時に破棄して作り直す。
- `direction` は `opponent-note-anonymize.ts` のホワイトリストには**入れていない**(匿名化された二次記録には不要。ホワイトリスト方式なので未知キーは黙って落ちる)。

### カードを「ダメージ計算ウィンドウ」に入れない

- カードが狭いときは相手ビルドの箱を技列の上に積む。判定は**ビューポート幅ではなくカード自身の幅**(`.damage-row-body` の `container-type: inline-size` + `@container (max-width: 744px)`)。サイドナビ256pxと2カラム/縦積みの切り替えが噛み合って「ビューポートが広い方がカードが狭い」領域(1200〜1590px)が存在するため、メディアクエリでは条件を書けない。
- **`@container` は詳細度を上げない**。`.damage-row-build` の基本定義より後ろに書かないと、同詳細度の後続ルールに `flex`/`width` を上書きされて何も起きない(実測で踏んだ)。
- 技列の箱を相手ビルドの箱と同じ高さにするには `.damage-row-columns { min-height: 100% }` が必要(親の `wrap` は stretch で伸びるが、その中のflexコンテナは高さautoのままなので `align-items: stretch` が中身の高さまでしか効かない)。横スクロールバー用の余白は `.damage-row-columns-wrap` ではなく共通の親 `.damage-row-body` に付ける(wrap側に付けると技列だけ数px低くなって下端が揃わない)。
- 検証: 1920/1440/1280/1024/900/700/390px の全幅でページ全体の横スクロールなし、努力値入力のはみ出しなし、＋ボタンは常に可視(6列で `disabled`)。`npx astro build` Complete! / `npm test` 142件pass。

## 計画(2026-07-26 第4弾: フルHD前提のUI品質改善)

機能面は揃ったが見た目の完成度が低い。**PC(1920×1080)を第一ターゲット**に、ボックス一覧(`/box`)と個体編集(`/box/[id]`)のUI品質を作り直す。既存の機能・DOM構造依存のJSは壊さない。

### 現状の問題点(1920×1080 実スクリーンショットで確認)

**ボックス一覧 `/box`**
1. カードの高さが中身(技の数・アイテム有無)でバラバラ。グリッドの行が不揃いで散らかって見える。
2. 「+ 個体を追加」タイルがポケモンカードと違う高さ・違う質感で、同じ列に並んでいるのに揃わない。
3. カード見出しがニックネームだけで**種族名が出ない**(「カミ様」だけでは何のポケモンか分からない)。
4. 努力値が H/A/B/C/D/S の数字の羅列で、0 が大半を占めて視覚ノイズになっている。実数値が無い。
5. タイプバッジの有無がカードごとに不整合(カミ様にはFAIRY、他は無し)。しかもスプライトに被っている。
6. ツールバーの「検索/絞り込み/並べ替え」が左寄せ・高さ不揃い・ラベルと入力の間隔がバラバラ(`label { min-width: 6.5em }` の影響)。
7. ★(エース)と🗑(削除)が常時カード右上に浮いていて、視線を奪う。削除が誤操作しやすい位置にある。
8. ページ見出し「ボックス」とログイン情報の縦位置が揃っていない。件数表示も無い。

**個体編集 `/box/[id]`**
1. **フォームに項目ラベルが1つも無い**。種族/ニックネーム/性格/特性/持ち物/テラスタイプが全部プレースホルダ頼りで、値が入ると何の欄か分からなくなる(ワイヤーフレーム `Pokemon.png` はラベルありが正)。技欄も同様。
2. ページ見出しが「個体を編集」固定で、どの個体を見ているのか分からない。
3. 能力値行のヘッダ「種族値/努力値(0〜32)/実数値」が列とずれている。スライダーは黒い太トラックで野暮ったく、性格補正の±も出ない。努力値の残り合計も出ない。
4. メモ欄が高さ200px近くあり、情報密度に対して過大。
5. 「保存済み」の状態表示と「この個体を削除」が同じ行に並び、削除ボタンが最も目立つ要素になっている。
6. 「攻撃調整」「耐久調整」(準備中)がページ最上部に置かれ、実装済みの内容より上に来ている。
7. ダメージ計算カードの文字が小さすぎ(実測 ~10px)、努力値/実数値グリッドの桁が揃わない。列追加の「＋」が縦長の細い帯になっていてボタンに見えない。「保存済み」がカード右下に半端に浮く。
8. ダメージ計算が0件のときの空状態が点線バー1本だけで、何ができる画面なのか伝わらない。
9. 1920px では右カラムに大きなデッドスペースが残る(カード1枚 + 空白)。

### 方針
- **フルHD最適化を最優先**。ただし既存のブレークポイント(1200px で2カラム、`@container` によるカード内の縦積み)は壊さず、狭い幅でも破綻しないことを維持する。
- 共通デザイントークン(余白スケール・影・タイポ)を `global.css` に集約し、ページ側は scoped style だけを持つ既存方針を継続する。
- 配色(primary `#27acd9` / success `#409f89` / danger `#f8705b`)と「反転ホバー」のボタン方式は踏襲する。色を作り直すのではなく、**余白・整列・情報階層・タイポグラフィ**で品質を上げる。
- ワイヤーフレーム(`docs/ui_proposal/Box.png` `Pokemon.png` `DamageCard.png` `battle_assistant.jpg`)の構造は正として維持し、その上に仕上げを乗せる。

### タスク分割(sonnet サブエージェントで実施)
| # | 範囲 | 主な対象ファイル | 依存 |
|---|---|---|---|
| A | デザイン基盤: 余白/影/タイポのトークン追加、フォーム部品(input/select/slider/textarea)の統一、ページシェル(サイドバー・ヘッダ・コンテンツ幅) | `src/styles/global.css`, `src/layouts/AppLayout.astro`, `src/components/AppSidebar.astro` | なし(最初に実施) |

### 守るべき制約(エージェントへの指示に含める)
- 既存のクラス名・ID・DOM構造に依存する同ファイル内 `<script>` と `tests/e2e/damage-calc.spec.ts` を壊さない。特に `.damage-row` / `.damage-column` / `.damage-row-total-result` / `.damage-column-result` / `#opponent-notes-section` / `.damages` / `.move` は改名しない。

### 進め方(反復)
一度の改修で終わりにせず、**改善案が出尽くすまでラウンドを回す**。1ラウンドは以下:

4. 再度スクリーンショットを撮って回帰確認。指摘が出尽くしたら終了。
