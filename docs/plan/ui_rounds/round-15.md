## ラウンド15の指摘(2026-07-27 UI/UX/プレイヤー視点レビュアー講評・Coordinator統合: `/search` `/pokemon/[name]` `/moves/[name]` `/share/[slug]`)

**10ラウンドぶりの講評ラウンド**(ラウンド10〜14は既存指摘の消化)。ラウンド12で改訂したレビュー観点を使う**最初のラウンド**。対象4画面はラウンド13〜14で作り直したばかりで、**3レビュアー体制で見るのは初めて**。

### 統合にあたってのCoordinatorの判断

- **UXが「優先度C(要判断)」とした期待値の件を、優先度Aに格上げした。** UXは「暗算すれば出せる」という利便性の問題として挙げたが、プレイヤー視点レビュアーが**実データで裏を取り**、Coordinatorもコードを確認した結果、**表示されている数値そのものが誤り**(下記A-1)。利便性ではなく正確性の問題なのでAとする。
- **UIが挙げた `/search` 結果へのサムネイル追加は採用しない。** round-09.md **C-4** に「『素早く絞る』画面なのでテキストリストのほうが速いという反論がある。現状のリスト構造は維持し、A-7の下線と階層だけ直すのが安全」と記録済み。UIレビュアー自身もこれを踏まえて提案から外している。**再提起しない。**
- **ラジオの件はラウンド14と矛盾しない。** ラウンド14で入れた `color-scheme: light dark` は**選択状態**の見え方を改善した。今回の指摘は**未選択状態のコントラスト(1.47:1)とブランド色の不一致**で、`accent-color` が `input[type=range]` にしか指定されていない(`global.css:604`)ことに起因する別問題。ラウンド14の判断を覆すものではなく積み残し。
- **プレイヤー視点が挙げた「`/pokemon` に弱点表を追加」は見送る。** 新しい表を1枚増やすことになり機能追加寄り。まずA-7(複合タイプの注記)で誤読を防ぐほうが安い。
- **★の凡例は UX と プレイヤー視点の両方が指摘**したため1件に統合(B-1)。

### 優先度A(必ず直す)

- **A-1 `/moves` の期待値が連続技のヒット回数を無視している(実バグ)**(指摘者: プレイヤー視点、UXも同趣旨をCで指摘): 【問題】`expectedValue` は `move.power * accuracy / 100` のみで `hits` を参照していない(`src/pages/moves/[name].astro:135-151`、**Coordinatorがコードとデータで確認済み**)。スケイルショットは同じ画面に「平均3.0回ヒットします」と書いてあるのに期待値は1ヒット分の **22.5**(実質は 25×0.9×3.0 ≈ **67.5**)。連続技23件すべてで同じ過小評価。さらに **`ふくろだたき` は `detail/moves.json` 上 `power: 1`** なので `power == null` の除外条件に**引っかからず**、「期待値1」という無意味な数値が出る(実際の威力は使用者のパーティ構成依存 → `damage-calc.md` §3補)。 → 【提案】`hitsView` が既に持つヒット回数情報(固定回数 / 2〜5回の平均3.0 / `check_hit_each_time` の幾何分布期待値)を期待値にも渡し、「1ヒットあたり」と「技1回あたり(平均◯回ヒットを考慮)」の2段で出す。`ふくろだたき` は `hitsView` 側と同じ条件で期待値からも除外し理由を表示する。
- **A-2 `/share` にタイプ欄が無く、画像も0枚**(指摘者: プレイヤー視点、UI): 【問題】`share/[slug].astro:159-172` の `<dl>` は ポケモン/性格/特性/持ち物/テラスタイプ/技構成 のみで**タイプが一度も出ない**。メガリザードンXは `types: ["ほのお","ドラゴン"]`(通常のリザードンの ほのお/ひこう とは別)なので、技構成のドラゴンクローがタイプ一致である理由も、弱点がどう変わったかも第三者には読めない。あわせて `<img>` が0枚で、round-09.md の「既にある語彙(公式絵+タイプアイコン)を移植する」が `/pokemon` `/moves` には適用済みなのに**この画面だけ取り残されている**。コンテンツ終端y=594、下に486pxの空白。 → 【提案】`detail/pokemon.json` から `imageId` と `types` を引き、公式絵160px(`officialArtworkUrl()`)+ タイプアイコン28pxピル(`typeIconUrl()`、`/pokemon` の `.identity-type-chip` と同形)を「育成内容」パネルに追加。SSRで静的HTMLに焼く(A-2で確立済みの方式、クライアントJS不要)。空いている右側(x>1100)を使う。
- **A-3 `/share` にサイト名がどこにも出ない(ラウンド13の退行)**(指摘者: UX): 【問題】`global.css:997-1011` の `@media (min-width: 900px) { .app-topbar-row-brand { display: none } }` は「サイドバーが常設でブランドリンクを持つため不要」という `chrome="app"` 前提のコメント付き。ラウンド13で `chrome="public"` を入れて `AppSidebar` を描画しなくした結果、**この前提が崩れた**。第三者が初めてリンクを踏んで開く唯一の対外画面で「これは何のサービスか」が本文から読み取れない(404画面でも同様)。 → 【提案】当該メディアクエリを `.app-shell:not(.is-public) .app-topbar-row-brand { display: none }` にスコープする。**`AppLayout` の scoped `<style>` 側には書かないこと**(ラウンド13 A-1 で確立した「global.css 側の詳細度で打ち消す」設計を壊さないため)。
- **A-4 `/share` のポケモン名・技名が詳細ページにリンクしていない**(指摘者: UX): 【問題】`share/[slug].astro:160-171` は `<dd>{pokemon.species_name}</dd>` / `<dd>{pokemon.move_names.join(' / ')}</dd>` の素のテキストで `<a>` が無い。`/pokemon` `/moves` は未ログインでも閲覧できる(`src/middleware.ts` にゲート無し)ので、共有されたビルドを見た第三者が「この技は採用に値するか」を調べようとしても、`/search` で名前を手入力し直す必要がある。 → 【提案】テキストをリンク化するだけ(新規データ・API不要)。区切りの ` / ` はリンク外に置く。
- **A-5 `/pokemon`⇔`/moves` の戻るリンクが常に `/search` 固定**(指摘者: UX): 【問題】`pokemon/[name].astro:188` と `moves/[name].astro:236` がどちらも `backHref="/search"` を静的に埋め込んでいる。「技一覧から1件開いて戻る」「技から覚えるポケモンを開いて戻る」という、この4画面の存在意義そのものの往復で、画面が用意する唯一の明示的な戻る導線が毎回検索画面へ飛ばす。 → 【提案】ラウンド13 A-6 で確立した「URLクエリをページ内スクリプトが読んで静的HTMLを書き換える」パターンを踏襲。**共通契約: リンク元が `?from=pokemon:<名前>` または `?from=move:<名前>`(値は `encodeURIComponent`)を付与し、着地先が `location.search` の `from` を読んで戻るリンクの `href` と文言(例:「← リザードンに戻る」)を書き換える。`from` が無ければ既定の `/search` のまま。** 不正値・未知の接頭辞は無視して既定に落とすこと。
- **A-6 ダークで未選択ラジオのコントラストが1.47:1、選択色もブランド色でない**(指摘者: UI): 【問題】ダークの未選択ラジオは塗りつぶし円 RGB(59,59,59) でパネル背景 RGB(28,31,40) に対し**約1.47:1**(非テキスト要素の目安3:1を大きく下回る)。選択色も既定の RGB(0,117,255) でサイトのprimary(シアン系)と色相が合わない。原因は `accent-color` が `input[type=range]`(`global.css:604`)にしか指定されておらず、ラジオ・チェックボックスがブラウザ既定描画に委ねられていること。 → 【提案】`global.css` に `input[type="radio"], input[type="checkbox"] { accent-color: var(--color-primary); }` を追加(range の宣言の近くにまとめる)。**適用後にダークの未選択のコントラストが3:1に届くか実測し、届かなければ `appearance: none` + カスタム border で明示的に描く方式へ切り替える。** 素の `<input type="radio">` `<input type="checkbox">` が他ページに残っていないか横断grepすること(`/box/[id]` の詳細設定サイドバーにチェックボックスがある)。
- **A-7 タイプ相性に「複合タイプは掛け合わせ」の注記が無い**(指摘者: プレイヤー視点): 【問題】`getTypeEffectiveness` は単一の防御タイプごとに3バケットへ分類するだけで、複合タイプの合成倍率がどこにも書かれていない。こおり技は「ほのお 0.5倍」「ひこう 2倍」だが、**ほのお/ひこう複合のリザードンには 0.5×2 = 等倍**。「ひこうがばつぐんの欄に載っている」だけを見て「こおり技が刺さる」と誤読する典型的な罠が設計に残っている(`ruleset.md` §4「複数タイプを持つ防御側には各タイプの倍率を順に掛け合わせる」)。 → 【提案】タイプ相性パネルの下に1行注記を追加(例:「相手が複数タイプを持つ場合は各タイプの倍率を掛け合わせてください(例: ほのお/ひこう相手にこおり技は 0.5×2 = 等倍)」)。計算・データの追加は不要。

### 優先度B

- **B-1 ★(タイプ一致)の可視凡例が無い**(指摘者: UX、プレイヤー視点): `aria-label="タイプ一致"` はスクリーンリーダー限定で、目視ユーザーは★の意味(自分と同じタイプの技=威力1.5倍)を推測するしかない。STAB技が先頭に固められる設計のため初画面はほぼ全セルに★が付き、「おすすめ」等と誤読されうる。 → 技フィルタ近傍に1行の凡例。
- **B-2 `/search` 結果の実コンテンツ幅171px vs 確保幅1080px(6.3倍)**(指摘者: UI): 最長「リザードン(キョダイ)」で171px。4件表示時にパネル右側84%が空白。 → `<ul>` に `column-width: 220px; column-gap: var(--space-6)` で多段化(CSSのみ、構造・JS不変)。**サムネイル追加は round-09 C-4 で却下済みなので行わない。**
- **B-3 `/moves` 変化技で下に592pxの空白**(指摘者: UI): `.move-extra-grid` が内容量に関わらず `1fr 1fr` を維持するため、左右とも1行の注記だけのケースで空スペースが確保され続ける。 → `isStatusMove` のとき1カラムに切り替える。**これは緩和策であって抜本解決ではない**(空白の大半は情報量そのものの少なさに起因)。
- **B-4 タイプ相性ボックスが1バッジのために528px幅を専有(専有率21%)**(指摘者: UI): 5バッジなら429px使用で81%と適正だが、1バッジだと110pxしか使わない。「単色の板に小さなピルが1つ浮く」見た目になり、これは例外ではなくよくあるケース。 → `width: fit-content; min-width: min(50%, 260px); max-width: 100%`。左端は揃えたまま右端だけ縮む。
- **B-5 `/pokemon` の「分類」フィルタ(4択)がセレクトで過剰**(指摘者: UX、試算つき): `/search` のラジオ5択は実測418px。同じ `.radio-label` で4択なら概算306pxで1080pxに十分収まる。現状のセレクト(94px)は開かないと選択肢が見えず2手かかる。**一方「タイプ」は13〜18択で概算1150〜1600px超となり折り返すため、セレクトのまま維持**(状態異常7択のアイコントグル化が折り返して撤回された前例と同型)。 → 分類のみラジオ化。
- **B-6 タイプアイコンの規格が3種類混在**(指摘者: UI): `/pokemon` 識別ブロック=28pxピル(背景+タイプ名テキスト)、`/moves` 識別ブロック=40pxの裸の円、`/moves` タイプ相性内=20pxピル。同じ「タイプ」概念が1画面ペアで3規格。 → `/moves` 識別ブロックを `/pokemon` と同じ「アイコン+タイプ名のピル」構成へ寄せる(サイズ40pxは維持可)。
- **B-7 「グリッド本体値」のフォントサイズが画面間で1.4倍差**(指摘者: UI): `/pokemon` 種族値は実描画高さ12px(`1.05em`)、`/moves` の6列グリッドは17px(`1.5rem`)。同じ役割の部品で視覚的な強さが違う。 → `/share`・`/box` の実数値とも突き合わせて基準を1つに揃える。
- **B-8 `/pokemon` にチャンピオンズ限定である旨の断りが無い**(指摘者: プレイヤー視点): `/moves` 側は0件時に「**現在のデータでは**」と限定しているのに、`/pokemon` の「覚えられる技(N種)」には限定表現が無い。「知っているはずの技が無い」をバグと誤解するリスクは双方向にある(→ `integration.md` の learnset の節)。 → 見出し近傍に一言添える。
- **B-9 テラスタル時の相性変化の注記が無い**(指摘者: プレイヤー視点): テラスタル後は防御側の実効タイプが(ステラを除き)単一化する(`ruleset.md` §4)。「事前にこの技が通るか」を調べる画面なのに、このケースが実装にもスクショにも無い。 → タイプ相性パネル下に1行。
- **B-10 ラジオ本体が13pxで操作対象として最も弱い**(指摘者: UI): ラベル文字14〜16px+余白に対しradio本体が13px。 → `width: 1.05em; height: 1.05em` 程度に拡大(A-6とセットで実施)。

### 優先度C・要判断

- `/search` の「最近注目されているもの」の空状態が同じ事実の言い換え2文(「みんなの検索から傾向が見えてくると〜」と「まだデータがありません〜」)。**セクション自体の存廃はユーザー判断待ち(round-09.md B-5)。残すと決まった場合は1文に統合する**、という条件付きの指摘として記録する。
- `/moves` の404/非公開ページが所有者以外にとって行き止まり(「自分の育成を管理する」しか選べない)。中立的な「トップへ」を足すか、据え置くか。
- `/pokemon` 識別ブロックの3項目(覚えられる特性/進化前/進化後)で箇条書きの有無が不統一。
- 「値が無い」ことを示す語彙が4種類併存(「なし」「現在のデータでは〜いません」「(未設定)」「-」)。実害は確認できず、用語集として整理する余地。
- `/pokemon` の実数値注記「±10%前後で変動する」は、補正なし性格では変動0になるため一般化しすぎ。
- **次ラウンドの検証候補(スクショに含まれておらず未確認)**: 優先度が負の技(`トリックルーム` -7 等12件)の表示、最長のポケモン名(`ムゲンダイナ(ムゲンダイマックス)` 17文字)、`オーガポン(いしずえ,テラスタル)` のように**種族名に「テラスタル」が埋め込まれたフォルム**と個体ごとに選ぶ「テラスタイプ」の混同。

### 良くなっている点(次のラウンドで壊さないこと)

1. `.card-hint` の負マージン罠(ラウンド13で `/share` が踏んだもの)は `/pokemon`(`.stat-grid-hint`)・`/moves`(`.move-note`)とも専用クラスに切り出し済みで**再発なし**。
2. タイプ相性ボックスのテキストコントラストはライト実測5.25:1でAA達成。ラウンド8の「lethalチップ2.45:1」のような逆転は再発していない。
3. リンク色AA対応(`--color-primary-strong`)は4画面すべてで機能。
4. `/pokemon` 種族値グリッドと `/share` 実数値グリッドは `4.5rem repeat(6, minmax(0,1fr))` で完全一致、`H A B C D S` の語彙も `/box` と揃っている。
5. `/pokemon` 技グリッドは4列264pxで**省略0件**、威力の右揃えも維持(ラウンド13の是正が壊れていない)。
6. `/share` の性格補正 ▲(赤)/▼(青) はライト/ダークで意味の反転なし。
7. 空状態・0件表示がすべて非エラー調で統一(`/search` 0件「該当なし」、`/pokemon` 絞り込み0件、`/moves` 変化技の非該当表示)。**赤系の警告色を使っていない。**
8. メガリザードンXの実数値をメガ進化後の種族値(A130/B111/C130/D85)で計算しており、ベース種族の数値を誤用していない(プレイヤー視点レビュアーが手計算で検算)。
9. `/search` のカテゴリ5択・`/pokemon` の絞り込みの選択肢は、実際のマスターデータと過不足なく一致(架空の選択肢が無い)。
10. `わるあがき`(タイプ無し技)が「常に等倍」と正しく表示される(jpoke知識ベースの蓄積ルールが効いた実例)。
