### 優先度A(すべてユーザー直接指示。全件必ず直す)

#### 共通

- **28-G1 テラスタイプ画像に専用アイコンを使う**(指摘者: ユーザー)
  【問題】ラウンド21(21-B2)とラウンド23(23-G2)で「宝石型のテラス専用アイコンは縁が欠けて汚いので、通常タイプの丸アイコン(`typeIconUrl`)に統一する」と決めていた。今回ユーザーが `scripts/type-icons/generate_type_icons.py` の切り出しロジックを作り直し(`stitch_tera_icon()`: 英字部分だけを削除して左右の本物の尖った縁を繋ぎ合わせる方式)、`public/type-icons/tera/1..19.png` を再生成した。
  → **21-B2 と 23-G2 を撤回する。** テラスタイプの画像はすべて専用アイコン(`teraTypeIconUrl()` = `/type-icons/tera/{typeId}.png`)に戻す。
  【提案】差し替え対象は次の4箇所:
  1. `src/pages/box/[id].astro` の `applyTeraImage()` 内 `typeIconUrl(teraName)` → `teraTypeIconUrl(teraName)`。**この関数は左パネルとダメージ計算カード(相手ビルドのテラス表示)の両方から呼ばれる**ので、ここ1箇所でどちらも切り替わる。
  2. 同ファイルのテラスタル・ドロップダウン(`buildTeraDropdown`)の**ボタン画像**と**リスト項目画像**。現在は `teraTypeImageUrl()`(= `raw.githubusercontent.com` の横長リボン画像、外部ホスト)を使っている → `teraTypeIconUrl()`(ローカル)へ。**これによりラウンド25からの積み残し「テラス画像が外部ホスト依存」も同時に解消する。**
  3. `src/pages/box/index.astro`(ボックス一覧カードのテラスバッジ)の `typeIconUrl(type)` → `teraTypeIconUrl(type)`。
  4. `import` 文の追加/削除(`teraTypeImageUrl` が未使用になったら import から外す。`src/lib/sprite-urls.ts` の関数自体は消さない)。
  【注意】**専用アイコンは宝石型(ジグザグの尖った縁)を持つ正方形画像なので、`border-radius: 50%` で丸くトリミングしてはいけない**(縁が削れて、今回ユーザーが直した意味が無くなる)。丸アイコン前提で当てている `border-radius` は、テラス表示側だけ外すこと。通常タイプアイコン(`typeIconUrl`、角丸ピル)側の丸トリミングは**そのまま維持**する。

#### 個体編集 左サイド(`.top-block-icon` 帯とその下の入力行)

- **28-L1 ポケモン画像を帯の全幅で中央配置する**(指摘者: ユーザー)
  【問題】実測のとおり、アイコン中心 x=383 に対し帯の中心は x=475.5 で、**92.5px 左に寄っている**。ラウンド27(27-H1)で「絶対配置だと重なる恐れがある」と判断して flex 2分割(`.top-block-icon-center` flex:1 + `.top-block-icon-corner` 固定幅)にした結果で、round-27.md の積み残しにも「アイコンの幾何学的中央寄せ」として残していた項目。
  → **27-H1の「中央ゾーン+右コーナー列のflex 2分割」の判断を撤回する。**
  【提案】`.top-block-icon` を `position: relative` にし、`#species-icon-box` を帯の**全幅に対して**中央寄せ(`margin-inline: auto` もしくは flex + `justify-content: center` を帯そのものに当てる)。コーナー列 `.top-block-icon-corner` は `position: absolute; inset-block: 0; right: 0;` のオーバーレイにして、アイコンの中央寄せに影響しないようにする。
  **27-H1が絶対配置を避けた理由(アイコン160px + テラスドロップダウン170px + アイテムで帯幅400px弱を食い合って重なる)は、28-L4でテラスドロップダウンを帯の外に出すことで解消する**(帯に残るのはタイプバッジ・アイテム表示・テラス画像だけになり、必要幅が大きく減る)。それでも**重なりは実測で必ず確認すること**(要件: アイコンの矩形とコーナー列の矩形が1pxも重ならないこと。長いアイテム名「とつげきチョッキ」「こだわりスカーフ」などでも確認)。

- **28-L2 タイプアイコンは右上、アイテム(画像+名前)とテラスタイプ(画像)を上下に重ねて右下**(指摘者: ユーザー)
  【問題】現状の右下(`.top-block-icon-info`)には「アイテム表示」と「テラスタル選択ボックス(ドロップダウン)」が入っている。ユーザーの指示では右下は**アイテム(画像+名前)の下にテラスタイプ画像**という2段構成で、選択ボックスは下の入力行へ移る(28-L4)。
  【提案】`.top-block-icon-corner` の構成を「上: `#species-type-badge`(右上・右寄せ) / 下: `.top-block-icon-info`(右下・右寄せ、中身を縦2段: 1段目=アイテム画像+アイテム名、2段目=テラスタイプ画像)」にする。テラス画像は**読み取り専用の `<img>`**(クリックで開かない。選択は28-L4の入力欄側で行う)。テラス未設定のときは画像を出さない(高さは詰めてよい)。

- **28-L3 アイテム画像を縮小する**(指摘者: ユーザー)
  【問題】`#item-image` は 41×41 で、隣のアイテム名の文字(実測 13px 程度)に対して3倍以上あり不釣り合い。
  【提案】**「アイテム文字より少し大きい程度」= 20px 前後**(文字13px に対して 1.5倍程度)に縮小する。`width`/`height` 属性と CSS の両方を合わせること。テラス画像(28-L2)は縮小指示が無いので、アイテム画像と同程度〜やや大きい範囲で、右下の2段が帯(160px)からはみ出さないサイズにする。

- **28-L4 テラスタル選択ボックスを持ち物入力欄の右側に置く**(指摘者: ユーザー)
  【問題】テラスタル選択ボックス(`#tera-dropdown-button` + `#tera-dropdown-list` + hidden な `#tera` select)は、ラウンド26(26-L2)で帯の中に移設されていた。帯の中央配置(28-L1)の邪魔になるうえ、ユーザーは入力欄として扱いたい。
  → **26-L2の「テラスドロップダウンをアイコン領域内へ移設」を撤回する**(ラウンド25で入力行にあった状態に戻す形になる)。
  【提案】`.field-grid.field-grid-single`(現在 `#item` 入力欄だけが入っている全幅の行)を**2列**にし、左=`#item`(持ち物)、右=テラスタル選択ボックスにする。列幅は同ファイル内の他の2列行(`.top-block-fields` の種族/ニックネーム、`.move-fields-grid` の技1/技2 = 実測 195px + 195px)と揃える。
  ウィジェットのロジック(開閉・選択・保存: `buildTeraDropdown`、`#tera` select が保存経路の値の実体)は**一切変えない**。DOM上の位置と、ボタン内の見た目だけを変える。
  **ボタンの中身**: これまでは横長リボン画像1枚だけを表示していたが、正方形の専用アイコン(28-G1)に変わると幅が余るため、**アイコン + テラスタイプ名のテキスト**を並べる(未設定時は従来どおり「テラスなし」のplaceholder)。※ ユーザーは中身まで指定していない。入力欄の右側という新しい文脈で「何が選ばれているか」を読めるようにするCoordinator判断。

#### 個体編集 ダメージ計算(相手ビルド領域 `.damage-row-build`)

- **28-D1 相手ポケモンアイコンは最初の5段分の高さを使う**(指摘者: ユーザー)
  【問題】「段」= 相手ビルド領域の行。1段目=攻守切り替えボタン(`.damage-row-actions`, 24px)、2〜5段目=種族名/特性/持ち物/テラス(`.damage-row-build-fields`, 4×27px=108px)、6〜7段目=努力値/実数値(`.damage-ev-grid`, 61px)。現状スプライトは 112×112 で上端が**2段目の頭**(y=125)にあり、1段目とは並んでいない。
  【提案】`.damage-sprite-box` を**1段目の上端から5段目の下端まで**(現行実測なら y=98〜233、高さ約135px)に伸ばす。つまり「攻守ボタン+入力欄4段」を左列、その右にスプライトを縦いっぱいに置く形。画像自体は `object-fit: contain` で領域に収め、**縦横比を崩さないこと**。
  【副次】この構造変更に伴い、`.damage-row-actions` は `.damage-row-build-main` の外(上)にある現在の位置から、左列の1段目として扱う組み替えが必要になる。**`.damage-item-badge`(スプライト右下のアイテム画像バッジ)と `.damage-type-badge` の位置も追随させること**(絶対配置でスプライト箱を基準にしている)。

- **28-D2 攻撃・防御切り替えボタンを種族名などの入力欄と同じ幅にする**(指摘者: ユーザー)
  【問題】`.damage-row-direction-toggle` は実測 **75px**、種族名などの入力欄は **202px**。
  → ラウンド26(26-D3)の「攻守ボタンの幅を短縮しアイコンを拡大」の**幅短縮部分を撤回する**(赤/青ハイライトの配色は維持)。
  【提案】幅を左列と同じ **202px(= `width: 100%` of 左列)** にし、「攻撃」「防御」の2ボタンで等分(各101px)する。

- **28-D3 ステータス(努力値/実数値)を相手ビルド領域の全幅にする**(指摘者: ユーザー)
  【問題】`.damage-ev-grid` は実測 202px で、右のスプライト(112px)のぶん右側が空いている。
  【提案】`.damage-ev-grid` を左列から出し、**相手ビルド領域の全幅(実測 321px)**に広げる。28-D1でスプライトが5段目までになるので、6〜7段目はスプライトの下を通って全幅を使える。数値の桁が広がったぶん、H/A/B/C/D/S の列が窮屈でなくなること(現状 `130 67 75 187155205` のように数字同士がくっついて見える箇所がある)を実測で確認する。

#### 個体編集 右サイド(`#damage-detail-panel-body`)

- **28-R1 天候の上の空白領域を削除**(指摘者: ユーザー)
  【問題】`.damage-detail-panel-header` が `[1561,65 359x36]` を占めており、中の閉じるボタンは幅0(このレイアウトでは非表示)。**36pxの空帯**になっている。
  【提案】この帯を潰す(閉じるボタンが表示される幅では従来どおり出す必要があるなら、ボタンが非表示のときだけ高さ0にする)。**閉じるボタンのDOM・ID(`#damage-detail-panel-close`)は消さないこと。**

- **28-R2 急所を最上部に配置し、その下に横線を追加**(指摘者: ユーザー)
  → **ラウンド27(27-R2)の「急所を攻撃側ボックスの中に移す」を撤回する**(ラウンド25の25-R1「急所を独立した帯として天候より前に出す」に戻す形。ただし今回は「その下に横線」が追加される)。
  【提案】`renderColumnLevelDetailPanel()` で `buildCriticalRow()` を `attackerSide` ではなく `detailPanelBodyEl` の**先頭**に append する。急所行の直下に区切り線(`border-bottom: 1px solid var(--color-border)`、既存の区切り線トークンと同じ色・太さ)を引く。急所が攻撃側だけの設定である**仕様は変えない**(`column.critical` の読み書き先は同じ)。

- **28-R3 「攻撃(自分)」→「攻撃側」、「防御(相手)」→「防御側」。天候などと同じタイトル形式に**(指摘者: ユーザー)
  → ラウンド23(23-R3)の「『攻撃側(この個体)』→『攻撃(自分)』に短縮」を**撤回する**(2列分割をやめた27-R1で短縮の理由が消えている)。
  【提案】`buildSideSection()` の `title` 引数に渡す文字列を、`row.direction` にかかわらず **`"攻撃側"` / `"防御側"` 固定**にする。見出しの見た目は天候・フィールドのラベル(`.damage-detail-field-row-label`)と同じタイポグラフィにする。
  【注意】`title` は `aria-label`(`${title}の能力ランク` / `${title}の状態異常`)にも使われている。**「自分/相手」の区別が消えるので、aria-label には `row.direction` から求めた側(この個体/相手)の情報を別途足すこと**(スクリーンリーダー利用者にとっての退行を作らない)。

- **28-R4 攻撃側・防御側もそれぞれ横線でセクションを区切る**(指摘者: ユーザー)
  【提案】`.damage-detail-side` の各セクション先頭に区切り線を入れる(急所の下・攻撃側の上・防御側の上で計3本)。28-R2の線と二重線にならないよう、`border-top` に統一して重複を避ける。

- **28-R5 ランク入力欄はタイトルの次の行に移動**(指摘者: ユーザー)
  【問題】現在 `.damage-detail-side-heading-row` が「見出し(左) + ランク(右)」の横並び。
  【提案】見出しを単独行にし、ランク入力欄をその次の行へ。ランク欄は「ランク」ラベル+スピンボックスの並びを維持する。`#`/クラス(`.damage-detail-rank-field` / `.damage-detail-rank-input` / `.is-nonzero`)は**改名しない**。

- **28-R6 「テラス (未設定)」→「テラスタル」に表記変更**(指摘者: ユーザー)
  → ラウンド23(23-R3)の「『テラスタル』→『テラス』に短縮」を**撤回する**。
  【提案】`buildToggleButton("テラス", …)` → `"テラスタル"`。あわせて、その隣に出ている `(未設定)` の注記(`.damage-detail-tera-note`)を**表示しない**(ユーザーの表記変更後の文字列に `(未設定)` が含まれないため)。
  【注意】**テラスタイプ未設定時にボタンを `disabled` にする挙動(ラウンド17 A-1 の実バグ対応)は絶対に消さないこと。** 理由は `disabledTitle` に残っているのでホバーで伝わる。注記の DOM を消す場合も、`disabled` と `title` は維持する。

- **28-R7 「相手の壁」→「リフレクター・ひかりのかべ」に変更**(指摘者: ユーザー)
  → ラウンド23(23-R3)の「『相手側の壁』→『相手の壁』に短縮」を**撤回する**。
  【提案】`wallText` を `row.direction` による出し分け(`"自分の壁"` / `"相手の壁"`)をやめ、**常に `"リフレクター・ひかりのかべ"`** にする(壁の行は防御側セクションの中にあり、28-R3で見出しが「防御側」になるため、自分/相手の区別は文脈で足りる)。`column.wallEnabled` の保存キー・`resolveColumnDerivedFields()` のロジックは**一切変えない**。ボタン幅が足りずに文字が折り返す/はみ出す場合は、ボタンを行の全幅にしてよい。

- **28-R8 状態異常のplaceholderを「なし」→「状態異常」に変更**(指摘者: ユーザー)
  【問題】`DAMAGE_AILMENTS` の先頭(value="")のラベルが「なし」で、未選択時にも「なし」と表示される。
  【提案】**未選択(value="")のときに select に表示される文字列だけ**を「状態異常」にする。`.damage-detail-ailment-select.is-ailment-unselected`(破線枠+muted文字色のplaceholder風表示、ラウンド24 24-L3の視覚言語)は維持する。
