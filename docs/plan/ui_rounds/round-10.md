## ラウンド10の要件(2026-07-26 ユーザー指示 第3弾)

### 1. 技列1つのときの累計チップ重複は**そのままでよい**(B-3を撤回)

ラウンド8 B-3 で「技列が1つのカードでは累計チップと1発目の結果チップが完全に同じ数値を表示している」と指摘し、`.damage-row-total-result` をカード下端の全幅バーに移す案を出したが、**ユーザーの判断により現状維持とする。ラウンド8 B-3 は撤回。今後この重複を問題として再提起しないこと。**

### 2. ダメージ計算カードを「同じ高さのまま幅を半分にして2×2配置」にできるか

ユーザーの言葉: **「技カードがスカスカ。同じ高さのまま幅を半分程度にして、2x2配置でも成立するか？」**

#### 実測による検証結果(1920×1080、カード4枚、Playwrightで実際にCSSを注入して測定)

**検証A: `.damage-rows-list` を2列gridにするだけ(内部レイアウトは無変更)** → **破綻する。**
`.damage-row-build` が `flex: 0 0 300px` を持つため、カード幅384pxのうち300pxを箱が占め、技列(`flex: 1 1 0`)が**約50pxに潰れる**。「1発目」「確1 240〜283 (161〜190%)」「+ 技を追加」がすべて1文字ずつの縦書きになり判読不能。**この案は不可。**

**検証B: 2列grid + 内部を縦積み(相手ビルド箱を上・技列を下、`.damage-row-body` を `flex-direction: column`)** → **表示は成立するが、高さの要件を満たさない。**

| 項目 | 実測 |
|---|---|
| カード幅 | **384px**(狙いどおり半分) |
| カード高さ | **421 / 602 / 545 / 444px**(技列1つ/3つ/2つ/1つ) |
| 相手ビルド箱 | 362×**260px**(幅362pxでは高さ260pxが下限) |
| 技列1つ | 362×102〜125px |
| 努力値グリッドのセル幅 | **45〜54px**(現在の300px幅版より広く、余裕がある) |
| **はみ出し・文字の潰れ** | **0件**(`scrollWidth > clientWidth` の要素なし) |
| リスト全体の高さ | **1215px** |

**重要**: 幅を半分にしても**中身は一切潰れない**。努力値グリッドは7列で45〜54px/セルを確保でき、現在の300px幅版よりむしろ余裕がある。**問題は幅ではなく高さである。**

#### 「同じ高さのまま」が成立しない理由

内部を縦積みにすると、カード高さ = 相手ビルド箱260px + 技列(1つあたり約107px) + 追加ボタン になる。**相手ビルド箱の260pxが動かせない床**であり、技列3つのカードは602pxまで伸びる。

さらに**2×2にしても密度が改善しない**: グリッドの行の高さは左右のうち高い方で決まるため、同じ4枚を縦1列に積んだ場合(約1240px)と2×2(実測1215px)で**ほぼ差が無い**。**「2列にしたぶん縦が半分になる」という期待は成立しない。**

#### 成立させるために必要なこと(未実施・要判断)

「スカスカ」の実体は**技列の1つが102px使って3行(「1発目」ラベル行 / 技名input行 / 結果チップ2段)しか持っていない**こと。362px幅なら1行に収まる情報量である。

- (a) **技列を1行に畳む**: `[1発目] [技名input] [確2 114〜134 (74〜88%)]` を横1行に。102px → 約34px(**技列3つで約200px回収**)。
  - **ただしこれはラウンド5で入れた「結果チップの主役化」(`確N` を大きく太字で先頭・数値を従に2段)を弱める方向**である。計画書ラウンド8「維持すべき点」に挙げた項目に抵触するため、**ユーザーの明示的な承認が必要**。
- (b) **相手ビルド箱のフィールド行を2列にする**: 幅362pxなら「特性 / 持ち物」「テラス / (空き)」を横並びにでき、2行ぶん約44px回収 → 箱260px → 約216px。
- 見積: (a)+(b) で **1枚あたり約350px**(現在の全幅版333pxとほぼ同じ高さ)。**2×2なら4枚が約730pxに収まる**(現在は3枚で908px)。→ **1画面に見える枚数が3枚→4枚**、かつ横方向の空白も消える。

#### 判断が必要な点

**(a)「技列を1行に畳む」を実施してよいか。** これを入れないと「同じ高さのまま幅を半分」は成立せず、2×2にしても密度は改善しない((b)だけでは技列1つ434px / 技列3つ約540pxにしかならない)。(a)を入れる場合、ラウンド5の「結果チップの主役化」は**1行内での強調(確Nを太字・大きめ、数値を小さく右寄せ)に置き換わる**ことになる。

### ラウンド10の実施結果(2026-07-26)

#### 2×2は見送り。ユーザー提案の「N発目と技名を同行にする」を単独で採用した

ユーザーからの追加の問い: **「N発目と技を同行にすれば入る?」**

**実測回答: 同行化は効くが、2×2を成立させるには足りない。** 技列102pxの内訳は「1発目」ラベル12px + 技名行27px + 結果チップ39px + padding/gap 24px。ラベルを技名行に載せると **102px → 88px(−14px/列)**。

| 構成 | カード高さ(技列1/3/2/1) | 4枚の総高さ |
|---|---|---|
| ① 変更前(1列・幅779px) | 276 / **333** / 276 / 276 | 1253px |
| ② 同行化のみ(1列・幅779px) | 276 / **289** / 276 / 276 | **1210px** |
| ③ 同行化 + 2×2(幅384px) | 407 / **559** / 517 / 430 | 1144px |

**2×2を見送った根拠**: 真の壁は技列ではなく**相手ビルド箱の260px**。幅を半分にすると箱が技列の上に来るので、カード高さは必ず「260px + 技列」になる。技列を14px縮めても3技列のカードは559px。②で技列1つのカードが276pxのまま動かないことが、箱260pxが天井を決めている証拠である。箱のフィールド行を2列化して216pxまで詰めても3技列で514pxになるため、「同じ高さのまま幅を半分」は達成不能と結論した。

#### 実装した内容(`src/pages/box/[id].astro` のみ)

1. **順序ラベルの同行化**: `.damage-column` を `display: grid; grid-template-columns: auto minmax(0, 1fr)` にし、1行目にラベル(1列目)と `.damage-column-move-row`(2列目)を並べ、それ以降の子(条件チップ・連続回数・撃破済み注記・結果チップ)は `grid-column: 1 / -1` で全幅。
   - **`.damage-column-result` には一切触っていないので、ラウンド5の「結果チップの主役化」(`確N` 太字 + 数値を下段)は無傷。** 当初懸念したトレードオフは発生しなかった。
2. **切り替えはビューポート幅ではなくコンテナクエリ**(`.damage-row-techniques-row` に `container-type: inline-size`、`@container (min-width: 240px)`)。
   - 理由(実測): `.damage-row-build` が全幅で300px固定なため、`.damage-column` の幅は**ビューポート幅に対して単調でない**。1920px→448px / **1600px→149px** / 1440px→311px / **1280px→151px** / 1024px→397px / 900px→273px / 700px→329px。**1600pxが最も狭くなる**のは3カラム(サイドバー常設)に切り替わる境界だから。メディアクエリで分岐すると必ずどこかの幅で破綻する。
   - `pitfalls.md`「`@container` は詳細度を上げない」に従い、基本定義より**後ろ**に配置した。
   - 240px未満(1600px/1280px/折り返し前の狭幅)では従来の縦積みに自動で戻る。

#### 実装中に見つけて直した既存バグ: 幅390pxで37pxの横スクロール

**`.damage-row-build` が全幅で300px固定**なので、狭いビューポートでも横並びが維持され、幅390pxでは `.damage-row-body` 329pxのうち箱が300pxを取り、**技列に19pxしか残っていなかった**。19pxの技列に連続技のヒット回数行(数値入力51px + 「回」22px)が入ると **right=427px** まで飛び出し、**幅390pxで37pxの横スクロール**が発生していた。

- **ラウンド8の検証に連続技のカードを含めていなかったため見逃していた**(ラウンド8では「390pxは1px残」と記録していたが、連続技があると37pxだった)。
- 修正: `.damage-row-body` に `flex-wrap: wrap`、`.damage-row-techniques-row` の `min-width: 0` → **`140px`**(折り返しのトリガー。`flex-basis: 0` は第3弾の「flex-wrap誤爆防止の安全策として変更不可」に従い据え置き)。
- **140pxは「壊れている幅だけを折り返し、既存のデスクトップ挙動を1pxも変えない」ように逆算した値**。閾値は 箱300 + gap9.6 + 140 = **449.6px**。390px(body 329)は折り返し、1600px(459)・1280px(460)は折り返さず従来どおり。**150pxにすると1600pxと1280pxまで折り返してカード高さが変わる(=デスクトップの密度を無断で変える)ので採らなかった。**

#### この過程で判明した既存課題(未対応・記録のみ)

- **1600px と 1280px で技列が149〜151pxしかなく、技名inputが131〜133pxになる。** 「ヘビーボンバー」(実測約85px)は入るが余裕がない。原因は `.damage-row-build` の300px固定。**1600pxが最狭になるのは3カラム常設への切り替え境界だから**であり、ラウンド8 C-2で「閾値1600pxは正しい」と判断した箇所と同根。折り返し閾値を150pxに上げれば技列は459pxに広がるが、そのぶんカードが縦に伸びてデスクトップの密度が変わるため、**どちらを取るかは要判断**。
- ラウンド8 B-3(技列1つのときの累計チップと結果チップの数値重複)は**ユーザー判断により撤回済み**。今後問題として再提起しないこと。

#### 2×2配置は実装後にユーザー判断で中止・撤回(2026-07-26)

上記の実測を示したうえでユーザーが2×2を選択したため一度実装したが、**その後ユーザー指示により中止し1列の縦積みに戻した。**

- 撤去したもの: `#opponent-notes-section` と `.card-damage` の `container-type` 化 / `@container dmgsection (min-width: 740px)` による2列グリッド / 2列時に相手ビルド箱を行いっぱいへ広げる `@container dmgcard (max-width: 520px)`。
- 撤去後の実測(1920px・カード4枚): 列数1 / カード幅779px / カード高さ 276・289・276・276px / リスト1210px。**2×2導入前の値と完全に一致**。全幅(1600/1440/1280/1024/900/390px)で1列・横スクロールなし。テスト199/199 pass。
- **判断材料(再提案しないための記録)**: 総高さは2×2が66px短い(1144px vs 1210px)が、カード1枚が276〜289px → **407〜559px** に伸び、1画面に入る枚数が **3枚 → 2枚半** に減る。`align-items: start` では左右の行に**実測152pxの段差**が出る。段差を消すために高さを揃えると短い側のカード内に空白が出て、「スカスカ」が別の形で戻る。
- **残した変更は2つ(2×2とは独立して有効)**: (1)「N発目」と技名の同行化、(2)幅390pxの横スクロール修正。どちらも上記のとおり実測済み。
