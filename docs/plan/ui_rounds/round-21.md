## ラウンド21の要件(2026-07-27 ユーザー指示・第7弾)

ラウンド20の実装中(エージェントEが右パネルを実装している最中)にユーザーから届いた第7弾。**ユーザー指示なので3レビュアーの講評より優先**する。以下、**ユーザーの言葉をそのまま引用**したうえで具体化する。

**ラウンド20との重複について**: 今回のリストの「個体編集 右パネル」3項目(セクション分け / 壁を防御側へ / 揮発状態)は **ラウンド20の 20-R1 / 20-R2 / 20-R3 と同一内容**で、ラウンド20で実装中。**このラウンドでは再掲しない**(→ `round-20.md`)。

**このラウンドはラウンド20の判断を2件是正する**(20-L4 が小さすぎた / 20-D4 の表記が伝わらなかった)。該当箇所に明記してある。

## 全体

### 21-G1 ドロップダウンの下矢印を統一する

> 「下矢印の表示方法が異なる複数のドロップダウンリストが混在しているように見える。UIは種類ごとに統一したい。」

**現状は2種類**(調査で確定):

| 種別 | 対象 | 実装 | 見え方 |
|---|---|---|---|
| **A** | `box/[id].astro` の `#edit-form select`(1387-1400行付近)と `#opponent-notes-section select`(871-884行付近、`is:global` に複製) | `appearance: none` + `background-image: var(--select-arrow)`(SVGデータURI、`.edit-shell` に light/dark の2値を定義。374/380行付近)を **`:hover, :focus, :focus-visible` のときだけ**適用 | **hover/focus時だけ矢印が出る** |
| **B** | `box/index.astro` の `#sort-select`(665行付近)、`pokemon/[name].astro` の `#moves-filter-type`(577行付近) | `global.css` の共通ルール(447-470行)を継承するだけで `appearance` を上書きしていない | **OSネイティブの▼が常時表示** |

**重要な経緯**: `box/[id].astro:362-371` のコメントに「**ラウンド4ユーザー指示『2種類のドロップダウンが混在している。ホバーしたときだけ下向き記号が表示されるほうに統一する』**」と残っている。**つまりユーザーは同じ指摘を2回している。ラウンド4では `box/[id].astro` の中だけ直して、他ページを直し忘れていた。**

**提案**: **A方式(hover限定のSVG矢印)を `global.css` に昇格させる。**
- `--select-arrow`(light/dark)の定義を `.edit-shell` から `:root` / ダークのメディアクエリへ移す。
- `select` の共通ルール(`global.css:447-470`)に `appearance: none` と hover/focus 時の `background-image` を統合する。
- `box/[id].astro` 側の重複定義(2箇所)を削除する。**`is:global` 側の複製も忘れずに**(JS生成の select に効かせるために置かれている)。
- `box/index.astro` / `pokemon/[name].astro` の select は**自動的にA方式になる**(個別対応不要)。
- **`appearance: none` にすると矢印が消えるので、非hover時に「これは選べる」と分かる手掛かりが border だけになる。** 全ページで実際に見て、選べることが伝わるか確認すること。伝わらないと感じたら**常時薄く矢印を出す方式に変えてよい**(その場合はラウンド4の判断を撤回することになるので、理由を報告に書くこと)。

## ボックス画面 `/box`

### 21-B1 アイテム画像を1.5倍に

> 「アイテム画像を1.5倍くらい大きくする」

**現状**: ラウンド20(20-G1)で 22px → **28px**(`var(--icon-size-md)`)にしたところ。
**提案**: **42px**(28 × 1.5)。

**⚠️ 制約**: 持ち物画像は PokeAPI のドット絵(**32×32相当**)を都度フェッチしている(`src/lib/sprite-urls.ts:72` `itemImageUrl()`)。**42pxは元解像度を超えるので粗く見える。** 実際に `deviceScaleFactor: 3` の拡大クロップで見て、耐えられない場合は `image-rendering: pixelated` を当てて「意図的なドット絵」に見せる(ぼやけるよりは良い)。**判断と実際の見え方を報告すること。**

### 21-B2 テラスタイプ表示に通常のタイプ画像(丸アイコン)を使う

> 「テラスタイプ表示には普通のタイプ画像(丸アイコン)を使う」

**現状**: 20-B1 で `teraTypeIconUrl()` を使って `public/type-icons/tera/{id}.png`(**宝石型のジグザグ縁**)を表示している。
**提案**: `typeIconUrl()` に差し替えて `public/type-icons/{id}.png`(**角丸ピル**)を使う。`border-radius: 50%` で丸く表示するのは既存のやり方どおり。

**補足(調査で判明)**: どちらのアセットも既に正方形に切り出し済みで、「リボン(横長)」なのは切り出し前のPokeAPI生データの話。**丸く見えているのはCSSの `border-radius: 50%` によるもの。** 形状の違いはジグザグ縁の有無だけ(`scripts/type-icons/generate_type_icons.py:31` のコメント)。

### 21-B3 技の背景にタイプ背景色を置く

> 「技の背景にタイプ背景色を置く」

**現状**: `.card-move-chip`(`box/index.astro:624-633`)は **background も border も無いテキストのみ**。
**提案**: 技名からタイプを引いてタイプカラーの背景を敷く。

**実装に必要なもの(すべて既存)**:
- 技名→タイプ: `src/lib/pokemon-master-data.ts:134-158` の **`loadMoveTypeMap()`**。`box/[id].astro` が技入力欄の枠色付けに既に使っている。**`box/index.astro` は現在importしていないので追加する。**
- タイプ→色: **`TYPE_COLORS`(19タイプ分の16進カラー)が `box/[id].astro:2611-2617` の `<script>` 内にローカル定義されている**。共有モジュールは無い。**`src/lib/type-colors.ts` として切り出し、両ページから import すること**(コピーして二重管理にしない)。

**⚠️ 注意**:
- **コントラストを計算して確かめること。** タイプカラーは彩度が高く、その上に `--color-text-muted` の文字を置くと**ライトでもダークでもWCAG AA(4.5:1)を割る**可能性が高い。ラウンドで結果チップが lethal 2.45:1 / risky 2.72:1 / safe 2.84:1 と大きく割っていた実例がある。**背景を薄く(タイプカラーを 15〜20% 程度で `color-mix`)して文字は既存色のまま**が最小の修正。
- **`.card-move-chip` は Astro の scoped style が効かない**(カードは `document.createElement()` で生成)。**CSSは `<style is:global>`(269行〜)側に書く。**
- **21-L7 と矛盾しないこと**(下記参照)。

### 21-B4 21-B3 と 21-L7 の関係(Coordinatorの判断)

ユーザーは `/box` には「技の背景にタイプ背景色を置く」、`/box/[id]` 左パネルには「**技に背景色をつけると選択中のハイライト表示のように見えてしまう。背景色はつけず**、タイプアイコンを技名の左に置く」と、**画面ごとに逆のことを指示している。**

**これは矛盾ではなく、部品の種類が違うため**とCoordinatorは判断した:
- `/box` の技チップは**静的な表示テキスト**。背景色が付いても「選択中」には読めない。
- `/box/[id]` 左パネルの技欄は **`<input>`(操作できる部品)**。入力欄に背景色が付くと、**focus / 選択状態の表現と衝突する**。ユーザーの指摘はまさにこれ。

**したがって指示どおり画面ごとに違う実装にする。次ラウンド以降で「不統一だ」と再提起しないこと。**

## 個体編集 `/box/[id]` — ヘッダー

### 21-H1 個体削除をゴミ箱＋赤背景の定番デザインに

> 「個体削除はゴミ箱＋赤背景の定番デザインにする」

**現状**: `<button id="delete-button" class="btn-ghost save-row-delete">この個体を削除</button>`(`box/[id].astro:114`、`topbar-actions` スロット)。`.btn-ghost`(`global.css:836-846`)で背景透明・枠なし・`--color-text-muted`。`.save-row-delete`(`841-845`行)で**hover時だけ** `--color-danger-soft` 背景 + `--color-danger` 文字になる。**アイコンは無い。**

**⚠️ ラウンド3 B-9 の判断を撤回する。** 当時のコメントに「誤操作の抑止のため既定は muted」と明記されている。今回のユーザー指示はその逆(常時赤)なので、**コメントを書き換えて「ラウンド21で撤回」と記録すること。**

**提案**:
- **常時 `--color-danger` 背景 + 白文字**、ゴミ箱アイコン + ラベル。
- アイコンは**インラインSVGのゴミ箱**にする。**プロジェクト内の既存の削除ボタン2箇所は絵文字 `🗑` を使っている**(`box/index.astro:1025`、`box/[id].astro:5436`)が、絵文字はOS/フォントで見た目が変わるため定番デザインには向かない。**SVGを新規に1つ書き、他2箇所も揃えるかは判断して報告すること**(揃えるなら別項目として次ラウンドに回してよい)。
- **誤操作の抑止**: 常時赤になるぶん押しやすくなるので、**削除の確認ダイアログが既にあるか確認し、無ければ付ける**。無いまま常時赤にするのは危険。
- **コントラストを計算して報告すること**(`--color-danger #f8705b` 背景 + 白文字はライトで AA を割る可能性がある。割るなら暗い明度違いを使う。**新色は作らず既存色の明度違いをページscopedで持つのは可**)。

## 個体編集 `/box/[id]` — 左パネル

### 21-L1 タイプアイコンは横並び配置

> 「タイプアイコンは横並び配置」

**現状**: `#species-type-badge` に `applyTypeBadge()`(`2658-2690`行付近)が動的生成。複合タイプ時は `.type-badge-multi` で縮む(ラウンド20で `var(--icon-size-sm)` 以上に拡大済み)。**現在は縦積みになっている。**
**提案**: `display: flex; flex-direction: row` にして横並びにする。**複合タイプでもアイコンサイズを縮めないこと**(横に伸ばす余地はある)。

### 21-L2 アイテム画像を2倍にしてポケモンアイコンの右下に配置

> 「アイテム画像を2倍に大きくして、ポケモンアイコンの右下に配置」

**現状**: `#item-image`(`2208`行付近)は `.top-block-icon`(`2189`行)の中に、公式絵とは**別要素として並んでいる**。ラウンド20で `var(--icon-size-md)`(28px)に拡大済み。
**提案**: **56px**(28 × 2)にし、`/box` のカードと同じく**公式絵に重ねる絶対配置(右下)**にする。`/box` の `.card-item-badge` が同型の実装なので**構造を参考にする**(ただし別ページなのでコピーではなくこのページのCSSとして書く)。

**⚠️ `[hidden]` は詳細度で負ける。** 持ち物なしの個体で**空の白丸が残らないこと**を必ず確認する。`.card-item-badge` は同じ事故を過去に**2回**起こしている。`display` を指定したクラスには `.foo[hidden] { display: none }` を併記する。

**⚠️ 21-B1 と同じく、56pxはPokeAPIのドット絵(32×32相当)の実解像度を大きく超える。** 拡大クロップで実際に見て、粗さが許容できるか報告すること。

### 21-L3 ニックネームは種族名の下に配置

> 「ニックネームは種族名の下に配置する」

**現状**: `.top-block-fields`(`2163`行)の順序は **種族(2165) → 特性(2179) → ニックネーム(2182)**。
**提案**: **種族 → ニックネーム → 特性** に並べ替える。

**⚠️ `#nickname` の id と `textInputIds`(`3299`行付近)/ `buildPayload`(`3118`行付近)の参照は絶対に壊さない。** 消すと保存時にニックネームが空で上書きされる(`PUT /api/owned-pokemon/:id` は全項目上書き契約)。**順序を変えるだけで、要素・id・イベント登録は触らない。**

### 21-L4 技の上に性格を表示する(読み取り専用)

> 「技の上に性格も表示する。ただし選択できないようにして、ステータス側の上下選択から自動決定したものを表示するだけに留める。」

**背景**: ラウンド4のユーザー指示で**性格の `<select>` は廃止**され、能力値ラベルの▲▼クリックから性格名を**逆算**する方式になっている(`natureNameFromBoosts()` `2803`行付近、`currentLeftNature()` `2949`行付近)。**現在、確定した性格名が画面のどこにも出ていない。**

**提案**: 技欄の**すぐ上**に、**読み取り専用の1行**として性格名を表示する。
- 値は `currentLeftNature()` の戻り値。**`refreshNatureButtons` / 実数値の再計算と同じタイミングで更新**する(`3167-3170`行付近と `3220-3232`行付近が該当)。
- **`<input readonly>` や `<select disabled>` にしない。** 操作できる部品に見えると「なぜ押せないのか」という疑問を生む。**ラベル+値のテキスト表示**にする(21-R1 で右パネルに導入する「ラベルは背景なし・入力部品は囲む」の区別と揃える)。
- 無補正の場合の表示: `natureNameFromBoosts()` は上昇/下降が同じ、または両方未選択のとき**「まじめ」**を返す(`2789`行付近のコメント)。**「まじめ」とそのまま出す**(「無補正」と言い換えない。保存される値と画面の表示は一致させる)。
- **保存ロジックは一切変えない。** 表示を足すだけ。

### 21-L5 特性はそのポケモンに属する特性だけの選択ボックスにする

> 「特性はそのポケモンに属する特性だけを候補とする選択ボックスにする。予測変換も不要。」

**現状**: `<input id="ability" list="ability-list" type="text">`(`2190`行)+ `<datalist id="ability-list">`(`2451`行)。datalist の中身は `/master-data/autocomplete/abilities.json`(**全特性のフラットリスト。種族との紐付けなし**)。**種族による絞り込みは一切していない。**

**データは既に存在する(新規生成不要)**:
- `public/master-data/detail/pokemon.json`(1290件)の各レコードに **`abilities: string[]`**。
  例: `{ "name": "ピカチュウ", "types": ["でんき"], "abilities": ["せいでんき", "ひらいしん"], ... }` / コラッタは3特性 `["にげあし","こんじょう","はりきり"]`。
- 生成元: `scripts/build-master-data/extract_autocomplete.py` の `build_pokemon()` → `vendor/jpoke` の `PokemonData.abilities`。
- **同じファイルを読む前例が既にある**: `src/lib/pokemon-master-data.ts` の `loadBaseStatsMap` / `loadLearnsetMap`。**同型の `loadAbilitiesMap()` を1つ足せばよい。**

**提案**:
- `<input list>` を **`<select id="ability">`** に置き換え、**種族が確定したらその種族の `abilities` だけを `<option>` に入れる**。
- **種族未選択のときは空(または disabled)**にする。種族を変えたら候補を作り直し、**現在の値が新しい候補に無ければクリアする**。
- **`#ability` の id と、`textInputIds` / `buildPayload` の参照は維持する。** ただし `<input>` → `<select>` に変わるので、**`textInputIds`(input用のイベント登録)から外して select 用の `change` 登録に移す必要がある**。ここを漏らすと**特性を変えても保存されない**。必ず実機で保存を確認すること。
- **右パネル(相手ビルド)の特性入力**(`5479-5486`行付近、`abilityInput.setAttribute("list", "ability-list")`)は**今回のスコープ外**(ユーザーの指示は左パネルの話)。**触らないこと。** ただし `#ability-list` datalist を消すと右パネルが壊れるので、**datalist 自体は残す**。

**⚠️ 調査で判明した制約**: **隠れ特性(夢特性)の区別データは存在しない。** `abilities` は単なるフラット配列で、どれが隠れ特性かを示すキーは `vendor/jpoke` の生データ(`ps-champ-ja/pokedex.json`)の時点で失われている。**「隠れ特性だけ別枠」のような要件が来たら新規データ源が必要**、という事実を報告に残すこと。

### 21-L6 テラスタイプを画像選択ボックス化し、「テラスなし」を未選択で代用

> 「テラスなし、は未選択 (placeholder) で代用し、テラスタル選択は画像を選択肢にする画像選択ボックス化する」

**現状**: `<select id="tera">`(`2242-2244`行)。先頭に `<option value="">テラスなし</option>`、続けて `TERA_TYPES`(19タイプ、フロントマター `44-47`行)を `.map()`。**`<select>` は placeholder 属性を持てないため「テラスなし」を通常の option として置いている**(`2230`行のコメントに明記)。

**提案**: **画像を選択肢にする選択UIに置き換える。**
- **既存の前例を再利用する**: `buildIconToggleGroup(options, current, onChange, ariaLabel)`(`4857-4887`行付近)。`role="radiogroup"` の `<div class="damage-detail-icon-group">` に `<button class="damage-detail-icon-btn" aria-pressed>` を並べる実装で、**右パネルの天候・フィールドが既にこれを使っている**。
- **⚠️ そのCSSは `#damage-detail-panel-body` スコープ**(`1921-1960`行付近)。左パネルで使うには**id接頭辞なしの共通クラスに格上げする**か、左パネル用に複製する。**格上げする場合は右パネルの見た目が変わらないことを確認すること**(右パネルはエージェントEがラウンド20で改修したばかり)。
- 「テラスなし」= **どのボタンも `aria-pressed="false"`** の状態で表現する。**未選択であることが分かる手掛かりを必ず置く**(「テラスなし」というテキストか、選択解除できることが分かる見せ方)。**「選ばない」という選択肢が消えてはいけない** — 一度選ぶと解除できないUIにしないこと。
- 画像は `typeIconUrl()`(21-B2 でボックス一覧もこちらに揃えるので、**同じ丸アイコンで統一される**)。
- **`#tera` の id と保存経路は維持する。** 値の実体(`""` または タイプ名)は変えない。
- **右パネル(相手ビルド)のテラス select**(`5517`行付近、`emptyOpt.textContent = "テラスなし"`。`TERA_TYPES` は `3393-3396`行に**重複定義**されている)は**今回のスコープ外。触らないこと。** ただし**重複定義に気づいたことは報告する**(次ラウンドで統合する候補)。

### 21-L7 性格補正の上下ボタンが小さすぎ・色が判別困難、ラベル色も赤青に

> 「性格補正の上下ボタンが小さすぎて押しづらく、色の判別も困難。A,B,...のラベル色も赤・青に変わるようにする。」

**⚠️ ラウンド20の 20-L4 を是正する。** 20-L4 で「三角形の実寸10×6px、クリック領域14×12px」まで小さくしたが、**小さすぎた。** ユーザーの「三角形をボタン本体として小型化する」という当初の指示は満たしたが、**押しやすさと色の判別が犠牲になった。**

**提案**:
- **クリック領域を最低 24×24px** にする(一般的なタッチターゲットの下限)。三角形の実寸も **14×9px** 程度まで戻す。
- **色の判別**: 現在は `aria-pressed="true"` のときだけ色が付く。**非選択時の三角形が薄すぎないか**を確認し、選択時との差をはっきりさせる。**コントラストを計算して報告すること。**
- **A/B/C/D/S のラベル文字自体も、上昇なら赤・下降なら青に変える。** これは**相手ビルドカード側で 20-D3 が既に実装した表現(`--stat-up` / `--stat-down` のプレーンテキスト色、ライト4.86-4.94:1 / ダーク7.2-7.6:1)と同じもの**なので、**そちらの色定義を再利用して揃えること。**
- **色だけで意味を伝えないこと(WCAG 1.4.1)。** ▲▼ボタン自体が形で方向を示しているので、ラベルの色は補強にすぎない。この条件は既に満たされる。

### 21-L8 技欄に背景色をつけず、タイプアイコンを技名の左に置く

### 21-D4 カード全体の背景色を方向別に(攻撃=薄い赤 / 防御=薄い青)

2. `#opponent-notes-section .card-damage[data-direction="attack"] { background: ... }` / `[data-direction="defense"] { ... }` を書く。

**⚠️ 必ず守ること**:
- **薄く。** `color-mix(in srgb, var(--color-surface-alt) 92%, <accent> 8%)` 程度から始める。**カードは「外が濃く内が明るい」階調**(`.card-damage` が `--color-surface-alt`、内側の `.damage-row-build` / `.damage-column` が `--color-surface`)なので、外側だけに色を乗せれば階調は保たれる。

### 21-D5 能力ラベルのフォントの違和感

> 「能力ラベルのフォントが他と異なり違和感がある。」

**調査結果(重要)**: **`font-family` の明示的な上書きは `box/[id].astro` にも `global.css` にも存在しない**(grep 0件)。`global.css:762-780` の `button { font: inherit }` により本来は body 継承のはず。

**真因の推定**: **H(HP)だけ `<span class="damage-ev-col-label">`(`5557-5560`行付近)、A/B/C/D/S は `<button class="damage-ev-col-label damage-ev-nature-cycle">`(`5563-5570`行付近)と要素種別が違う**(20-D3 でA〜Sをクリック可能にしたため)。`font-size` / `font-weight` は `.damage-ev-col-label`(`1313-1320`行付近、`0.76rem` / `700`)で共通指定されているので**差は無いはずだが、`<button>` はブラウザのUAスタイル(フォントスムージング・レンダリング)の影響を受けやすく、`font: inherit` だけでは完全に揃わない場合がある。**

**提案**: **まず実機で `getComputedStyle` の `font-family` / `font-size` / `font-weight` / `font-synthesis` / `-webkit-font-smoothing` を H と A で比較して実測し、何が違うのかを特定してから直すこと。** 推定で直さない。
- 差が無いのに見た目が違うなら、**HPだけ `<button disabled>` にして要素種別を揃える**のが最も確実(`cursor: default` で押せないことを示す)。
- **これはCoordinatorの推定なので、実測して違っていたらそのまま報告すること。**

### 21-D6 マルチヒット技のデフォルトヒット回数をMaxに

> 「マルチヒット技のデフォルトヒット回数はMaxにする。」

**現状**: `refreshHitCountVisibility()`(`4611-4654`行付近)の最終行
```js
applyCorrection(clampInt(attackState.hitCount, range[0], range[1]));
```
`attackState.hitCount` は新規技行で常に `1`(`3526`行 `hitCount: 1`、`3771`行 `column.hitCount = attack.hitCount ?? 1`)なので、多段技を選ぶと **`range[0]`(最小保証ヒット数)にクランプされる**。

**提案**: **多段技に切り替わった直後だけ `range[1]`(最大)を渡す。** 通常のクランプ範囲 `[range[0], range[1]]` は変えない。
- **⚠️ 保存済みの値を上書きしないこと。** 既存のメモを読み込んだときは `attack.hitCount` が保存値なので、**そちらを優先する**。「新規に多段技を選んだとき」と「保存値を復元したとき」を区別すること。ここを間違えるとユーザーが設定した回数が勝手に変わる。
- データ: `src/lib/pokemon-master-data.ts:107-132` の `loadMultiHitMoveMap()` が `/master-data/autocomplete/moves.json` の `hits?: [min, max]` を読む(例: みだれづき `[2, 5]`)。**単発技はキー自体が存在しない。**
- ラウンド19でヒット数入力に付けた説明(「実際のヒット数は技ごとの確率で決まる乱数です。ここでは指定した回数ヒットした場合を計算します。」)は**維持する**。既定が最大になるなら、なおさらこの断りが要る。

### 21-D7 「乱3 (…) → 確4」をやめ、最終結果1つだけにする

> 「乱3 () → 確4 という表記は意味が通じない。すべて込みの最終結果1つだけを表示する」

**⚠️ ラウンド20の 20-D4 を是正する。** 20-D4 で「未撃破」を廃して確定数と致死確率を出すようにしたが、**`乱N (x%) → 確M` という2段構えの表記が伝わらなかった。**

**由来**: この2段表記は 20-D4 より前からある。`00-foundation.md`「結果表示の分担」に `累計408〜480 (177〜209%) 乱1 (25.0%) →確2` という例が載っており、「最初に致死率が0を超える位置の判定 + そこがまだ確殺でなければ確殺到達位置を『→確N』として併記」という設計だった。**この設計を撤回する。**

**提案(Coordinatorの解釈)**: **判定は1つだけ出す。「確実に倒せるのは何発目か」を答える。**
- 10発以内に確殺に到達する → **`確N`** のみ(`乱M (x%) →` の前段は出さない)
- 10発以内に確殺に到達しない → **`10発以上`**(技列側の既存の語彙に揃える)
- 累計ダメージと割合(`累計408〜480 (177〜209%)`)は**そのまま残す**(これは判定ではなく実測値なので意味がある)
- **確率の丸め規則は維持**: 小数第1位まで。ただし `0.0%` / `100.0%` は `<0.1%` / `>99.9%` と表示する。
- **⚠️ 技列側(`.damage-column-result`)は既に確定数を1つだけ出しているので触らない。** カード合計側だけの修正。**技列側が退行していないことを必ず確認する。**
- **⚠️ ラウンド19で実装した「威力が固定値でない技(カウンター等14件)を含む場合の断り書き」と severity を `none` に落とす扱いを絶対に壊さない。**

**この解釈が違っていたら報告すること。** 「すべて込みの最終結果1つ」を「確殺到達位置」と読んだが、「最初に倒せる可能性が出る位置」と読む余地もある。**実装したうえで、両方の案をスクリーンショットで示して報告すること。**

### ✅ 不完全なボディの `PUT /api/owned-pokemon/:id` が個体を全消去していた(2026-07-28 修正済み)

**修正コミット**: `fix(api): 不完全なボディの PUT が個体データを全消去する問題を修正`

**採った方針**: 当初挙げた3案のうち **1案(空ボディを400)と2案(必須フィールド化)の組み合わせ**。
`_shared.ts` に `readRequiredJsonBody()` を足してボディ無しを400にし(`body.data ?? {}` を使っていた
8エンドポイントすべてに適用)、`validateOwnedPokemonRequestBody` に `{ mode: 'replace' }` を追加して
**PUT のときだけ `buildPayload` が送る13キーの存在を必須**にした(`undefined` は拒否、`null` は許容)。
**POST は緩いまま**にした(`/box` の「＋ 個体を追加」が空個体を登録する仕様のため)。
3案(PATCHセマンティクスへの変更)は影響範囲が広いので採らなかった。

**⚠️ 1回目の修正は不完全だった(記録)**: 実装者は「7箇所すべて修正した」と報告したが、
**`{}` を送るケースが残っており、Coordinatorの実測で個体が1回消えた。**
「ボディがあるか」だけを見ても塞がらず、**「上書きに必要な項目が揃っているか」を検証層で見る**必要があった。
**実装者の完了報告を実測で確かめたから見つかった。**

**Coordinator実測(修正後)**: ボディなし / `{}` / `move_names` 欠け / `null` / `[]` / `"x"` の**6ケースすべて400・DB不変**。
完全な payload のみ200。`/box/[id]` の自動保存も200で従来どおり永続化。`npm test` **256件全pass**。

以下は**原因の記録**:

**Coordinatorがコードを読んで存在を確認した。** 経路:

| # | 場所 | 挙動 |
|---|---|---|
| 1 | `src/pages/api/_shared.ts:60-66` | `readJsonBody` が**空ボディをエラーにせず `null` を返す** |
| 2 | `src/pages/api/owned-pokemon/[id].ts:55` | `validateOwnedPokemonRequestBody(body.data ?? {})` で `null` が **`{}`** になる |
| 3 | `src/lib/owned-pokemon-validation.ts:46-106` | **全フィールドが `X !== undefined && ...` の任意項目**なので `{}` が検証を通る |
| 4 | `updateOwnedPokemon` | **全項目上書き契約**で走り、`species_name` / `nature` / `ability_name` / `item_name` / `evs` / `move_names` がすべて空で保存される。**400ではなく200が返る** |

**実害**: ラウンド21のCTA復元エージェントが、検証のため `is_public` を切り替えようとしてフィクスチャ `c8680844-...` を全消去した(ローカルSupabaseへ直接PostgREST PATCHで復元済み)。

**さらに、このセッションで複数のエージェントが報告した「誰も触っていないのにフィクスチャが書き換わる」現象の有力な原因**でもある。検証後の復元にPUTを使ったエージェントのリクエストが空ボディ扱いになり、復元のつもりが消去になっていた、という筋が通る。

**修正方針は3案あり、どれを採るかで意味が変わるのでユーザー判断が要る**:
1. **空ボディを400にする**(最小)。`readJsonBody` が `null` を返したら PUT は `badRequest` にする。**他のエンドポイントにも `body.data ?? {}` のパターンが無いか横断確認が必要。**
2. **`species_name` を必須にする**。「全項目上書き契約なのに全項目が任意」という設計の矛盾そのものを直す。ただし「＋個体を追加」の空個体登録(`owned-pokemon-validation.ts:67-71` のコメント)と衝突するので、そちらの経路を分ける必要がある。
3. **PUTをマージ(PATCH)セマンティクスに変える**。最も安全だが、**画面からUIを消した項目を `data-*` で保全している既存の作りが不要になる**ため影響が広い。

**このラウンドのスコープ外なので実装していない。** → 積み残し。

「復元のつもりのPUTが消去になる」経路と、**復元時は必ず GET で全フィールド突き合わせる / 確実にやるならローカルSupabaseへ直接 PostgREST PATCH を送る**という手順を記載した。
