## ラウンド9(2026-07-26): 未レビュー画面の実態調査 — **調査のみで終了(ユーザー指示によりループ終了)**

### このラウンドの位置づけ

ラウンド1〜8はすべて `/box` と `/box/[id]` に集中していた。**`/search` `/pokemon/[name]` `/moves/[name]` `/share/[slug]` の4画面は一度も講評していない**ため、同じ画面を磨き続けるより未レビュー画面を見る方が価値が高いと判断してラウンド9の対象にした。

**撮影と実測までを行い、opusアドバイザーの講評を依頼した時点でユーザーからループ終了の指示があった。実装は行っていない。** 以下は**メインエージェントが自分で実測して確認した事実**であり、次に着手するときの出発点として記録する(アドバイザーの講評は未反映)。

### 実バグ(UI改修とは別)

- **`/search` は検索状態をURLに読みも書きもしていない。**(※当初「書き出しているのに読み戻していない」と記録したが、これはメインエージェントの誤りだった。`?q=` 付きでページを開いた後に `location.href` を見たため「URLが更新された」と誤読していた。アドバイザーの再実測により訂正。)
  - `src/pages/search/index.astro` に `searchParams` / `replaceState` / `pushState` / `location.search` が**1つも存在しない**。`<form>` 要素も無いのでEnterでも遷移しない。
  - `/search?q=リザードン` を直接開くと `#query` の value は `""`、ステータスは「キーワードを入力してください」、`#results-section` は hidden。
  - **致命的な理由**: `/search` は `/pokemon` と `/moves` の唯一の入口であり、両詳細ページの `backHref="/search"` が指す唯一の戻り先。**「検索 → 技を開く → 戻る」を1往復するだけで検索語が消える。**
- **`/share/[slug]`(公開共有ページ)にログイン中ユーザー向けのUIがそのまま出ている。** トップバーの「ログイン中: dev@localhost」「ログアウト」と、アプリのサイドバー(ボックス/チーム(準備中)/トレンド(準備中)/開発者向け)が表示される。**第三者が見る唯一の対外的な画面**である点を踏まえた設計が必要。
- **`/share/[slug]` の実数値が「実数値を計算する」ボタン押下待ち**(「未計算(ボタンを押すまでPyodideはロードされません)」)。**`/box` と `/box/[id]` は同じ実数値を純JSで即座に計算している**(ラウンド3 B-12で確立済み)。公開ページだけがエンジン依存なのは不整合。
- **`/box/[id]` は読み込むだけでDBに書き込む**(ラウンド8の積み残し#5を定量化した)。Pyodideの初期化完了後、**対戦相手メモ1件につき `PUT` が1回**飛ぶ(メモ3件なら3回)。ユーザーは何も操作していない。
  - **保存される `client_result` は前後でバイト単位で同一**(キー構成・長さとも一致)。内容を1ビットも変えない無駄な書き込みである。
  - `opponent_notes.updated_at` は毎回更新される(実測 08:18:13 → 08:57:22)。
  - 一方 **`owned_pokemon.updated_at` は変化しない**ので、**`/box` の「最終更新順」の並びは壊れていない**(当初懸念したほどの実害は無い)。
  - 原因は `recalcRow()` 末尾の無条件 `scheduleRowSave(row)`。コードには「エンジン初期化後は再計算して上書きする」という意図的なコメントがあるため、無条件に消すのではなく **「再計算結果が読み込んだ値と異なるときだけ保存する」ガードを入れる**のが妥当(未実装)。

### 検証環境についての注意

- 共有ページを見るために `PUT /api/owned-pokemon/:id/share` で一時的に公開し、撮影後に非公開へ戻した。**`is_public` は `false` に戻っており、`/share/<slug>` は404を返すことを確認済み**。ただし **`share_slug` は `0a8f8d562f` が残る**(APIが `is_public` しか受け取らず、slugを消す口が無いため)。実害は無いが、初期状態(`null`)とは厳密には異なる。

#### 幅の使い方についての結論(重要・実装者が誤りやすい)

**`.panel-content` の1080pxは維持する。区切り線だけが1664pxまで伸びるのは計画書冒頭の確定仕様であってバグではない。** メインエージェントが「罫線の右3割が空白」と記録したが、これは仕様どおりである。
- 真の問題は「1080pxが広すぎる」ではなく「**1080pxを2列でしか使っていない**」。`ul.moves` は1080px幅を2カラムで使っているが、リンクの実測幅は平均90px・最大128px(72件)で、**文字が乗っているのは約230px = 21%**。6列にすれば1セル180pxで収まり、72件が36行→**12行**になる(`ul` の高さ 921px → 約340px)。
- **実装者が「罫線の右が空いている」を理由に `.panel-content` の `max-width` を外す/`margin: 0 auto` を足すことは確定仕様への抵触なので禁止。**
