### 41-B1: ボックス画面のテラスタイプバッジ(ユーザーの言う「タイプアイコン」)を上シフト

- **前提確認(調査済み)**: `box/index.astro` のカードには技・種族の「タイプアイコン」は存在しない(ラウンド4で撤去済み、タイプはtitleツールチップのみ)。このページで唯一「タイプのアイコン」と呼べる視覚要素は**テラスタイプバッジ(`.card-tera-badge`、宝石型のタイプアイコン)**であるため、ユーザーの「タイプアイコン」はこれを指すと判断する。
- 現状: `.card-badge-row`(`box/index.astro:496-512`)は`position: absolute; top: 50.56875px`(**固定px**)、子は`[itemBadge(36px), teraBadge(24px)]`の順でDOM構築される(`box/index.astro:1505-1526`)。39-B1/40-B2で「1920px・特定のカード実測」を基準に、テラスバッジの底辺がポケモンスプライト(`.card-art .card-sprite-img`)の底辺と一致するようこの`top`値を調整した経緯がある(diff実測0.04px)。
- **懸念**: `top`が固定pxである一方、`.card-art`は`width: min(56%, 113px); aspect-ratio: 1/1`でカード幅に応じて縮む(グリッド列数やビューポート幅次第)。1920px以外の幅・カードサイズでは、テラスバッジの底辺がスプライトの底辺より**下**にずれ(見切れて見え)ている可能性がある。
- 要件: **テラスバッジ(タイプアイコン)を、ポケモンスプライトの底辺と同じかそれより上の高さになるよう上シフトする。**
- 対応方針: 実装者はまず実機(ライト/ダーク、1920px以外の幅も含む複数ブレークポイント、`npm run shot -- --page box`)で`.card-tera-badge`と`.card-art .card-sprite-img`それぞれの`getBoundingClientRect()`を比較し、**実際にどの条件で「底辺より下」にずれているか**を特定してから、ずれが解消するよう`top`(または相対単位化)を調整すること。39-B1/40-B2の「アイテムバッジも連動して動くことは許容される」という前提は今回も踏襲してよいが、40-B2で行った`gap`/`margin-left`の調整結果(間隔・左寄せ)は壊さないこと。

### 41-B2: 「更新順」でお気に入りにすると自分自身の位置も変わってしまう問題の根本修正

- **前提(ラウンド40-B1で判明済みだが未解決)**: `togglePin()`(`box/index.astro:1639-1673`)は`PUT /api/owned-pokemon/:id`に全項目を送信し、`updateOwnedPokemon()`(`src/lib/owned-pokemon.ts:221-254`)が**無条件で`updated_at: new Date().toISOString()`を書き込む**(243行目)。ラウンド40はこれを踏まえ「更新順」ソート時のピン優先の再ソートを外す対応(`sort !== "updated_at"`のときだけ`is_pinned`優先ソート)をしたが、**トグルした個体自身が新しい`updated_at`で位置を動くこと自体は「要件で明示的に許容」として残した**(round-40.md 40-B1参照)。
- **今回の要件はこの許容範囲を覆す**: 「更新順」表示中にお気に入りボタンを押しても、**トグルした個体自身の位置も含めて何も動いてはいけない**、という趣旨のユーザー指摘(「対策して」で再提起されたのはこの部分)。**round-40.mdの「トグルした個体自身が動くことは許容」という判断をここで撤回する。**
- 根本原因: `is_pinned`だけを変えたいトグル操作が、既存の「全項目上書きPUT」経路(`updateOwnedPokemon`)を経由するせいで、他のフィールド変更(実際の編集保存)と同じ「更新時刻を進める」扱いを受けてしまっている。
- 対応方針: **ピン留めの単独更新には、`updated_at`を変更しない専用の更新経路を新設する。** 実装者の判断で構わないが、想定される形:
  - `src/lib/owned-pokemon.ts`に`updatePinStatus(userId, id, isPinned, supabase)`のような、`is_pinned`列だけを`update()`し`updated_at`に触れない関数を追加する。
  - `src/pages/api/owned-pokemon/[id].ts`の`PATCH`(現在`methodNotAllowed`、95行目)を実装し、`{ is_pinned: boolean }`のみを受け付けてこの新関数を呼ぶ(既存の`PUT`=全項目置換契約はそのまま変更しない。§6.2のPUT契約に影響しない)。
  - `box/index.astro`の`togglePin()`を、この新しいPATCH(または相当のAPI)を呼ぶように変更する。
  - **`is_pinned`優先ソート(1417-1419行目、`sort !== "updated_at"`条件)は、このB2の修正後も引き続き必要か実装者が判断してよい**(「最終更新順」以外のソートで依然お気に入りを最上部に固定する仕様は維持する前提)。
- 検証: 使い捨て個体(または既存フィクスチャ、必ず元に戻す)で「更新順」表示中にお気に入りをトグルし、**トグルした個体を含む全カードの表示順が変化しないこと**をPlaywright実機操作で確認する。あわせて、通常の個体編集(種族名変更等)の保存では引き続き`updated_at`が更新されることも確認する(退行防止)。

### 41-L1: アイテム選択ボックスをテラスタルと同様のアイコン+テキスト表示にする

- 現状: `#item`(`LeftPanel.astro:216`)はプレーンな`<input type="text" list="item-list">`(ネイティブdatalist、アイコンなし)。テラスタイプ(`LeftPanel.astro:226-248`)は`#tera`(隠しselect)+`#tera-dropdown-button`(アイコン+テキストのボタン)+`#tera-dropdown-list`(`<li>`にアイコン+テキストの選択肢)というカスタムドロップダウン。
- 要件: **アイテム選択もテラスタイルと同じ構造(アイコン+テキストのボタン+選択肢リスト)にする。**
- 参照実装: `LeftPanel.astro`のテラスドロップダウン一式(マークアップ226-248行目、CSSは`.tera-dropdown-*`系一式974行目以降、JSは`<script>`内の`buildTeraDropdown`)をテンプレートにする。アイテム名→アイコンURLの解決は既存の共有関数`applyItemImage()`(`src/lib/box-id/shared-core.ts:212`、内部で`itemSpriteMapPromise`/`itemImageUrl()`を使用)を流用できる(コピーではなく可能な限り再利用)。
- 候補一覧(アイテム名の全件リスト)は現在`<datalist id="item-list">`(box/[id].astro:393)が使っており、この候補がどこで生成されているか実装者が特定し、同じ候補源から新ドロップダウンの`<li>`一覧を作ること。
- 注意点:
  - テラスは19種類程度だが、アイテムは候補数がかなり多い(数百件規模)。**テラスドロップダウンと同じ全件表示ではなく、入力式のフィルタ(検索)を残すか、`.move-picker-window`のような絞り込みUIにするか**は実装者の判断でよいが、**既存の「アイテム名を打って絞り込む」操作性を失わないこと**(datalistの代替として一覧から探すだけになると、既存ユーザーの操作感が悪化する)。
  - 保存経路(`buildPayload`が参照する`#item`の値)は変更しない。テラスと同様、隠し`<input>`または`<select>`を実体として保持し、表示用ウィジェットだけを新設する形にする。
  - `#item-list`(`<datalist>`)自体は右パネル(相手ビルド)側やダメージカードの技候補等、他の入力欄が引き続き使う可能性があるため、**削除しない**(テラスの`#tera`(隠しselect)と同じ扱い)。

### 41-L2: 技選択テーブル(`.move-picker-window`)を性格補正ボタンより手前に表示する

- **これは新規バグではなく、ラウンド40(40-L3-2)で「対症療法」扱いのまま未解決だった問題の再発**(round-40.md「根本原因(なぜ手前に来ていたか)は未解明のまま`reposition()`のスキャン対象に追加する対症療法で解消。今後同種の要素を追加する際は同じ問題が再発しうる」)。
- 現状のスタッキング設計(`LeftPanel.astro` 1522-1575行目のコメントに詳細な経緯記録あり): `.move-picker-window`は`position: fixed`・`z-index`指定なし(auto)で`document.body`の先頭の子として挿入される。CSS2.1のスタッキング順では「position指定のない通常フロー要素」より「position指定+z-index:auto」の方が前面になるはずで、`.stat-nature-up`/`.stat-nature-down`(`LeftPanel.astro:615-641`)は`position`を持たない通常フロー要素のため、理論上は`.move-picker-window`より背面になるはずである。
- **にもかかわらず実機では性格補正ボタンが手前に表示される**(ラウンド40で実測済みの既知のバグ)。ラウンド40の対応は「ウィンドウの座標を性格補正ボタン群の下にずらして重ならないようにする」という**位置回避**であり、**スタッキング順そのものは直っていない**。今回ユーザーが再度「後ろにある」と指摘しているのは、この回避策が効かないケース(技リストの表示件数変化・ウィンドウの高さ変化・別のブレークポイント等でボタンとウィンドウが再び重なるケース)が起きている可能性が高い。
- 要件: **今回は座標のずらしではなく、根本原因(なぜ通常フロー要素であるはずの性格補正ボタンが`position:fixed`要素より前面に描画されるか)を実際に特定すること。** 調査の手がかり:
  - `document.elementFromPoint()`で、ウィンドウと性格補正ボタンが重なる座標において実際にどちらの要素が取得されるかを確認する。
  - `.stat-nature-btn`・`.stat-row`・`.stat-table`・`.panel-left`・`.top-block-fields`等、性格補正ボタンの祖先要素すべてに対し`getComputedStyle()`で`position`/`transform`/`filter`/`will-change`/`contain`/`isolation`等、新しいスタッキングコンテキストを作るプロパティが指定されていないか総当たりで確認する(`.stat-nature-up[aria-pressed="true"]::before`が`filter: drop-shadow(...)`を使っている点に注意。`filter`はスタッキングコンテキストを生成するプロパティであり、**`::before`疑似要素にfilterを使うと、そのホスト要素`.stat-nature-btn`自体が新しいスタッキングコンテキストになる**可能性があるため、まずここを疑うこと)。
  - 原因が特定できたら、`reposition()`による座標回避ロジック(`left-panel.ts`、40-L3-2で追加した部分)は**残してよいが、根本のスタッキング順も是正**し、重なった場合でも技選択ウィンドウが常に手前になるようにする。
- 検証: 技入力欄をクリックしてウィンドウを開いた状態で、性格補正ボタンの座標と意図的に重なる位置に配置し(またはウィンドウ表示中に性格補正ボタンをクリックして)、`document.elementFromPoint()`でウィンドウ側の要素が取得されることを実機で確認する。

### 41-L3: 性格上昇補正(▲)の強調表示を下降補正(▼)と同様に縁取りする

- **前提確認(重要)**: 現在のコード(`LeftPanel.astro:674-689`)では、上昇(`.stat-nature-up[aria-pressed="true"]::before`)・下降(`.stat-nature-down[aria-pressed="true"]::before`)の**両方に**`drop-shadow`4方向重ねによる縁取りが既に実装されている(ラウンド34-L3で上昇側のコントラスト不足を修正済みのはず)。**縁取りの技法自体は既に両方にあるが、色が異なる**(上昇=`--color-danger-soft`、下降=`--color-primary-strong`)。
- ユーザーは「上昇補正の縁取りが下降と同様になっていない」と再度指摘しているため、**コード上は対称でも実機で見た目に差がある(視認性・強調の強さが違って見える)可能性が高い**。実装者はまず実機スクリーンショット(`--scale 3`程度の拡大クロップ、ライト/ダーク両方)で両方の三角形を並べて確認し、以下いずれかを切り分けること:
  1. 単純にコントラスト比・視認性がまだ不足している(34-L3の改善が不十分) → 縁取り色を再調整する。
  2. 41-L2の性格補正ボタンのスタッキング問題(filter起因の可能性)と関連し、`filter`の重なりが視覚的に潰れて見えている → 41-L2の調査結果と合わせて対応する。
  3. 別の要因(41-L1のアイテムドロップダウン化やレイアウト変更の影響等)。
- 対応: 原因に応じて、**新色は作らず既存トークンの中から**上昇・下降で「同程度の強調に見える」組み合わせを選び直す(34-L3・32-L6の経緯を踏まえ、輝度コントラスト比を実測しながら調整する)。

### 41-L4: 技選択テーブルの表記修正とトグルスイッチ化

- 現状: `left-panel.ts`(1041-1046行目付近)にチェックボックス`<input type="checkbox">` + ラベルテキスト「覚える技だけ表示する」がある(見た目はネイティブチェックボックスのまま、トグルスイッチ風の装飾は無い)。
- 要件:
  1. 文言を「覚える技だけ表示する」→**「覚える技のみ表示」**に修正する。
  2. 見た目をチェックボックスから**トグルスイッチ**(スライド式のON/OFF)に変更する。**このプロジェクトに既存のトグルスイッチ規格が無いか確認してから作ること**(実装者はまずグローバル・各コンポーネントに`toggle`や`switch`という名前のクラスが無いか検索する。無ければ新規CSSで一般的なトグルスイッチ(角丸の背景トラック+丸いつまみ、`aria-checked`または`role="switch"`を使うか、`<input type="checkbox">`をvisually-hiddenにしてCSSで装飾するか、どちらでもよい)を作る)。
  3. 機能(チェック状態の保存・フィルタロジック)自体は変更しない。`aria-label`等アクセシビリティ属性は維持する。

### 41-H1: 「すべて折りたたむ」ボタンをヘッダーへ再移動(**40-H1を撤回**)

  - `AppLayout.astro`自体は編集禁止。`box/[id].astro`側の`<Fragment slot="topbar-actions">`(既存、削除ボタンが入っている)に追加する形は38-H1と同じ手法を再利用してよい。
  - 38-H1で作った状態管理(すべて折りたたみ済みか判定・ラベル交互切り替え)ロジックは変更不要、置き場所だけを変える。
