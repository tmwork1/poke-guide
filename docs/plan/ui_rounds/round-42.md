### 42-T1: タイプアイコン資産の再生成(専用エージェント、資産生成)

- **現状**: `scripts/type-icons/generate_type_icons.py` が PokeAPI のタイプ画像(横長リボン)から通常タイプ用の正方形アイコン(`public/type-icons/N.png`、19枚)を生成している。`crop_icon_square()` は「アイコン中心基準の正方形」を検出した高さ`h`(画像の高さ、40px程度)で切り出し、96×96にリサイズしている。スクリプトのdocstringには「アイコンは正方形の内接円の中に収まる限り、表示側の`border-radius: 50%`で欠けが生じない」という前提が書かれているが、**ユーザーは「一部タイプでタイプアイコンの模様が見切れている」と報告している**(過去ラウンド40-T1で「フェアリー見切れ」の指摘があったが、その時はコード上の丸トリム箇所を探しても再現せず「対応不要」と保留していた経緯がある。今回は「一部タイプ」とより広く指摘されている)。
- **要件**: 「模様が見切れないような丸アイコンを作成・保存させて、以降はそれを使う」。実際に画面表示で使われている全ての箇所(`.move-type-icon`(LeftPanel)・`.damage-type-badge-img`(DamageCalcSection)・その他`border-radius: 50%`を伴う丸トリム箇所)で、円形に切り取ったときに模様(タイプのマーク部分)が欠けないアイコンを新たに生成し、`public/type-icons/*.png`(通常タイプ19枚。テラス用`public/type-icons/tera/*.png`は対象外、既に宝石型アイコンで別対応済み)を差し替える。
- **進め方(専用エージェントへの指示、資産生成タスクとして独立実行する)**:
  1. まず**現状の見切れを実データで検証する**: 19タイプの`public/type-icons/N.png`それぞれについて、画像内の不透明(alpha>0)ピクセルの外接矩形(または実際のマーク=白色系ピクセルの範囲)を計算し、画像の正方形キャンバスに内接する円の範囲と比較する。マークが円の外にはみ出しているタイプを実測ですべて特定する(「一部」がどのタイプなのか、推測ではなく実測で確認すること)。実際の表示サイズ(14〜28px、`.move-type-icon`は20〜22px程度)でレンダリングして目視確認も行う。
  2. 原因を特定した上で、`generate_type_icons.py`の生成方式を修正する。想定される対応(実装者の判断に委ねる): (a) 出力する正方形のマージンを広げてマーク周囲に余白を持たせ、内接円により余裕を持って収まるようにする、(b) 正方形への切り出し自体はやめ、あらかじめ円形にマスクした透明PNG(マークの外側は完全に透明)として保存し、表示側の`border-radius: 50%`(既にCSSで円形に見せている)が実質的に「透明な四隅を切り落とすだけ」になるようにする、のいずれか、または両方の組み合わせ。**pitfalls.mdの「画像資産そのものの欠陥は資産を作り直すのが第一候補」の方針どおり、CSS側(object-fit・表示サイズ)の調整ではなく資産自体を作り直す。**
  3. 全19タイプを再生成し、`public/type-icons/N.png`を上書き保存する。再実行可能なスクリプトなので、既存の`main()`実行フローを踏襲してよい(依存: Pillow、`python scripts/type-icons/generate_type_icons.py`)。
  4. 生成後、19タイプ全部について「模様が欠けていないこと」を実測(またはPillowでの再検証スクリプト)で確認する。**フェアリー以外のタイプの見た目も崩れていないこと**(既存の丸トリム箇所のスクリーンショットで確認)。
  5. `npm run shot`で`/box/[id]`(左パネルの技タイプアイコン)・ダメージカード(相手ビルドのタイプバッジ)双方をライト/ダーク双方で撮影し、Read toolで目視確認する。
- **注意**: このエージェントは`scripts/type-icons/generate_type_icons.py`と`public/type-icons/`配下(`tera/`を除く)以外のファイルを一切編集しないこと(担当外ファイルへの混入事故が過去ラウンド27で実際に起きているため、`git status --short`で必ず確認する)。

### 42-B2: マジカルシャイン等、長い技名が見切れる問題(box一覧)

- 現状: `.card-move-chip`(`box/index.astro`)は`font-size: 0.75rem`(12px、20-G3で確立した下限)、`white-space: nowrap; overflow: hidden; text-overflow: ellipsis`。実測でハバタクカミのカードの技チップ「マジカルシャイン」が「マジカルシャ...」のように省略されている(Coordinatorがラウンド41検証中のスクリーンショットで実際に確認済み)。
- 要件: **技名の文字サイズを小さくして対応する。**
- **注意(このプロジェクトの確立仕様との関係)**: `0.75rem`(12px)は`00-foundation.md`および20-G3で確立された「フォントサイズの下限」であり、複数ラウンドで「12px下限を割らないこと」が繰り返し維持事項として明記されている。**今回はユーザーが明示的にこの技チップの文字サイズを下げるよう指示しているため、この1箇所に限定した例外として12px未満に下げてよい**(過去のラウンド32-R1でアイコンサイズの一般規則に例外を設けた前例と同種の扱い)。ただし可読性を完全に犠牲にしないこと。
- 対応: `.card-move-chip`の`font-size`を、実際に長い技名(「マジカルシャイン」6文字、「みずのちかい」等)が省略されずに収まる値まで下げる。**マスターデータ(`public/master-data/autocomplete/moves.json`等)を実際に集計し、最も長い技名がこのチップ幅(カード幅218px前後、2列グリッドの1セル分)に収まるフォントサイズを実測で決めること**(推測で決めない)。下げすぎて他の技名(短い技)の見た目が不自然に小さくなりすぎないか、スクリーンショットで確認する。

### 42-D2: 相手ビルドカードを覆う背景領域を削除

- 要件: **相手ビルドカードを覆う背景領域を削除する。**
- 対応: `.damage-row-build`の`background`指定を削除する(`background: transparent`にするか、プロパティ自体を消す)。**pitfalls.mdの「打ち消したつもりで1階層上を打ち消している」事故を避けるため、削除前に必ず`getComputedStyle`でこの背景色の出どころが本当に`.damage-row-build`自身であることを確認してから消すこと**(親の`.card-damage`や`.damage-row-body`側ではないことを確認)。**この変更は00-foundation.mdの「外が濃く内が明るい」階調ルールの一部をこの箱に限り撤回するものである**、と計画書に明記すること。技列側の箱(`.damage-column`)の背景は今回の指示の対象外なので変更しない。

### 42-D3: 計算結果が10発以上のときは確定数表記をせず、ダメージ量のみ表示する

- 現状: `describeStandaloneLethal()`/`describeSeriesVerdict()`(`src/lib/box-id/damage-calc.ts`)は、10発当てても確殺に至らない場合`{ label: "10発以上", severity: "safe" }`を返し、`setResultVerdict(el, detailText, label)`がこの`label`(「10発以上」)を太字の`.damage-result-verdict`として、ダメージ量(`detailText`、`.damage-result-detail`)と並べて表示する。この挙動は個別技カードの結果(`.damage-column-result`)と、累計結果(`.damage-row-total-result`)の両方で使われている。
- 要件: **ラベルが「10発以上」になるケースでは、確定数表記(`.damage-result-verdict`のラベル部分)自体を出さず、ダメージ量(`detailText`)だけを表示する。**
- 対応: `setResultVerdict()`(または呼び出し元)に、labelが`` `${MAX_STANDALONE_ATTACKS}発以上` ``(「10発以上」)のときは`verdictSpan`を生成・appendしない分岐を追加する(`detailSpan`だけを追加する)。個別技カード側・累計結果側の両方に適用すること。**`severity`(背景色。42-D4以前は薄青系)は「10発以上」の場合も付与されたままでよいか(=色付きの帯の中にダメージ量だけが表示される見た目になるが、これはこのままでよいと判断してよい。もし見た目上違和感が強ければ実装者の判断でsafeのままとする)。**
- 確認: 既存フィクスチャ(フシギバナ(キョダイ)の対戦相手メモ「でんきショック」等、10発以上になるケース)で、確定数ラベルが表示されずダメージ量のみになることをスクリーンショットで確認する。

### 42-D4・42-D5: ダメージ計算カードの圧縮表示(折りたたみ状態)の作り直し

**背景**: ラウンド36〜40で折りたたみ機能を作ったが、ユーザーから「圧縮前後で情報の欠落が大きく、現状では圧縮表示のメリットが乏しい」という総評があった。Coordinatorが実機で確認したところ、現在の折りたたみ状態(`[data-collapsed="true"]`)は次のようになっている(実測、`getBoundingClientRect()`):
- 高さ102.75px、左側`.damage-row-build`は`flex: 0 0 auto; width: auto`で**幅266.84px**(スプライト+名前+攻守バッジのみが収まる幅まで縮む)、右側`.damage-row-techniques-row`は残りの**幅481.59px**まで広がる。**展開時の比率(build=340px固定+残りがtechniques側)と、折りたたみ時の比率(266.84px : 481.59px)が異なっている**。
- 左側で見えているのは: スプライト画像+アイテム/タイプの小バッジ+名前+攻守バッジのみ。**特性名・持ち物名(テキスト)・テラスタイプ(テキスト)・努力値/実数値は一切表示されない。**
- 右側で見えているのは: 使用技名を「/」区切りで並べた1行(`.damage-row-collapsed-moves`、ellipsis省略あり、実測で「スケイルショット/フレアド...」のように途中で切れて情報が失われている)+ 累計結果(`.damage-row-total-result`、これは実際には現在も表示されている)。**技ごとのヒット数・詳細設定(ランク・状態異常・急所・テラス発動等)は一切表示されない。**

**要件**:

#### 42-D4: 左側(相手ビルド)の圧縮方式
1. **折りたたみ時も`.damage-row-build`の幅を展開時と同じ配分(`flex: 0 1 340px; width: 340px`、または展開時と同一の値)に維持する**(`#opponent-notes-section .card-damage[data-collapsed="true"] .damage-row-build { flex: 0 0 auto; width: auto; }`という現在の上書きを撤回する)。
2. 情報はなるべく減らさず、次の方式で圧縮する:
   - **アイテム・テラスタルはアイコンのみ**(名前テキストは表示しない。現在も`.damage-item-badge`/`.damage-type-badge`としてスプライトに重ねる小アイコンは存在するので、これを流用してよい。既存のアイコンが「見える状態」になっていることを確認する)。
   - **ステータスは実数値のみ**(種族値・努力値・スライダーは表示しない。H/A/B/C/D/Sの実数値6つだけをコンパクトな1行(または2行)で表示する。展開時の`.damage-ev-grid`をまるごと出すのではなく、実数値だけの新しい表示を追加すること)。
   - 種族名・ニックネーム・攻守バッジは現状どおり表示する。**特性名の扱いは指示に明記が無いため実装者の判断**(表示するなら1行で、省略するなら理由をコメントに残す)。

#### 42-D5: 右側(ダメージ計算)の3段表示
折りたたみ時の技列側(現在の「/」区切り1行)を、次の3段に作り直す:
1. **1段目: 技名**。設定されている技を「 + 」で連結し、複数回ヒットする技(`hitCount > 1`)には`(N発)`を付記する。例: 「スケイルショット(5発) + フレアドライブ」。`hitCount === 1`の技には`(1発)`を付けない(展開時の技カードの表記慣習(「ヒット」欄が2以上のときだけ意味を持つ)に合わせる)。技が無い列は表示しない。
2. **2段目: 詳細設定**。ランク補正(0でなければ表示)・状態異常(設定されていれば)・テラスタル発動・急所固定・その他ON になっている揮発状態(じゅうでん等)を、コンパクトなチップ/略記で列挙する。**すべての項目が既定値(未設定)のときはこの段自体を出さない、または「設定なし」等の最小表示にする**(情報が無いのに空白の段を確保しない)。表現形式(アイコン+数値、または短いテキストチップ)は実装者の判断でよいが、既存の右パネル詳細設定(`right-panel.ts`の`buildSideSection`等)が使っている用語・アイコンとなるべく揃えること(新しい語彙を作らない)。
3. **3段目: 累計の結果**。現在の`.damage-row-total`(`.damage-row-total-result`)をそのまま流用してよい(既に折りたたみ時も表示されているため、大きな変更は不要。位置・見た目を3段構成の中で自然に見えるよう調整する)。

**制約**:
- 折りたたみの目的は「省スペース化」なので、展開時の高さ(実測で技カード1枚あたり200px超)よりは明確に低いこと。ただし今回の要件により、ラウンド36時点の目標(高さ約102.75px、`.damage-sprite-box`基準)は**必然的に増える**(3段の情報を追加するため)。この増加は本要件により許容されるトレードオフであることを計画書に明記し、実装者は「展開時より十分コンパクトであること」を新しい基準として、実測した高さを報告すること。
- 技列が複数ある場合(加算ダメージ計算、最大6列)、1段目の「技名+ヒット数」列挙が長くなりすぎたら`text-overflow: ellipsis`+`title`属性でフルテキストを保持する(現在の`.damage-row-collapsed-moves`と同じ考え方)。
- 2段目の「詳細設定」は技列(カラム)ごとに異なりうる(急所・状態異常等は行全体ではなく列ごとの場合もある。`right-panel.ts`のコメントを読み、どの設定が行単位でどの設定が列単位かを正確に把握してから実装すること)。列が複数ある場合にこの段をどう集約するかは実装者の判断でよいが、**列ごとに異なる設定があるのに1つにまとめて誤解を招く表示にならないよう注意する**。
