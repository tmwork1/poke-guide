# UI改善ラウンド 26

[← 索引](../ui_plan.md)

## ラウンド26の要件(2026-07-28 ユーザー指示・第11弾)

**ユーザー指示は3レビュアーの講評より優先。** ラウンド25(第10弾)の実装中に届いた。**`/box/[id].astro`はラウンド25のエージェントが編集中のため、このラウンドの実装はラウンド25の完了・Coordinator検証のあとに着手する**(同一ファイルへの並行編集はしない。特に26-L2は26-L2/25-L1/25-L2と同じ領域=`.top-block-icon`まわりを触るため、順序を守らないと衝突する)。

ユーザーの言葉をそのまま引用:
> 個体編集画面 左サイド
> - 特性はデフォルトで一つ目の特性を設定する。特性なし状態は発生しなくなる。
> - 今のポケモンアイコンサイズのまま、アイコン領域を全幅に拡大。タイプ画像、アイテム画像+アイテム名、テラスタイプ画像を余裕をもって配置する。もともとアイコン横に配置していた入力欄は下に移動。
> - アイテム段と技段の間にも横棒を配置
>
> 個体編集画面 ダメージ計算
> - 攻守を参照したカード全体の背景色の切り替えを廃止。代わりに、攻撃・防御選択ボタンのハイライト色を赤・青に変更
> - 確定数による色の切り替えは累計ダメージ表示にのみ行い、個別ダメージカードの背景色は固定
> - 攻撃・防御ボタンの幅を短縮し、空いた一段分ポケモンアイコンを大きくする。その際、相手ビルドカード領域を右に伸ばして(ダメージ列を短縮して)よい
> - 相手ビルドの種族名以外の文字が小さい
> - 相手ビルドの特性はデフォルトで一つ目の特性を設定

**⚠️ このラウンドはラウンド23の23-D6(方向別背景色を8%→12%に濃くする)を実質的に撤回する**(背景色の切り替え自体を廃止するため)。該当箇所に明記した。

## 個体編集 `/box/[id]` — 左パネル

### 26-L1 特性はデフォルトで一つ目の特性を設定する(特性なし状態を無くす)

**現状(調査で確定)**: `rebuildAbilityOptions()`(左パネル、3779-3812行目)・`rebuildRowAbilityOptions()`(相手ビルド、6747-6789行目)はどちらも、種族の候補一覧を再構築したあと `abilitySelectEl.value = abilities.includes(previousValue) ? previousValue : ""` としており、**保存済みの値が新しい候補に含まれない場合は空文字("特性を選択"のプレースホルダー)にフォールバックする**。新規個体・種族変更直後は`previousValue`が空なので、常に「特性を選択」の空欄状態になる。

**提案**: フォールバック先を`""`ではなく`abilities[0]`(候補の先頭)にする。
- 両方の関数(左パネル3809行目、相手ビルド6783行目)を同じ考え方で直すこと。**26-R2(相手ビルドの特性も同様)と同じ修正なので、まとめて対応してよい。**
- `if (abilitySelectEl.value !== previousValue) scheduleSave();`(3811行目)・`onFieldInput()`(相手ビルド6787行目)の呼び出しは維持し、デフォルト設定時も保存が走ることを確認する。
- **⚠️ 種族名を確定した瞬間に特性が自動で埋まり自動保存されることになる。** 検証時、既存フィクスチャの種族名を書き換えて確認しないこと(pitfalls.md「入力欄を直接操作するテストは使い捨て個体で」)。
- 「特性を選択」というプレースホルダー`<option>`自体(3798-3801行目・6772-6775行目)は、候補が0件のとき(種族未確定)の表示として引き続き必要なので消さない。**「保存済みの値が候補に無い」ケースだけ、空欄ではなく先頭候補にする。**

### 26-L2 アイコン領域を全幅に拡大し、タイプ画像・アイテム画像+アイテム名・テラスタイプ画像を余裕をもって配置。入力欄は下に移動

**⚠️ このラウンドの実装時点で、ラウンド25(25-L1・25-L2)により`.top-block-icon`まわりはすでに作り替わっている前提で着手すること。** 25-L1でテラス画像バッジ(`#tera-image-badge`)を種族アイコン脇から廃止し、25-L2でテラスタイプ選択をPokeAPIリボン画像のカスタムドロップダウンに置き換えている(round-25.md参照)。**行番号は本ラウンド着手時点でズレているので、必ずgrepで最新の構造を確認すること。**

**現状(ラウンド24時点、ラウンド25で変わる前の構造。着手時に必ず再確認すること)**: `.top-block`は横並び2カラム(`.top-block-fields`=種族/ニックネーム/特性/性格の縦積み入力欄、`.top-block-icon`=種族アイコン+バッジ類)。`.top-block-icon`はアイコンサイズ(96px相当、要確認)ぶんの幅しか持たない。

**提案**: `.top-block-icon`(アイコン領域)を**全幅**に拡大する(`.top-block-fields`と横並びではなくする)。**アイコン自体のサイズ(現状のポケモンアイコンの大きさ)は変えない。** 空いた横幅を使って、以下を余裕を持って横に並べる:
- ポケモンアイコン(現サイズ維持)
- タイプ画像(`#species-type-badge`、1〜2個)
- アイテム画像+**アイテム名(テキスト)**(現状はアイテム画像のみで、アイテム名の文字表示は`.field-grid`側の入力欄にしかない。**アイテム名をこの全幅アイコン領域にも表示する**、という新しい表示要素)
- テラスタイプ画像(25-L2で作るカスタムドロップダウン。**このラウンドで、その位置をアイコン領域内に移設する**)

**もともとアイコン横に配置していた入力欄(`.top-block-fields`、種族/ニックネーム/特性/性格)は、アイコン領域の下に移動する**(横並び2カラム→縦積み2段に変える)。
- **⚠️ このラウンドは25-L2で作ったカスタムドロップダウンのUIロジック(開閉・選択・保存)自体は再利用し、「どこに配置するか」だけを変える。** ウィジェットを作り直す必要はない。
- **⚠️ アイテム名の表示は新規要素。** 既存の`#item`入力欄(`.field-grid`内)とは別に、読み取り専用の表示(`<span>`等)を置くか、入力欄自体をこのアイコン領域に移設するかを判断すること(移設する場合、入力欄のIDや保存経路(`buildPayload`等)を変えないこと)。
- 実機で、全幅にしたことで間延びして見えないか(左右の余白がスカスカにならないか)を確認し、必要なら`justify-content`や要素間の`gap`で調整すること。

### 26-L3 アイテム段と技段の間にも横棒を配置

**現状**: `.field-grid`(アイテム欄+テラス欄の2列)と技入力欄(技1〜4)が縦に並んでいるが、間に区切り線が無い(推定。着手時に実機で確認すること)。

**提案**: アイテム欄の行と技欄の行の間に横罫線(`border-top`等、既存の区切り線トークンを使う。他画面の区切り線と同じ色・太さに揃える)を追加する。

## 個体編集 `/box/[id]` — ダメージ計算

### 26-D1 攻守によるカード全体の背景色切り替えを廃止し、攻撃・防御ボタンのハイライト色を赤・青にする

**🔴 ラウンド23の23-D6(方向別背景色を8%→12%に濃くする)を実質的に撤回する。** 背景色の切り替え自体を無くすため、濃さの調整という前提が消える。

**現状(調査で確定)**: `#opponent-notes-section .card-damage[data-direction="attack"]`/`[data-direction="defense"]`(1221-1226行目)がカード全体(`.card-damage`)の背景を`color-mix`で12%着色している。一方、攻撃/防御セグメントボタン(`.damage-row-direction-option[aria-checked="true"]`、1410-1413行目)は**攻撃・防御どちらが選択されていても同じ色**(`--color-primary-strong`背景)。

**提案**:
1. `.card-damage[data-direction="attack"/"defense"]`の背景色ルール(1221-1226行目)を削除する。カードの背景は方向によらず固定(基底の`--color-surface-alt`)に戻る。
2. `.damage-row-direction-option[aria-checked="true"]`を、攻撃側は赤系(`--color-danger`系)・防御側は青系(`--color-primary`系)に分ける。**現在`attackOption`/`defenseOption`(6553-6562行目)にはどちらか区別するクラス・属性が無い**ため、`.damage-row-direction-option--attack`/`--defense`のような修飾クラス(または`data-role`属性)を追加すること。
   - **⚠️ コントラストを計算すること。** 現在の`--color-primary-strong`+`--color-primary-contrast`の組み合わせはライト4.62:1/ダーク8.87:1で選定済み(1405-1409行目コメント参照、素の`--color-primary`+`--color-primary-contrast`はライト2.66:1で不合格だった実例あり)。**`--color-danger`系で同様にWCAG AA(4.5:1)を満たす組み合わせを計算してから採用すること。** 割れる場合は`--color-danger-strong`のような一段暗い値を使う(pitfalls.md「結果チップの低コントラスト事故」と同型の罠)。
3. **⚠️ ラウンド25(25-D1)で`.card-damage.is-selected`(カード全体の選択枠)を既に廃止済み。** 今回背景色も廃止すると、カード自体の見た目は方向によらずほぼ均一になる。「どちらの向きか」はセグメントボタンの色だけで伝わることになるので、**実機で見て、方向の判別がしやすいか確認すること**(色だけで状態を伝えないというWCAG 1.4.1の原則に照らし、ボタンのテキスト自体(「攻撃」「防御」)が引き続き文字で残ることを確認する)。

### 26-D2 確定数による色分けは累計ダメージ表示のみ、個別ダメージカードの背景色は固定

**現状(調査で確定)**: `.severity-bar`クラスが**2箇所**で使われている。`.damage-column-result`(技列個別の結果、5750行目)と`.damage-row-total-result`(累計結果、6965行目)。どちらも`data-severity`属性(確1=lethal/確2=risky/確3以降・10発以上=safeなど)で背景色が変わる(4850行目コメント参照)。

**提案**: **`.damage-column-result`(個別の技列カードの結果)の背景色は`data-severity`によらず固定色にする**。`.damage-row-total-result`(累計、カード全体の合計)側だけ、これまでどおり`data-severity`で色分けを続ける。
- 実装方法: `.severity-bar`の背景色ルールが`data-severity`セレクタで定義されている箇所を確認し、**`.damage-column-result[data-severity=...]`だけを対象外にするか、`.damage-column-result`に個別の固定背景色ルールを追加して上書きする**(詳細度に注意、pitfalls.md「詳細度の罠」参照)。
- **文字色・判定文言(確N/10発以上等)はこれまでどおり技列側にも表示してよい**(色分けだけを無くす。情報自体は残す)。
- **DOM/クラス名(`.severity-bar`/`.damage-column-result`/`data-severity`属性そのもの)は変えない**(JS側の`setResultVerdict`等が参照しているため)。

### 26-D3 攻撃・防御ボタンの幅を短縮し、空いた分ポケモンアイコンを大きくする。相手ビルドカード領域を右に広げてよい

**現状(調査で確定)**: `.damage-row-build`は`flex: 0 0 300px; width: 300px`固定(1289-1291行目)。内部は2行構成: 1行目`.damage-row-actions`(攻守セグメント`.damage-row-direction-toggle`が`flex:1 1 0`で行の全幅を占有、1373-1380行目)、2行目`.damage-row-build-main`(種族アイコン`.damage-sprite-box`96px/88px画像+`.damage-row-build-fields`の縦積み入力欄、1312-1323行目・1464-1478行目)。

**提案**:
1. 攻守セグメント(`.damage-row-direction-toggle`)の幅を縮める(`flex:1 1 0`で行全幅を占有する現状をやめ、内容量に応じた幅にする)。
2. 空いた分(および必要なら行を再構成して)ポケモンアイコン(`.damage-sprite-box`/`.damage-sprite-box img.sprite-icon`、現96px/88px)を大きくする。**具体的な再配置(セグメントとアイコンを同じ行に並べる、等)は実装者の判断でよい。目的は「アイコンを大きくする」こと。**
3. `.damage-row-build`の固定幅300px自体を広げてよい(「相手ビルドカード領域を右に伸ばして」)。**その場合、技列側(`.damage-row-columns-wrap`/`.damage-column`)の幅がその分縮む。** ラウンド10で発見された「箱を固定300pxにした結果、狭い幅で技列が19pxまで潰れて横スクロールが発生した」実バグ(1254-1263行目コメント参照)が再発しないよう、**1920/1600/1440/1280/1024/900/700/390/360pxすべてで技列が潰れて横スクロールしないか確認すること**。
4. **⚠️ ラウンド25(25-D2)で技列カード(`.damage-column`)自体が左右分割(左に番号帯・右に本体)されている前提で作業すること。** 技列の必要最小幅がラウンド24以前と変わっている可能性がある。着手時に実測すること。

### 26-D4 相手ビルドの種族名以外の文字が小さい

**現状(調査で確定)**: 種族名(`.pokemon-name-row input[type="text"]`)は`font-size: 0.92rem`(14.7px、1341-1349行目)。一方、特性/持ち物/テラスの入力欄(`.damage-row-build-grid select/input`、1429-1440行目)・努力値/実数値グリッドのラベルと値(`.damage-ev-row-label`/`.damage-ev-col-label`/`.damage-stat-value`、1591-1684行目)はいずれも**0.76〜0.78rem(12.16〜12.48px)**で、20-G3で定めた「12px下限」ぎりぎりに詰められている。

**提案**: 種族名以外(特性・持ち物・テラス入力欄、努力値/実数値グリッドのラベル・数値)のフォントサイズを一段階上げる。
- **⚠️ これは過去ラウンド(特に20-G3・ラウンド3の密度最適化)が「12px下限を満たしつつ最大限詰める」方針で意図的に選んだ値を緩める指示。** 過去の判断を「間違っていた」と否定するのではなく、**ユーザーが今回あらためて「小さい」と指摘した**ことを優先する。
- 26-D3でアイコンを大きくし箱の高さに余裕ができる可能性があるため、**26-D3と合わせて実装し、空いた縦幅を文字サイズの拡大にも充てられないか検討すること**。
- **カード3枚が1080pxに収まる制約(00-foundation.md)は維持したまま、before/afterの実測値を報告する。**

### 26-R2(相手ビルドの特性デフォルト) — 26-L1に統合

「相手ビルドの特性はデフォルトで一つ目の特性を設定」は、26-L1で説明した`rebuildRowAbilityOptions()`(6747-6789行目)の修正と同じ内容。**26-L1の実装時にまとめて対応する。**
