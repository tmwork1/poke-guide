# チーム編成サジェスト: 「全員との相性」考慮状況と汎用ポケモンの露出調査

- 調査日: 2026-08-05
- 対象: チーム編集画面のポケモンサジェスト機能(`src/lib/team-suggest.ts` / `src/pages/api/team-suggestions.ts`)
- 発端: 「サジェストは単一ポケモンとの併用率しか表示していないが、選定自体はチーム全員との相性を考慮できているか」「ブリジュラスのような強ポケモンが、汎用性が高いという理由で意図的にサジェストから除外されていないか」という2つの疑問

## 結論(要約)

| 質問 | 回答 |
|---|---|
| 1. チームメンバー全員との相性を考慮できているか | **できている。** 表示上は代表1匹の根拠しか出さないが、スコア自体は全メンバーとの親密度の合算。ただし「6体同時共起」の厳密な相性ではなく、ペアごとの親密度を独立に足し合わせる近似 |
| 2. 汎用ポケモンを狙い撃ちで除外するハードコードがあるか | **無い。** 種族名によるブラックリストや汎用性ペナルティは存在しない。ただし統計的手法(lift)の副作用として、既に使用率が高く幅広い型と組まれる汎用ポケモンは、多くの相方に対してスコアがほぼ0に潰れる。実測ではブリジュラスがデフォルト表示(上位6件)に入る相方は全体の約17%にとどまる |

## 質問1: 全員との相性を考慮できているか

`src/pages/api/team-suggestions.ts:120` で `seedSpecies` はチームメンバー全員の種族から作られる(1匹だけではない):

```ts
const seedSpecies = [...new Set(members.data.map((m) => m.species_name).filter(...))];
```

これを `rankPartnerSpecies()`(`src/lib/team-suggest.ts:226-258`)が受け取り、候補ごとに各メンバーとの親密度(lift)を `score += affinity` で**加算**する。段2の型選択でも `weightSeedArchetypes()`(同 162-196行目)が全メンバーをループする。

一方でコード内コメント(`team-suggest.ts:220-224`)に設計上の近似が明記されている:

> 自チームの種族それぞれからの親密度を足し合わせ、候補種族を順位付けする。合成を単純和にしているのは、各メンバーが独立に候補を支持すると見なす素朴な仮定による(厳密には「自チーム全員と同時に共起したチーム」を数えるべきだが、6体の組み合わせで条件付けると母集団が数チームまで落ちて推定が成立しない)。

つまり「6体全員が揃ったチーム」の共起を直接見る設計ではなく、各メンバー×候補のペア親密度の独立和という近似(データが疎な1041チームしかないための妥協)。UIの根拠テキストが1匹しか出さないのは、`topSeed`(最もスコア寄与の大きいメンバー)だけを表示用に選んでいるため(`team-suggest.ts:253`)であり、**スコア計算自体は全員を見ている**。

## 質問2: 汎用ポケモンを除外するハードコードの有無

`team-suggest.ts` / `team-suggestions.ts` / `migrations/016` / `migrations/021` / `[id].astro` 全体を grep したが、種族名によるブラックリストや条件分岐は存在しない。

汎用ポケモンが上位に出にくい原因は `shrunkLogLift()`(`team-suggest.ts:63-79`)という統計手法の**自然な結果**:

```ts
const expected = (seedTeams * candidateTeams) / totalTeams; // 独立を仮定した期待共起数
const lift = coTeams / expected;                            // 実測 / 期待
const confidence = coTeams / (coTeams + AFFINITY_SHRINK_K);
return Math.log(lift) * confidence;
```

コード冒頭のコメント(`team-suggest.ts:17-19`)にブリジュラスを実例とした説明がある:

> 実測でガブリアスの共起1位はブリジュラス(36.8%)だが、ブリジュラスは全1041チームの37%が採用しているので lift は 0.99 ── ただ人気なだけで、誰に対しても同じ顔ぶれを出すことになる。

これはコメント・テスト内の実例としての言及のみで、`if (speciesName === 'ブリジュラス')` のような条件分岐はどこにも無い。

## 追加検証: ブリジュラスの実際の露出頻度(ローカルDB実測)

上記コメントの「lift 0.99」という例1件だけでは「常にほぼ出ない」のか「特定の相方に限った話」なのか判別できないため、ローカルSupabase(`postgresql://127.0.0.1:54322`、合算プール実データ = ランキング1041チーム + アプリ2チーム = 1043チーム、ブリジュラス採用387チーム = 37.1%)に対し、`team_partner_species_stats` と同じロジックのSQLを直接実行して検証した。

### 全候補中の順位分布

条件(`co_teams >= 2` かつ `candidate_teams >= 5`)を満たす**全103種の相方候補(seed)**について、ブリジュラスがそのseedにおける全候補中で何位に来るかを集計:

| 指標 | 結果 |
|---|---|
| デフォルト表示件数(6件)以内に入るseed数 | **18 / 103(約17%)** |
| 平均順位 | 21.7位(平均候補プール数 30.9件中) |

### 個別の例

順位1位になる相方(ブースター、メガエルレイド、ルカリオ)がある一方、想定通りガブリアスとの組み合わせでは lift 0.991・スコア -0.009 で **29位/30候補中**(ほぼ最下位、デフォルト表示に入らない)。

```
seed_species  = ガブリアス
候補: メガフラエッテ(1位, lift 1.58) / ブラッキー(2位) / メガガルーラ(3位) / ... / ブリジュラス(29位, lift 0.991)

seed_species  = ペリッパー
候補: メガラグラージ(1位, lift 30.8) / メガジュペッタ(2位) / メガスターミー(3位) /
      フラエッテ(えいえん)(4位) / ブリジュラス(5位, lift 2.42) / ...
```

### 解釈

ブリジュラスの母集団全体の採用率が37%と高いため、**もともと使用率が高く幅広い型と組まれやすい相方(ガブリアス、メガマフォクシー、イダイトウ等の「定番アタッカー」)と組み合わせると、独立仮定の期待共起数自体が既に高く、実測との差がほとんど出ずスコアが0付近に潰れる**。逆に採用率が中程度で構築が偏る相方(ペリッパー等)だと、共起が期待値を明確に上回りスコアが立つ。

ユーザーが最初にチームへ入れやすいポケモンほど採用率が高い定番ポケモンである可能性が高く、そうした相方に対してブリジュラスのスコアがゼロ付近に潰れやすいという構造がある。種族名でのハードコード除外ではなく統計的に必然の副作用だが、体感としては「強いポケモンなのにサジェストに出てこない」という印象を生みやすい。

## 修正提案(未実装・要検討)

以下は本調査で洗い出した改善候補であり、実装の要否・優先度はユーザー判断待ち。

1. **使用率とのブレンド**: `share = lambdaX * lift由来スコア + (1 - lambdaX) * 採用率` のように、段2 (`chooseArchetypeForSpecies`) と同様の縮小推定の考え方を段1のスコアにも部分的に取り入れ、「lift はほぼ0だが採用率が非常に高い」候補を完全に沈めない構成にする。ただし段1と段2でスコアの尺度(log-lift vs 確率)が異なるため単純合成はできず、正規化方法の検討が必要。
2. **表示の補完**: 「相性ベースのおすすめ」とは別枠で「環境上位ポケモン」を並記し、`rankSpeciesByUsage()`(現状はチームが空の時のみ使用)を空でないチームでも参考枠として併用する。スコアリング本体を変えずに露出機会だけ増やせる。
3. **現状維持**: lift ベースの設計は「意外性のある/根拠のある提案」を優先する意図的な設計であり(コード冒頭のコメント参照)、定番ポケモンが出にくいのはむしろ狙い通りという解釈もありうる。その場合は本ドキュメントを「既知の仕様」として残すのみで良い。
