## ボックス画面 `/box`

### 27-B1 アイテム画像をニックネームと技の間に配置し、アイテム名も右に表示する

**現状(調査で確定)**: `.card-badge-row`(持ち物バッジ+テラスバッジ)は`position: absolute; right/bottom`でカード画像(`.card-art`)の右下に重ねる形で配置されている(424-433行目付近)。アイテム名(テキスト)は現在カード上に表示されていない(アイテム画像のみ)。`.card-body`の順序は「名前→技→実数値」(ラウンド20 B2で確定)。

**提案**: アイテム画像を`.card-badge-row`の重ね配置から切り離し、**`.card-body`内の名前行と技グリッドの間に新しい行として配置**する。アイテム画像の右にアイテム名(テキスト)を表示する(持ち物なしの個体は何も表示しない、または薄い表現にする。round-25/26のitem-name-displayと同じ「muted文字色」の考え方を踏襲してよい)。
- **⚠️ アイテムを画像重ね配置から出すため、`.card-badge-row`に残るのはテラスバッジだけになる。** 27-B2(テラスの再配置)と合わせて実装すること(同じ`.card-badge-row`まわりを触るため)。
- カード高さが変わる可能性がある。1画面に入る枚数を実測して報告すること。

### 27-B2 テラスタイプをアイコンの右下・アイコンと被らない程度に右へ寄せて配置

**現状**: テラスバッジ(`.card-tera-badge`)はアイテムバッジと同じ`.card-badge-row`内で横並びになっており、画像の右下に重なって配置されている(23-B2でアイテムと同じ25px程度に縮小済み)。

**提案**: 27-B1でアイテムを`.card-badge-row`から外した後、**テラスバッジ単体を画像(`.card-art`)の右下に残す**。位置を、画像の輪郭と被らない程度に右へ寄せる(現状より`right`のオフセットを浅くする、または画像の右端からわずかに外側にはみ出す配置にする)。**カードの`overflow`設定(345-355行目付近、`overflow: hidden`)によりカード外にはみ出す配置ができない場合は、その旨を報告し、カード内で被らない最大限の位置に留めること。**

### 27-B3 しぼりこみ条件を「お気に入り」だけにする

**現状(調査で確定)**: `#tag-filter-toolbar`(773-776行目)が現在の絞り込みUIで、**タグによる絞り込み**(`.tag-filter-list`、複数タグ選択+すべて一致)を提供している。お気に入り専用の絞り込みは現状無い。

**提案**: `#tag-filter-toolbar`(タグ絞り込みUI)を**「お気に入りのみ表示」の単一トグル**に置き換える。既存のタグフィルタ機能(`tagFilterList`・関連する絞り込みロジック)をどう扱うか(削除するか、無効化するか)を判断し、報告すること。**検索(`#search-input`)・並べ替え(`#sort-select`)はこのラウンドの対象外**(変更しない)。
- **⚠️ 機能の縮小(タグ絞り込みの廃止)を伴う。** ユーザー指示が明示的なので実施してよいが、既存のタグ関連コード(`is_pinned`とは別に個体が持つ`tags`フィールド自体)は**保存経路・入力欄(個体編集側のタグ入力があれば)は変えない**。あくまで**一覧画面の絞り込みUIだけ**を対象にする。

### 27-B4 お気に入り設定時のハイライトを廃止し、マークの表示だけにする

**現状(調査で確定)**: `.box-grid .card-pokemon.is-pinned { border-color: var(--color-risky); background: var(--color-risky-soft); }`(370行目)が「ピン留め」(=お気に入り)時のカード全体のハイライト。★/☆アイコン(`pinButton`、1162-1164行目)は既に「マークの表示」として機能している。

**提案**: `.is-pinned`のCSSルール(370行目)を削除し、カードのハイライト(枠線色・背景色変更)を無くす。★/☆のマーク表示(`pinButton`のテキスト切り替え)はそのまま維持する。
- **クラス名`.is-pinned`・JS変数・API(`is_pinned`)は変えない**(見た目だけの変更)。
- **ラウンド12以降「ピン留めは常に上部固定」(1136-1137行目)というソート仕様がある。これは維持する**(ハイライト表現だけを無くす。並び替えの仕様は変えない)。

## 個体編集 `/box/[id]` — ヘッダー(ポケモン画像領域)

### 27-H1 ポケモン画像領域を横幅いっぱいに広げ、画像を中央寄せ。タイプは右上、アイテム・テラスは右下に右寄せ配置

**⚠️ ラウンド26(26-L2)で作った`.top-block-icon`(全幅化・アイコンサイズ不変・入力欄を下段へ)という土台はそのまま活かし、その中身の並べ方を作り替える。**

**現状(調査で確定)**: `.top-block-icon`(978行目)は`flex-direction: row`で、1つ目の子が種族アイコン(`species-icon-box`、160px)、2つ目の子が`.top-block-icon-info`(981行目、タイプ/アイテム画像+名前/テラスドロップダウンを横並びにするラッパー)。つまり現状は**「アイコン→(右に)タイプ・アイテム・テラスが横一列に続く」**というflow配置で、画像は中央寄せでもバッジは角配置でもない。

**提案**: `.top-block-icon`を**位置指定の効くコンテナ**(`position: relative`、全幅)にし、
- ポケモン画像(`species-icon-box`)を**コンテナ内で中央寄せ**にする(`margin: 0 auto`または`justify-content: center`)。**アイコンサイズは変えない**(round-26で拡大した現状のサイズを維持)。
- タイプ画像(`#species-type-badge`)を**コンテナ右上**に配置する(`position: absolute; top; right;`等)。
- アイテム画像+アイテム名、テラスタイプのドロップダウン(`#tera-dropdown-button`)を**コンテナ右下**にまとめ、**右寄せ**(右端に揃える)で配置する。
- **⚠️ アイテム画像+アイテム名(round-26の26-L2で追加した`#item-name-display`)は、この並べ替えでも残すこと**(削除の指示は無い)。
- **⚠️ 絶対配置にする場合、画像中央寄せとタイプ/アイテム/テラスの絶対配置が重ならないか(特に画像が大きいとき)を実機で確認すること。** 重なる場合は、画像の左右にタイプ/アイテム/テラス用の余白(`padding`)を確保するなどして回避すること。
- 900px以下などの狭い幅で崩れないか確認すること(30-foundation.mdのレイアウト原則、`.top-block-icon`の既存`@media`分岐(1010行目、`flex-wrap:wrap`)を参考にする)。

## 個体編集 `/box/[id]` — ダメージ計算

### 27-D1 相手アイコンの左側スペースに入力ボックスを配置する(以前のレイアウトに戻す)

**現状(調査で確定)**: ラウンド26(26-D3)で、攻守セグメント(`.damage-row-direction-toggle`)の幅を縮め、空いた分でスプライト(`.damage-sprite-box`)を拡大したため、現在の`actionsRow`(1行目)は**[攻守トグル][スプライト]**という横並びになっている(6674行目`actionsRow.appendChild(directionToggle)`、6743行目`actionsRow.appendChild(spriteBox)`)。名前input・特性/持ち物/テラス選択・努力値グリッドは`buildMain`→`buildFields`(2行目、6681-6686行目)にまとめられており、**アイコンとは別の行**にある。

**⚠️ 「以前のように」の出典(調査で確定)**: ラウンド8以前は「相手名input(29px)の右に公式絵72pxが乗っていた」(1305-1310行目付近のコメント参照。名前inputが左、公式絵が右という並び)。ラウンド8で「名前+3入力の縦スタック」と公式絵を横並び2カラムにする構成へ変わり(このときも入力欄が左・スプライトが右)、ラウンド26(26-D3)でスプライトだけが1行目(攻守トグルの隣)に上がった。**ユーザーが「以前のように」と言っているのは、「入力欄がスプライトの左に来る」という、ラウンド26以前から一貫していた並び順を指していると考えられる。**

**提案**: **名前input・特性/持ち物/テラス選択・努力値グリッドなど、入力ボックス一式をスプライトの左側に配置し直す。** 具体的な構造(1行目に統合するか、2行目のまま列を入れ替えるか)は実装者が判断してよいが、**「スプライトの左に入力欄が来る」**という関係を実現すること。
- **⚠️ ラウンド26(26-D3)で拡大したスプライトサイズ(112×112px)・`.damage-row-build`の幅(340px)は変えない**(このラウンドは配置の左右関係だけを変える)。
- **⚠️ ラウンド10で発見された実バグ(箱の固定幅により技列が潰れて横スクロールが発生)が再発しないよう、1920〜360pxの全ブレークポイントで技列側が横スクロールを起こさないか確認すること。**
- 実装方針を決めたら、なぜその構造にしたかを報告すること。

## 個体編集 `/box/[id]` — 右パネル

### 27-R1 攻撃側と防御側の設定を別セクションにして縦に分けて配置する

**🔴 ラウンド23の23-R3(「攻撃側と防御側の設定は、パネルを左右2分割して並べて配置」)を撤回する。** ワイヤーフレーム`docs/ui_proposal/個体編集_右サイド.png`(ラウンド25でも参照済み)は攻撃側ボックス・防御側ボックスを縦に積む構成であり、ユーザーが今回改めてそれを明示的に指示している。

**現状(調査で確定)**: `#damage-detail-panel-body .damage-detail-sides`の基本定義(2414-2421行目)は`display:flex; flex-direction:column`(縦積み)だが、**`@media (min-width: 480px)`(2425-2432行目)で`display:grid; grid-template-columns: 1fr 1fr`に上書きされ、通常のデスクトップ幅では常にこちらが有効**になっている。

**提案**: この`@media (min-width: 480px)`ブロック(2425-2432行目)を削除する(基本定義の縦積みがそのまま効くようにする)。**攻撃側→防御側の順で縦に並ぶ**(現在の呼び出し順、6509行目→6524行目のとおり)。
- ラウンド25(25-R1)で「攻撃(自分)」「攻撃(相手)」の見出しが2列レイアウトで2行に折り返す問題が報告されていたが、**縦1列にすることで幅の制約が緩み、この問題が自然に解消するはずなので、実機で確認して報告すること**。

### 27-R2 急所を攻撃側の設定に移動する

**🔴 ラウンド25の25-R1(「急所を独立した帯として天候より前(最上部)に出す」)を撤回する。** ワイヤーフレームでは急所は「攻撃側」ボックスの中に含まれる項目であり、ユーザーが今回明示的に「攻撃側の設定に戻す」よう指示している。

**現状(調査で確定)**: `criticalRow`(6421-6436行目)が`detailPanelBodyEl`の先頭、天候より前に独立して描画されている。`buildSideSection()`(6153行目〜)は25-R1でcritical関連のパラメータを削除済みで、攻撃側・防御側どちらの呼び出しにもcriticalを渡していない。

**提案**: `criticalRow`を`detailPanelBodyEl`の先頭に出すのをやめ、**攻撃側(`attackerSide`)の設定の中**に含める。以下のいずれかの方法で実装すること:
- (a) `buildSideSection()`に`critical`/`onCriticalChange`パラメータを復活させ(ラウンド24以前の元の形に近い)、**攻撃側呼び出しだけに値を渡し、防御側呼び出しには`undefined`を渡す**(急所は攻撃側だけの設定という仕様は変えない)。
- (b) `buildSideSection()`のシグネチャは変えず、`renderColumnLevelDetailPanel()`側で`attackerSide.appendChild(criticalRow相当の要素)`のように、攻撃側の呼び出しの直後に追加する。
どちらでも良いが、**急所が防御側には出ないこと**を実機で確認し、採用した方法を報告すること。
- 「(攻撃側の設定)」という注記(6432-6435行目)は、急所が視覚的にも攻撃側ボックスの中に入るため、**不要になるなら削除してよい**(判断して報告)。

### 27-R3 防御側の設定で、壁のボタンを揮発状態より前に配置する

**現状(調査で確定)**: `wallRow`(6548-6562行目)は`buildSideSection(defenderSide, ...)`の呼び出しが完了した**後**に`defenderSide.appendChild(wallRow)`で追加されており、`buildSideSection()`内部で最後に追加される揮発状態グループ(`.damage-detail-group`、その他の状態)の**後ろ**に来ている。

**提案**: `wallRow`(壁のボタン)を、防御側の揮発状態グループより**前**に来るよう並べ替える。`defenderSide.appendChild(wallRow)`(末尾追加)ではなく、揮発状態グループの要素を取得して`defenderSide.insertBefore(wallRow, 揮発状態グループの要素)`にするか、`buildSideSection()`側に「壁」を組み込む余地を作るなど、実装しやすい方法を選んでよい。
- **壁は防御側だけの設定という仕様(ラウンド20 20-R2)は変えない。**
- 27-R1(縦1列化)・27-R2(急所を攻撃側へ)と同じ関数群を触るため、まとめて実装すること。
