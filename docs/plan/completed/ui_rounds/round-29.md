## ラウンド29 の指摘(2026-07-29 UI/UX/プレイヤー視点レビュアー講評・Coordinator統合: `/box` `/box/[id]`)

**このラウンドの位置づけ**: ラウンド20〜28は9ラウンド連続で「ユーザーの直接指示」だけで回っており、**3レビュアー体制の講評はラウンド17が最後**だった。その間にこの2画面のレイアウトは大きく作り替わっている。今回は「個々の指示は満たしているが、全体として整合が取れているか」を見るための構造レビュー。

UIレビュアーの総評が今回の核心を言い当てている:

> 個々の指示は忠実に実装されているが、**「指示された部分だけ密度・余白の基準が変わり、指示されなかった部分との差が開いた」**箇所が複数ある。特に右パネルは、指示された項目(表記変更・区切り線・並び順)はすべて達成されている一方、**箱の大きさそのもの(359×1015px)は一度も指示の対象になっておらず、中身が増減しても箱は動かないため、空白量だけがラウンドを追うごとに積み残っている。**

### 優先度A(必ず直す)

- **29-R1 右パネルの余剰空白と、空状態の文言の噛み合わせ**(指摘者: UI A-1 / UX A-2 ※同一問題を2体が独立に指摘)
  【問題】密な状態(ダメージ計算カード4枚)でも `#damage-detail-panel-body` `[1561,65 359x1015]` の中身は `.damage-detail-sides` 下端 y=749 で終わり、**下端まで331pxが完全な空白**。さらに空状態(技0件・ダメージ計算0件の個体)では中身が `.damage-detail-panel-empty` の1行だけになり、**359×1015pxの帯のほぼ全体(約950px)が空白**になる。中央カラムも空状態では「まだダメージ計算がありません」カード(約150px)の下に約800pxの空白が続く。
  加えて、空状態の文言「技列をクリックすると設定が表示されます。」は、**その状態ではクリックできる技列がそもそも存在しない**(中央は空状態のCTAだけ)。存在しない操作を促す文言になっている。
  【提案】
  1. パネル本体の直下(JS生成の内容全体と `.damage-detail-panel-empty` を含む親)に **`margin-block: auto`** を追加する。中身がパネルより短い間は上下中央へ寄り、長くなれば `auto` が0に収束して従来どおり上端起点のスクロール(`overflow-y: auto`)に戻る。
     ⚠️ **`justify-content: center` をflexコンテナ側に付ける方法は使わないこと。** 中身がコンテナより長くなったとき上端がoverflowで見切れる既知の不具合がある(UIレビュアーが代替案として明示)。
  2. 密な状態の331pxは中央寄せだけでは埋まらないので、`.damage-detail-section-heading` の `margin` と `.damage-detail-sides` の `gap` を1.4〜1.6倍に広げ、5ブロック間の余白として分散させる。
  3. 空状態の文言を、実際に押せる操作を指す内容に変える(例:「相手ポケモンを登録すると、ここに設定が表示されます」)。**中央のCTA「+ ダメージ計算を追加」を指し、存在しない「技列のクリック」を促さないこと。**
  【`.panel` の確定仕様との関係】右パネルが画面端まで伸びる帯であること自体は `00-foundation.md` の確定仕様なので、**帯の高さは変えない**。変えるのは中身の寄せ方と余白配分だけ。

- **29-R2 右パネルの攻撃側/防御側が、どちらの個体を指すか色でも判別できない**(指摘者: プレイヤー視点 A-1)
  【問題】ラウンド28(28-R3)で見出しから自分/相手の情報が消えた結果、**防御向きカードでは攻撃側=相手・防御側=自分と反転する**のに、可視情報からは判別できない。プレイヤー視点レビュアーが実機DOMで確認したところ、`aria-label` には `攻撃側(相手)の能力ランク` / `防御側(自分)の能力ランク` と正しく残っており(スクリーンリーダーには伝わる)、**晴眼ユーザーにだけ伝わっていない**。テラスタルボタンの活性/非活性(攻撃側=フシギバナ=テラスなし=disabled、防御側=メガリザードンX=テラスほのお=enabled)とも整合しており、反転が実際に起きていることが裏付けられている。
  ここは「ランク」「テラスタル」等を**実際に書き込む場所**なので、相手の能力を自分のものと思って動かす誤操作につながる。
  【提案】**見出しの文言には手を入れない**(28-R3のユーザー指示に抵触するため)。代わりに、カードの攻撃/防御トグルで既に使っている配色(赤=攻撃 / 青=防御)を、右パネルの `攻撃側` / `防御側` セクションの**区切り線とラベル文字色に流用**する。新色は作らず既存トークンの転用のみ。
  色だけに依存しない代替として、`.damage-detail-section-heading` の直後に**既存の攻撃/防御ボタン内で使っているアイコンを再利用**して添えること(色弱環境への配慮。WCAG 1.4.1)。

- **29-R3 攻撃側・防御側のチップ列が列幅の半分しか使っていない**(指摘者: UI A-2)
  【問題】列幅327pxに対し、攻撃側の「状態異常」(約170px)「テラスタル」(約160px)「じゅうでん」(約160px)が**それぞれ単独で1行を占め、右半分約150pxが毎回空く**。防御側の「状態異常」「テラスタル」も同様。一方、直下の「リフレクター・ひかりのかべ」は全幅327px、揮発状態チップ8個は2〜4個/行で隙間なく詰まっている。**同じトグル系部品の中に「単独行で半分空ける」「全幅」「隙間なく詰める」の3つの幅規格が混在**している。
  【提案】攻撃側の「状態異常」「テラスタル」「じゅうでん」を1行にまとめる(`display: flex; flex-wrap: wrap; gap: 0.5rem`)。防御側の「状態異常」「テラスタル」も同様。これらは独立したトグル/セレクトで意味的な上下関係を持たないため、横並びにしても読み取り順は変わらない。
  【試算】「状態異常」(6.5em≈104px)+「テラスタル」(約90px)+「じゅうでん」(約90px)+gap = 300px前後で327pxに収まる想定。**実測で確認すること。** 収まらなければ2行に分けてよい(単独行で半分空ける状態さえ解消されればよい)。

- **29-R4 右パネルが「今どのカードの設定か」を示していない**(指摘者: UX A-1)
  【問題】右パネルと選択中カードの紐付けは、**カード側の技列に付いた2pxの青枠のみ**。右パネル自体(x=1561〜)には対象を示すテキストが一切ない。カード列は x=737〜1508 で、**横に850px以上離れている**。4枚のカードを行き来しながら右パネルで条件を調整する運用では、視線移動のたびに対象を見失う。
  【提案】`#damage-detail-panel-close` のDOMは維持したまま、急所ブロックの直上に**選択中カードの「相手ポケモン名 — 技名」を1行表示する見出し**を追加する(例: 「カイリュー — スケイルショット」)。
  【28-R1との関係】28-R1で消したのは**中身が空の36px帯**であり、中身のあるヘッダー行を置くことは28-R1の判断と矛盾しない(UXレビュアーが明示的に確認している)。ただし**空帯を復活させないこと**: 対象が無い(空状態)ときはこの行ごと出さない。

### 優先度B(直せるとよい)

- **29-B1 `/box` の検索placeholderが実際の検索対象を伏せている**(指摘者: UX B-1、Coordinatorがコードで実在確認)
  【問題】placeholderは「ニックネーム・種族・特性・技など」だが、**実装(`src/pages/box/index.astro:1141-1148`)の haystack は `nickname` / `species_name` / `ability_name` / `item_name` / `tera_type` / `move_names` の6項目**で、**持ち物とテラスタイプも実際に検索できる**。26体の密な一覧では同一種族が複数並ぶため、最も強く個体を差別化するのは持ち物であることが多い。使える機能が文言で伏せられている。
  【提案】placeholderを「**ニックネーム・種族・持ち物・テラス・特性・技**」にする。**機能追加ではなく、既存機能の開示。**

- **29-B2 `/box` の「★ お気に入りのみ表示」のON状態が判別できるか未検証**(指摘者: UX B-2)
  【問題】提供した全スクリーンショットで `is_pinned` の立った個体が無く、**トグルON時の見た目を撮影できていない**。OFF時は隣の検索窓・並べ替えセレクトと同程度の枠線・背景で、二値トグルであることが外見から伝わりにくい。
  【提案】ON時に既存の選択状態トークンで明確な「押されている」表現(背景塗り・枠線色)を付ける。新色は作らない。**実装後、実際にONにしたスクリーンショットで区別できることを確認すること**(DBの `is_pinned` は変更せず、DOMのクラスを付けて撮る)。

- **29-D1 条件チップ「攻撃+6」が技の分類を区別しない固定文言**(指摘者: プレイヤー視点 B)
  【問題】カード4枚目(あくのはどう=**特殊技**)で「攻撃+6」と表示されるが、実際に加算されているのは**特攻(C)ランク**。`resolveColumnDerivedFields()`(`src/pages/box/[id].astro:4929-4947`)が技分類により `atk`/`spa` へ自動振り分け済みで、**計算自体は正しい**。表記だけが誤解を招く。
  【提案】`collectConditionChips()`(`src/pages/box/[id].astro:6253-6254`)で `getMoveCategory(a.moveName)` を使い、物理技なら「攻撃+N」「防御+N」、特殊技なら「特攻+N」「特防+N」と出し分ける。**右パネルの単一「ランク」入力欄自体は変えない。チップ表記だけの修正。**

- **29-D2 ふくろだたきのヒット数ツールチップが事実と異なる**(指摘者: プレイヤー視点 B)
  【問題】`refreshHitCountVisibility()`(`src/pages/box/[id].astro:6082-6130`)は `range[0] !== range[1]` の技すべてに「実際のヒット数は技ごとの確率で決まる乱数です」と出すが、**ふくろだたきのヒット数は乱数ではなく、選出中の生存かつ状態異常でないポケモンの数で決定的に決まる**(出典: `vendor/jpoke/src/jpoke/handlers/move_attack.py:3049-3054`)。他の22件の多段ヒット技はこの汎用文言で正しく、**ふくろだたきだけが例外**。
  【提案】技名 `"ふくろだたき"` の分岐を追加し、「実際のヒット数はパーティの生存数(状態異常でない数)で決まります。乱数ではありません。」に差し替える。

- **29-B3 左パネルのアイテム/テラス画像とタイプバッジのサイズ差**(指摘者: UI B-2)
  【問題】右上のタイプバッジ約42px に対し、右下のアイテム画像16px・テラス画像16px。**タイプバッジだけが他の2.6倍**。3つとも同じ帯・同じ隅配置という**同一階層**にあるため、`00-foundation.md` の「ページ内階層による差」では正当化されない。
  【提案】タイプバッジを縮小すると視認性が落ちるので、**アイテム/テラス画像を16px→20px程度に引き上げる**方向。
  ⚠️ **ラウンド28の積み残しに「`.top-block-icon-corner` の幅119pxはアイコンとの余裕が0.5pxしかない」がある。** 実装時は必ず実測し、**アイコン矩形とコーナー列の矩形が1pxも重ならないこと**を確認する。長い持ち物名(「とつげきチョッキ」「こだわりスカーフ」)でも確認。**収まらなければ現状維持で報告すること**(無理に押し込まない)。

### 優先度C / 見送り

- **29-C1 ダメージ計算カードのバッジが絵の輪郭から浮くケースがある**(指摘者: UI B-1、Coordinator判断でCへ降格)
  ハバタクカミの行でブーストエナジーのバッジがスプライト本体の輪郭より下寄りになり、絵とバッジの間に余白の帯ができる。ポケモンごとに透過部分の量が違うため、箱の隅基準だと絵ごとにばらつく。**視覚的破綻ではなく軽微なばらつき**なので今回は見送る。対応するなら箱のサイズ(28-D1で確定した5段分)は変えず、オフセットの微調整に留めること。

- **29-C2 発動条件つき特性が効いているか読み取れない**(指摘者: プレイヤー視点 B、Coordinator判断で見送り)

  【Coordinator判断】**指摘は正しいが、静的リストの新設を伴うため機能追加寄り。** 今回は見送り、記録のみ。実害が出た時点で再検討する。

- **29-C3 実数値行が性格補正のみを含むこと**(指摘者: プレイヤー視点 C)
  `/box` 一覧カードの実数値は持ち物・特性・テラスタルの補正を含まない。**本編のステータス画面と同じ慣習**であり、上級者向けには誤解が生じにくい。対応不要。

- **29-C4 「確1」〜「確4」の凡例**(指摘者: UX C-1)

### ユーザー判断待ち(実装しない。次に手が空いたときに確認する)

- **29-U1 switch-in で自動発動する特性(いかく等)と、右パネルの「ランク」表示が食い違う**(指摘者: プレイヤー視点、Coordinatorがコード経路を確認)
  `_build_pokemon()` はUIの「ランク」入力値を `Battle` 構築**前**に `pokemon.boosts[stat]` へ直接代入し(`src/lib/pyodide-engine.ts:460-466`)、その後 `Battle(p1, p2, seed).start()` が呼ばれる(:576-577, :802-803)。`start()` は両者の switch-in イベントを発火するため、**いかくが「ランク」入力とは無関係に自動適用され、上書きではなく加算で乗る**(レビュアーのネイティブ実行: `boosts["atk"]=2` → `start()` 後は `1`)。`いかく` を持つ種族はこのフォーマットに**47種**存在する。
  **天候/フィールドはこの問題を持たない**: `_apply_field()` は `battle.start()` の**後**に呼ばれる(:578, :804)ため、ひでり等の自動天候があってもUIで選んだ天候が最後に勝つ。**ランクだけが `start()` より前に設定されるため非対称。**
  【Coordinator判断】**実装しない。** jpokeの計算自体は実戦を正しく再現しており(相手が場に出た瞬間にいかくは発動する)、バグではない。問題は「ランク 0」と表示されているのに実際は -1 が乗っている**表示と実態の乖離**。これを「意図した仕様」とするか開示するかは**ユーザーの判断が要る**。→ 出典つきで `.claude/skills/jpoke/references/integration.md` §6補2 に追記済み。

- **29-U2 ダメージ計算カードの「攻撃/防御」トグルに主語が無い**(指摘者: UX A-3)
  ラベルは「攻撃」「防御」の2文字のみで「自分が」「相手が」の主語が無い。round-25の設計では技名の `placeholder`(「技」⇄「相手の技」)がこの区別を担う想定だったが、**実運用では技名が常に入力済みなので placeholder は消えている**。実際、4枚すべてが入力済みで、方向の手がかりが2文字のラベルと色分けだけに縮退していた。
  【Coordinator判断】**実装しない。** UXレビュアーの提案(「自分が攻撃」「自分が防御」へ)は、ラウンド28の 28-R3 で**ユーザーが明示的に見出しから自分/相手を外した判断と逆方向**にあたる。指摘した問題自体は実在する(プレイヤー視点レビュアーも右パネル側で同じ構造の問題を独立に検出している)ため、**文言を増やさない 29-R2(配色+アイコンの流用)を先に実施し、それでも足りないかをユーザーに確認する。**

- **27-B2 `/box` のテラスバッジの浮き感**(ラウンド27から継続、ユーザー判断待ち)
  宝石型アイコンに変わっても浮きは解消していない(UIレビュアーが `box26-*.png` で確認)。位置は `right: -1.5rem`(`src/pages/box/index.astro:436`)で公式絵の輪郭からはみ出す。
