## ラウンド17の指摘(2026-07-27 UI/UX/プレイヤー視点レビュアー講評・Coordinator統合: `/box` `/box/[id]`)

**この2画面を3レビュアー体制で見るのはラウンド12以来**(ラウンド13〜16は `/search` `/pokemon` `/moves` `/share`)。その間に `global.css` が2回変わっている(ラウンド14の `color-scheme: light dark`、ラウンド15のラジオ・チェックボックスの `appearance: none` 化)。**ラウンド16で改訂した観点を使う最初のラウンド。**

### 統合にあたってのCoordinatorの判断

- **プレイヤー視点のA-1(テラスタルの2倍STAB)を最優先とする。** これは表示の問題ではなく**計算結果が誤る実バグ**で、Coordinatorが `vendor/jpoke` とアプリ側のコードで裏を取った(下記A-1)。
- **UIのチェックマークのコントラスト指摘は、ラウンド15の作業の取りこぼし。** ラウンド15では**未選択の枠**しか検証しておらず(6.35:1を達成と報告)、**選択時のチェックマーク**は未検証だった。矛盾ではなく漏れ。
- **UIが挙げた「実数値のフォントサイズが3階層に分裂」は、揃えずに原則として明文化する**(ラウンド16のB-7と同じ扱い)。→ 下記「Coordinatorの判断: 実数値のサイズ階層」
- **UXの「`H A B C D S` と▲▼の凡例が無い」は優先度Cに落とす。** UXレビュアー自身が「対戦経験者が主対象」「常時表示だとラウンド12 B-2で見出しを0.64emに留めた判断と衝突する」と書いており、その通り。**確N/乱N/未撃破の凡例(A-4)とは別**で、そちらは実施する(略語の難易度が違う)。
- **プレイヤー視点のC-2(OHKO技の未検証)とUIの「最長個体名17文字」は、実装ラウンドの検証項目に組み込む**(DBに個体を作らず `cloneNode` + テキスト差し替えで確認する)。

### 優先度A(必ず直す)

- **A-1 「テラスなし」の個体で「テラスタル」にチェックを入れると、無警告で2.0倍のタイプ一致補正がかかる(実バグ)**(指摘者: プレイヤー視点。**Coordinatorがコードで裏取り済み**): 【問題】jpokeは `self.tera_type = tera_type or self.base_types[0]`(`vendor/jpoke/src/jpoke/model/pokemon.py:89`)で**未指定なら第1タイプに黙ってフォールバック**する。アプリは `teraType: el("tera").value || undefined`(`src/pages/box/[id].astro:3045`、相手側は `:3743`)→ `tera_type=spec.get("teraType") or None`(`src/lib/pyodide-engine.ts:422`)で `None` をそのまま渡している。STABの計算は `if tera_matches and original_matches: base = 8192`(= **2.0倍**、`vendor/jpoke/src/jpoke/core/damage.py:203-205`)。**サイドバーの「テラスタル」チェックボックスは、対応するビルドのテラスタイプが空でも常に操作可能**(`src/pages/box/[id].astro:4726-4741`、disabled化なし)。
  - **実データで壊れる例**: メガリザードンX(`types: ["ほのお","ドラゴン"]`)は現在「テラスなし」。この状態で「テラスタル」を押すと、フレアドライブ(ほのお)が**1.5倍ではなく2.0倍**で計算される。画面には「テラスなし」と出たままなので、プレイヤーは通常のタイプ一致の数値だと誤解する。
  - → 【提案】該当ビルドのテラスタイプが空(`""`)のときは**チェックボックスを `disabled` にし**、`title` か隣接テキストで「テラスタイプを設定してください」と示す。`buildSideSection()` が `terastallized` に加えて対応ビルドのテラスタイプ文字列を受け取れるようにするだけで実装可能(新規データ・機能追加は不要)。
  - **代替案**(disabled化が難しい場合): チェック時に実際に使われるタイプを可視化する(例:「テラスタル(ほのお ※未設定のため元タイプを使用)」)。**無警告で2倍になることだけは必ず解消すること。**
- **A-2 自動保存が失敗しても、画面に理由が一切出ない**(指摘者: UX。**Coordinatorがコードで裏取り済み**): 【問題】`#autosave-status-text { display: none; }`(`src/pages/box/[id].astro:136`)で**常時非表示**にされている span に、失敗時のメッセージ `statusTextEl.textContent = "保存に失敗しました。"`(同 `:3171`)を書き込んでいる。表示が変わるのは `#retry-button` が現れることだけ(`:115` の `.visible`)なので、**ユーザーには理由の説明が無いまま「再試行」ボタンだけが唐突に出る**。
  - これは**ラウンド11のユーザー指示「ヘッダーから『保存済み』表示を削除」の副作用**。コードのコメント(`:126-135`)自体がこの形を意図したと認めている。しかし**保存ボタンが無く自動保存に全面依存する画面**で、過去に個体の性格が書き換わる事故も起きている場所である以上、失敗の理由が伝わらないのは割に合わない。
  - → 【提案】`#autosave-status[data-state="error"] #autosave-status-text { display: inline; color: var(--color-danger); }` にする。**通常時(saved/saving/idle)は従来どおり非表示なので、「ヘッダーを簡素化する」という元の要件は壊さない。** あわせて `#retry-button` に `title` / `aria-label="保存に失敗しました。クリックして再試行"` を付ける。
- **A-3 「状態異常」セレクトが確保幅の3.3倍過剰**(指摘者: UI): 【問題】セレクト本体は約267pxだが、選択肢の最長は「もうどく」(4文字)で必要幅は矢印込み80px程度。**267/80 ≈ 3.3倍**で固定1の基準(3倍)超。原因は `.damage-detail-ailment-select { flex: 1 1 auto; min-width: 0; }`(`src/pages/box/[id].astro:1979-1985`)で、**ラウンド12 A-1の検索欄1192px問題と同型**(`flex: 1 1 auto` が行内の余白を全部飲む)。ダークでは「意味のない暗い矩形」としてより目立つ。 → 【提案】`flex: 0 0 auto; width: 6.5em` 程度に固定する。空いた余白は他の行(ランク・テラスタル)と同様に詰めてよい。
- **A-4 チェックボックスのチェックマークがライトでWCAG非文字コントラスト3:1を割る**(指摘者: UI。**Coordinatorがコードで裏取り済み**): 【問題】チェックマークは `border: solid var(--color-surface)`(`src/styles/global.css:557`)で描かれており、**ライトでは白(#ffffff)がシアン背景(`--color-primary` #27acd9)に乗って約2.63:1**。ダークは `--color-surface` が #1c1f28 になるため約6.26:1で問題なし。**ラウンド15は未選択の枠(5.98:1 / 6.34:1)しか検証しておらず、選択時のチェックマークが漏れていた。**
  - **注意**: `--color-primary-contrast` はライトで `#ffffff`(`global.css:52`)なので、そこに差し替えても**ライトは同じ2.63:1のまま解決しない**。
  - → 【提案】**チェック時の塗りを `--color-primary-strong`(#1a7ea1、ラウンド13でリンク色のAA対応のために追加済み)にする。** 白いチェックマークとの比は **4.62:1** になる。ダークでは `--color-primary-strong` は `var(--color-primary)` にエイリアスされているので現状維持。**実装後に両モードで実測して3:1以上を確認すること。**
- **A-5 確N/乱N/未撃破の判定表記と赤/黄/緑の重大度配色に、目視できる凡例が無い**(指摘者: UX): 【問題】`.severity-bar[data-severity]`(`src/styles/global.css:874-902`)が lethal=赤 / risky=黄 / safe=緑 / none=灰 の4系統を持ち、各技列・カード合計に `確1` `乱2` `未撃破` `N発以上` を常時表示するが、**これらの略語を説明する可視テキストが画面のどこにも無い**。唯一の補足 `TOTAL_RESULT_HINT`(`:3356-3358`)は `title` 属性(`:4434`, `:5360`)で**ホバー時のみ**表示され、**この画面の主目的(倒せるか)を左右する情報がマウスオーバーしないと読めない**。 → 【提案】結果表示の近く(相手ビルド箱の最下段、または「詳細設定」見出し直下)に常時見える1行キャプションを追加する(例:「確N=乱数最小でもN発で確定 / 乱N=N発目から確率で撃破 / 未撃破=このN発では倒せない」)。ホバーtitleは補助として残してよい。

### 優先度B

- **B-1 ダメージ計算カードの保存失敗が、画面外にスクロールすると気づけない**(指摘者: UX): カードのfooterは失敗時のみ表示される設計自体は妥当だが、カード4枚で `scrollHeight` 1337px(1画面1080pxに収まらない)。右サイドバーは固定表示なので、**画面外のカードで失敗しても常時見える場所に反映されない**。 → 常時可視な場所(右サイドバー見出し、またはA-2の保存状態表示)に失敗件数だけ出す(例:「⚠ 1件保存に失敗」)。**代替案**: 各カードのタイトル行(常時表示部分)に小さい赤ドットの永続インジケータ。
- **B-2 技を未入力のスロットでも(i)ホバーで「空の吹き出し」が出る**(指摘者: UI): `setupMoveDetailTooltips`(`:2954-2982`)は技名が空のとき `tooltip.innerHTML = ""` で早期returnするが、`.move-detail-tooltip` は `min-width: 12em; padding; border; box-shadow` を持つ(`:649-696`)ので、**中身が空でも枠・影・パディングだけの矩形がポップアップする**。 → 技名が空のとき `.move-detail-trigger` を `pointer-events: none` にするか、`update()` 内で吹き出しを開かせない分岐を追加する。
- **B-3 右サイドバーの見出しが技名だけで、どのカード(相手)の設定かが分からない**(指摘者: UX): 見出しは「技1(スケイルショット)だけの設定」(ラウンド12 B-1で技名を含めるよう改善済み)だが、**同じ技名を複数カードが持つ場合**、カード列をスクロールした後に視線を戻すと判別できない。カード側の選択強調は左端3pxの弱いバー(ラウンド12 B-4で意図的に弱く設計)なので、対象カードが画面外だと強調も見えない。 → 見出しに相手個体名を足す(例:「カイリュー: 技1(スケイルショット)だけの設定」)。文字列の組み立てだけの変更。
- **B-4 ニックネーム入力欄が「種族→特性」という構築の思考順を分断している**(指摘者: プレイヤー視点、**条件付き固定項目「並び順」の産物**): 入力順は 種族 → **ニックネーム** → 特性(`:2092-2113`)。プレイヤーの思考順は「種族→特性(種族依存)→持ち物→努力値/性格→テラス→技」で、**ニックネームは対戦の意思決定に関与しない装飾項目**。 → `.top-block-fields` 内を 種族 → 特性 → ニックネーム に入れ替える(DOM順のみ。`flex` は `.field` 単位なので幅計算に影響しない)。
- **B-5 ヌケニン(HP種族値1)でHの努力値スライダーが操作できるのに実数値が変わらない**(指摘者: プレイヤー視点): jpokeは `if base == 1: return 1`(`vendor/jpoke/src/jpoke/model/stats.py:19-22`、アプリ側の複製も `:2750`)。**HP種族値1は全1290種でヌケニンのみ**(実データ集計済み)。努力値を投じても実数値が動かないのを「バグでは」と誤解しうる。 → `baseStats[0] === 1` のとき、H行に「(種族値1で固定)」の注記を出す。

### 優先度C・要判断

- `H A B C D S` と▲▼の凡例(UX)。**対戦経験者が主対象**であり、常時表示するとラウンド12 B-2で見出しを0.64emに留めた判断と衝突する。折りたたみ式にする案が出ているが、優先度は低い。
- 「残り18」表示に上限66の分母が無い(UX)。**ラウンド3 B-7で削除 → ラウンド5で「残り」として復活**という経緯があり(510ルールとの誤連想を避けるための意図的判断)、再度触るかはユーザー判断。
- ピン留め(エース)と危険度チップが同じ `--color-risky` を共有(UX)。両画面を行き来すると色の意味が食い違う。実データにピン留め個体が無く画面確認はできていない。
- 多段ヒット技のヒット数入力の既定値(最小保証回数)の理由が画面に無い(プレイヤー視点)。`title` に一言足す程度で可。
- 種族選択ボックス右上の小アイコン2つ(実測15px)が、同ページの他のアイコン規格(28px / 24px)の中で最小(UI)。
- **次ラウンドの検証候補**: OHKO技(じわれ等)を含むカード、最長個体名 `ムゲンダイナ(ムゲンダイマックス)` 17文字での省略。

### Coordinatorの判断: 実数値のサイズ階層は「揃えず、原則に追記する」

UIが「同じ『実数値』という概念が3サイズに分裂している」と指摘した(①左パネル `.stat-row-real` 16.8px / ②相手ビルド `.damage-stat-value` 12.16px / ③`/box` カード `.card-stat-real-value` 11.8px)。**ラウンド16のB-7と同じ扱いで、揃えずに `00-foundation.md` の「タイポグラフィ原則」に階層として明記する。**

理由: ②はダメージ計算カード3枚を1080pxに収める制約、③は218px正方形カードに6列を収める制約があり、**拡大すると別の「幅・高さが内容量で正当化できるか」違反を生む**。UIレビュアー自身も「即座に16.8pxへ揃える必要はない」と書いている。**再提起しないこと。**

### ラウンド15からの積み残しの検証結果
