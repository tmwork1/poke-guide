## データモデル案(P2でレビューを受ける)

**マイグレーション `007_teams.sql` が必要**(既存テーブルの列追加・jsonb拡張では表現できない。チームは `owned_pokemon` と独立した寿命を持つ)。

```sql
CREATE TABLE teams (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  name text,                      -- 空/未設定を許容(一覧で「無題のチーム」と表示)
  memo text,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_teams_user_updated ON teams (user_id, updated_at);

CREATE TABLE team_members (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id uuid NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,   -- lib層が join なしで絞れるよう非正規化
  owned_pokemon_id uuid NOT NULL REFERENCES owned_pokemon(id) ON DELETE CASCADE,
  slot int NOT NULL CHECK (slot BETWEEN 1 AND 6),
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (team_id, slot),
  UNIQUE (team_id, owned_pokemon_id)
);
CREATE INDEX idx_team_members_team ON team_members (team_id);
```

- **`user_id` を `team_members` にも持たせる理由**: `getSupabaseAdminClient()` は service_role で RLS をバイパスするため、**lib層が自分で `.eq('user_id', userId)` しないと他人のデータが返る**(`stack.md` 3節)。join 前提にすると絞り忘れが起きやすい。
- **`ON DELETE CASCADE` の効果**: `/box` で個体を削除すると、その個体を含むチームの枠が**自動で空きに戻る**。アプリ側の後始末が不要になる(受け入れ基準 10)。
- RLS + GRANT は `005_owned_pokemon_rls.sql` の定型をそのまま踏襲(select/insert/update/delete の4ポリシー + service_role / authenticated への GRANT)。**anon への GRANT は付けない**(公開共有はスコープ外)。
- G-2 / G-3(種族・持ち物の重複禁止)は `owned_pokemon` 側の値に依存するため **DB制約では表現しない**。lib のバリデーション(純粋関数)で担保する。

### API 案

| メソッド | パス | 契約 |
|---|---|---|
| GET | `/api/teams` | 自分のチーム一覧(メンバー込み) |
| POST | `/api/teams` | 空チーム作成(`/box` の「空個体を作る」に倣う) |

## 決めた根拠(聞かずに判断した項目)

- **公開共有はスコープ外**: 個体側の共有機構(`006`)と RLS・URL設計が絡み、一覧と編集が動くことが先。anon への GRANT を今回付けないことで、後から付ける方向にしか動かない(安全側)。
- **「絞り込み」をツールバーに置かない**: 図にはあるが、チームに絞る軸(タグ等)が現時点で存在しない。`/box` も同じ理由でタグ絞り込みを廃止済み。
- **チーム数の上限は設けない**: 大会ごとに構成案を溜める使い方を阻害する。レート制限で乱造は抑える。
- **`memo` 列を最初から入れる**: 「この構成は誰向け」を書く欄はチーム機能に必ず要る。後から足すと追加マイグレーションになるため、列だけ先に用意する(UIに出すかはP2で判断 → **R-17 で「出す」に確定**)。

## 設計レビュー(2026-07-29 データ設計/導線/プレイヤー視点・Coordinator統合)

3体を並列で走らせ、優先度A 12件・B 8件・C 5件を受領。重複を排除して17件を採用、3件を却下した。

### 採用した指摘

#### R-1 G-2の判定キーは `species_name` では機能しない(指摘者: プレイヤー視点)**【設計の根幹を覆した指摘】**
【問題】`autocomplete/pokemon.json` 全1290件を実集計した結果、**1つの `dexNo` に複数の `name` が対応する組が205件**(最大8件/種族)実在する。`species_name` 一致で判定すると、実ゲームでは同一種族として重複禁止になる組み合わせが**素通りする**。実名で確認された例:
- **ロトム(`dexNo=479`)**: `ロトム` / `ヒートロトム` / `ウォッシュロトム` / `フロストロトム` / `スピンロトム` / `カットロトム` の6種が別名 → **6体全部ロトムのチームが組める**
- **オーガポン(`dexNo=1017`)**: 仮面4種 × テラスタル前後で8種の別名
- **メガシンカが最も実害が大きい**: 直近コミット `76f1529` により個体の `species_name` にメガ後の名前が入る(`src/pages/box/[id].astro:3693-3701` `resolveMegaStoneItem`)。`ライチュウ`(`dexNo=26`)は 無印 / `メガライチュウX` / `メガライチュウY` の3つの別名を持ち、**実質同じポケモン3体が同居できる**
- 逆方向(同名扱いで誤ブロック)は `pokemon.json` 内の `name` 重複が**0件**のため発生しない。欠陥は「弾くべきものを弾けない」方向にのみ倒れている

【対応】**判定キーを `dexNo` に変更した**(「編成ルール」表 G-2 を書き換え済み)。`species_name` → `dexNo` の逆引きが必要になるが、これは**サーバー側でも可能**であることを確認済み: `src/pages/api/search.ts:22` が `import pokemonList from '../../../public/master-data/autocomplete/pokemon.json'` で静的 import している実績がある(Vite がバンドルするため Cloudflare でも動く)。
**`dexNo` を引けない `species_name`(空個体・マスターデータに無い名前)は G-2 の判定対象外**とする(→ R-15)。

#### R-2 他人の `owned_pokemon` を自分のチームに紐付けられる(指摘者: データ設計)**【セキュリティ】**
【問題】書き込みは全て `getSupabaseAdminClient()`(service_role)経由で **RLS をバイパス**するため、DB制約にもRLSにも頼れない。`owned_pokemon_id` の所有者検証が無いと、他人の個体IDを PUT に含めるだけで自分のチームの枠にでき、以後 `GET /api/teams/:id` 経由で**他人の育成データ(種族・技構成・持ち物)を閲覧できてしまう**。
【対応】**二重に防ぐ**: (1) lib層(`src/lib/team.ts`)が書き込み前に `owned_pokemon` を `.eq('user_id', userId)` で引き、`members[]` の全IDが本人のものであることを確認し、1件でも欠ければ **400** で拒否。(2) 後述の RPC 関数内でも同じ検証を行い最後の砦にする。

#### R-3 編成ルールのサーバー側強制が無い(指摘者: データ設計)
【問題】G-1〜G-3 の「実装」列がUI挙動(`disabled`・グレーアウト)しか書いておらず、devtools から直接 PUT を叩けば6体超・種族重複・持ち物重複のチームが保存できる。
【対応】`src/lib/team-validation.ts` の純粋関数 `validateTeamComposition()` を **`PUT` 実行前に必ず通す**。payload内の slot 重複・`owned_pokemon_id` 重複もここで弾き、**生のPostgres一意制約違反(500)をクライアントに露出させない**。

#### R-4 全DELETE→全INSERT置換に原子性が無い(指摘者: データ設計)
【問題】`owned_pokemon` の PUT は**単一行 UPDATE** なので原子性の問題が原理的に存在しないが、`team_members` は**複数行の子テーブル**。supabase-js の呼び出しは個別の PostgREST リクエストなので、「DELETE成功 → INSERT失敗」で**チームのメンバーが全消失**しうる。これは今回初めて踏む種類のリスクで、既存の実績が使えない。
【対応】**Postgres関数 `replace_team_members()` を `007` に含め、`supabase.rpc()` で単一トランザクションとして呼ぶ**。マイグレーション実行系がファイル全体を1クエリとして送る実装(`scripts/db/run-migrations.mjs:47`)なので、`$$` を含む関数定義をそのまま書ける(確認済み)。**同時更新は後勝ちで良い**(自動保存のデバウンスは同一タブ内で直列化されるため、複数タブ同時編集は仕様として許容する)。

#### R-5 空き枠のAPI契約が未定義(指摘者: データ設計)
【問題】`owned_pokemon_id` は `NOT NULL` なので、空き枠はDB上「該当slotの行が存在しない」ことでしか表現できない(CASCADEは行ごと消すだけで `null` の行を残さない)。契約が無いと実装者が「空きは `owned_pokemon_id: null` の要素を送る」と誤解し NOT NULL 違反を書く。
【対応】契約を明文化(後述「確定した設計 > API契約」)。**GET も PUT も `members` は 0〜6要素、欠けている slot が空き**。

#### R-6 純粋関数に渡す引数の形が未記載(指摘者: データ設計)
【問題】`team_members` 自体は `species_name`/`item_name` を持たないため、このままでは実装者が `team-validation.ts` 内に Supabase クエリを書き、`stack.md` の「検証層は純粋関数」規約が崩れて `tests/team-validation.test.ts` が DB 無しで書けなくなる。
【対応】シグネチャを確定した(後述)。**マスターデータの解決(`species_name`→`dexNo`)も純粋関数の外**に出し、呼び出し元が解決済みの `dexNo` を渡す。これで検証層は JSON import にもDBにも依存しない。

#### R-7 選択バーに検索が無いと使えない(指摘者: 導線)
【問題】`box/[id].astro` の左パネル相当(幅 `minmax(320px, 440px)`・高さ `100vh - 65px`)に1項目48〜56pxで並べると**縦に入るのは実測17〜20件が限度**。個体100件なら5〜6画面スクロールしないと末尾に届かない。
【対応】**選択バー上部に検索欄を固定配置**(ニックネーム・種族名の部分一致。`/box` の検索と同じ語彙)。並べ替えは今回入れない(優先度B相当のため)。

#### R-8 6枠カードの中身が未定義では目的を果たせない(指摘者: 導線)
【問題】設計書が「`.card-team-slot` を6枠縦に積む」としか書いておらず、判断材料が乗らない。
【対応】1枠に載せる項目を確定(後述「確定した設計 > 画面」)。空き枠は**「＋ この枠に入れる」の明示的な文言**を持つプレースホルダーにする(空白の箱にしない)。

#### R-9 ボックス0件で `/team/[id]` を開いた場合の設計が無い(指摘者: 導線)
【問題】新規ユーザーが `/team` → 追加 → `/team/[id]` と進んだ直後に**高確率で踏む**状態。
【対応】選択バーに `/box` の `.empty-state` と同じ語彙で「ボックスに個体がありません。先にボックスで個体を登録してください」+ `/box` へのリンクを出す。

#### R-10 グレーアウトの理由は4種類あり、書き分けないと基準6・7を実質満たさない(指摘者: 導線)
【問題】理由は ①この枠に既に入っている ②種族重複 ③持ち物重複 ④6体上限 の4種。`title` 属性に頼ると数十件のグレー行を1つずつマウスオーバーする羽目になり、「理由が目視できる」を字面だけ満たす。
【対応】**理由ごとの定型文言を常時テキストで表示**(「編成済み」「種族が重複」「持ち物が重複」「6体編成済み」)。色だけに頼らない。**判定順は G-1(6体上限)→ G-2(種族)→ G-3(持ち物)** とし、**最初に該当した理由を1つだけ**出す(→ R-18 のニャオニクス問題もこれで一意に決まる)。

#### R-11 6枠リストの横幅方針が未判断(指摘者: 導線)
【問題】`00-foundation.md` の「全幅 vs 1080px」の分類判断を設計書がしていない。相性チェックが無く右サイドバーも無いため、`1fr` のままだと1920pxで横長カードが1280〜1560pxに間延びする。
【対応】**6枠カードの列は `.panel-content`(1080px・左寄せ)に収める**。6枠リストは「複数列に足していくカードグリッド」ではなく「この構成を読んで判断する対象」なので、確定仕様の後者に当たる。

#### R-12 一覧カードの中身が未定義だと「並べて見比べる」目的を果たせない(指摘者: 導線)
【問題】受け入れ基準12・13を満たしても、カードにチーム名しか出ないなら結局1件ずつ開くことになり、ページの存在理由が消える。
【対応】一覧カードに **体数バッジ(例 `4/6`。`/box` の `#pokemon-count-badge` と同じ `badge tnum` トークンを流用)+ メンバーの公式絵ミニサムネイル列** を出す。`team_members` の参照で取得済みの範囲なのでマイグレーション追加は不要。

#### R-13 枠から個体編集への導線が無い(指摘者: 導線)
【対応】6枠カードに「個体を編集」リンク(`/box/<owned_pokemon_id>`)を添える。既存の参照IDをリンク化するだけ。

#### R-14 無題チームのソート位置が未定(指摘者: データ設計)
【対応】`name` の昇順ソートは `nullsFirst: false`(既存 `listOwnedPokemon` のニックネームソートと同じ)。**無題チームは末尾**。

#### R-15 空個体(`species_name` が空文字)の扱いが未定義(指摘者: データ設計)
【問題】`/box` の「＋個体を追加」は `species_name` 空の個体を作る(`owned-pokemon-validation.ts:109-116`)。空文字同士が G-2 で重複扱いになるか不明。
【対応】**選択バーには出す**(ボックスにあるものは全部出す)。**G-2 の判定対象外**(`dexNo` を引けないため)。表示名は `/box` と同じフォールバック(ニックネーム→種族名→「未設定」)。

#### R-16 「同一個体の重複は G-2 に包含される」は根拠が誤り(指摘者: プレイヤー視点)
【問題】実際に防いでいるのは `UNIQUE (team_id, owned_pokemon_id)`(DB層)。G-2 にバグがあっても同一個体の二重登録は防がれる。
【対応】「編成ルール」表の記述を訂正済み。実装者が「G-2さえ実装すれば足りる」と誤解しないようにする。

#### R-17 `memo` を出すか出さないかを保留のまま実装に進めない(指摘者: 導線)
【対応】**出す**。`/team/[id]` にチーム名入力と並べて1行のメモ欄を置く。PUT の契約に既に含まれており実装コストが小さいうえ、列だけ作ってUIが無い中途半端な状態を避けられる。

#### R-18 ニャオニクスは G-2 と G-3 のどちらで弾かれるのか(指摘者: プレイヤー視点)
【問題】`mega-stones.json` 85件の集計で、`メガニャオニクス(オス)` と `メガニャオニクス(メス)` が**同じ持ち物名 `ニャオニクスナイト` を共有**している。`species_name` は別だが `dexNo` は同じ(性別違い)。
【対応】R-10 の判定順(G-2 が先)により **G-2「種族が重複」で弾かれる**。理由表示は1つだけなので混乱しない。

### 却下した指摘(理由つき。再提起しないこと)

- **`/box` から `/team` への導線を足す**(導線・優先度B) → 今回のスコープ外。指摘者自身が「今回のデータ設計を全く変えずに後から足せる」と確認しているため、後回しにしても手戻りにならない。
- **レギュレーション別の伝説枠制限**(プレイヤー視点・優先度B) → `autocomplete/pokemon.json` は `name`/`dexNo`/`imageId`/`forme`/`types` の5列のみで、伝説・禁止級を示すフラグが**一切存在しない**(集計で確認済み)。マスターデータの拡張が前提になるため今回は実装不可能。**将来やるなら `scripts/build-master-data/` で dex 単位のフラグを追加するところから**。
- **一覧の並べ替えに「最終使用順」を足す**(データ設計・優先度C) → チームに「最終使用」の概念が無い。将来「大会で実際に使った記録」と紐付くなら、その機能とセットで考える。

### 実装中に見つかった実バグ

- **【Coordinatorが発見・修正済み】狭幅で6枠カードが1文字ずつ縦に折り返され読めなくなる。** 900px 幅で「フ / シ / ギ / バ / ナ」「な / や / み / の / タ / ネ」と1文字ずつ縦積みになり、カード1枚が縦700px以上に伸びていた。
  - **原因**: 900px ではサイドバー256px + 選択バー約380pxを引くと中央カラムが約264pxしか残らないのに、そこへ横長カードを入れていた。実装者は**「横スクロールが出ないこと」だけを確認**しており、`min-width: 0` を足して横スクロールを消した結果、潰れて読めなくなるほうの破綻に気づかなかった。
  - **これは `box/[id].astro` が過去に踏んだ罠と同一**(`00-foundation.md` 245行目「`.edit-layout` の2カラム化の閾値を 900px → 1200px に上げた」)。
  - **対処**: 2カラム化の閾値を 900px → **1200px** に統一(3箇所のメディアクエリ)。1200px未満では選択バーを `position: static` に戻して縦積みにし、`max-height: 60vh` で内部スクロールさせる。1200px以上の見た目は不変(`#team-slots` 幅 1080px を維持)。
  - **教訓**: **「横スクロールが無いこと」は狭幅レイアウトの合格条件ではない。** 潰れて読めなくなる破綻は横スクロールを伴わない。画像を目視するまで分からない。

- **【報告のみ・実害なし】`migrations` の適用先が2つある。** `.env` の `DATABASE_URL` はリモートSupabase、`.dev.vars` / `.env.local` はローカル(127.0.0.1:54322)を指しており、**開発サーバーが実際に使うのはローカル側**。`npm run migrate` はシェルの `DATABASE_URL` に従うため、どちらに当たるかが実行環境で変わる。今回は結果的に両方に007が適用された。データ損失は無い(全マイグレーションが `CREATE TABLE IF NOT EXISTS` で、唯一の `DROP` は `006` の廃止済み `builds` のみ)。

`docs/plan/ui_parallelization.md`(`box/[id].astro` が3領域1ファイル同居で並列実装できなくなった調査)を受けて、`team/[id].astro` が同じ罠を踏んでいないか実測した。

### 関数の分類(script内18関数を実測)

`if (layoutRoot) { ... }` という単一クロージャの中に定義されている18関数を、領域ごとに仕分けた。

### `box/[id].astro` と同型の罠を踏んでいるか

**踏んでいる。規模が小さいだけで構造は同じ。** `team/[id].astro` も「// --- 6枠の描画 ---」「// --- 選択バーの描画 ---」「// --- 自動保存 ---」のようにコメントで領域を区切っているが、実行時は `if (layoutRoot) { ... }` という1つのクロージャスコープを左パネル・中央が共有している(`box/[id].astro` の `if (form) { ... }` と同じパターン)。

呼び出しを実測した結果、以下の共有コアが領域をまたいで密結合していることを確認した:

| 関数 | 呼び出し元(領域別) |
|---|---|
| `renderSlots()` / `renderSelectList()` | 互いに他方を呼ぶ相互依存。中央の「枠から外す」ボタン(957〜958行目)が両方を呼び、左の選択行クリック(1044〜1045行目)も両方を呼ぶ。**membersBySlot という共有状態(Map)をどちらの領域から更新しても、もう一方の再描画が必須**という関係 |
| `firstEmptySlot()` | 中央の `renderSlots()` 内(969行目)+ 左の選択行クリック(1041行目)の両方から呼ばれる |
| `displayName()` / `applySprite()` | 中央の `buildFilledSlotContent()`(843/836行目)+ 左の `buildSelectRow()`(1015/1011行目)の両方から呼ばれる |
| `candidateOf()` / `currentCandidates()` | 左の `buildSelectRow()`(1027行目)専用の呼び出しだが、中央が所有する `membersBySlot` を読む(領域の状態を越境して参照) |
| `buildPayload()` → `saveNow()` → `scheduleSave()` | 左(選択行クリック 1046行目)・中央(枠を外すボタン 958行目)・チーム名/メモ入力(1162行目)の3方向すべてから呼ばれる保存チェーン |

`box/[id].astro` の `scheduleRowSave`/`scheduleRowCalc`(ダメージ計算⇔右サイドを合計27箇所で行き来)と本質的に同じ構図(**2領域が同じ状態を異なるUIから触る、実質1つの機能**)が、`team/[id].astro` でも `membersBySlot` を軸に既に発生している。

### 判断: 様子見でよい(今すぐ分割はしない)

理由:
1. **規模がまだ小さい。** スクリプト567行・関数18個は、`box/[id].astro` が並列化不能になった時点(4,546行・124関数)の1/8〜1/7。左右2領域(左パネル3関数・中央3関数)で、`box/[id].astro` の「3領域+共有コア」より単純。
2. **`ui` skillの改善ループがまだ1周も回っていない(講評前)。** どの粒度・どの領域に何件の指摘が来るかが未知数の段階で分割すると、実際の指摘の来方と分割境界が合わない「投機的な分割」になりかねない。まず1〜2ラウンドの実績を見てから判断する方が、分割コストに見合う。
3. 現状の共有コア(10関数)は分割してもさほど複雑にならない規模で、後から `shared-core.ts` に切り出す作業自体のコストは低い(box/[id].astroのような「切り出しにテストの安全網が要る」規模にはまだ達していない)。

### 分割を検討すべき閾値(次にこれを見る)

以下のいずれかに該当したら、次の `ui` ラウンドに入る前に構造分割を検討する。

1. **スクリプト行数が900行を超えたら**(現在567行の約1.5倍。`box/[id].astro` も規模拡大とともに指摘の並列化ニーズが顕在化したため、同じ兆候が出る前に手を打つ)
