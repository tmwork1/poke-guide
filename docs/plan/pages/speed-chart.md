## このページが答える問い

**「今このレギュレーションで、自分の育成中の個体はどのポケモンより先に動けるのか。あと何を変えれば抜けるのか」**

## 参照した資料(P1で実際に開いたもの)

- `docs/ui_proposal/すばやさ早見表.png` — **構造の正**。2列(実数値 / ポケモン)の縦長テーブル。1つの実数値行に複数の「振り方バッジ + 種族値ラベル + 補正ラベル」グループが入り、各グループの下にポケモンのアイコン+名前+補正の出どころ(特性名/技名)が並ぶ。
- `docs/ui_proposal/すばやさライン早見表 シーズンM-2(シングルバトル)|バトルデータベース チャンピオンズ.html` — 他者サイト例。ラベルの語彙(`最速` / `準速` / `120族 2倍` / `110族 S+2` / `123族 こだわりスカーフ`)はここに合わせる。**ただし母集団の絞り方は真似しない**(向こうは使用率TOP100 + 採用率10%以上。こちらはレギュレーション全件)。
- `docs/ui_proposal/個体編集.png` / `個体編集_全体レイアウト.png` / `個体編集_右サイド.png` — 遷移元。左パネルのステータス表(H/A/B/C/D/S × 種族値・努力値スライダー・実数値)のS行が入口になる。

## ユーザー確定仕様(2026-08-01 `AskUserQuestion`)

1. **独立ページ + 個体連携パラメータ**。`/speed-chart?owned=<個体id>` を作り、`/box/[id]` 左パネルのS行から遷移する。行クリックで `PUT /api/owned-pokemon/:id` を叩いて保存し、右カラムの表示を即時更新する。サイドバー「育成」にも項目を追加し、個体を持たずに素の早見表としても開ける。
2. **補正の範囲は「持ち物 + 特性 + ランク上昇技」**(参考サイト相当)。
3. **振り方は 最速 / 準速 / 無振り の3種**。

## スコープ内

### A. 早見表本体(左〜中央)

- **レギュレーション選択**。`REGULATIONS`(`src/lib/regulations.ts`)から選ぶ。既定値は「`?reg=` → 連携個体の `regulation` → `REGULATIONS` の末尾(最新)」の順に決める。**レギュレーション未指定は許さない**(「所属するポケモン」が定義できないため)。選択を変えたらURLの `?reg=` を `history.replaceState` で書き換える。
- **母集団**: そのレギュレーションで使える**全フォルム**。
  - 基礎: `vendor/jpoke/src/jpoke/data/regulation/pokemon.csv` で当該列が `1` の種族(M-A 213件 / M-B 235件)
  - メガシンカ: `autocomplete/mega-stones.json` の `species` のうち、対応する `item` が `regulation/item.csv` の当該列で `1` のもの(M-A 60件 / M-B 76件)。アプリはメガを独立した `species_name` として扱う(`src/lib/box-id/shared-core.ts` の `resolveMegaStoneItem`)ため、表でもメガは1フォルム=1行グループとして扱う。
  - 合計 **M-A 273フォルム / M-B 311フォルム**(P1で実測)
- **振り方(3種)**。チャンピオンズルール(IV=31固定・努力値0〜32・Lv50固定)で計算する。計算式は `src/lib/stats.ts` の `calcOtherStat` を**そのまま使う**(再実装しない)。
  | ラベル | 努力値S | 性格補正 |
  |---|---|---|
  | 最速 | 32 | 1.1 |
  | 準速 | 32 | 1.0 |
  | 無振り | 0 | 1.0 |
- **補正(すばやさ上昇要素)**。すべて jpoke のソースを唯一の出典とし、**アプリ側にポケモン名・技名・特性名をハードコードしない**。
  | 種別 | 対象 | 倍率/段階 | 表示ラベル |
  |---|---|---|---|
  | 持ち物 | こだわりスカーフ | `floor(S * 6144 / 4096)` | `こだわりスカーフ` |
  | 特性(倍率) | かるわざ / すいすい / すなかき / ゆきかき / ようりょくそ / サーフテール | 2倍 | `2倍` + 特性名 |
  | 特性(倍率) | はやあし / こだいかっせい / クォークチャージ | `floor(S * 6144 / 4096)` | `1.5倍` + 特性名 |
  | 特性(ランク) | かそく(+1) / いかりのこうら(+1) / びびり(+1) / ふくつのこころ(+1) / くだけるよろい(+2) / じょうききかん(+6) | `floor(S * (2+n)/2)` | `S+n` + 特性名 |
  | 技(ランク) | +2: からをやぶる / ギアチェンジ / こうそくいどう / みをけずる / ロックカット<br>+1: アクアステップ / おかたづけ / オーラウイング / オーラぐるま / くさわけ / しょうりのまい / スケイルショット / ソウルビート / ちょうのまい / ニトロチャージ / はいすいのじん / りゅうのまい | `floor(S * (2+n)/2)` | `S+n` + 技名 |
  - **その特性/技を実際に持てるフォルムにだけ**付ける(`detail/pokemon.json` の `abilities` / `learnset` で判定)。
  - **確率発動の追加効果は除外する**(あやしいかぜ / ぎんいろのかぜ / げんしのちから の10%上昇)。
  - 補正は**重ねがけしない**(スカーフ+りゅうのまいのような組み合わせは行にしない)。参考サイトと同じ。
  - 下降補正(スロースタート・くろいてっきゅう・まひ)は**出さない**。
- **行の構成**: 実数値の降順。同じ実数値に該当する組み合わせは1行にまとめ、行の中で「振り方 + 種族値ラベル + 補正ラベル」のグループに分ける(PNGの構造)。P1実測で **M-B: 3,024エントリ → 271の実数値行**。
- **ポケモン画像**: `autocomplete/pokemon.json` の `imageId`(`dexNo` ではない)。`src/lib/sprite-urls.ts` の既存ヘルパーを使う。

### B. 「この個体」カラム(右、PNGに無い追加要件)

`?owned=<id>` があり、かつログイン中の本人の個体であるときだけ表示する。

- **その個体で実現可能なすばやさ実数値**を列挙する。組み合わせは以下の直積(重ねがけあり):
  - 性格: S上昇(1.1) / 無補正(1.0) / S下降(0.9)
  - S努力値: 0〜32 の全33段階
  - 持ち物: 現在の持ち物 / こだわりスカーフ(そのレギュレーションで使えるとき)
  - **特性・技によるランク上昇は含めない**(その個体の「素の」到達可能値のみを扱う。ランク補正は戦闘中の一時的な状態であり、保存対象の育成内容ではないため)
- 表の各実数値行に対し、**「その値ちょうどに到達できる最小コストの組み合わせ」**を右カラムに出す。同じ実数値に複数の組み合わせがあるときは **S努力値が最小 → 性格補正が現在値と同じ → 持ち物が現在値と同じ** の順で1つに決める。
- 現在の個体のすばやさ実数値の行には `← 現在` を出す(クリック不可)。
- **クリックで適用**: `PUT /api/owned-pokemon/:id`(**全項目上書き**契約)で、その組み合わせの `nature` / `evs[5]` / `item_name` を書いた**全項目ペイロード**を送る。成功したら右カラムの `← 現在` を移動し、上部の個体サマリ(種族・性格・持ち物・S実数値)を更新する。
- **努力値合計はブロックしない**。チャンピオンズルールの合計上限66は入力制限を持たない仕様(`.claude/skills/jpoke/references/ruleset.md`)なので、超過する場合は**警告表示のみ**を出して適用は通す。
- 適用後に `/box/<id>` へ戻れる導線(トップバーの `backHref`)を残す。

### C. 遷移元(`/box/[id]` 左パネル)

- ステータス表の**S行の実数値セルの隣**に、早見表へのリンク(アイコンボタン)を1つ追加する。`href="/speed-chart?owned=<id>"`。
- **これ以外の `/box/[id]` の変更は禁止**(左パネルは8,500行のうちの1領域。ボタン1個の追加に留める)。

### D. マスターデータ生成の拡張(`scripts/build-master-data/extract_autocomplete.py`)

DBマイグレーションは**不要**。代わりに以下を追加する。

1. `autocomplete/pokemon.json` の各要素に `regulations: string[]` を追加(`jpoke.data.pokedex.POKEDEX[name].regulations`)。
2. `autocomplete/items.json` の各要素に `regulations: string[]` を追加(`jpoke.data.item.ITEMS[name].regulations`)。
3. **新規** `detail/speed-modifiers.json` を出力する。jpoke のハンドラ関数を `inspect.getsource()` して抽出する(P1で実行して動作確認済み):
   ```json
   {
     "items":     { "こだわりスカーフ": { "kind": "multiplier", "numerator": 6144, "denominator": 4096 } },
     "abilities": { "かるわざ": { "kind": "multiplier", "numerator": 2, "denominator": 1 },
                    "かそく":   { "kind": "rank", "stages": 1 } },
     "moves":     { "ロックカット": { "kind": "rank", "stages": 2 } }
   }
   ```
   - ランク上昇の抽出: `modify_stats(...{"spe": +n})` / `modify_attacker_stats(..., stats={"spe": n})` を正規表現で拾い、`n > 0` かつハンドラのソースに `chance|random|確率` を含まないものだけ採用する。
   - 倍率の抽出: `ON_CALC_SPEED` ハンドラのソースから `apply_fixed_modifier(value, N)` と `value *= N` を拾う。**下降(N < 4096 / 除算)は出力しない**。
   - **抽出結果が空になったら生成を失敗させる**(jpokeの実装変更でサイレントに空の表になるのを防ぐ)。

## P1で判断して決めたこと(ユーザーに聞かなかった論点と根拠)

- **母集団に使用率フィルタを入れない** — 要件2が「指定したレギュレーションに属するポケモンのすばやさを一覧できる」なので全件が正。実測で271行に収まり、絞らなくても読める。
- **補正を重ねがけしない** — 参考サイトも重ねていない。重ねると行数が1桁増え、「どの1手で抜けるか」という表の目的がぼやける。
- **右カラムでランク上昇を扱わない** — ランク補正は戦闘中の一時状態で、`owned_pokemon` に保存できる育成内容(性格・努力値・持ち物)ではない。「クリックしたらステータスやアイテムが更新される」という要件4の文面とも整合する。
- **努力値合計66超をブロックしない** — チャンピオンズルールは入力制限を持たない仕様(メモリ/`ruleset.md`)。既存の `/box/[id]` も超過を許して警告のみ出している。
- **ページ自体に認証を要求しない** — 表の中身は公開マスターデータのみで個人情報を含まない。`?owned=` の解決だけが認証を要する。

## 採用した指摘

### R-1 `PUT /api/owned-pokemon/:id` の全項目上書きで、画面が持たない項目が消える(指摘者: データ設計A-1 / 導線A-7)

【問題】`src/lib/owned-pokemon-validation.ts` の `REPLACE_REQUIRED_FIELDS` は `tags` / `memo` / `move_names` / `is_pinned` / `regulation` / `tera_type` / `ivs` を含む全13項目を**必須**とするが、「値がその個体の現在値か」は一切検証しない。`updateOwnedPokemon` もペイロードの列を無条件でUPDATEする。右カラムが `null` / `[]` / `false` のプレースホルダで埋めて送るとバリデーションを素通りし、**個体のメモ・タグ・技が黙って消える**。

【対応】仕様を次のように確定する。

- `index.astro`(SSR)が `getOwnedPokemon()` で取得した **`OwnedPokemonRecord` 全体**を `OwnedPanel` へ渡す。渡し方は `<script type="application/json">` での埋め込み(`ivs` / `evs` / `move_names` / `tags` は配列なので `data-*` 属性化に向かない)。
- `owned-panel.ts` は**必ずそのレコード全体を spread してから** `nature` / `evs` / `item_name` の3項目だけを上書きしてPUTする。
- 受け入れ基準 #20 を追加。

### R-2 補正の抽出は「手作業リスト」ではなく「jpokeの機械走査 + レギュレーション絞り込み」にする(指摘者: データ設計A-2 / プレイヤーA-1)

【問題】P1の対応表は手作業のピックアップだった。Coordinatorが検証したところ、**正規表現の書き方ひとつで両方向に取りこぼす**。

### R-3 `こだいかっせい` / `クォークチャージ` を表から除外する(指摘者: データ設計A-2 / プレイヤーB)

【問題】この2特性の1.5倍は「その個体の実数値(ランク補正込み)が最大の能力**1つだけ**」に乗る(`vendor/jpoke/src/jpoke/handlers/ability_paradox.py` の `_select_paradox_boost_stat` / `modify_speed`)。**種族が持っているかどうかでは決まらず、努力値・性格配分で対象が変わる。** 種族単位で機械的に「1.5倍」行を出すと、実際には乗らない個体まで乗るかのように表示してしまう。

【対応】**この2特性は倍率表から除外する。** 「その特性を持てるフォルムにだけ付ける」という種族単位の判定基準がそもそも成立しない補正だから。

- なお **M-A / M-B にはこの2特性を持つ種族が1件も存在しない**(Coordinator実測。`regulation/pokemon.csv` の所属種族と `detail/pokemon.json` の `abilities` を突き合わせて0件)。よって**今日の表示は1行も変わらない**。将来 jpoke にパラドックス勢を含むレギュレーションが増えたときに誤った行が出ないようにするための予防措置。

### R-4 メガシンカ種族に `こだわりスカーフ` を付けない(指摘者: プレイヤーA-2)

【問題】メガシンカ種族は持ち物がメガストーンに固定されるため、こだわりスカーフを同時に持てない。P1の設計は特性・技については「持てるフォルムにだけ付ける」と書いたのに、**持ち物にだけこの制限を書いていなかった**。早見表本体にありえない行が出るだけでなく、右カラムの「持ち物: 現在の持ち物 / こだわりスカーフ」の直積経由で**ゲーム上ありえない `item_name` をDBに保存してしまう**。

【対応】

- 早見表本体: `autocomplete/mega-stones.json` の `species` に載っている名前には、こだわりスカーフの行を生成しない。
- 右カラム: 連携個体の種族がメガ種族なら、持ち物の軸を「現在の持ち物」のみにする(スカーフを候補に出さない)。
- 受け入れ基準 #21 を追加。

### R-5 ワイヤーフレームのメガの特性名は誤っているので、構造だけを参照する(指摘者: プレイヤーA-3)

【問題】`すばやさ早見表.png` は「メガエアームド / くだけるよろい」「メガサメハダー / かそく」と描いているが、実データでは **メガエアームドの特性は `すじがねいり` のみ**(`くだけるよろい` は進化前エアームドの隠れ特性でメガ後に引き継がれない)、**メガサメハダーは `がんじょうあご` のみ**(`かそく` は無印サメハダー側)。Coordinator実測で確認済み。技ベースの例(メガキラフロル/ロックカット、メガプテラ/りゅうのまい)は `learnset` と一致していて正しかった。

【対応】**ワイヤーフレームは構造・レイアウトの正であり、ポケモン名・特性名の実例は正ではない。** P5の受け入れ検証で「ワイヤーフレームと違うポケモンが出ている」ことを不具合と誤認しない。

### R-6 `?owned=` 付きで開いたら個体の現在地へ自動スクロールする(指摘者: 導線A-3)

【問題】表の総高さは概算で **30〜40画面分**(271行 × 平均11.2エントリ)。ユーザーの導線は「個体編集のS行から来る → まず自分の現在地を見る」なので、開いた瞬間に現在地が画面外だと最初の一歩でつまずく。

【対応】`?owned=` があり右カラムが出るときは、個体の現在のS実数値の行へ初期スクロールする(`scrollIntoView({ block: "center" })`)。受け入れ基準 #22 を追加。

### R-7 右カラムの「到達不可」状態を明示的に描き分ける(指摘者: 導線A-2)

【問題】右カラムの候補は「性格3種 × S努力値33段 × 持ち物2種」の直積だが、丸めで多数が同じ実数値に潰れる。**Coordinator実測で、到達可能な相異なる実数値はドラパルト134通り / ハバタクカミ132通り / カイリュー103通り / ドオー69通り**。271行の**過半数が空欄になる**。空欄が「届かない」のか「読み込み中」なのか「壊れている」のか区別できない。

【対応】右カラムのセルは**3状態を目視で区別できるようにする**。

| 状態 | 表示 |
|---|---|
| 現在値 | `← 現在`(success トークン。クリック不可) |
| 到達可能 | `[ここにする]` ボタン + **内訳**(性格名 / S努力値 / 持ち物)。内訳を出すのは導線A-7「性格を変えると別の能力が下がることが分からないまま確定してしまう」への対応を兼ねる |
| 到達不可 | `−`(muted。ボタンではないことが分かる見た目) |

### R-8 目的の実数値へたどり着く手段を用意する(指摘者: 導線A-4)

【問題】30〜40画面分のスクロールに対し、レギュレーション切替以外のナビゲーション手段が無い。実数値は表中に何度も現れるのでブラウザの Ctrl+F も効かない。

【対応】ツールバーに **(a) 実数値のジャンプ入力**(数値を入れるとその値以上で最も近い行までスクロール)と **(b) 「現在地へ戻る」ボタン**(`?owned=` があるときだけ表示)を置く。ポケモン名での絞り込みはスコープ外(却下R-X5)。

### R-9 記号・略語の目視できる凡例を置く(指摘者: 導線A-5)

【問題】`最速` / `準速` / `無振り` / `120族` / `S+2` / `2倍` の意味が目視で追えない。参考サイトにも凡例は無いが、このアプリは既存ページで H/A/B/C/D/S に `aria-label` でフルネームを残す方針を取っており、今回だけ説明が無いのは一貫性を欠く。`aria-label` はスクリーンリーダー限定で目視ユーザーへの凡例にならない。

【対応】表の上(ツールバー内)に1行の凡例を置く。文言: `最速=S上昇性格+努力値32 / 準速=無補正+努力値32 / 無振り=無補正+努力値0 / N族=すばやさ種族値N / S+n=ランクn段階上昇 / 2倍・1.5倍=特性による倍率`

### R-10 保存失敗時の表示を決める(指摘者: 導線A-6)

【問題】4つの失敗状態のうち「適用の保存失敗」だけが完全に未設計。受け入れ基準13も成功ケースしか見ていない。

【対応】PUT失敗時は (a) エラー文言を右カラム上部に出す(danger トークン)、(b) `← 現在` マーカーを**動かさない**、(c) クリックした候補を再クリックできる状態に戻す。適用成功後もページに留まり、続けて別の行を適用できる(1回で終わりにしない)。受け入れ基準 #23 を追加。

### R-11 `/box/[id]` のS行へのリンク追加は「隣に足す」では実現できない(指摘者: 導線A-8)

【問題】Coordinator実測。`src/components/box-id/LeftPanel.astro` の `.stat-row` と `.stat-table-header` は `grid-template-columns: 6.4rem 2.4rem minmax(0, 1fr) 3.2rem 3.2rem` の**5列固定グリッドをH〜Sの6行すべてで共有**しており、同ファイル617行目に「**`.stat-table-header` と `.stat-row` の `grid-template-columns` は必ず同じ値にすること**」と明記されている。実数値セルの幅は 3.2rem(約51px)しかない。「S行の実数値セルの隣にボタンを1つ足す」は6列目の追加(= 全6行のレイアウト変更)になり、「これ以外の変更は禁止」という前提に抵触する。

【対応】実装方式をここで確定する。**グリッドを一切変更せず、S行の実数値セル(5列目)の内側に `position: relative` を張り、アイコンリンクを `position: absolute` でセルの右外側に重ねる。** 列定義・他5行の見た目は変更しない。この方式で成立しない場合はP4担当がCoordinatorへ報告し、**勝手にグリッドを変更しない**。

### R-12 共有状態に「個体の現在のS実数値」を加え、panel→table の逆方向通知を明示する(指摘者: データ設計A-3)

【問題】P1の共有状態リストは「現在のレギュレーション」「選択中の実数値行」の2つ(いずれも table→panel の一方向)だけで、受け入れ基準12「適用後に `← 現在` マーカーが移動する」に必要な **panel→table の逆方向**の経路が無い。`stack.md` は「共有コアが操作する状態も、どちらの領域が所有するかを設計段階で決める」ことを要求している。

【対応】共有状態を3つにし、所有者と向きを確定する。

| 状態 | 所有者 | 伝達 |
|---|---|---|
| 現在のレギュレーション | `chart-table.ts` | table → panel(`CustomEvent`) |
| 選択中の実数値行 | `chart-table.ts` | table → panel(`CustomEvent`) |
| **個体の現在のS実数値** | **`owned-panel.ts`** | **panel → table(`CustomEvent`)。table はこれを受けて行のハイライトを描き直すだけ** |

`src/lib/box-id/shared-core.ts` の `registerLeftPanelBridge` / `registerDamageCalcBridge` と同じ「登録」パターンでもよいが、**クロージャ共有は禁止**。

### R-13 表と右カラムを2つの独立カラムにせず、1行=横一列にする(指摘者: 導線A-9)

【問題】P1は右カラムを `.panel-right` にする設計だった。1920px幅で試算すると、サイドバー256pxを引いた1664pxのうち右カラム360pxを除いた1304pxの左端に、1080px制約の表が**左寄せ**で置かれるため、**表の右端と右カラムの間に約224pxの空白**ができる。行の高さが100〜400px超とばらつくこの表で、空白を挟んで左右の行を対応づけるのは読み取りコストが高く、さらに「行の高さをどちらが正とするか」という同期問題を持ち込む(= `box/[id]` と同じ轍)。

【対応】**`.panel-right` を使わない。** 1行を「実数値 / ポケモン群 / この個体」の**横一列**として描き、全体を `.panel-content`(1080px)の内側に収める。列幅の目安: 実数値 80px / ポケモン 780px / この個体 220px。

- **ファイル分割(ChartTable / OwnedPanel)は維持する。** `OwnedPanel` は独立したカラムではなく「**1行ぶんの『この個体』セルを描くレンダラ**」として `ChartTable` から呼ばれる形にする。責務の分離(到達可能値の算出・PUT・失敗表示は `owned-panel.ts` が持つ)は変えない。
- これにより行の高さ同期の問題自体が消える(同じ行要素の中の別セルになるため)。導線B「行の高さの同期方式が未定」も同時に解消。
- **P1「レイアウト方針」節の『「この個体」カラムは `.panel-right`』という記述はこれで撤回する。**

### R-14 マスターデータ生成の実装上の落とし穴(指摘者: データ設計B)

【対応】いずれも設計に反映する。

- `POKEDEX[name].regulations` / `ITEMS[name].regulations` は Python の `set` で、`json.dump` は直接シリアライズできない。**`sorted(...)` でリスト化してから書き出す。**
- `item.csv` 未収録のアイテム(270件中122件)は `regulations` が空配列になる。これは「**未対応・未追跡**」であって「非公開」ではない。`extract_autocomplete.py` にこの旨のコメントを残す(将来 `regulations: []` を「使用不可」と早合点した流用を防ぐため)。
- 受け入れ基準の `273` / `311` / `271` は **vendor/jpoke v0.2.0時点の実測値**である旨をテストのコメントに明記する。

### R-15 現行レギュレーションでは1行も出ない補正がある(指摘者: プレイヤーB)

【対応】P5で「表に出ていない = バグ」と誤認しないための申し送り。Coordinator実測で、M-A/M-B のどちらでも**保持フォルムが0件**なのは次のとおり。

- 特性: `いかりのこうら` / `じょうききかん`(+6) / `びびり`
- 技: `オーラウイング` / `ギアチェンジ` / `しょうりのまい` / `みをけずる` / (M-Aのみ)`はいすいのじん`
- 持ち物: `からぶりほけん` / `カムラのみ` / `ビビリだま`(3件ともレギュレーション未収録)

`でんきエンジン` は M-B に `エモンガ` 1件のみ実在する。

## 却下した指摘(理由つき。再提起しないこと)

- **R-X1「パラドックス特性を持つ19種がM-A/M-Bに所属する」(プレイヤーA)** — **事実誤認**。Coordinatorが `regulation/pokemon.csv` の所属種族と `detail/pokemon.json` の `abilities` を突き合わせた結果、M-A・M-Bとも**0件**。指摘の本質(種族単位で決まらない補正である)だけをR-3として採用した。なお同レビュアーが挙げた3種の種族値比較自体は正しかった(例: テツノカイナ 最速S=112 に対し無振りA=160)。
- **R-X2「右カラム専用のワイヤーフレームを描き起こしてからP2に入る」(導線A-1)** — 却下。ページ形態はP1でユーザーと確定済みで、R-7・R-13で右カラムのDOM構造・3状態・列幅まで文章で確定させたため、追加の作図は工程を増やすだけになる。
- **R-X3「適用を取り消せるトースト/確認ダイアログ」(導線A-7後半)** — スコープ外(将来)。`/box/[id]` 自体が確認なしの自動保存で統一されており、この画面だけ確認を挟むと操作モデルが割れる。副作用が見えない問題はR-7の「内訳表示」で対応する。
- **R-X4「補正の条件(天候・地形・被弾など)をツールチップで注記」(導線B / プレイヤーB)** — スコープ外(将来)。参考サイトも条件を出しておらず、ラベルに特性名・技名が併記されている時点で条件は特定できる。R-9の凡例で最低限の説明は満たす。
- **R-X5「ポケモン名での絞り込み」** — スコープ外(将来)。R-8の実数値ジャンプで「目的の行へ辿り着く」課題は満たせる。名前検索は `/search` の責務。
- **R-X6「`items.json` へのフィールド追加でバンドルサイズが増える」(データ設計C)** — 対応不要。`items.json` は15.7KBで、`regulations` 追加の増分は数KB。実装後に実測して問題があればそのとき考える。

## 確定した設計(P4への入力)

### データモデル

**DBマイグレーションは不要。** `owned_pokemon.regulation` は `migrations/013_regulation.sql` で追加済み。新規テーブル・新規列なし。

### マスターデータ生成(`scripts/build-master-data/extract_autocomplete.py`)

1. `autocomplete/pokemon.json` の各要素に `regulations: string[]`(`sorted(POKEDEX[name].regulations)`)
2. `autocomplete/items.json` の各要素に `regulations: string[]`(`sorted(ITEMS[name].regulations)`)
3. 新規 `detail/speed-modifiers.json`。R-2の機械走査で生成。**抽出結果が空、または下限を割ったら生成を失敗させる**(下限: 倍率特性6件以上・ランク上昇技15件以上)

### API

**新規APIは作らない。** 既存の `PUT /api/owned-pokemon/:id` のみを使う(R-1の全項目積み戻しを厳守)。
