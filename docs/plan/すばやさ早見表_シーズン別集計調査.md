# すばやさ早見表(/speed-chart)のシーズン別母集団化 調査メモ

2026-08-22、UI修正依頼「home/すばやさ: フィルタのレギュレーションをシーズンに置き換える」への
対応調査。**別タスクとして分離**し、今回の着手範囲には含めない。このメモは調査結果の記録のみ。

## 依頼の趣旨

`/speed-chart` のフィルタ(現状は `レギュレーション` = M-A/M-B の粒度)を、`シーズン`
(M-1〜M-5等、公式ランキングのシーズン表記)の粒度に置き換える。ユーザー確認により、
見た目のラベル変更だけでなく **母集団(採用率・使用率の集計対象)もシーズン単位で
作り直す** ことが求められている。

## レギュレーションとシーズンの関係(既存のDB設計)

- `season_regulations` テーブル(`migrations/013_regulation.sql`)が `season`(M-1等)→
  `regulation`(M-A等)の対応を1対多で持つ。1レギュレーションに複数シーズンが対応しうる
  (例: M-1・M-2 → M-A、M-3 → M-B)。
- `ranked_teams.season` は元から season 粒度(M-1等)を持つ。
- `owned_pokemon.regulation` / `teams.regulation` は regulation 粒度(M-A等)しか持たない
  (season 列は無い)。

## 「母集団」を構成する3つのデータソースと、season粒度の可否

1. **種族の合法性(チャートに載る行そのもの)**: `public/master-data/autocomplete/pokemon.json`
   の `regulations` フィールド由来(jpoke の `Regulation` Literal)。**regulation 粒度が
   最小単位** ── jpoke 自体がシーズンという概念を持たず、同一レギュレーション内でシーズンが
   変わっても合法ポケモンの集合は変化しない仕様。season 粒度のデータは存在せず、作ることもできない
   (ルール上season粒度で変わるものではない)。
   → **この軸はseason単位に置き換える対象にならない**(そもそも変わらない)。

2. **持ち物/技/性格の採用率(`suggestions` テーブル、`adoptionByRegulation`)**:
   `refresh_popular_builds()`(`migrations/013_regulation.sql`)が集計する。現状は
   `scope`(=`subject_key` の `|` 以降)が **regulation 単位** で固定。season 単位にするには
   この関数を season スコープで回すよう作り直すマイグレーションが要る(`ranked_team_members`
   → `ranked_teams.season` → season_regulations 経由の LEFT JOIN を `regulation` ではなく
   `season` 自体に変える。`owned_pokemon` 側は regulation しか持たないため、
   「season未対応の登録個体をどう扱うか」の仕様判断が追加で必要)。

3. **種族の使用率(`combined_species_usage` RPC, `migrations/021`, `speciesUsageByRegulation`)**:
   同様に regulation 単位の集計。season 単位にするには RPC 側のグルーピングキーを
   `regulation` → `season` へ変更する改修が要る。

## 見積もり所感

「フィルタの選択肢をseason粒度の文言にする」だけならUIのみの変更で済むが、
今回の要求(母集団もseason単位)は **軸2・3のバックエンド集計をseason単位で作り直す
DBマイグレーション + RPC改修 + 再集計(`refresh_popular_builds` 呼び出し)** を伴う。
`/speed-chart` のSSR(`src/pages/speed-chart/index.astro`)・`chart-table.ts` 側の
データ受け渡しもregulationキーからseasonキーへの置き換えが必要で、通常の「UI修正」より
一段大きい変更になる。

`owned_pokemon.regulation` がseason粒度を持たない点(=登録個体をseason別集計にどう
寄与させるか)は、着手前にユーザーと仕様を詰める必要がある。

## 次にやること(このタスクを拾うとき)

1. 上記「owned_pokemon側にseason情報が無い」問題の仕様判断をユーザーと確定させる。
2. `season_regulations` を軸にした集計クエリ・RPC改修の設計(migrationファイルの追加)。
3. `src/pages/speed-chart/index.astro` のSSR取得キーをregulation→seasonへ。
4. `src/lib/speed-chart/chart-table.ts` のフィルタUI・母集団解決ロジック改修。
5. 種族合法性(軸1)はregulation単位のまま据え置く(season選択時も内部的にはそのseasonが
   属するregulationの合法プールを使う)方針で問題ないか確認。
