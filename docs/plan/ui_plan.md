**このセッションで得た重要な運用上の教訓**(`.claude/skills/ui/references/pitfalls.md` にも記載):
- **エージェントの「復元しました」報告は検証の代わりにならない。** ラウンド21でCoordinatorが自分でDBを突き合わせて初めて、個体の性格が復元されていないことを発見した。
- **同じフィクスチャを使うエージェントを並列に走らせない。** 壊し合う。
- **実装者の「直しました」報告は実測の代わりにならない。** PUT全消去バグは1回目の修正が不完全で、Coordinatorが自分でリクエストを投げて初めて `{}` のケースが残っていると分かった。
- **入力欄を直接操作するテストは既存フィクスチャではなく使い捨て個体を使う。** ラウンド23の検証中、Coordinator自身が既存フィクスチャの種族名を直接書き換えて自動保存事故を起こした(直後に復元)。
- **実装が完了しコミットされていても、Coordinatorの実測検証と計画書への記録(Step 5・6)が終わるまでラウンドは「完了」ではない。** セッションがコンテキスト切れで中断すると、この2ステップが抜け落ちたまま次のセッションに引き継がれることがある。次のセッションのStep 0では**索引の日付が最新コミットの日付と一致しているか**も確認するとよい。

**その他:**
- **ユーザー判断待ちが4件**あるので、再開時はまずそれを確認するのが早い(→ round-22.md「実施しない」節)
- 新しい講評から始める場合は、ラウンド16で改訂した観点(→ round-16.md)を使う。**メタレビューはラウンド16以降、実施できていない**(ラウンド17は3レビュアー講評だったが21〜23はユーザー指示/積み残し整理のみで対象が無かった)。**次に3レビュアー講評をするラウンドが終わったら、そのラウンド番号にかかわらずメタレビューを検討すること**(round-17・round-21相当・今回の3ラウンド分が蓄積している)

## 新しいラウンドの追記ルール(持続可能性のための運用ルール)

- **1ラウンド = 1ファイル。** `docs/plan/ui_rounds/round-NN.md` を新規作成し、これまでどおりの書式(優先度A/B/C、実施結果の表など)で書く。**このui_plan.md本体には追記しない。**
- ファイル冒頭は次の2行から始める:
  ```markdown
  # UI改善ラウンド NN

  [← 索引](../ui_plan.md)
  ```
- 記録したら、上の「ラウンド履歴」表に1行追加し、「現在の状態」を最新の内容に書き換える。
- 複数ラウンドにまたがる内容(例: 「ラウンド6〜7の実施結果」)は、**その内容が指す最後のラウンド番号のファイル**に書く(この例では round-07.md)。
- 3ラウンドに1回のメタレビュー(SKILL.md Step 7)は、直近3ラウンドの `round-*.md` を直接読ませればよく、行範囲の指定は不要。
