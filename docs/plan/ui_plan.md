# UI 改修プラン

## ページ構成
3ページ構成

1. ホーム：サイトの入り口。DBの統計情報などを表示する。
2. ポケモン育成登録：battle-assistant の移植。パラメータ調整とダメージ計算を同時に表示する。
3. チーム登録：登録したポケモンで6匹チームを作成する。


## 開発の流れ
ホーム、チーム登録は後回し

育成登録は、まずbattle-assistantのポケモン管理をまるごと移植してから細かく調整する。

## レイアウト原則: カードとパネル

アプリ全体で「カード」「パネル」という語をどう使い分けるかの命名規約。**以下がこの節の確定済み現行仕様**(2026-07-26 帯構成+共通トップバー導入により全面差し替え。変遷の経緯は本節末尾の「変更履歴」を参照)。以下より後ろのラウンドログには、この現行仕様に至る前の前提で書かれた記述が残っている箇所があるが、内容が食い違う場合は常にこの節が優先する。

### 役割は2つ

- **カード** = 可算・追加削除できるコレクション要素
  - 該当: ポケモンカード(ボックス一覧)、ダメージ計算カード(個体編集)、将来のチームカード
  - クラス: `.card` + 用途別修飾子(`.card-pokemon` / `.card-damage`)
  - 視覚仕様: `--color-surface-alt` / `1px solid --color-border` / `--radius-md` / `--space-3` / `--shadow-sm`、hover で `--shadow-md` + `translateY(-2px)`、選択中は `.is-selected` で `border-color: --color-primary`
  - **浮いた箱**であることがカードの本質

- **パネル** = 画面端まで伸びる帯
  - 該当: 育成情報バー(左端)、詳細設定サイドバー(右端)、トップバー(上端)、ボックスのツールバー、検索結果・種族値表などの本文領域
  - クラス: `.panel` + 接する辺の修飾子
  - 視覚仕様: `--color-surface` / **角丸なし** / **外側marginなし** / `padding: --space-6 --space-5` / border は既定ゼロ
  - 罫線の修飾子: `.panel-left`(左端固定・`border-right`) / `.panel-right`(右端固定・`border-left`) / `.panel-top`(上端固定・`border-bottom`)
  - 縦に積んだ帯の継ぎ目: `.panel + .panel { border-top }`
  - 帯の中身の可読幅: `.panel-content { max-width: 1080px }`(`margin: 0 auto` を付けず**左寄せ**)

### `.panel-content` の使い分け(ユーザー確定仕様)
- **全幅にする(`.panel-content` を使わない)**: トップバー、ボックスのツールバー、カードグリッド
- **1080pxに押さえる(`.panel-content` を使う)**: 検索結果・注目枠、種族値表・特性・進化前・技一覧、共有ページの各項目
- 理由: 1920px幅で技一覧や本文の1行が長くなりすぎて読めなくなるため。操作系は全幅、読む対象は可読幅、という切り分け。

### 共通トップバー(`AppLayout`)
- `AppLayout.astro` が全ページ共通のトップバーを描画する。サイドバーの右隣から画面右端まで伸びる帯。
- `position: sticky; top: 0` で上端固定。z-index は 20(サイドバー30・オーバーレイ25・ダメージ詳細パネル60 より下で、被って操作を妨げない)。
- 高さは `:root` の CSS変数 `--topbar-height`(デスクトップ 65px / モバイル2段 129px)で公開する。左右の帯が `calc(100vh - var(--topbar-height))` で参照する。
- 中身: 左に「← 戻る」+ページタイトル+状態表示、右にページ固有操作+アカウント情報。
- ページ側のインターフェース:
  - props: `title`(トップバー見出しと `<title>` タグ兼用。`<title>` には「 | Poke-Commons」が自動付加される) / `backHref`(指定時のみ戻るリンク表示) / `backLabel`(既定「戻る」)
  - スロット: `topbar-status`(タイトル右の状態表示) / `topbar-actions`(右側の操作)
- アカウント情報は `AppLayout` が `Astro.locals.user` から自前で描画するのでページ側は不要。
- モバイル(900px未満)は2段。1段目=ハンバーガー+サイト名+アカウント、2段目=ページタイトル+操作。

### 「タイル」という語を使わない理由
tile は業界通念上「反復するグリッド項目」(Windows のライブタイル、Material の GridTile / ListTile)を指し、それは本プロジェクトの「カード」に当たる。領域の呼称に使うと意味が反転するため使わない。なおクラス名 `.add-card-tile`(カード追加枠)は**グリッド項目**なのでこの通念に沿っており維持する。

### 無効化したもの
- `.page` の中央寄せ(`max-width` / `margin: 0 auto` / 左右padding)を撤去した。帯が画面端まで届くようにするため。
- `.page-narrow` / `.page-wide` は空ルールに無害化した。参照が消えたら削除する。
- `box/[id].astro` の CSS変数保持セレクタは `.page-wide` から `.edit-shell` に付け替え済み。
- `.card-interactive` は廃止し、hover の浮き・影を `.card` 本体に統合した。

### 検証済みの事実
- `npm run build` 成功、ユニットテスト 199/199 パス。
- 1920px / 1280px で Playwright スクリーンショット実測。
- 個体編集ページで左右の帯がトップバー直下から画面下端まで途切れず伸びることを確認。

### 変更履歴
この節は次の3世代を経て現行仕様に至った。将来「なぜこうなっているのか」を追うための記録として残す。

1. **1世代目(2026-07-24頃 確定・現在は誤り)**: パネル = 角丸12px + 全周border + padding 24px の「囲み箱」。カードとの違いは色味と影の有無だけで、両方とも「浮いた箱」という形状は共通だった。
2. **2世代目(帯への再定義)**: ユーザーから「パネルはページの上下端もしくは左右端まで伸びている帯を期待していた」という指摘があり、パネルを**画面端まで伸びる帯**に再定義した。角丸・外側margin・影を撤去し、`.panel-left` / `.panel-right` / `.panel-top` の辺別修飾子と、本文の可読幅を絞る `.panel-content` を新設。`.page` の中央寄せは帯を妨げるため撤去した。この指摘が本節の設計そのものを覆す転換点であり、以降の実装はすべて帯を前提にしている。
3. **3世代目(現在。共通トップバーの新設)**: 帯構成にした結果、個体編集ページで左右の帯の上端がページ固有ヘッダーの高さに揺さぶられ、上側が途切れて見える問題が起きた。左右の帯が画面上端から一貫して始まるよう、全ページ共通の `AppLayout` にトップバー(帯)を新設し、`--topbar-height` を介して左右の帯の高さ計算をトップバーに固定した。

### 実装済みの反映(2026-07-26。`npm run build` 成功・ユニットテスト199/199 pass)
- `global.css`: 旧 `.card`(実体はパネル用途だった)→ `.panel` に改名。新規に上記原則の `.card` を定義。`.card-interactive` は廃止し、hoverの浮き上がり・影を `.card` 本体に統合。選択状態は `.card.is-selected`。`--shadow-lg` をライト/ダーク両方に定義。ブレークポイント 900 / 1200 / 1600px の意味をファイル冒頭コメントに明記した。
- `box/index.astro`: `.pokemon-card` → `card card-pokemon`。ツールバーは `panel panel-top panel-toolbar`。ピン留め状態は `.is-pinned`(`--color-risky`)で、選択状態 `.is-selected`(`--color-primary`)とは別の意味論として区別する。カードグリッド自体は `.panel-content` を使わず画面幅いっぱいに広げる。
- `box/[id].astro`: `.damage-row` → `card card-damage`。外側カードが `--color-surface-alt` になったため、内側の `.damage-row-build` / `.damage-column` は `--color-surface` に変更(設計図どおり「外が濃く内が明るい」の階調)。左右の編集フォーム・詳細設定サイドバーは `.panel panel-left` / `.panel panel-right`。CSS変数保持セレクタは `.edit-shell` に付け替え済み。
- `search/index.astro` / `pokemon/[name].astro` / `moves/[name].astro` / `share/[slug].astro` / `damage-calc/index.astro` / `damage-calc-poc/index.astro`: `class="card"` → `class="panel"`(いずれも1画面1骨格領域の用途のため)、可読幅が必要な本文には `.panel-content` を使用。
- `.add-card-tile` は維持(グリッド項目=カード追加枠として上記の「タイル」通念に適合するため)。

### 既知の課題への対応(2026-07-26)
- `/damage-calc` は単一固定フォーム(行の追加削除なし)でカード原則の例外だったうえ、`box/[id].astro` のダメージ計算(相手カード×技列を追加削除できる2段階UI)が機能的に上位互換だったため、`/box` への302リダイレクトにして廃止した(URLブックマーク対策としてファイル自体は残し、中身のみリダイレクト化)。
- 唯一の依存だった `share/[slug]` の「この育成でダメージ計算する」CTA(`/damage-calc?share=<slug>` 遷移、未ログインの第三者が使える唯一の計算導線)は、**未ログイン第三者向けの計算導線を失うことを承知の上でCTAごと削除して統合する、というユーザー判断**によりCTAごと削除した。この経緯は将来同種の判断をする際の材料として残す。結果、`share/[slug]` は閲覧専用ページになった。
- `AppSidebar` の「アプリ」セクション(「ダメージ計算」のみが所属)を削除し、`current` の型からも `"damage-calc"` を除去した。

## 決定事項・進捗(2026-07-25 カード刷新・計算エンジン拡張)

参照ワイヤーフレーム: `docs/ui_proposal/Box.png`, `Pokemon.png`, `battle_assistant.jpg`

### ボックス一覧のカード
- カードは `<a>` 全体をクリック可能にし、「編集」ボタンは廃止。ピン留め/削除はカード右上のアイコンボタン1つずつで表現(クリック時は `preventDefault`+`stopPropagation` でカードの遷移を止める)。
- 公式絵を主役にし、テラスタイプ画像を左下・持ち物画像を右下に重ねる。テラス画像は横長バナーなので**右上に置くと右上のアイコンと衝突する**ため左下に固定。
- 種族名は書かずニックネームのみ表示(種族は公式絵で伝わる)。ニックネーム未設定時のみ種族名にフォールバック。「最終更新」の表示は廃止。

### 個体編集画面(左パネル)
- 「図鑑で見る」を廃止。`src/lib/owned-pokemon-form.ts` の `pokemonDetailHref`/`toPokemonPathSegment` も呼び出し元が無くなったため削除した(同等処理は `src/lib/pokemon-slug.ts` にある)。
- ラベル要素を廃止し placeholder + `aria-label` に統一。入力欄は2列グリッドに詰め、値が長い「種族」「特性」だけ1行を使い切る(`.field-span-all`)。
- 「その他の設定(レベル・タグ・ピン留め・共有)」は `<details>` で既定折りたたみ。
- 縦1080に収める目的の実測値: 左パネル高さ **816px**(折りたたみ時)、下端Y=951px @1440x1080。

### ダメージ計算カード(右カラム)
- 「対戦相手メモ」を「ダメージ計算」に刷新。**1行=1体の相手**で、行を縦に積むと独立した並列計算、**行の中で列を横に連結すると加算ダメージ計算**(最大6列)。
- 相手ビルド(種族・性格・特性・持ち物・テラス・努力値6+実数値)はカード上で直接入力。天候・地形・壁・急所・ランク補正・状態異常・テラスタル発動・乱数シードは行ごとの `<dialog>`(⚙詳細)に集約。
- 計算・保存はどちらも自動(デバウンス600ms/1000ms)。「計算する」「保存」ボタンは無い。相手ポケモン名が非空になった時点で初めて `POST /api/opponent-notes`。
- **制約**: 場・ランク・状態異常・テラスタル・急所は jpoke の `calc_lethal` が単一のバトル状態で動くため**攻撃列全体で共通**。列ごとに変えられるのは技名と連続回数のみ。
- 判定チップは「その列までを当てた時点の累計致死率」。前の攻撃で既に確殺している列は `N発目で撃破済`(`確1` を引き継ぐと「この技単体で確1」と誤読されるため)。累計致死率0%なら `未撃破` とし、2列目以降は累計ダメージ量を併記する。
- 保存は既存 jsonb 列の拡張のみでマイグレーション不要。`field.attacks[]`(最大6件)+ `attackerBoosts`/`defenderBoosts`/`*Ailment`/`*Terastallized` を追加。`attacks` を持たない旧メモは1列に変換して表示する。`move_name`(トップレベル列)には `attacks[0].moveName` を必ず入れる(空だと匿名化二次記録がスキップされる既存仕様のため)。

### 計算エンジン(`src/lib/pyodide-engine.ts`)の拡張
`PokemonSpec` に `boosts` / `ailment` / `terastallized`、`CalcDamagesOptions` に `hitCount` を追加し、複数技の累計致死率を返す `calcLethalSequence()` を新設した。
- **既存バグの解消**: これまで `teraType` は `Pokemon.tera_type`(候補タイプ)を設定するだけで `terastallize()` が呼ばれず、**テラスタイプを選んでもダメージに一切反映されていなかった**(`/damage-calc` も同様)。
- jpoke は `teraType` 省略時に自身の第1タイプを自動設定するため、`terastallized: true` だけで常に発動する。
- ステルスロック等の設置技は `calc_damages` では `ON_SWITCH_IN` が発火せず**効果ゼロ**なので、UIには置かない(置くと嘘の結果になる)。
- ブラウザ実測での検証値(ウーラオス(いちげき) インファイト → ディンルー): 基準 282〜332 / 相手の防御ランク+2 → 140〜168 / 自分の攻撃ランク+2 → 560〜660 / 急所固定 → 422〜498 / リフレクター → 141〜166 / 攻撃側やけど(あんこくきょうだ) → 半減 / かくとうテラス発動 → 282〜332 → 376〜444(STAB 1.5→2.0)。

`npx astro build` / `npm test`(123件)は全てpass済み。

## 決定事項・進捗(2026-07-25 第2弾: カード情報の再配置・画像フォルム対応)

### 全体: 特殊フォルムのポケモン画像
`public/master-data/autocomplete/pokemon.json` の各レコードに **`imageId`(PokeAPIの画像ID)** を追加した。従来は `dexNo`(全国図鑑番号)で画像URLを組んでいたため、メガシンカ・キョダイマックス・リージョンフォームがすべてベース種族の画像になっていた。
- 解決元は `vendor/jpoke/src/jpoke/data/pokeapi/ja_to_id_map.json` の `sections.pokemon.by_ja_name`(日本語フォルム名→PokeAPI ID)。ビルド時のネットワークアクセスは不要。
- `dexNo` は「本来の全国図鑑番号」の意味のまま残し、画像用途だけ `imageId` に切り替えた(`loadDexNoMap` → `loadImageIdMap` に改名)。
- 実測: 1290件中237件が専用画像IDに解決(例 メガリザードンX=10034、メガフシギバナ=10033、リザードン(キョダイ)=10196)。

### ボックス一覧のカード
上下2ブロック構成にした。**上半分**=公式絵・ピン留めスター・削除アイコン(テラスタイプ画像は公式絵の左下)。**下半分**(区切り線で分離)=ニックネーム / 持ち物(小アイコン+名前) / 技一覧 / 努力値H〜Sの6列グリッド。
- レベル・性格・特性・タグはカードから外した(検索とタグ絞り込みのロジックは従来どおり動く)。
- 持ち物画像は公式絵への重ね表示をやめ、下半分の持ち物行へ移した。

### 個体編集画面(左パネル)
- ニックネーム・性格・特性はそれぞれ1行を使い切る(種族と同じ扱い)。
- **「その他の設定(レベル・タグ・ピン留め・共有)」はセクションごと削除**。ただし `PUT /api/owned-pokemon/:id` は全項目上書きの契約なので、SSRで読んだ値を `#edit-form` の `data-level` / `data-tags` / `data-pinned` に埋め込み、自動保存のペイロードに載せ直して既存値を保全している(消してはいけない)。
  - 副作用: 公開共有トグル(`PUT /api/owned-pokemon/:id/share`)とタグ入力のUIが無くなった。APIと `/share/[slug]` は残っているので、UIを戻す場合は git 履歴の該当箇所を参照する。レベルはチャンピオンズが常にLv.50なので実害なし。
- 努力値バーは行の余剰スペースいっぱいに伸ばす(global.css の `width: 5.5em` を打ち消し、数値入力だけ固定幅)。
- 空いた縦スペースはメモ欄が吸収する(デスクトップのみ、カードを縦フレックスにして `min-height: calc(100vh - 200px)`)。
- 実測: 左パネル高さ900px・下端Y=1035px @1440x1080、メモ欄165px。

### ダメージ計算カード

### 加算ダメージ計算(累計致死率)の実装方針変更
当初は jpoke の `Battle.calc_lethal()` に攻撃列を `(技, ヒット数)` のリストで渡す方針だったが、**実装してブラウザで実測したところ機能しないことが判明したため、`calcLethalSequence()` は自前でHP分布を維持する方式に変更した。**
- 原因: `jpoke/core/lethal.py` の `_lethal_loop` は `fainted()`(=`any()` 判定)で「HP分布に1つでもHP=0の分岐が現れた」時点で計算全体を打ち切る。1発目で一部の乱数だけが致死する組み合わせ(例: 25%)では、生存している残り75%の分岐に対してすら2発目以降が計算されず、`lethal` が1件しか返らない(多段技では0件になる)。
- 変更後: `jpoke.utils.lethal_dist` の分布演算(`to_dist`/`subtract_dist`)でHP分布を関数側で維持し、打ち切りは「全分岐でHP=0(確率100%)」に限定する。
- **トレードオフ(既知の制約)**: `calc_lethal()` が内部で行うターン終了時処理(たべのこし回復、どく/やけどの継続ダメージ)と追加効果系ハンドラ(がんじょう・きあいのタスキ等)は加算計算に反映されない。単発の `calcDamages()` も従来からこれらを考慮していない(`Battle.calc_damages()` が1発分の乱数計算しか行わないため)ので、既存の精度レベルに揃えた形。
- 実測(ハバタクカミ→ディンルー、ムーンフォース、seed=1、相手HP230): 単発 `乱1 25.0%` / 3連 `attackCount 1→0.25, 2→1.0` で確定2発・3列目は「2発目で撃破済」/ 連続回数3の単発は `確1`。単発 `calcDamages` の値は変更前と一致(回帰なし)。

### JSテンプレートリテラルの注意
`src/lib/pyodide-engine.ts` の `BOOTSTRAP_PYTHON` はJSのテンプレートリテラルなので、**中でバッククォートを使ってはいけない**。Pythonのdocstring内であっても文字列がそこで終端し、以降のPythonコードがTypeScriptとしてパースされて `[PARSE_ERROR] Expected a semicolon ...` でビルドが落ちる(実際に踏んだ)。Python側でコメント中に識別子を引用したいときはシングルクォートか「」を使う。`${...}` も同じ理由で書かない。

## 決定事項・進捗(2026-07-25 第3弾: DamageCard.png に沿ったダメージ計算カードの再構成)

`docs/ui_proposal/DamageCard.png`(battle_assistant.jpg と同じ構造)を正として、1枚のカードの中身と配置を作り直した。

### カードの構造
1枚のカード = **相手ビルドの箱** + **技列の箱 × N** + **加算条件追加ボタン(＋)**。両方の箱は同じ枠線・背景で、`align-items: stretch` により同じ高さに揃え、下端の区切り線+結果表示の位置を合わせる。

| 箱 | 上から | 最下段(区切り線の下) |
| --- | --- | --- |
| 相手ビルド(320px) | 攻守切り替えボタン+⚙+🗑 / 相手種族名+アイコン(名前の右) / 性格 / 特性 / アイテム / テラスタイプ / 努力値HABCDS / 実数値HABCDS | **加算後のダメ・致死率**(全技列の合計) |
| 技列(190px) | 技名 / 連続回数 / (空きスペース=今後「計算の細かい条件」を置く場所) | **技ごとのダメ・致死率** |

- 特性・アイテム・テラスタイプは図のとおり1項目1行の縦積みにした(以前は2列グリッド)。
- **性格は図に無いが残した**: 実数値の計算に必要で、これを外すと実数値行が正しく出せない。
- 努力値/実数値は「行ラベル1列 + H/A/B/C/D/Sの6列」の7列グリッド。DOMは行優先(見出し7セル→努力値7セル→実数値7セル)で生成すること。
- 「+ ダメージ計算を追加」タイルは図の「ダメージ計算追加ボタン」で、カードの外・下側に置く。
- 実測: 1枚あたり280px @1920x1080。第2弾の「1行149px」目安は図の構成(実数値・加算後結果が縦に積まれる)により撤回した。

### 結果表示の分担(重要)
- **技列 = その技だけを繰り返した場合の独立した判定**。エンジンが返す `lethal` は「攻撃列を先頭から順に当てた累計」なので列単体の値には使えない。列の1発分ダメージ(`perAttackDamages[i]`)から、エンジンと同じ分布演算(`subtract_dist(minimum=0)` 相当)をTS側で回して「何発で倒れるか」を求めている(上限10発、超えたら「10発以上」)。battle_assistant.jpg でも各列は独立した計算結果を表示している。
- **相手ビルドの箱 = 加算後(全列合計)**。累計ダメージと、最初に致死率が0を超える位置の判定。そこがまだ確殺でなければ確殺到達位置を「→確N」として併記する(例: `累計408〜480 (177〜209%) 乱1 (25.0%) →確2`)。
- 確率は小数第1位まで丸めるが、`0.0%` / `100.0%` になる場合は `<0.1%` / `>99.9%` と表示する(確率0・確殺と見分けが付かなくなるため)。

### 攻守切り替え(新機能)
1枚のカードにつき「この個体が攻撃」⇄「この個体が受け」を切り替えられるようにした。保存先は既存の `field` jsonb に追加した `direction: 'attack' | 'defense'`(**マイグレーション追加なし**。未指定の既存メモは `attack` として解釈)。
- `field.attackerBoosts` / `attackerAilment` / `attackerTerastallized`(と `defender*`)は「**攻撃側/防御側という役割**に対する値」であり、`direction` によってどちらが所持ポケモンかが入れ替わる。`attacker*` を「常に所持ポケモン」と読んではいけない。
- 相手が攻撃側になるとき、相手のspecに `moveNames` は積まない。`pyodide-engine.ts` の `_resolve_move()` が技リストに無い技名から `Move` を新規生成するため計算できる。
- 向きに追随して言い換える表示: 技列のplaceholder(「技」⇄「相手の技」)、詳細ダイアログの見出し(「攻撃側(この個体)」⇄「攻撃側(相手)」)、壁のラベル(「相手側の壁」⇄「自分側の壁」)。ダイアログは `row.dialogEl` にキャッシュされるので、切り替え時に破棄して作り直す。
- `direction` は `opponent-note-anonymize.ts` のホワイトリストには**入れていない**(匿名化された二次記録には不要。ホワイトリスト方式なので未知キーは黙って落ちる)。

### カードを「ダメージ計算ウィンドウ」に入れない
battle-assistant 同様、カードを囲む `.card` パネルと「ダメージ計算」見出し・説明文を廃止し、ページ直下にカードを直接並べる(`#opponent-notes-section` は `<style is:global>` のスコープ接頭辞とJSの初期化ガードが参照しているのでIDだけ残す)。エンジン初期化状況の1行は準備完了後に `hidden` で隠す。

> **この時点(第3弾)の方針であることに注意。** 当時の `.card` は現在の「パネル」(枠+影なしの骨格領域)に相当し、それを廃止する記述だった。その後、冒頭の「レイアウト原則: カードとパネル」の確定により、ダメージ計算カード自体が可算のコレクション要素としての `.card`(`--color-surface-alt` の枠 + `--shadow-sm` の影、hoverで浮き上がる)を持つようになっており、この記述と現在の実装は食い違っている。囲みと見出しを廃止する判断自体は維持しつつ、枠・影の有無については冒頭の原則が優先する。

### 横幅まわり(実測して直した箇所)
- このページだけ `.page` の既定(1080px)を `.page-wide { max-width: 1700px }` で広げた。1080pxでは技列が1つしか見えず加算ダメージ計算が使えない。**この時点の方針であることに注意。** 現在は帯構成への移行により `.page` の中央寄せ自体を撤去し `.page-wide` は空ルールに無害化済み(冒頭の原則を参照)。このページの横幅確保は現在 `.edit-shell` が担う。
- `.edit-layout` の2カラム化の閾値を **900px → 1200px** に上げた。左の編集フォームは能力値行の都合で最小幅が実測736pxあり、`minmax(320px, 480px)` でも左トラックがそこまで膨らんで右カラムが226pxに潰れ、ページ全体が横スクロールしていた。左パネルを `min-height: calc(100vh - 200px)` にするメディアクエリも同じ閾値に揃えること。
- カードが狭いときは相手ビルドの箱を技列の上に積む。判定は**ビューポート幅ではなくカード自身の幅**(`.damage-row-body` の `container-type: inline-size` + `@container (max-width: 744px)`)。サイドナビ256pxと2カラム/縦積みの切り替えが噛み合って「ビューポートが広い方がカードが狭い」領域(1200〜1590px)が存在するため、メディアクエリでは条件を書けない。
- **`@container` は詳細度を上げない**。`.damage-row-build` の基本定義より後ろに書かないと、同詳細度の後続ルールに `flex`/`width` を上書きされて何も起きない(実測で踏んだ)。
- 技列の箱を相手ビルドの箱と同じ高さにするには `.damage-row-columns { min-height: 100% }` が必要(親の `wrap` は stretch で伸びるが、その中のflexコンテナは高さautoのままなので `align-items: stretch` が中身の高さまでしか効かない)。横スクロールバー用の余白は `.damage-row-columns-wrap` ではなく共通の親 `.damage-row-body` に付ける(wrap側に付けると技列だけ数px低くなって下端が揃わない)。
- 検証: 1920/1440/1280/1024/900/700/390px の全幅でページ全体の横スクロールなし、努力値入力のはみ出しなし、＋ボタンは常に可視(6列で `disabled`)。`npx astro build` Complete! / `npm test` 142件pass。

## ラウンド6の計画(2026-07-26 密度の回復)

### 背景と判断
ラウンド5で「技列の空きスペースが目立つ」というユーザー指示に応え、相手ビルドを上段全幅・技列を下段に置く2段組へ作り直した。空きは解消したが、**カード1枚が 303px → 395〜446px に増え、1画面に2枚強しか入らなくなった**(ラウンド3では3枚が1080px内)。「複数体を並べて同時に見る」がこの画面の目的なので後退である。

さらに実測すると、**空きスペースは消えたのではなく移動している**。技列が1つだけのカードでは、下段の「＋」の右側に大きな余白が残る(上段が全幅になったぶん、下段の空白が横方向に伸びた)。

**判断: 横並び構成には戻さない**(戻すと元の空きスペース問題が再発する)。代わりに**上段(相手ビルド)を横方向に詰めて高さを削り**、下段の余白も同時に解消する。密度と余白の両方を解ける方向であり、ユーザー指示のどちらとも矛盾しない。

### やること
1. **上段を1〜2行に圧縮する。** 現在は「相手名+アイコン」「特性/持ち物/テラス(3列)」「努力値/実数値グリッド(2行)」「累計結果チップ」が縦に積まれている。上段は全幅780px近くあるので、**特性/持ち物/テラスを努力値・実数値グリッドと同じ行に横並びで載せる**等で行数を減らす。
2. **下段の余白を使う。** 技列が少ないときに「＋」の右へ余白が伸びる問題を解消する。技列を余白いっぱいに広げる、または上段の要素を下段の空きへ回すなど。
3. **目標: カード1枚 300px以下、3枚が1080px以内。** 実測して報告すること。
4. **フォントサイズを下げて高さを稼がないこと。** ラウンド3の教訓(真因は `min-height` の取りこぼしであってタイポグラフィではなかった)を踏襲する。まず高さの内訳を計算で分解してから削る。

### 壊してはいけないもの(ラウンド5で入れたばかり)
右サイドバーの3カラム構成と選択状態 / 天候・フィールドのアイコン選択 / 壁の単一トグルと物理特殊の自動判定 / 能力ランクの攻守1つずつと後方互換 / ▲▼による性格切替 / 残りポイント表示 / 結果チップの主役化(`確N` を先頭に太字) / タイプアイコンの円形画像 / placeholder方式 / 技列6個での横スクロール無し。

> **この計画は、この形では実行されなかった。** 計画策定後、ユーザーから `docs/ui_proposal/ダメージ計算カード.png`(⚙ボタン廃止・技列縦積み・各技列にON表示、を反映した更新版)が示され、密度回復の手段そのものが「上段(相手ビルドの箱)の圧縮」ではなく「対話設計の作り直し」に変わった。実際に行われた変更はコード上「ラウンド6ユーザー指示」「ラウンド7ユーザー指示(方針転換)」として記録されており、内容は次節「ラウンド6〜7の実施結果」を参照。結果として**カードの高さは相手ビルド302px/技列313pxまで縮み、この計画が掲げた「カード1枚300px以下・3枚が1080px以内」という目標はほぼ達成された**(技列側が313pxで僅かに超過)。達成手段(技列の縦積み・カード全体設定の廃止による技列側の情報量減少)は、この計画時点で想定していた「上段を1〜2行に圧縮する」とは異なる。

## ラウンド8の指摘(2026-07-26 opusアドバイザー講評: `/box/[id]` + `/box`)

カード3枚(技列3つ/2つ/1つ)の実使用状態を1920×1080で実測して得た指摘。**A-5 はメインエージェント側でも独立に真因まで再現確認済み**(computed style を実測)。

### 総括: 残っている問題は3種類

1. **高さの内訳がまだ最適化されていない**(`scrollHeight` 1205px、3枚が1画面に入らない)。主因は「相手ビルド箱の名前行が公式絵72pxで1行まるごと占有していること」と「押せない破線ボックス48px」。**ここを直すと相手アイコンを拡大しながら同時に高さが縮む**(ユーザーの2大要望が両立する)。
2. **ライトモードのコントラストがまた同じ形で落ちている。** ラウンド3で結果チップを直したが、今度は `--color-text-muted` on `--color-surface-alt` が **4.26:1** でAA割れ。ダークは5.89:1で問題なし。**「ライトだけ落ちる」というこのプロジェクト固有の再発パターン。**
3. **幅390pxの破綻は装飾の問題ではなく、Astro scoped style の詳細度バグ**(`.card-item-badge` / `.damage-row-footer` に続く**3例目**)。

### 実測した高さの内訳(1920×1080、カード3枚)

| | 現在 | A-1〜A-3適用後(見積) |
|---|---|---|
| カード1(技列3) | 380 | **329** |
| カード2(技列2) | 319 | **302** |
| カード3(技列1) | 319 | **272** |
| カード計+gap | 1034 | **919** |
| ページ `scrollHeight` | **1205** | **約1090** |

`.damage-row-build` は300×**302pxで3枚とも固定**。`.damage-row-columns-wrap` は 316/249/**125px** と内容で伸縮する。**つまりカード高さを決めているのは常に相手ビルド箱**であり、技列が1つのカードでは右カラムに約190pxの空白が残る。ユーザーが2度指摘した「技列側の空きスペース」は、技列が多いケースでのみ解消していた。

### 優先度A(必ず直す)

- **A-1 相手ビルド箱の名前行が公式絵72pxで1行を占有している** → 再構成で **−43px/枚**、同時に相手アイコンを **72→96px** に拡大できる。
  【問題】相手名 input(29px)の右に72pxの公式絵が置かれ、特性・持ち物・テラスの3入力はその**下**から始まっている。名前行の高さは72pxで、inputとの差 **43pxが純粋な空気**。名前行72.0 + 特性/持ち物/テラス3行67.8 = **142.2px** が `.damage-row-build` 302px の47%を占める。**「相手アイコンが小さい」と「技列側の空白」は同じ1箇所が原因。**
  【提案】スプライトを名前行から出し、「名前input+3入力」の縦スタックと**横に並べる**。左スタック 29+2.4+67.8=**99.2px**、右のスプライトは99.2pxまでタダで伸ばせるので **96px箱 / 88px画像**にする(現在72/64、**+33%**)。
  - JS `renderRow` 内で `nameRow` と `selectsRow` を新設 `.damage-row-build-fields`(縦flex)にまとめ、それと `spriteBox` を新設 `.damage-row-build-main`(横flex)に入れる。`nameRow.appendChild(spriteBox)` は `buildMain.appendChild(spriteBox)` に変える。
  - `.pokemon-name-row` / `.damage-row-build` / `.damage-row-body` は**改名も削除もしない**(親が変わるだけ)。新設2クラスは保護リスト外。
  - `.damage-sprite-box` 72→96px、`img.sprite-icon` 64→88px。**JS側の `width`/`height` 属性と `spriteFallback.style.cssText` も必ず追随させること**(CSSだけ変えると食い違う)。
  - 幅の検算: 箱の内寸 300−padding19.2−border2 = 278.8px。96+gap6 を引いて入力欄は **176.8px** 残る。「わざわいのうつわ」(約97px)+padding≒106pxなので12字でも収まる。既存の `overflow:hidden / text-overflow: ellipsis / title` は維持。
  - **併せて `.damage-item-badge`**(現在 `bottom:-6px; left:-6px` でスプライト箱の左下=名前inputとの継ぎ目に浮いている)を `bottom:-4px; right:-4px` に移し、`/box` の `.card-item-badge` と同じ 22px円形+`1px solid var(--color-border)`+`var(--shadow-sm)` に揃える。テラスバッジは右上なので衝突しない。

- **A-2 「技列は最大3つまでです」の破線ボックスが48px居座り、コントラスト1.68:1で読めない** → 撤去で **−48px**。
  【問題】`.damage-add-column-button:disabled { opacity: 0.4 }` により muted `#6b7280` が surface-alt 上で実効 `#c0c3ca` = **1.68:1**。文字として機能していないのに48px+gapを消費し、**これがカード1を380pxにしている唯一の原因**(13 + max(302, 316+6+48=370) = 383)。
  【提案】上限到達時は**スロットごとCSSで隠す**(DOMは残す)。`renderColumns` の上限判定で `addSlot.dataset.max = "true"` を立て、`.damage-add-column-slot[data-max="true"] { display: none }`。※代替案(右寄せ20pxキャプションに落とす)を採る場合も **`opacity: 0.4` は必ず外すこと**。

- **A-3 「+ 技を追加」を右カラムの下端に固定+圧縮** → 空白が「末尾の穴」から「意図的な余白」に変わり **−14px/枚**。
  【問題】カード3は技列125px・相手ビルド箱302pxで**右カラム下端に約190pxの空白**。検討した3案のうち、**相手ビルド箱を技列に合わせて縮める案は173pxまで削る必要があり公式絵拡大の要望と正面衝突するため不可**。**技列を `flex: 1 1 auto` で伸ばす案は箱の中に190pxの空白ができるだけで悪化する**。
  【提案】右カラムに**下端のアンカー**を置く。`.damage-row-techniques-row` に `justify-content: space-between`(または `.damage-add-column-slot` に `margin-top: auto`)。右カラムの上端(技列)と下端(追加ボタン)が相手ビルド箱の上下端と揃い、「片方だけ短い」という読みが消える。併せて `.damage-add-column-button` の `padding: 0.5em 0.6em → 0.28em 0.6em`、`font-size` 0.78rem 相当で48→約34px。**フォントを下げるのはこのボタン1個だけで、数値・技名には一切触らない。**

- **A-4 左カラムのヘッダと数値グリッドの列がずれている。真因は `em` の基準font-sizeの食い違い。**
  【問題】`.stat-table-header` は `font-size: 0.78rem` で `grid-template-columns: 6.8em 3.2em 1fr 3.4em 3.6em`、`.stat-row` は font-size 指定なし(1rem)で**同じ `em` 指定**。`em` は自身のfont-size基準なので実寸が別物になる: 1列目 85.0px vs 108.8px(**ずれ23.8px**)、種族値列 39.9 vs 51.2、努力値入力列 42.4 vs 54.4、実数値列 44.9 vs 57.6。
  【提案】両方を **`6.8rem 3.2rem minmax(0, 1fr) 3.4rem 3.6rem`** に変える(行側の実寸は変わらない)。併せて **`#ev-remaining`(残り18)を `.stat-table-header-real` から `.stat-table-header-ev` 側へ移し**、`justify-content: space-between` で左「努力値(0〜32)」・右「残り18」に。**残ポイントが努力値入力欄の真上に来て意味も合う**。`.stat-table-header-real` の `flex-direction: column` を外して1行「実数値」だけにする(ヘッダ2行→1行で **−17px**)。

- **A-5 幅390pxの破綻3件。うち1件は Astro scoped style の詳細度バグ**(メインエージェント側で computed style を実測し再現確認済み)。
  【問題・実測値】`.app-topbar-account-desktop` の computed `display` が **`flex`**。`global.css` の `.app-topbar-account-desktop { display: none }`(詳細度 0,1,0)が、`AppLayout.astro` の scoped `.app-topbar-account { display: flex }`(scopedで `[data-astro-cid-*]` が付き **0,2,0**)に**負けている**。結果:
  - ログイン表示が上下2箇所に重複 → `scrollWidth 491` vs `clientWidth 390` の**横スクロール**(はみ出し要素も両アカウントブロックと特定済み)
  - 「この個体を削除」が **46×169px**(`white-space: normal` のまま1文字ずつ縦に折り返し)。**w900でも3行に折れており、モバイル限定の問題ではない**
  - ページタイトルが**幅2px**に潰れて消滅、トップバーだけで高さ **259px**
  【提案】

#### 「同じ高さのまま」が成立しない理由

内部を縦積みにすると、カード高さ = 相手ビルド箱260px + 技列(1つあたり約107px) + 追加ボタン になる。**相手ビルド箱の260pxが動かせない床**であり、技列3つのカードは602pxまで伸びる。

#### 成立させるために必要なこと(未実施・要判断)

「スカスカ」の実体は**技列の1つが102px使って3行(「1発目」ラベル行 / 技名input行 / 結果チップ2段)しか持っていない**こと。362px幅なら1行に収まる情報量である。

- (b) **相手ビルド箱のフィールド行を2列にする**: 幅362pxなら「特性 / 持ち物」「テラス / (空き)」を横並びにでき、2行ぶん約44px回収 → 箱260px → 約216px。
- 見積: (a)+(b) で **1枚あたり約350px**(現在の全幅版333pxとほぼ同じ高さ)。**2×2なら4枚が約730pxに収まる**(現在は3枚で908px)。→ **1画面に見える枚数が3枚→4枚**、かつ横方向の空白も消える。

#### 判断が必要な点

**(a)「技列を1行に畳む」を実施してよいか。** これを入れないと「同じ高さのまま幅を半分」は成立せず、2×2にしても密度は改善しない((b)だけでは技列1つ434px / 技列3つ約540pxにしかならない)。(a)を入れる場合、ラウンド5の「結果チップの主役化」は**1行内での強調(確Nを太字・大きめ、数値を小さく右寄せ)に置き換わる**ことになる。

## 11-8 の修正(2026-07-26 ユーザー指示 追加)

ユーザーの言葉(そのまま引用): **「状態異常は種類が多く場所をとるのでリストから選択する方式にする」**

**上の「実施結果」で導入したばかりの状態異常アイコン化(`buildIconToggleGroup()`化)を撤回する。** 状態異常は「なし」込み7択(強天候削除と違いラウンド11で個数は変えていない)あり、アイコン+ラベル1個あたりの専有面積が天候・フィールド(なし込み5択、1行に収まる)より広く、複数行に折り返して省スペース化の効果を打ち消していたと判断されたための修正。

### 変更内容
- 攻撃側/防御側それぞれの状態異常ピッカーを、直前の実装(アイコントグル)から**リスト選択方式**に戻す。「リストから選択」という言葉どおり、素朴な `<select>`(ドロップダウン)に戻すのが最も直接的な解釈であり、**選択肢が何個あっても表示は常に1行**という要求(「場所をとる」の解消)に最も強く合致する。カスタムのリストボックス/コンボボックスを新規に作る積極的な理由はないため、**ネイティブ `<select>` への回帰を推奨する**(ラウンド11以前と同じ実装パターン。ただし文言短縮は維持してよい: 「状態異常なし」ではなく短い「なし」等)。
- 今回のアイコン化のために追加した状態異常専用SVG(`ICON_AILMENT_POISON` 等6種)は、選択肢ピッカーとしては使われなくなる。**未使用コードとして削除する**(残すとdead codeになる)。ただし他の用途(例: ダメージ計算カード上での状態異常アイコン表示等、既に別の場所で使っていないか確認すること。使っていなければ削除でよい)。
- **天候・フィールドのアイコントグル化はそのまま維持する**(今回ユーザーが問題視したのは状態異常のみ。「場の設定」の1行圧縮は5択で成立しており対象外)。
- `buildSideSection()` 内の `ailmentSelect` を select に戻す際、**11-8実施結果で追加した「選択肢配列に存在しない残存値の正規化」(`sanitizeColumnChoices()`)は select 化後も引き続き必要**(値の集合自体は変わらない=どく/もうどく/まひ/やけど/ねむり/こおり+なし、ゆめうつつ除外のまま)。正規化ロジック自体は変更不要、参照している選択肢配列(`DAMAGE_AILMENTS`)さえ更新されていれば動く。
- 省スペース化のレイアウト(「見出し+ランク」1行/「テラスタル(+急所)」1行という3行構成)のうち、状態異常の行は「アイコン1行(複数行に折り返すことがある)」から「`<select>` 1行(常に1行)」に変わるため、**むしろ縦はさらに縮む**見込み。実装後に幅296px/336pxでの高さを再実測し、上の「実施結果」に記載した数値(723px)からどれだけ縮んだかを追記すること。
