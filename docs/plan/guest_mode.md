# 未ログイン利用・ゲストモード仕様書

## 1. 目的

ポケガイドを未ログイン状態でも一定範囲まで利用可能にし、ユーザーがログイン前にアプリの操作感・機能・利便性を確認できるようにする。

ログインを利用開始の前提条件とせず、原則として以下の方針とする。

* 閲覧・操作・一時的なデータ作成は未ログインでも可能
* アカウントへの永続保存・複数端末同期など、アカウントに依存する機能のみログイン必須
* ログインを要求する前に、ユーザーが実際のアプリUIを操作できる状態を提供する

## 2. 基本方針

ログイン状態による機能の境界は以下とする。

| 機能            | 未ログイン | ログイン済み |
| ------------- | ----: | -----: |
| バトルデータ閲覧      |     ○ |      ○ |
| 上位チーム閲覧       |     ○ |      ○ |
| すばやさ表         |     ○ |      ○ |
| ダメージ計算        |     ○ |      ○ |
| ボックス閲覧        |     ○ |      ○ |
| ポケモン作成        |     ○ |      ○ |
| ポケモン編集        |     ○ |      ○ |
| ポケモン削除        |     ○ |      ○ |
| チーム作成         |     ○ |      ○ |
| チーム編集         |     ○ |      ○ |
| チーム削除         |     ○ |      ○ |
| ゲストデータの端末内保存  |     ○ |      ○ |
| box/data・matchup・ranked(選択個体を使った参照機能) | ○ | ○ |
| 対戦相手メモ(opponent-notes) | × | ○ |
| チーム提案(team-suggestions) | × | ○ |
| アカウントへの永続保存   |     × |      ○ |
| 複数端末間の同期      |     × |      ○ |
| アカウント固有データの利用 |     × |      ○ |

対戦相手メモ・チーム提案をスコープ外とする理由は8.1を参照。

## 3. 未ログイン状態

未ログインユーザーは「ゲストモード」として扱う。

ゲストモードでは、ログイン済みユーザーと可能な限り同一のUIを使用する。

ログイン前専用のデモ画面を別途構築するのではなく、実際のアプリ画面をそのまま操作できる状態を基本とする。

## 4. ゲストデータ

### 4.1 保存先

未ログイン状態で作成・編集したデータはブラウザ内に保存する。

保存先は原則として `localStorage` 等のクライアント側ストレージとする。

ゲストデータはサーバー上のユーザーデータとして保存しない(11章の移行時を除く)。

`localStorage` が利用できない環境(プライベートブラウジング等で例外を投げる場合)では、書き込み・読み込みを必ず try/catch で保護し、メモリ上のみで動作する(リロードで消える)状態に degrade する。エラーを握りつぶして無反応にはしない。既存の `src/lib/box-id/damage-calc.ts` の localStorage try/catch を参考にする。

### 4.2 対象データ

ゲストモードでは少なくとも以下を保存可能とする。

* 作成したポケモン
* ポケモンの設定内容
* 作成したチーム
* チーム構成

### 4.3 データ保持

ブラウザを再読み込み・再起動しても、端末内に保存されたゲストデータは維持する。

以下の場合はデータが失われる可能性がある。

* ブラウザのサイトデータ削除
* `localStorage` 等の削除
* 別ブラウザからのアクセス
* 別端末からのアクセス

必要に応じて、ゲストデータが端末内のみで保存されることをUI上で案内する。

### 4.4 ゲストID

ゲストが作成するポケモン・チームのIDは、サーバー発行のUUIDと明確に区別できる形式(例: `guest-` prefix付きの非UUID文字列)を用いる。

理由:

* 誤ってサーバーAPIへ送信された場合、既存の `isValidUuid` 等のバリデーションで確実に弾かれる(事故を早期検知できる)
* 11章の移行処理で「移行済みか未移行か」を判定しやすい

## 5. 初期サンプルデータ

### 5.1 目的

初回アクセス直後からボックスやチームの利用イメージを確認できるようにする。

### 5.2 ボックス

ゲストモードの初回利用時は、複数のサンプルポケモンをボックスに表示する。

サンプルポケモンは通常の登録ポケモンと同じUIで表示する。

ユーザーはサンプルポケモンに対して以下の操作を行える。

* 詳細表示
* 編集
* 複製
* 削除
* チームへの追加

### 5.3 チーム

必要に応じて、初回状態で1〜2個程度のサンプルチームを用意する。

サンプルチームも通常のチームと同様に編集可能とする。

### 5.4 初期化条件

サンプルデータはゲストモードの初回利用時のみ生成する。

ユーザーがサンプルデータを削除した後、ページを再訪するたびに自動復元しない。

## 6. ボックス

未ログイン状態でも通常のボックス画面を表示する。

従来の「利用するにはログインが必要」という全面的な制限画面は廃止する。

未ログイン状態でも以下を可能とする。

* ボックス一覧の閲覧
* ポケモンの新規作成
* ポケモンの編集
* ポケモンの削除
* ポケモンの複製
* 並び替え等の通常操作

保存先のみログイン状態によって切り替える。

* 未ログイン：端末内
* ログイン済み：アカウントデータ

### 6.1 実装上の注意(SSR焼き込みとhydration)

`box/[id].astro` の詳細編集フォーム(`src/components/box-id/LeftPanel.astro` 等)は、現状ログイン済みユーザーの値をSSR時にHTML属性へ直接埋め込む実装になっている。ゲストの値はサーバーが知らないため、この経路はそのまま使えない。

対応方針:

* `box/[id].astro` には既に「新規作成(`isNewMode`)時は空レコードでSSRする」経路があるため、ゲストの詳細画面は同じ空骨組みでSSRし、クライアント側でlocalStorageの値をフォームへ流し込む(hydrate)方式を基本とする
* 種族非依存の付帯データ(`moveAdoptionBySpecies`・`speciesUsageByRegulation` 等)は認証不要で取得できるため、追加APIは不要
* box一覧のみを先に対応し詳細を後回しにすると、一覧から個体をタップした時点でログイン画面に戻ってしまい体験が破綻する。**「一覧+詳細+CRUD」をひとまとまりの実装単位とする**(17章のフェーズ分割を参照)

## 7. チーム

未ログイン状態でも通常のチーム管理画面を表示する。

以下を可能とする。

* チーム一覧の閲覧
* チームの新規作成
* チーム編集
* チーム削除
* ボックス内ポケモンの選択
* チームメンバーの入れ替え

ゲストモードで作成されたチームは端末内に保存する。

### 7.1 実装上の注意

`team/[id].astro` は既にSSR時点の初期チームを `data-initial-team` としてJSON埋め込みし、以後の編集はクライアント側でその構造を操作する実装になっている。ゲスト対応は「JSONの取得元をサーバーAPIからlocalStorageへ切り替える」形で済み、box詳細より対応コストは低い。

チームメンバーはポケモンをID参照する構造のため、ゲスト時はゲストポケモンのローカルID(4.4)を参照する。サーバー側の `team_members.owned_pokemon_id` はSupabase UUID前提の外部キーであるため、ゲストのチームデータ自体はサーバーへ送らず、ローカルの参照関係もローカルIDのみで完結させる。ログイン後の変換は11章を参照。

## 8. その他の機能

以下の機能は原則としてログインを要求しない。

* バトルデータ
* 採用率等の統計情報
* 上位チーム
* すばやさ表
* ダメージ計算
* その他、ユーザー固有データを必要としない閲覧機能

ゲストモードのボックスデータを利用可能な機能については、端末内のゲストデータを参照する。

`box/data`・`box/matchup`・`box/ranked` は選択中個体のデータをクライアント側でJSONとして扱う実装のため、ゲストの選択個体もクライアント側から同様に注入すれば動作する。これらが依存するAPI(`/api/opgg-usage`・`/api/ranked-teams`・`/api/matchup-targets`・`/api/damage-calcs`・`/api/suggestions`・`/api/search`)はいずれも認証不要のため、追加のサーバー対応は不要。box/team本体より対応コストが低いため、17章のフェーズではP5(box/team対応後)に位置づける。

### 8.1 スコープ外とする機能

以下はゲストモードの対象外とし、明示的にログインを要求する。

* 対戦相手メモ(opponent-notes): 個体に紐づく対戦記録であり、アカウントの継続利用価値の中核であるためログイン誘因として残す
* チーム提案(team-suggestions): サーバーが `member_ids`(UUID)から個体情報をDB参照する契約になっており、ゲスト対応にはインライン個体データを受け付ける別APIの新設が必要で、費用対効果が見合わない

これらの機能をゲストが使おうとした場合は、機能を非表示にするのではなく、カード内などに「ログインすると使えます」という控えめな導線を表示する(10章参照)。

## 9. ゲストモード表示

未ログイン中であることは表示するが、操作を妨げない程度の控えめな表現とする。

例：

> お試しモード
> ログインするとデータをアカウントに保存できます。

付近にログインボタンを配置する。

ログイン誘導のためにモーダルや全面オーバーレイを頻繁に表示しない。

## 10. ログイン導線

ログインは以下のタイミングで自然に案内する。

* ゲストモード表示部分
* ヘッダー等のログインボタン
* アカウント保存を行おうとした場合
* 複数端末同期等のログイン必須機能を利用しようとした場合
* 対戦相手メモ・チーム提案等、8.1でスコープ外とした機能を利用しようとした場合

ログインしていなくても通常操作を継続できる場面では、ログインを強制しない。

## 11. ゲストデータのアカウント移行

未ログイン状態でデータが作成されている場合、ログイン成功後にゲストデータをアカウントへ移行できるようにする。

対象：

* ポケモン
* チーム

ログイン成功後、必要に応じて以下の確認を表示する。

> お試し中に作成したデータがあります。
> アカウントに保存しますか？

選択肢：

* 保存する
* 保存しない

「保存する」を選択した場合、ゲストデータをアカウント側のデータへ追加する。

### 11.1 移行APIの設計

移行は専用エンドポイント(例: `POST /api/guest-migration`)を新設し、ゲストのポケモン・チームをまとめて1リクエストで送る。クライアントが個体ごとに逐次POSTする方式は、途中失敗時の後始末がクライアント任せになるため避ける。

サーバー側の処理順序は以下で固定する(外部キー制約上、この順序以外は成立しない)。

1. ポケモンを一括insertし、`ゲストのローカルID → 新規発行UUID` の対応表を作る
2. チームをinsertし、`team_members.owned_pokemon_id` は対応表でローカルIDを新UUIDへ解決してから書き込む
3. 対応表で解決できないメンバー参照(例: 移行対象から除外されたポケモンを参照している場合)はそのメンバーをスキップし、警告として結果に含める

移行データは信頼できないクライアント入力として扱い、既存の `owned-pokemon-validation.ts` / `team-validation.ts` によるバリデーションを必ず通す。また移行可能な件数に上限(例: ポケモン200件・チーム50件程度)を設け、既存の `rate-limit.ts` を適用する。

### 11.2 冪等性

Supabase/PostgRESTには複数テーブルにまたがるトランザクションが無いため、完全な原子性(全部成功か全部失敗かの二択)は前提にしない。代わりに再試行しても安全な設計にする。

`owned_pokemon` テーブルに `guest_local_id` 列(nullable)と `unique(user_id, guest_local_id)` 制約を追加するマイグレーションを行う。移行APIはこの列を使って「同じゲストローカルIDが既に移行済みかどうか」を判定し、再送されても重複登録しない。

移行完了後は、同一データが再度取り込まれないようにする(この判定に `guest_local_id` を用いる)。

### 11.3 失敗時の扱い

ゲストデータは、移行成功が確認できるまでlocalStorageから削除しない。移行が成功した後も即座に削除せず、「移行済み」であることをローカル側にも記録した上で保持する(ユーザーが手動で消せるようにする)。

一部のみ移行できた場合(11.1の3のスキップ等)は、全か無かのように装わず、成功件数・スキップ件数をユーザーに正直に提示する。

## 12. データ競合

ログイン先アカウントに既存データが存在する場合、ゲストデータによって既存データを自動的に上書きしない。

原則としてゲストデータを追加扱いとする。

ID等がゲストデータとサーバーデータで衝突しないよう、移行時に新しい識別子を割り当てる(11.1参照、ゲストIDは4.4の非UUID形式のためサーバー側IDと衝突しない)。

## 13. トップページ

未ログイン時のトップページは、一般的な宣伝用LPとして大規模に作り込む必要はない。

アプリの概要と、実際の機能へ直接進める導線を優先する。

例：

# ポケガイド

ポケモンの個体・チームをまとめて管理。

[試してみる]

「試してみる」からボックス等の主要機能へ遷移する。

遷移後はデモ専用画面ではなく、通常のアプリ画面をゲストモードとして表示する。

## 14. UX方針

ゲストモードでは以下を重視する。

* 本番UIとデモUIを分離しない
* 未ログイン状態でも主要操作を最後まで試せる
* ログイン要求によって操作フローを中断しない
* ログインによるメリットを「利用可能になること」ではなく「保存・同期できること」とする
* サンプルデータによって初回状態を空画面にしない
* サンプルデータも通常データと同じ方法で操作できるようにする

## 15. 基本ユーザーフロー

未ログインユーザーの基本フローは以下とする。

1. ポケガイドへアクセス
2. 「試してみる」を選択
3. ボックスを表示
4. サンプルポケモンを確認
5. ポケモンを編集、または新規作成
6. チームを作成
7. その他の計算・データ機能を利用
8. 必要に応じてログイン
9. ゲストデータをアカウントへ移行
10. 以降はアカウントデータとして利用

## 16. ログイン済みユーザーへの影響

ログイン済みユーザーについては、原則として現在の利用方法を変更しない。

ゲストモード対応に伴って、データアクセス層では以下の違いを吸収する。

* 未ログイン：ローカルデータ
* ログイン済み：サーバー上のアカウントデータ

各画面のUIコンポーネントは可能な限り共通化する。

### 16.1 データアクセス層の抽象化方針

現状、`box/index.astro`・`box/[id].astro`・`team/index.astro`・`team/[id].astro` はそれぞれ独立してAPIへ `fetch()` している(共通のstore/repository層は存在しない)。

ゲスト対応にあたっては、`src/lib/data/pokemon-repo.ts` / `team-repo.ts` のようなクライアント側アダプタを新設し、`list/get/create/update/remove` 相当のメソッド内で「ログイン済みなら既存API呼び出し、未ログインならlocalStorage操作」を分岐する。

* インターフェースの形は現行APIのレスポンス形をそのまま正とする(ログイン済み経路のコード・挙動を変えないため)
* 既存の `fetch()` 呼び出し箇所をこのアダプタ呼び出しへ機械的に置換できるようにする
* この置換自体(挙動を変えない回)を独立した実装フェーズとして先に行う(17章のP0)

## 17. 実装上の優先順位

実装はフェーズに分割し、Codexへの委任は1フェーズ(目安として1画面ぶんのクライアントロジック書き換えまで)を1回の委任単位とする。`box/[id].astro` と `team/[id].astro` は行数が大きいため、同一委任に含めない。

| フェーズ | 内容 | 優先度 |
| --- | --- | --- |
| P0 | データ層の骨組み。`guest-store.ts`(localStorage I/O)+ `pokemon-repo.ts`/`team-repo.ts` をまずサーバー経路のみで実装し、既存の直接fetch呼び出しを置換する。挙動を変えない回とし、以降のフェーズの差分を小さくする | 高 |
| P1 | ボックス一覧+詳細のゲスト対応(ログインゲート解除、空骨組みSSR+hydration、CRUD/複製/削除、自動保存のローカル経路)。サンプルポケモンの初期生成を含む | 高 |
| P2 | チーム一覧+詳細のゲスト対応(ログインゲート解除、ローカルID参照のメンバー管理、自動保存のローカル経路)。サンプルチームの初期生成を含む | 高(サンプルチームは中) |
| P3 | ゲストモード表示(9章)、トップページの「試してみる」導線(13章) | 高〜中 |
| P4 | 移行API(`POST /api/guest-migration`)、`guest_local_id` 列追加マイグレーション、ログイン時の移行確認UI、競合処理(12章)。P1〜P3と並行して着手可能 | 高〜中 |
| P5 | `box/data`・`box/matchup`・`box/ranked` のゲスト対応 | 低〜中 |

### 優先度：低

* 大規模なログイン前LP
* スクリーンショット中心の紹介ページ
* デモ専用の別UI
* 対戦相手メモ・チーム提案のゲスト対応(8.1によりスコープ外)

## 18. 完了条件

以下を満たした場合、ゲストモード対応完了とする。

* 未ログイン状態で主要画面へアクセスできる
* 未ログイン状態でポケモンを作成・編集できる
* 未ログイン状態でチームを作成・編集できる
* 作成したゲストデータがブラウザ再読み込み後も維持される
* 初回アクセス時にサンプルデータが表示される
* ログインを行わなくてもアプリの主要な操作感を確認できる
* ログイン後にゲストデータをアカウントへ移行できる(部分移行の場合は結果を正直に提示する)
* ログイン済みユーザーの既存データ・既存操作に影響を与えない
