# ポケモン読み取り(ゲーム画面OCR): 実機カメラ撮影への耐性強化計画

**背景(2026-09-16のセッション)。** `/box` のカメラFAB → `/box/new?ocr=1` の「ポケモン読み取り」モーダル(Tesseract.js)は、モバイル版のスクリーンショットでは種族・努力値・性格・わざ・特性まで正しく反映できたが、**Switchの画面をスマホのカメラで撮影した写真では全く認識できなかった**。原因の分析と改善案をここにまとめる。このセッションでは実装しない。実装時はcodexへ委任し、Coordinatorが実写真で検証する。

関連ファイル:
- `src/lib/game-screen-ocr-image.ts` — 前処理(ガウスぼかし→固定閾値で二値化)。Node/ブラウザ共通の純関数
- `src/lib/game-screen-ocr-parse.ts` — OCR行テキストの解釈(ラベル照合・数値抽出・マスター照合・性格逆算・複数パスのマージ・登録済み判定)
- `src/lib/box-id/game-screen-ocr.ts` — モーダル本体。`resizeForOcr`(長辺1600pxに縮小)、`recognize`(閾値170/180/190の3パス、PSM 6)、フォーム反映、登録済み遷移
- `tests/game-screen-ocr-parse.test.ts` / `tests/game-screen-ocr-image.test.ts`

## 現状の堅牢性の整理

### レイアウト揺れには強い(変更不要)

- 座標指定は一切なく、画像全体をTesseract(`tessedit_pageseg_mode: "6"`=1ブロックのテキスト)にかけ、**行テキストだけ**で解釈する
- ステータス行は「こうげき」等のラベルへの編集距離(誤読形 `ころげき`/`ぼうきょ`/`こくほう` 等も許容、0.4以上)+数値範囲(実数値40〜999、EV0〜32)で特定する。位置が多少ずれても行として読めれば拾える
- 前提にしているのは行の**順序**だけ: 種族=最初のステータス行より上、わざ=最後のステータス行〜「特性」行の間の最大4行、特性=「特性」行のラベル除去後
- 余計な行(左側の3Dモデルや背景の誤読)はラベル・マスター照合に引っかからず無視される
- 名前はすべてマスター(種族・習得わざ・特性)への最近傍照合で復元するため、数文字の誤読は吸収できる

### 撮影条件には弱い(ここが失敗要因)

1. **固定閾値の二値化**(`preprocessGameScreenImage`): グレースケール輝度をガウスぼかし(σ=1.2)後に閾値170/180/190で二値化し、「明るい画素=文字」として反転する。つまり「暗い背景に白文字、輝度分布はスクリーンショット相当」を仮定している。カメラ撮影では露出・ホワイトバランス・映り込み・照明ムラで輝度分布が丸ごとずれ、文字と背景が閾値の同じ側に落ちて画像全体が真っ白/真っ黒になり、OCR出力が空になる。3閾値の幅(±10)ではこの変動を吸収できない
2. **文字解像度不足**: 長辺1600pxに縮小するため、画面全体を写した写真では右ペインの文字が10〜15px程度になる。Tesseract jpnモデルの実用下限(おおむね20px以上)を下回る
3. **幾何・ノイズの補正なし**: 台形歪み(斜めから撮影)、画面のモアレ/画素格子、手ブレ、映り込みを扱っていない。σ=1.2のぼかしはスクショ上のUI模様(細かい網目)向けの値

モバイル版で動いたのは、スクショが「画素が正確・輝度が既知・文字サイズ十分」という前提を全部満たしていたため。

## 改善案(効果が大きい順)

### 1. 二値化を局所適応+極性自動判定にする(最優先)

`game-screen-ocr-image.ts` に、固定閾値の代替として次を追加する(既存関数は残し、スクショ向けとして併用してもよい)。

- **局所適応閾値**: 各画素を「周囲ウィンドウ(文字高の2〜3倍、例えば縮小後で31〜51px)の平均輝度 − 定数C」と比較する(Bradley/積分画像方式ならO(N))。照明ムラ・映り込みで局所的に明るさが違っても、文字と背景の相対差で判定できる
- **極性自動判定**: 二値化後に黒画素比率を数え、文字側が少数派(通常5〜20%)になるよう白黒を反転する。「白背景に黒文字」のUI(将来のテーマ変更・別画面)にも対応できる
- **コントラスト正規化**: 二値化前にヒストグラムの1%/99%点で輝度をストレッチする。露出不足・過多の写真を同じ土俵に乗せる
- 3パス構成は残し、閾値バリエーションではなく「定数C」や「ウィンドウ幅」のバリエーション(または固定閾値1パス+適応閾値2パス)にする。`mergeGameScreenOcrResults` はそのまま使える
- テスト: `tests/game-screen-ocr-image.test.ts` に「輝度全体を±60ずらした画像」「左右で明るさが違う画像」「白黒反転した画像」でも同じ文字領域が黒になることを加える

### 2. 右ペインの切り出しで文字解像度を確保する

縮小前に対象領域だけを切り出し、その領域が長辺1600px(または2000px)になるようにする。

- **案A(UI誘導)**: モーダルの説明どおり「右側だけ」を寄って撮ってもらう前提を強め、ガイド画像に「このくらい寄る」例を追加する。実装コストほぼゼロだが、ユーザー操作に依存する
- **案B(自動クロップ)**: 画面全体が写っている場合に備え、画像の右1/3〜1/2を候補として切り出したパスも回す(右ペインは常に右端にあるため座標依存でも許容範囲)。切り出し幅は横長画像のときだけ適用し、縦長(既に寄って撮った/スクショ)は全体を使う
- **案C(手動クロップUI)**: ファイル選択後にトリミング枠を出して調整させる。最も確実だが、「確認せずに即反映」という現在の方針との折り合いが要るので優先度は低め
- まずA+Bで様子を見る

### 3. 幾何補正・ノイズ対策(効果は限定的、後回し)

- **軽い台形補正**: 二値化後に文字行の傾きを推定して回転補正(deskew)。Tesseract自体が数度の傾きには耐えるので、まずは不要かもしれない
- **モアレ対策**: 縮小時に `imageSmoothingQuality: "high"` を明示し、ぼかしσを画像サイズに応じてスケールする(現在は縮小後固定1.2)
- **複数フレーム**: カメラ撮影は1枚なので対象外

### 4. 失敗時の診断情報

現状は失敗すると `alert` で撮り直しを促すだけで、どの段階で落ちたか分からない。

- 開発時だけ(`import.meta.env.DEV`)二値化画像とTesseract生テキストを `console.debug` に出す、または `?ocr=1&debug=1` でモーダル内に二値化プレビューを出す
- Node側で同じ前処理を実行できるので、`scripts/` に「写真ファイル→二値化PNGとOCR生テキストを `.tmp-ocr/` に書き出す」CLIを足す(`scripts/lib/page-session.mjs` とは別、`tesseract.js` をNodeで直接呼ぶ)。実写真での回帰確認をブラウザなしで回せる

## 検証手順(実装時)

1. 失敗した実写真を `.tmp-ocr/` に置き、上記4のCLIで現状の二値化結果・生テキストを保存する(修正前の基準)
2. 改善1を実装し、同じ写真で二値化画像が「文字が黒・背景が白」になり、生テキストにステータスラベルが出ることを確認する
3. `npm test`(既存586件+追加分)
4. ブラウザ実測: `npm run probe -- --page "box/new?ocr=1" --file "#game-screen-ocr-library-file=<写真>" --wait-ms 60000 --eval "location.href"` で、実写真から新規作成 or 登録済み遷移まで通ることを確認する。作られたテスト個体は同一オリジンの `fetch('/api/owned-pokemon/<id>',{method:'DELETE'})` で削除する
5. モバイル版スクショ(既存の動作ケース)が退行していないことも同じ手順で確認する

## 注意点

- `preprocessGameScreenImage` はNode/ブラウザで同じ画素を出す純関数として書かれている(`CanvasRenderingContext2D.filter` 不使用)。適応閾値もこの制約を守る
- 処理時間: 適応閾値の積分画像方式なら1600px画像で数十ms、パス数を増やすとTesseractの認識時間(1パス数秒)が支配的なので、パス数は3のまま中身を入れ替える
- CSPは `worker-src 'self' blob:` 済みで変更不要
