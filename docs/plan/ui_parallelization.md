# UI改修作業は、部品ごとに分割して並列化できるか(調査資料)

**調査日**: 2026-07-30(実測更新) / **対象コミット**: main (44e2dd3) / **対象**: `src/pages/` 配下の全ページ + `.claude/skills/ui-loop`(2026-07-31に `ui` から改名)の運用フロー

## 要旨

現状、UI改修の実装は「ファイル単位」で並列化されている(`ui-loop` skillの規則「同じファイルを2体に触らせない」)。ところが最大のページ `/box/[id]` は左サイド・ダメージ計算・右サイドという3つの独立した領域が**すべて1つの8,513行のファイルに同居**しており、この規則のせいで3領域を並列にできず毎回直列実行になっている。実際にラウンド31では左8件・ダメージ計算6件・右サイド4件、計18件の指摘が「担当ファイル同一」を理由に1本の作業列で処理された(このファイルは調査当初の160fb1bから3,000行以上肥大化している)。

このファイルは幸い、スクリプト部分がすでにIIFEで包まれていない**フラットなESモジュール**として書かれており、関数を3つの `.ts` に切り出す作業自体の難易度は低い。一方でCSSは `is:global` ブロックへの依存(scoped styleがJS生成要素に効かないという既知の制約)があり、分割時に適用順序が意味を持つ点は要注意。テストによる安全網がほぼ無い(DOM操作ロジックの単体テストはゼロ)ため、分割は**見た目を一切変えない「構造分割ラウンド」を1回独立して挟む**のが最も安全な進め方になる。

**今回の実測で判明した重要な訂正**: 当初「3領域にきれいに分割できる」という前提を置いていたが、実際にはスクリプト全体(4,546行)が `if (form) { ... }`(4462行目)という1つのブロックの中に、さらにダメージ計算・右サイドの実装一式が `if (opponentNotesSection) { ... }`(5225行目、`if (form)` の内側にネスト)という形で同居しており、**3領域は実行時に1つの連続したクロージャスコープを共有している**。右サイド(詳細設定サイドバー)の関数群もこのスコープ内で他のダメージ計算関数と同じインデント深度に並んでいるだけで、コード構造上の隔壁はコメント(`--- 詳細設定サイドバー ---` 等)のみ。呼び出しグラフを実測した結果、`scheduleRowSave`(14箇所)・`scheduleRowCalc`(13箇所)・`refreshRowConditionChips`(8箇所)など**ダメージ計算・右サイドの間だけで6関数・計40箇所超が双方向に呼び合っており**、汎用ユーティリティ層(左サイド⇔ダメージ計算)も合わせると**共有コア関数は合計17個・呼び出し箇所は60箇所超**にのぼる。「3分割」というより「3領域+それらをまたぐ共有コア」という4分類が実態に近い。詳細は4節を参照。

## 2. なぜ並列化できていないのか

`.claude/skills/ui-loop/SKILL.md` のStep 4は実装の並列化について次のルールを持つ:

> 「**ファイル単位で担当を割り、同じファイルを2体に触らせない**。」— エージェント1: `box/index.astro` / エージェント2: `box/[id].astro` / エージェント3: `global.css` ほか共通基盤、という例が示されている。

この規則自体は正しい(同一ファイルへの並行編集はGitの競合や意味的な衝突を生む、ラウンド20・27で実際に発生済み)。問題は**粒度がファイル単位に固定されている**ことで、`box/[id].astro` のように1ファイルの中に独立した3領域が同居していると、その3領域は規則上ずっと直列にしかならない。

### 実例:ラウンド31の指摘配分

| 担当領域 | 指摘件数 | 担当ファイル | 並列実行の可否 |
|---|---:|---|---|
| ボックス一覧 | 2 | `box/index.astro` | 可(他領域と並列可能) |
| 左サイド | 8 | `box/[id].astro` | 不可(同ファイルの他2領域と直列) |
| ダメージ計算 | 6 | `box/[id].astro` | 不可(同ファイルの他2領域と直列) |
| 右サイド | 4 | `box/[id].astro` | 不可(同ファイルの他2領域と直列) |

3領域・計18件はどれも設計上は独立した指摘(左サイドの入力欄整列、ダメージ計算の削除ボタン色、右サイドのランク横並び、など互いの実装に依存しない)。**ファイルさえ分かれていれば3体の実装エージェントに同時に投げられた作業**が、1ファイルであるという理由だけで1本の作業列を通っている。

## 3. 分割の実現可能性

3領域を実ファイルとして切り離せるかを、スクリプト・テンプレート・CSSの3層で確認した。

### スクリプト層 — 分割しやすい

`<script>` の中身は関数群を無名関数(IIFE)で包んでおらず、先頭で `import` 文を使う**ふつうのESモジュール**として書かれている。これは好条件で、`updateEvRemaining` / `refreshNatureButtons`(左サイド系)、`renderColumns` / `renderDetailPanel`(ダメージ計算・右サイド系)といった関数を、役割ごとに `.ts` ファイルへ `export` し直し、ページ側は薄いオーケストレーション層として `import` するだけで済む見込みが高い。書き直しというより「切り出し」に近い作業になる。

### テンプレート層 — Astroの標準機能で対応可能

Astroは子コンポーネント(`<LeftPanel />` のような分割)を標準サポートしており、SSRで必要なデータ(`pokemon`・技情報など)をpropsで渡す形に組み替えれば、テンプレートも3ファイルに分けられる。

### CSS層 — 要注意点あり

Astroの scoped `<style>` は `document.createElement()` で動的生成した要素には効かない(`pitfalls.md`に記録済みの既知の制約)。このためダメージ計算カードの大部分は `<style is:global>` に頼っている。`is:global` は名前のとおりスコープを持たないため、3ファイルに分割しても「後に読み込まれた定義が同詳細度で勝つ」というCSSの適用順序に依存したルールが複数存在する(`@media`/`@container`を基本定義より前に書いて無効化した事故が過去2回)。**分割時にファイルの読み込み順が変わると、この手のルールが静かに壊れる。**

### 4.3 提案する分割案

**現状(1ファイル)**: `box/[id].astro`(8,513行)に左サイド・ダメージ計算・右サイドがすべて同居し、かつ3領域は`if (form) { ... if (opponentNotesSection) { ... } }`という単一のネストしたクロージャスコープを共有している(3節参照)。

**提案(4分類に対応する5ファイル構成)**:
- `box/[id].astro` — オーケストレーター(SSR取得・コンポーネント呼び出しのみ)
- `LeftPanel.astro` + `left-panel.ts` — 左サイド専用一式(22関数)
- `DamageCalcSection.astro` + `damage-calc.ts` — ダメージ計算専用一式(54関数)
- `RightPanel.astro` + `right-panel.ts` — 右サイド専用一式(16関数)
- `shared-core.ts` — 共有コア(17関数)を明示的に `export`。各領域は暗黙のクロージャ参照ではなく `import` 経由でこれらを呼ぶ形に書き換える

境界は「見た目上の3領域」ではなく**実際の呼び出しグラフ**で引く必要がある。共有コアは領域間の暗黙のクロージャ依存を、独立ファイル間の明示的な `import`/`export` 契約に変換する作業そのものであり、単純な「切り出し」より一段階難易度が高い。特に `scheduleRowSave`/`scheduleRowCalc` は状態(`DamageRowState`/`DamageColumnState`)を直接書き換えるため、`shared-core.ts` 側にその状態の所有権をどう持たせるか(引数で渡すか、モジュール内で保持するか)を設計する工程が追加で必要になる。

## 5. 期待される効果(保守的な見積もり)

分割の効果が出るのは**`box/[id].astro` が対象になるラウンドの実装ステップ(Step 4)に限られる**。このページは物量・改修頻度ともにプロジェクト最大なので、レバレッジ自体は大きい。ただし4節の実測により、ダメージ計算と右サイドは `scheduleRowSave`・`scheduleRowCalc`・`refreshRowConditionChips`・`renderDetailPanel`・`selectColumn` など6関数・合計40箇所超の呼び出しで密結合していることが分かったため、**「3体完全並列」を前提にした理論値1/3縮小という見積もりは楽観的すぎる**。

- 分割後も、指摘が共有コア(4.2節の関数、またはそれらが操作する `DamageRowState`/`DamageColumnState`)に触れる場合は、ダメージ計算・右サイドの担当エージェントは引き続き直列実行にせざるを得ない(同一ファイルではなくなっても、同じ状態を書き換える2箇所の変更はレビュー・競合の観点で同時に進めるべきではない)。
- 一方、**左サイド**は共有コアとの接点が `buildAttackerSpec`・`recalcStats` と汎用ユーティリティ数個に限られ、ダメージ計算・右サイドに比べて独立性が高い。そのため現実的な見積もりは「左サイド1系列 // ダメージ計算+右サイドをまとめた1系列」の**実質2並列**であり、所要時間の短縮幅も**理論値で最大2分の1程度**にとどまると見るのが妥当。
- ラウンド31相当(左8件・ダメージ計算6件・右サイド4件)であれば、左サイド8件を1系列、ダメージ計算+右サイド計10件をもう1系列に振り分ける形になる見込み。ダメージ計算・右サイドの指摘同士がたまたま共有コアに触れなければ3体目として並列投入できる場合もあるが、それは指摘の内容次第であり毎回保証されるものではない。
- `box/index.astro`・共通CSSなど元々ファイルが分かれている部分は現状でも並列化できており、追加の恩恵は無い。

## 6. リスクと進め方

**最大のリスク**: この4,546行のスクリプトに対する**単体テストは0件**。安全網は Playwright の `tests/e2e/damage-calc.spec.ts` と、目視でのスクリーンショット比較(`scripts/shot.mjs`)のみ。動作を1ミリも変えないつもりの「切り出し」であっても、この規模のコードでは実測しない限り破損に気づけない。

進め方:
1. **見た目の変更を一切含まない「構造分割ラウンド」を1回独立して設ける。**ユーザー指示やレビュアー講評の実装と同時に行わない。
2. 切り出し前に、関数ごとの呼び出し元・呼び出し先を洗い出し、3領域 + 共有ユーティリティの4分類に仕分ける。
3. 分割後、ライト/ダーク・全ブレークポイントのスクリーンショットが**分割前と1ピクセルも変わらない**ことを受け入れ条件にする(差分ゼロが合格ライン)。
4. `is:global` ブロックを移動する際は、適用順序に依存するルールが無いかを個別に確認する(本資料3節を参照)。

| 対象 | 判断 |

| `box/index.astro` | 1,593行・単一の関心事。既に単独ファイルとして並列実行できている。 |
| `global.css` | 1,240行だが直近の改修での変更頻度は低く、衝突の実例も無い。分割コストに見合わない。 |

## まとめ

並列化を阻んでいるのは「並列化の仕組みが無いこと」ではなく、**`box/[id].astro` 1ファイルに3つの関心事が同居し、しかも実行時に1つのクロージャスコープを共有していること**。スクリプトが素のESモジュールで書かれている点は幸運で、切り出し自体の技術的難易度は高くない。ただし実測の結果、`scheduleRowSave`・`scheduleRowCalc`・`refreshRowConditionChips` などダメージ計算・右サイドの間を合計40箇所超で行き来する共有コア(全体では17関数・60箇所超)が存在することが分かっており、**「3領域」ではなく「3領域+共有コア」の4分類**として扱う必要がある。単体テストが無いため、分割は独立した「構造のみ変更するラウンド」として切り出し、スクリーンショット差分ゼロを合格ラインにするのが安全。並列化の効果も、共有コアに触れる指摘は引き続き直列になる前提で、理論値1/3ではなく実質2並列(左サイド // ダメージ計算+右サイド)程度に見積もるのが妥当(5節参照)。
