# UI改修作業は、部品ごとに分割して並列化できるか(調査資料)

**調査日**: 2026-07-30 / **対象コミット**: main (160fb1b) / **対象**: `src/pages/` 配下の全ページ + `.claude/skills/ui` の運用フロー

## 要旨

現状、UI改修の実装は「ファイル単位」で並列化されている(`ui` skillの規則「同じファイルを2体に触らせない」)。ところが最大のページ `/box/[id]` は左サイド・ダメージ計算・右サイドという3つの独立した領域が**すべて1つの5,512行のファイルに同居**しており、この規則のせいで3領域を並列にできず毎回直列実行になっている。実際にラウンド31では左8件・ダメージ計算6件・右サイド4件、計18件の指摘が「担当ファイル同一」を理由に1本の作業列で処理された。

このファイルは幸い、スクリプト部分がすでにIIFEで包まれていない**フラットなESモジュール**として書かれており、関数を3つの `.ts` に切り出す作業自体の難易度は低い。一方でCSSは `is:global` ブロックへの依存(scoped styleがJS生成要素に効かないという既知の制約)があり、分割時に適用順序が意味を持つ点は要注意。テストによる安全網がほぼ無い(DOM操作ロジックの単体テストはゼロ)ため、分割は**見た目を一切変えない「構造分割ラウンド」を1回独立して挟む**のが最も安全な進め方になる。

## 1. 現状:ページごとの規模

| ページ | ファイル | 行数 | 備考 |
|---|---|---:|---|
| 個体編集 | `src/pages/box/[id].astro` | 5,512 | 左サイド・ダメージ計算・右サイドが同居 |
| ボックス一覧 | `src/pages/box/index.astro` | 1,213 | 単一の関心事、分割不要 |
| 共通レイアウト | `src/layouts/AppLayout.astro` | 305 | |
| サイト全体CSS | `src/styles/global.css` | 1,020 | 直近の改修ラウンドでの変更頻度は低い |

`box/[id].astro` の内訳: **1つの `<script>` タグだけで3,236行・関数約111個**を占める。テンプレート側も scoped `<style>`(約690行)と `<style is:global>`(約1,480行)の2枚看板構成で、コンポーネント分割は一切行われていない。

プロジェクト内で複数コンポーネントに分割されているページは**1つも無い**(`src/components/` にあるのは共通サイドバー `AppSidebar.astro` のみ)。すべてのページが「フロントマター + テンプレート + スクリプト + スタイル」を1ファイルに収めるモノリシック構成。

## 2. なぜ並列化できていないのか

`.claude/skills/ui/SKILL.md` のStep 4は実装の並列化について次のルールを持つ:

> 「**ファイル単位で担当を割り、同じファイルを2体に触らせない**。」— エージェント1: `box/index.astro` / エージェント2: `box/[id].astro` / エージェント3: `global.css` ほか共通基盤、という例が示されている。

この規則自体は正しい(同一ファイルへの並行編集はGitの競合や意味的な衝突を生む、ラウンド20・27で実際に発生済み)。問題は**粒度がファイル単位に固定されている**ことで、`box/[id].astro` のように1ファイルの中に独立した3領域が同居していると、その3領域は規則上ずっと直列にしかならない。

### 実例:ラウンド31の指摘配分

| 担当領域 | 指摘件数 | 担当ファイル | 並列実行の可否 |
|---|---:|---|---|
| ボックス一覧 | 2 | `box/index.astro` | 可(他領域と並列可能) |
| 左サイド | 8 | `box/[id].astro` | 不可(同ファイルの他2領域と直列) |
| ダメージ計算 | 6 | `box/[id].astro` | 不可(同ファイルの他2領域と直列) |
| 右サイド | 4 | `box/[id].astro` | 不可(同ファイルの他2領域と直列) |

3領域・計18件はどれも設計上は独立した指摘(左サイドの入力欄整列、ダメージ計算の削除ボタン色、右サイドのランク横並び、など互いの実装に依存しない)。**ファイルさえ分かれていれば3体の実装エージェントに同時に投げられた作業**が、1ファイルであるという理由だけで1本の作業列を通っている。

## 3. 分割の実現可能性

3領域を実ファイルとして切り離せるかを、スクリプト・テンプレート・CSSの3層で確認した。

### スクリプト層 — 分割しやすい

`<script>` の中身は関数群を無名関数(IIFE)で包んでおらず、先頭で `import` 文を使う**ふつうのESモジュール**として書かれている。これは好条件で、`updateEvRemaining` / `refreshNatureButtons`(左サイド系)、`renderColumns` / `renderDetailPanel`(ダメージ計算・右サイド系)といった関数を、役割ごとに `.ts` ファイルへ `export` し直し、ページ側は薄いオーケストレーション層として `import` するだけで済む見込みが高い。書き直しというより「切り出し」に近い作業になる。

### テンプレート層 — Astroの標準機能で対応可能

Astroは子コンポーネント(`<LeftPanel />` のような分割)を標準サポートしており、SSRで必要なデータ(`pokemon`・技情報など)をpropsで渡す形に組み替えれば、テンプレートも3ファイルに分けられる。

### CSS層 — 要注意点あり

Astroの scoped `<style>` は `document.createElement()` で動的生成した要素には効かない(`pitfalls.md`に記録済みの既知の制約)。このためダメージ計算カードの大部分は `<style is:global>` に頼っている。`is:global` は名前のとおりスコープを持たないため、3ファイルに分割しても「後に読み込まれた定義が同詳細度で勝つ」というCSSの適用順序に依存したルールが複数存在する(`@media`/`@container`を基本定義より前に書いて無効化した事故が過去2回)。**分割時にファイルの読み込み順が変わると、この手のルールが静かに壊れる。**

## 4. 提案する分割案

**現状(1ファイル)**: `box/[id].astro`(5,512行)に左サイド・ダメージ計算・右サイドがすべて同居。

**提案(4ファイル構成)**:
- `box/[id].astro` — オーケストレーター(SSR取得・3コンポーネント呼び出しのみ)
- `LeftPanel.astro` + `left-panel.ts` — 左サイド一式
- `DamageCalcSection.astro` + `damage-calc.ts` — ダメージ計算一式
- `RightPanel.astro` + `right-panel.ts` — 右サイド一式

境界は「見た目上の3領域」ではなく**実際の呼び出しグラフ**で引く必要がある。コメントには「左パネル用」と書かれていても、保存処理(`buildPayload`・`scheduleSave`)のように3領域から共有で呼ばれる関数もあるため、切り出し前に依存関係を関数単位で洗い出す工程を挟むこと。

## 5. 期待される効果

分割の効果が出るのは**`box/[id].astro` が対象になるラウンドの実装ステップ(Step 4)に限られる**。このページは物量・改修頻度ともにプロジェクト最大なので、レバレッジは大きい。

- ラウンド31相当(左8件・ダメージ計算6件・右サイド4件)なら、実装エージェントを3体並列に投入でき、直列実行に比べて**実装ステップの所要時間が理論値で最大3分の1**に縮む見込み。
- `box/index.astro`・共通CSSなど元々ファイルが分かれている部分は現状でも並列化できており、追加の恩恵は無い。

## 6. リスクと進め方

**最大のリスク**: この3,236行のスクリプトに対する**単体テストは0件**。安全網は Playwright の `tests/e2e/damage-calc.spec.ts` と、目視でのスクリーンショット比較(`scripts/shot.mjs`)のみ。動作を1ミリも変えないつもりの「切り出し」であっても、この規模のコードでは実測しない限り破損に気づけない。

進め方:
1. **見た目の変更を一切含まない「構造分割ラウンド」を1回独立して設ける。**ユーザー指示やレビュアー講評の実装と同時に行わない。
2. 切り出し前に、関数ごとの呼び出し元・呼び出し先を洗い出し、3領域 + 共有ユーティリティの4分類に仕分ける。
3. 分割後、ライト/ダーク・全ブレークポイントのスクリーンショットが**分割前と1ピクセルも変わらない**ことを受け入れ条件にする(差分ゼロが合格ライン)。
4. `is:global` ブロックを移動する際は、適用順序に依存するルールが無いかを個別に確認する(本資料3節を参照)。

## 7. 対象外(触らなくてよい部分)

調査の過程で「分割しても意味が薄い」と判断した箇所。無駄な作業を避けるため明記する。

| 対象 | 判断 |
|---|---|
| `box/index.astro` | 1,213行・単一の関心事。既に単独ファイルとして並列実行できている。 |
| `global.css` | 1,020行だが直近の改修での変更頻度は低く、衝突の実例も無い。分割コストに見合わない。 |
| 今後作る新規ページ(チーム編成など) | `new-page` skillの対象。最初から機能単位でファイルを分けて作れば、この調査の問題は発生しない。 |

## まとめ

並列化を阻んでいるのは「並列化の仕組みが無いこと」ではなく、**`box/[id].astro` 1ファイルに3つの独立した関心事が同居していること**。スクリプトが素のESモジュールで書かれている点は幸運で、分割自体の技術的難易度は高くない。ただし単体テストが無いため、分割は独立した「構造のみ変更するラウンド」として切り出し、スクリーンショット差分ゼロを合格ラインにするのが安全。
