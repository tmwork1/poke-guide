# パフォーマンス計測ダッシュボード

再現性のあるパフォーマンス評価・改善サイクルの管理表。運用は以下の4ステップの繰り返し。

1. 画面遷移・ボタンクリック・画面を閉じる等の代表的な操作に目標タイムを設定する
2. `tests/perf/scenarios/*.perf.spec.ts` で実測するシナリオを整備する
3. 目標タイムからの超過具合(超過率)で課題の優先度を整理する(このファイルの表、自動生成)
4. 優先度順に改善対応し、`npm run test:perf` で再計測する

## 再計測のしかた

```bash
npm run dev             # 別ターミナルで起動しておく(起動済みならスキップ可、webServerが自動検出する)
npm run test:perf       # tests/perf/scenarios 配下を実行し、このファイルの表を自動更新する
```

計測対象は `astro dev`(開発サーバー)。本番ビルド(`astro preview`)は `build:master-data` を含め
起動コストが高く、素早く繰り返し計測する用途に向かないため、開発サーバーを対象にしている。
絶対値は本番より遅くなるが、同一条件で毎回計測するため改善前後の相対比較には十分機能する。

1シナリオにつき3回計測し、中央値を採用する(`playwright.perf.config.ts` の `repeatEach: 3`)。

## 目標タイムの目安(RAILモデル準拠)

新しいシナリオを追加するときはこの目安を基準に `targetMs` を設定し、外れる場合は `note` に根拠を書く。

| 分類 | 内容 | 目標タイム |
|---|---|---|
| page-load | 通常のページ遷移 | 1500ms(許容上限 3000ms) |
| page-load | Pyodide初期化を伴う初回表示(ダメージ計算関連) | 5000ms |
| interaction | ボタンクリック等への即時UI反応(モーダル開閉、フィルタ適用など) | 300ms |
| interaction | API呼び出しを伴う操作(保存・送信など) | 800ms |
| close | モーダルclose・画面離脱時の後処理 | 300ms |

## シナリオの追加方法

`tests/perf/lib/perf.ts` の `perfScenario` / `timeNav` / `timeAction` を使い、
`tests/perf/scenarios/<対象>.perf.spec.ts` に追加する。実装済みシナリオを参照。
計測結果の集計・この表への反映はレポーター (`tests/perf/lib/perf-reporter.ts`) が自動で行うため、
シナリオ側はファイルI/Oを意識しなくてよい。

### ✅ 解消済み: opgg-usage系devサーバー詰まり(2026-09-08)

`data-index-load`(バトルデータ, `/data`)・`data-top-builds-load`(データ: 上位チーム, `/data/top-builds`)・
`ranked-teams-load`(上位チームの表示, `/ranked-teams`)・`box-matchup-load`(相性チェックを表示)は、
2026-08-31〜09-01時点で `/api/opgg-usage`系が同時リクエストでdevサーバー側に詰まる既知バグ
([[project_opgg_usage_dev_server_stall]])の影響で42,000〜89,000ms(目標1500msの28〜60倍)の極端な値、
または120秒タイムアウトで表から欠落していた。

根本原因は `wrangler.jsonc` の `OPGG_USAGE` KVバインディングが `remote: true` になっており、
`astro dev` 起動のたびに本番Cloudflare KVへのリモートプロキシ接続(workerdプロセスをもう1つ起動、
実測+約530MB)を確立していたこと。この接続確立・維持自体がdev起動を不安定にし(30秒起動タイムアウトと
際どく競合)、同時リクエスト時のプロキシ詰まりも引き起こしていたと判断した(codex sol advisorによる調査、
2026-09-08)。ユーザー承認のうえ `remote: false`(ローカルKVエミュレーション)に変更した結果、
4シナリオとも700〜950ms台(目標達成)まで改善し、120秒タイムアウトも解消した。

**副作用**: ローカルKVは空スタートのため、OP.GGデータに依存する画面はdevでは実データが出ない
(既存コードは空/nullを空状態として表示するため画面自体は壊れない)。`box-matchup-load`
(相性チェックを表示)はこの副作用で「集計データがまだありません。」という正当な空状態表示になるため、
シナリオ側の読み込み完了判定をカード描画・空状態表示のどちらでも良いように修正済み。

#### S1: バトルデータカードを共有レンダラーに統合し、`/data` を遅延描画にする

`BattleDataCard.astro` は「`/box/data` と `/data` でマークアップを完全に一致させるため実装をここへ
一本化する」とコメントしていたが、実際には `box/data.astro` にゲスト用の `document.createElement` 版が
二重実装されていた(ラウンド1のプレビュー三重実装と同じ構図)。カード本体を
`src/lib/battle-data-card-html.ts` の `renderBattleDataCardHtml()` へ抽出し、SSR・ゲスト描画・
`/data` の遅延挿入の3つが同じ出力を使うようにした。

`/data` は先頭8件だけSSRし、残り227件は `<article>` と `data-search-text` だけを出して本体データを
JSONで埋め込む。`IntersectionObserver`(rootMargin 1200px)で画面に入る手前から挿入し、
レールのジャンプと検索の絞り込みでは Observer を待たずに同期描画する。

#### S2: Pyodideの先読みを、ダメージ計算を使う画面だけに限定する

**ラウンド1の「/box/matchup の5.5MBは無駄」という記述は誤診だった。** `matchup-panel.ts` は
`calcDamages()` で実際に相性を計算しているので、`/box/matchup` と `/team/[id]` の相性タブでは必須。

実際に無駄だったのは `/box/[id]` の育成タブ。先読みは2箇所あり、
`bulk-adjust.ts` 側は「耐久調整」ボタンをエンジン準備完了で有効化するためのものだったが、
このボタンは `.stat-adjust-actions { display: none }` により**現在ユーザーに見えていない**
(実測で 0x0)。表示していないボタンのために初回訪問で約6.2MBを取得していた。

- `bulk-adjust.ts`: 先読みを廃止。有効化条件からエンジン準備を外し、押された時点で初期化して
  ダイアログに「計算エンジンを準備中…」を出す(再表示しても永久にdisabledにならないようにするため)。
- `damage-calc.ts`: `?tab=damage` で初期表示する場合だけ従来どおり先読み。育成タブでは
  ダメージタブボタンの `pointerdown` を一度だけ拾って初期化する。
- `pyodide-engine.ts`: Save-Data 指定時と `slow-2g`/`2g` では先読み自体を見送る。

実測(dev, 390x844): 育成タブは6秒待っても Pyodide CDN / wheel へのリクエスト0件。
`?tab=damage` とダメージタブへの切替、`/box/matchup`(相性カード32件)は従来どおり。

Pyodideの内訳(CDN実測): `pyodide.asm.wasm` 2,991,722B + `python_stdlib.zip` 2,306,344B +
`pyodide.js` 5,960B + jpoke wheel 約967KB。`public/pyodide-sw.js` が cache-first でキャッシュするため
同じブラウザでは2回目以降は落ちない。削れたのは初回訪問ぶん。

#### S3: learnsetを用途ごとの派生JSONに分ける

`detail/pokemon.json`(1.6MB)の約79%は learnset で、これを読んでいた3つの画面はどれも全件を
必要としていなかった。用途に合わせて3種類の派生ファイルを出し、アプリからは
`detail/pokemon.json` を一切 fetch しないようにした(生成は派生元として残す)。

| 出力 | サイズ | 使う画面 |
|---|---|---|
| `detail/learnset/<種族名>.json` | 1,288枚 / 計1,389,912B(平均1,079B / 最大6,136B) | `/box/[id]` 育成パネル。常に表示中の1種族ぶんだけ |
| `detail/learnsets.json` | 1,416,596B | 種族選択ダイアログ。入力文字列で全種族の覚え技を横断検索するため全件が要る。開いたときだけ読む |
| `detail/speed-modifier-learnset.json` | 46,774B(884種族) | すばやさ早見表。`speed-modifiers.json` の `moves`(18件)に含まれるかの判定1箇所でしか使わない |

種族名はファイル名にそのまま使う(`public/item-icons/<日本語のアイテム名>.png` と同じ方式)。
Windowsで使えない文字だけを `%`+コードポイントへ変換し(該当は「タイプ:ヌル」1件)、
変換規則は `build.mjs` と `pokemon-master-data.ts` の2箇所に閉じている。

本番ビルド実測: `/data/speed-chart` のリソース転送量 1,970,677B → 391,737B(**-80%**)。
`/box/[id]` の detail 取得は `pokemon-core.json` + `learnset/<種族名>.json` 1件だけになった。
すばやさ早見表は前後とも189行で先頭10行一致、`#move-list` の先頭20件も一致。

**⚠️ 落とし穴**: 最初の実装では「全種族ぶんが要る」2画面(種族選択ダイアログ・すばやさ早見表)を
種族ごとの個別fetchのループに置き換えてしまい、1リクエストが1,290リクエストになる退行が入った。
分割ファイルは「1件だけ要る画面」専用で、横断検索する画面にはバルクファイルを別に用意すること。

### 残っている改善余地(2026-09-09 ラウンド2時点)

- **`/data` のHTMLがまだ1.88MB**(うち約1.24MBは遅延カード用の埋め込みJSON)。
  これをシーズン単位のAPIに逃がせば、ドキュメント本体は約640KBまで落ち、
  さらにCDNで全ユーザー間・シーズン切替間で共有キャッシュできる。リクエストは1本増える。
- **`もちもの選択の自動保存` が目標800msに対して1,400〜1,600ms。**
  2026-09-08まで主因としていたPyodideプリフェッチは今回廃止済みで、育成タブでは一切走らない。
  残っているのはデバウンス700ms+PUTの往復だが、超過分の切り分けは未了。
  ただし上記のとおり現在のdev計測は全体が1.3〜2倍に膨らんでいるため、
  **切り分けは静かなマシンで測り直してから**行うこと。
- **`detail/moves.json`(103KB)が `/box/[id]` で4回リクエストされている**(Resource Timing実測)。
  HTTPキャッシュには載っているはずだが、共有ローダーを経由していない呼び出しが残っている可能性がある。
- **`/box/[id]` を本番ビルドで計測できない。** `astro preview` は dev のような認証バイパスを持たないため
  ログインページへリダイレクトされる。CLS・転送量の前後比較をこの画面で続けるなら、
  計測用のセッションCookieを渡す手段が要る。

### 表から欠落しているシナリオ

2026-09-08時点で無し。`/share/[slug]`(共有ページ)は使い捨て個体を作成して共有ONにする
シナリオ(`share-page-load`)を追加済み。`damage-calc-poc`(POC画面)は本番導線に無いため対象外。
