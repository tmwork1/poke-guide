### 「チームメモ編集と自動保存」の目標値は妥当か

dashboardは`もちもの選択の自動保存`(box/[id])について、2026-09-09ラウンド3で合算値(1,461ms)を
「PUT往復505ms + 残り約956ms(700msデバウンス)」に分解し、**700msデバウンスは仕様上の下限**と
判断して目標を800ms→1,200msへ改めた実績がある(dashboard.md 225-238行)。

`team-ranked.perf.spec.ts`の`team-composition-autosave`(145-173行)は、このシナリオと同じ構造
(700msデバウンス + PUT完了まで)でありながら、**PUT往復だけを切り出す別シナリオを持たない**。
現状の1,430msから700msを引くと実質730msで、これはbox側の「残り約956ms」より短く、目標800msに
近い。つまり**同じ理由でこの目標値も800msのままでは不公平**であり、box側と同じ論理(700msは
UXの仕様であり性能改善の対象外)を適用するなら、目標は1,200ms前後へ改めるのが筋が通る。
ただし実際のPUT往復時間を計測していないため、正確な内訳は「確度の低い仮説」に回す。

`src/pages/api/teams/[id].ts`のPUTハンドラは認証→レート制限チェック→バリデーション→
`replaceTeam()`(所有権検証SELECT→UPDATE→RPC→再SELECT、最大4回の順次DBラウンドトリップ、
`src/lib/team.ts` 239-301行)という経路を通る。box側の`もちもの選択`のPUT(単一テーブル更新)より
DBラウンドトリップが多い構造であるため、**PUT往復時間はbox側の505msより長くなる可能性が高い**
(要計測)。

### 🟢達成項目のスケール耐性

3件とも「少数データのローカル環境」での計測であり、本番の実データ量でも同じ余裕を保つかは
別問題である。特に「チーム詳細の表示」「チーム一覧の表示」は、発見B・C・Dで述べる**バックグラウンド
での全件先読み**を計測対象に含んでいない(終点がSSR済み要素の可視化やローディング表示の非表示
であり、これらのバックグラウンド処理はその後も続く)。データ量が増えるほど、計測に写らない
ネットワーク・DOM構築コストだけが増えていく構造になっている。

## 発見

### 発見A(最重要): `team-mate-card.ts`の250ms遅延が、除去可能な形で/team/[id]の全操作に効いている

CLAUDE.mdの「長押しとPCでの代替操作」節は、`team-mate-card.ts`の250msダブルタップ遅延を
「最頻操作であるタップの体感を必ず悪化させる」悪例として明記している。実際にこの遅延は、
**/team/[id]の4つの相互作用箇所すべて**(編成タブの6枠タップ、相性タブの自チーム表示、
データタブの自チーム表示、もちもの入替ダイアログのメンバータップ)で発生しており、
かつ**そのうち3箇所は遅延を払う理由が実質的に存在しない**ことがコードから確認できる。

**機序**: `src/lib/team-mate-card.ts` 64-109行の`renderTeamMateSlots()`は、
`onSlotTap`・`onSlotDoubleTap`・`onSlotLongPress`のいずれか1つでも渡されると、
無条件で以下のclickハンドラを組む(94-109行)。

```ts
button.addEventListener("click", () => {
    if (longPressed) { longPressed = false; return; }
    if (tapTimer !== undefined) {
        window.clearTimeout(tapTimer);
        tapTimer = undefined;
        onSlotDoubleTap?.(slot);
        return;
    }
    tapTimer = window.setTimeout(() => {
        tapTimer = undefined;
        (onSlotTap ?? onSlotClick)?.(slot);
    }, 250);
});
```

`onSlotDoubleTap`が**渡されていなくても**、`tapTimer = window.setTimeout(...)`の分岐は
無条件に実行される。つまりダブルタップの受け口が無いのに、シングルタップの実行だけが
毎回250ms遅延させられる。

`src/pages/team/[id].astro`での呼び出し箇所を全て確認した:

- **もちもの入替ダイアログ**(650-658行): `onSlotTap: onRedistributionMemberTap, onSlotLongPress: clearRedistributedItem` ── `onSlotDoubleTap`は渡していない。それでも上記の理由で250ms遅延を払う。**ダブルタップの受け口が存在しないぶん、この遅延には一切の機能的な意味が無い(純粋な損失)。**
- **編成タブ**(1738-1746行)・**相性タブの自チーム表示**(1747-1755行)・**データタブの自チーム表示**(1756-1764行): いずれも`onSlotTap: onFormationSlotTap, onSlotDoubleTap: onFormationSlotDoubleTap, onSlotLongPress: onFormationSlotLongPress`。ここで`onFormationSlotDoubleTap`(1728-1730行)と`onFormationSlotLongPress`(1731-1733行)の実装を見ると、

  ```ts
  function onFormationSlotDoubleTap(slot: number): void {
      if (membersBySlot.has(slot)) removeMemberFromSlot(slot);
  }
  function onFormationSlotLongPress(slot: number): void {
      if (membersBySlot.has(slot)) removeMemberFromSlot(slot);
  }
  ```

  **完全に同一の処理**(`removeMemberFromSlot(slot)`)を呼んでいるだけである。つまりダブルタップは長押しの完全な重複であり、ダブルタップというジェスチャー自体に何の追加価値も無い。CLAUDE.mdが定める「モード/遷移系はpointerdownベースの長押し(+PCは右クリック)」の原則にそのまま従えば、ダブルタップの割り当てそのものが不要である。

**影響範囲**: `/team/[id]`の編成操作(枠タップで選択→別の枠タップで入替、既存メンバーの選択解除)、
相性・データタブでの自チーム表示タップ、もちもの入替ダイアログでのメンバー選択・入替がすべて、
タップから実際の反応まで250msの遅延を挟む。これは「チームを編成する」というこの画面の主機能の
体感速度に直接効く。dashboardの計測シナリオには含まれておらず(下記「計測シナリオの不足」)、
実測値としては可視化されていない。

**対策案**:
1. `team-mate-card.ts`のclickハンドラを、`onSlotDoubleTap`が**実際に渡されているときだけ**
   tapTimerによる遅延を使うよう変更する(渡されていなければ`onSlotTap`を即時実行)。
2. `team/[id].astro`の編成/相性/データタブの3箇所で、`onSlotDoubleTap: onFormationSlotDoubleTap`の
   受け渡しを削除する(`onSlotLongPress`が同じ動作を既に提供しているため機能損失なし)。

この2つを組み合わせると、/team/[id]内の4箇所すべてでタップの遅延がゼロになり、
かつ既存の削除操作(長押し・PC右クリック)は一切変更しなくて済む。

**推定効果**: タップ操作1回あたり最大250msの反応遅延を解消。頻度の高い操作(編成の組み替え)
ほど体感差が大きい。定量的な体感改善幅は要計測(`npm run probe --click`でtap→DOM更新までの
時間を計測可能)。

### 発見B: `/team`一覧が、全チームを自動で先読みしながら毎回リスト全体をDOMから作り直す

`src/pages/team/index.astro`の`loadList()`(304-330行)は、24件ずつ`GET /api/teams?limit=24&offset=...`
を呼び、**`hasMoreTeams`が真である限り`requestAnimationFrame`でloadList(false)を再帰的に呼び続ける**
(325-328行)。ユーザーのスクロールやクリックを待たない、いわば「全件自動先読み」である。

```ts
} finally {
    isLoadingMore = false;
    if (hasMoreTeams && loadedNextBatch) {
        window.requestAnimationFrame(() => void loadList(false));
    }
}
```

さらに`renderList()`(252-267行)は、呼ばれるたびに`listRoot.innerHTML = ""`で**それまで描画済みの
カードを含む全リストを空にしてから、`allTeams`全体(蓄積済みの全ページ)を再度作り直す**。
1チームのカードは`renderTeamCard`→`renderBoxPokemonCard`(6枠ぶん、スプライト読み込みを含む)を
呼ぶため、軽い処理ではない。

つまりチーム数がN件(N>24)のとき、初期表示は「24件ぶんのカードを`ceil(N/24)`回、
毎回1〜24枚分ずつ増える全件を再構築する」という**O(N²/24)のDOM構築**になる。加えて
`ceil(N/24)`回の逐次(並列化していない)APIラウンドトリップが発生する。

`matchesSearch()`(192-204行)を使う検索がクライアント側の全件フィルタ実装であるため、
全件取得自体はこの画面の検索要件上おそらく必要(検索のたびにAPIを叩かない設計、フロントマター
コメントにもその方針が明記されている)。したがって**全件取得をやめるべきという結論にはならない**が、
「毎回全リストを作り直す」ことは検索要件と無関係な無駄である。

**影響範囲**: チーム数が少ない(24件未満)ユーザーには影響ゼロ(1回のfetchと1回の描画で完結)。
チーム数が多いユーザーほど悪化する。dashboardの計測(1,211ms、0.82x達成)は先頭24件の
ローディング表示消灯までしか捉えておらず、この問題を可視化していない。

**対策案**: `renderList()`を、新規に届いたページぶんだけDOMに追加する差分描画に変更する
(検索条件が変わらない限り、既存カードは再利用する)。検索フィルタの再適用が必要なため、
「フィルタに一致しなくなったカードを外す/一致するようになったカードを足す」形の差分更新が必要になる
(単純な追記だけでは不十分)。

**推定効果**: 要計測(手元にチーム数の多いテスト環境が無いため、体感差の定量化は要計測)。

### 発見C(最重要級・要検証): `/team/[id]`が、タブに関わらず毎回「類似チーム」全件を逐次取得・再計算する

`loadSimilarBuilds()`は`/team/[id]`のマウント時、**現在アクティブなタブに関係なく**無条件に呼ばれる
(2198行 `void loadSimilarBuilds();`)。相性タブの計算(`runMatchup()`)がタブ切り替え時まで
遅延される(425-430行)のとは対照的である。

```ts
mobileTabsInitialized = true;
renderOverviewGrid();
renderFormationMobile();
void loadSuggestions();
void loadSimilarBuilds();   // ← "データ"タブを開いていなくても即座に走る
```

`loadSimilarBuilds()` → `loadRankedTeams(true)`は`GET /api/ranked-teams?season=...&limit=24&offset=0`
を1回呼ぶが、`renderSimilarBuilds()`(1296-1338行)内で`rankedTeamsHasMore`が真なら
`scheduleMoreSimilarBuilds()`→`requestAnimationFrame`→`loadMoreSimilarBuilds()`を呼び、
**発見Bと全く同じ「hasMoreな限りrAFで自動継続」パターン**でシーズン全件を24件ずつ逐次取得し続ける。

このシーズンの母数は小さくない。`src/lib/team-suggest.ts`19行目のコメントに
「実測でガブリアスの共起1位はブリジュラス(36.8%)だが、ブリジュラスは**全1041チーム**の37%が採用」
という記述があり、少なくともこのコメントが書かれた時点でシーズンあたり四桁規模の`ranked_teams`が
存在したことがわかる(現在の正確な行数は要計測)。24件ページングだと**40回超の逐次APIラウンド
トリップ**になる規模である。

しかも`renderSimilarBuilds()`は呼ばれるたびに(=ページを1つ読むたびに)、その時点で蓄積済みの
全ランク入りチームに対して`calculateTeamSimilarity()`(1304行)と`hasBuildMatch()`(1299-1302行、
内部でさらに`calculateBuildSimilarity()`を呼ぶ)を**2回ずつ**計算し直し、
`teamDataMobileSimilarRoot.innerHTML = ""`(1315行, 1335行)で結果リストのDOMを毎回作り直す
(発見Bと同型の「全件再計算+全件DOM再構築」)。計算コスト自体は1チームあたり数十演算で軽いが
(`src/lib/build-similarity.ts`参照、O(6×6)程度)、**「類似チームタブを一度も開かないユーザーにも
毎回、四桁件規模のDB行を取得する40回超のネットワークラウンドトリップを強制している」**点が
最大の問題である。

**影響範囲**: `/team/[id]`を開くすべてのケース(ページタブに関係なく)。モバイル専用アプリ
(CLAUDE.md)であることを踏まえると、モバイル回線での不要なデータ通信・バッテリー消費という
コストも伴う。Supabaseの読み取りクエリ回数にも直接効く(課金・レート制限の観点でも無視できない)。

**対策案**:
1. `loadSimilarBuilds()`の初回呼び出しを、相性タブの`runMatchup()`と同じ方針で
   **「データ」タブを開いたとき**に遅延させる(`setMobileTab`の`tab === "data" && tabChanged`分岐に
   `void loadSimilarBuilds()`を追加し、2198行の無条件呼び出しを削除する)。
2. 1で「データタブを開いてから結果が出るまでの体感」が悪化する分は、少なくとも初回24件の
   取得だけは即座に行い、以降の自動継続ページングだけを「タブが開いている間だけ」に絞る、
   といった折衷も検討できる。
3. 発見Bと合わせて`renderSimilarBuilds()`の差分描画化も検討する。

**推定効果**: 「データ」タブを一度も開かないユーザー(体感的には多数派と推測されるが要計測)に
対して、40回超のAPIラウンドトリップとそれに伴うレスポンス転送量を丸ごと削減できる。

### 発見D: `loadAllOwnedPokemon()`も同様に、タブに関わらず所持ポケモン全件を逐次取得する

2200-2209行の`loadAllOwnedPokemon()`は`GET /api/owned-pokemon`相当を48件ずつ`while (true)`ループで
全件取得するまで繰り返す(逐次、並列化なし)。これも2226行でマウント時に無条件に呼ばれる。

発見Cと異なりこちらは「編成タブの選択バー」「サジェストの手持ち一致判定」に使うため、
**多くのユーザーにとって実際に必要なデータ**であり、単純にタブ遅延させると編成タブを開いた
瞬間に選択バーが空という体感の悪化を招く。そのため対策の優先度は発見Cより低いが、
所持数が多いユーザー(ボックスをヘビーに使うユーザー)では同じ「逐次N/48回ラウンドトリップ」
構造がボトルネックになりうる。

**対策案**: 並列化(`Promise.all`でページを並列取得。ただしoffsetベースのページングは
Supabase側のページ番号を先に決め打ちする必要があり、総件数を先に1回取得しないと並列化しにくい)、
または「編成タブを開くまで最初の1ページだけで我慢する」設計変更。後者はサジェストの
手持ち一致判定精度に影響するため要検討。

**推定効果**: 要計測(所持ポケモン数の分布が手元にないため)。

### 発見E: ゲストモードのサジェストは、ログイン版のDB集計APIと違い、クライアント側でシーズン全件を舐めている

`fetchSuggestions()`(1154-1163行)はログインユーザーには`GET /api/team-suggestions`
(サーバー側でSQL集計、`src/pages/api/team-suggestions.ts`)を使うが、ゲストモードでは
`loadGuestSuggestions()`(1082-1150行)→`loadAllRankedTeamsForGuest()`(1058-1080行)を使う。
後者は発見Cと同じ「`while (true)`で24→50件ずつシーズン全件を逐次取得」パターンであり
(`limit = 50`、64行 `while (true) { ... }`)、取得後は`candidates`のMapを構築するのに
**全チーム×全メンバーをJSでループ**する(1101-1122行)。

`guestRankedTeamsPromise`によってページ内では1回しか実行されない(キャッシュされる)ため、
連続してサジェストを再計算しても再フェッチにはならないが、**初回のサジェスト表示まで
シーズン全件(四桁規模)の逐次フェッチが完了するのを待つ**構造になっている。
ゲストモードは「box新規追加不可」等の制約が既にあるプロダクト上の重要な導線
(`project_guest_mode_progress`)であり、ここが遅いとゲスト体験全体の印象に影響しうる。

**対策案**: 中〜大規模(DB側の変更を要する)。ログイン版と同じSQL集計RPCをゲスト用に
公開する(所有権チェックが不要な分、むしろログイン版より単純にできる可能性がある)、
または「候補を絞ってから全件走査する」のではなく「集計だけをサーバーで先に済ませる」よう
設計変更する。

**推定効果**: 要計測。ゲストの初回サジェスト表示までの時間を計測するシナリオが現状無い
(下記「計測シナリオの不足」)。

### 発見F(軽微): `/team/[id]`のSSRが、独立した2つのDB取得を直列に待っている

`src/pages/team/[id].astro`のフロントマターで、`getTeam()`(65-76行)と`listRankedSeasons()`
(96-105行)はどちらも`await`されるが、互いのデータに依存しない独立したSupabaseクエリである。
現状は直列(`getTeam`完了後に`listRankedSeasons`を開始)なので、SSRのTTFBに両者のレイテンシの
合計が乗る。

**対策案**: `Promise.all`で並列化する(`isGuestNewMode`分岐の扱いに注意しつつ、
両クエリを先に並列実行してから結果を使う形に組み替える)。

**推定効果**: DBラウンドトリップ1回ぶんのレイテンシ削減(ローカルSupabaseでは小さいが、
本番のネットワークレイテンシ下ではより効く可能性がある。要計測)。

## 計測シナリオの不足

`tests/perf/scenarios/team-ranked.perf.spec.ts`がカバーしていない操作:

1. **編成タブの枠タップ(選択→入替/削除)**: 発見Aの250ms遅延を定量化できるシナリオが無い。
2. **もちもの入替ダイアログを開く/枠をタップする**: ダイアログを開く操作自体、およびダイアログ内の

   team側には無い。`matchup-panel.ts`は共有モジュールのため、box側の計測結果をそのままteam側の
   参考にはできない(DOM構造・呼び出し元が違う)。
4. **「データ」タブを開く(類似チーム表示完了まで)**: 発見Cの影響を定量化する唯一の手段。
   特に「タブを開いてから最初の24件が出るまで」と「全件読み込みが完了するまで」を分けて
   計測すべき(前者はUXの体感、後者はネットワーク総コストの指標になる)。
5. **チームメモ編集のPUT往復のみ**(デバウンスを含まない): 「もちもの保存のPUT往復」に相当する
   分解シナリオが無い(現状評価の節で述べた目標値議論に必要)。
6. **多数チーム/多数所持ポケモンでの計測**: 発見B・Dはデータ量に依存する問題であり、
   現状のローカル開発DBのような少数データでは顕在化しない。ダミーデータでの負荷計測環境が無いと
   検証できない。
7. **ゲストモードでのチーム編集画面表示・サジェスト取得**: 発見Eを定量化する手段が無い。
8. **`/team`一覧のタブ切り替え(圧縮表示⇔展開表示)・検索**: 発見Bの「全件再描画」コストを
   直接見るシナリオが無い。
